# Vendor-identity baseline goldens (pre-feature-022 reference)

This directory holds the **pre-feature-022 vendor-identity reference
output** that T054 AS1 in `tests/integration/test_us4_non_regression.py`
uses to assert byte-identity of vendor-identity fields across the
20-document baseline corpus (SC-006 / MI-22).

Each per-document `evaluation_document.json` file plus the corpus-wide
`evaluation_run_summary.json` were captured under
`contract_set_version = "1.2.0"` — the LAST contract version BEFORE
feature 022 landed. The writer respects the pin (Codex P1 fix on PR #47,
2026-05-23): `supports_semantic_quality_fields("1.2.0")` returns
`False`, so no additive feature-022 fields appear in these goldens.

## What the goldens contain

- `evaluation_run_summary.json` — corpus-level metrics, NO
  `semantic_table_quality_metrics`, NO `semantic_document_statuses`.
- `inv_corpus_easy_01/evaluation_document.json` … `inv_corpus_missing_05_fail/evaluation_document.json` —
  20 per-document evaluation reports, each pinned to `contract_set_version: "1.2.0"`.
  Each `document_pass_fail` block has only the three v1.2.0 keys
  (`vendor_identity_passed`, `review_routing_passed`, `overall_passed`);
  the additive v1.3.0 `semantic_table_quality_passed` is ABSENT.

## Why `tests/evaluator_tests/fixtures/corpus_20/` and not `tests/stage1_vendor_identity/`?

The real `tests/stage1_vendor_identity/` 20-document baseline corpus
contains only `source.pdf`, `expected.json`, and `preprocess_output.json`
per folder — it does NOT carry committed `final_structured_payload.json`
files (those would have to be generated by running the full pipeline,
which requires Paddle / GPU and is not part of the test suite). The
evaluator's per-document path REQUIRES `final_structured_payload.json`
to exist before it can write `evaluation_document.json`.

`tests/evaluator_tests/fixtures/corpus_20/` is the canonical 20-doc
fixture that:

- has both `expected.json` AND `final_structured_payload.json` per folder
- is the same fixture used by the existing US3 tests
  (`tests/integration/test_us3_evaluator_reports.py` AS2 / AS4)
- exercises the same vendor-identity scoring code path that the real
  corpus would when its `final_structured_payload.json` files exist

So this golden is a stand-in baseline against which we assert
**vendor-identity scoring code byte-identity**, not against which we
assert real OCR pipeline output. The non-regression guarantee we care
about (MI-22) is purely about the evaluator writer, and the writer is
agnostic to whether the fixtures came from the real corpus or the
synthetic one.

## How to regenerate the goldens on a workstation

If a future change touches scoring or report rendering and the goldens
become legitimately stale, regenerate them with this script run from
the repo root:

```bash
PYTHONPATH=src python3 - <<'EOF'
import shutil, json
from pathlib import Path
from dartwing_ocr.evaluator import evaluate_corpus

REPO_ROOT = Path('.').resolve()
SRC = REPO_ROOT / "tests/evaluator_tests/fixtures/corpus_20"
GOLDEN = REPO_ROOT / "tests/integration/goldens/vendor_identity_baseline_pre_022"

# Clear stale artifacts (keep this README).
for child in list(GOLDEN.iterdir()):
    if child.name == "README.md":
        continue
    if child.is_dir():
        shutil.rmtree(child)
    else:
        child.unlink()

# Copy fixture and pin to v1.2.0.
for fold in sorted(SRC.iterdir()):
    if fold.is_dir():
        shutil.copytree(fold, GOLDEN / fold.name)
evaluate_corpus(GOLDEN, contract_set_version="1.2.0")

# Strip source-only inputs so goldens hold ONLY evaluation outputs.
for fold in sorted(GOLDEN.iterdir()):
    if not fold.is_dir():
        continue
    for f in list(fold.iterdir()):
        if f.name != "evaluation_document.json":
            f.unlink()
md = GOLDEN / "evaluation_run_summary.md"
if md.exists():
    md.unlink()
EOF
```

You can also regenerate from a real `tests/stage1_vendor_identity/`
corpus root once `final_structured_payload.json` files are present
(requires the workstation Paddle/GPU lane). Substitute `SRC` for that
path and rerun. The expectation is that vendor-identity scores are
identical regardless of which fixture root the pin uses, because the
evaluator scoring code is the same.

## How T054 AS1 consumes these goldens

`tests/integration/test_us4_non_regression.py::test_as1_*` runs the
evaluator on a clean copy of the same `corpus_20` fixture using the
post-feature default contract version (`v1.3.0`) and compares the
resulting per-document and run-summary outputs to these goldens **after
stripping the additive v1.3.0 fields** (`semantic_table_quality`,
`document_pass_fail.semantic_table_quality_passed`,
`semantic_table_quality_metrics`, `semantic_document_statuses`).

Any divergence on the vendor-identity portion fails AS1 — that is the
hard release gate for MI-22.
