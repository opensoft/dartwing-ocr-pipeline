# Feature Specification: Single-Voter Edge Extraction (Stage 1 Vendor-Identity)

**Feature Branch**: `005-single-voter-extraction`
**Created**: 2026-04-21
**Status**: Draft
**Input**: User description: "Single-voter extraction. Call this 005-single-voter-extraction. Brief: Implement the stage 1 extraction slice. Read one document's preprocess_output.json, call a single configured Ollama voter over HTTP, and emit edge_extraction_output.json conforming to the frozen v1.0.0 contract. The voter slot for the full-workstation stage 1 path is Gemma 4 E4B (per implementation-plan.md); later runtime profiles add a smaller Gemma 4 E2B voter for the Jetson edge-fast stack. Extraction must be pluggable-voter-ready so the later three-vote ensemble can slot in without reshaping this layer, and every extracted field must carry {value, confidence, evidence} plus vote_metadata for future multi-voter runs. Extraction ONLY — no routing, no consensus, no final payload, no line items, no cloud path, no latency gate, no ensemble logic yet."

## Clarifications

### Session 2026-04-21

- Q: FR-011 — how should `confidence` be adjusted for a field whose final `evidence` array is empty after reconciliation? → A: Hard cap: `confidence = min(confidence, CAP)` where `CAP` is a fixed constant pinned in config (recommend ≤ 0.3). Model-proposed `value` is retained; only `confidence` is clipped.
- Q: HTTP timeout behavior for the Ollama call (FR-015) — how long before the endpoint is declared unreachable, and what retry policy? → A: Single long timeout (pinned in plan at 180 s read / 10 s connect — see `research.md` §R-002), no retries inside the extractor. On timeout → hard failure: non-zero exit, no artifact written. Retry policy is an orchestrator concern.
- Q: How does the extractor learn about the Ollama endpoint and the voter's model/prompt configuration? → A: Endpoint URL from `OLLAMA_BASE_URL` env var (same convention as the devcontainer). Voter configuration (model tag, voter_id, prompt/adapter reference, sampling config, ungrounded-confidence cap) lives in a per-voter config file (YAML or JSON) selected by a `--voter <name>` CLI flag. Host-infrastructure config (endpoint) and voter-level config are separate concerns.
- Q: CLI invocation signature (FR-025) — exact subcommand name and per-document flag? → A: `python -m dartwing_ocr.extract --folder <path> --voter <name>`. Flat flags, single-op module, mirrors the existing `dartwing_ocr.validator` submodule pattern.
- Q: Model sampling configuration — what temperature/seed policy does the stage 1 voter use, and how does SC-009's determinism claim scope? → A: Temperature = 0 and a fixed seed (where Ollama and the selected model support it), defaulted in the voter config file and overridable per-voter. Best-effort value determinism; SC-009's contractual determinism remains scoped to schema shape, reconciliation logic, status derivation, and provenance invariants — not bit-exact string values.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Produce A Schema-Valid `edge_extraction_output.json` For One Document (Priority: P1)

A pipeline developer has a per-document folder containing a valid `preprocess_output.json` (produced by 003) and needs the stage 1 edge extractor to read that packet, call the configured host-Ollama voter, and write a schema-valid `edge_extraction_output.json` into the same folder. The output must populate every required field in the frozen v1.0.0 contract, with each extracted value accompanied by a confidence score and an evidence list that references identifiers from the preprocessing packet.

**Why this priority**: Without a schema-valid per-voter artifact, no downstream slice (routing, final payload, evaluation, future ensemble) can run. This is the minimum viable capability for the edge path and the artifact that proves the model boundary works.

**Independent Test**: Stage a per-document folder containing a committed `preprocess_output.json` for one corpus document. Run the extractor against that folder. Verify `edge_extraction_output.json` is written next to `preprocess_output.json`, validates against `contracts/stage1_vendor_identity/v1.0.0/edge_extraction_output.schema.json`, reports `contract_set_version == "1.0.0"`, carries the same `document_id` as `preprocess_output.json`, populates `model_runtime` with the voter's identifying metadata, populates `vote_metadata` with `voter_role == "primary_extractor"` and `consensus_mode == "single_voter_baseline"`, populates `document_type.value == "invoice"` with a confidence, and produces a fully-formed `vendor_candidate` and `invoice_header_fields` block where every scalar field carries `{value, confidence, evidence}` per the schema.

**Acceptance Scenarios**:

1. **Given** a per-document folder containing a valid `preprocess_output.json`, **When** the extractor runs against that folder, **Then** `edge_extraction_output.json` is written next to the input and validates against the frozen schema.
2. **Given** a successfully extracted document, **When** the output is inspected, **Then** `document_id` equals the one in `preprocess_output.json`, `contract_set_version == "1.0.0"`, `processed_at` is a valid ISO-8601 date-time, and `pipeline_version` is a non-empty string identifying the extractor build.
3. **Given** a successfully extracted document, **When** the `vendor_candidate` block is inspected, **Then** every required sub-field (`company_name`, `address.street_1`, `address.street_2`, `address.city`, `address.state`, `address.postal_code`, `address.country`, `tax_ids.ein`, `tax_ids.state_tax_id`, `tax_ids.vat_id`, `tax_ids.other_tax_id`, `website`, `phone`, `email`) is present with `value`, `confidence`, and `evidence` keys; `value` is either a non-empty string or `null`; `confidence` is a float in `[0.0, 1.0]`; `evidence` is an array (possibly empty) of strings, each matching `^p\d+_[bl]\d+$`.
4. **Given** a successfully extracted document, **When** `invoice_header_fields` is inspected, **Then** `invoice_number` and `invoice_date` carry `{value, confidence, evidence}` and `total_amount` carries `{value, currency, confidence, evidence}` with `value` being a number or `null` and `currency` being a string or `null`.
5. **Given** a successfully extracted document, **When** `status` is inspected, **Then** it is one of `"success"`, `"partial"`, or `"failure"` and is consistent with the presence and shape of any `warnings` entries (status `"success"` implies no hard failure warning; `"partial"` implies at least one non-fatal warning; `"failure"` implies the extractor could not produce a meaningful result).
6. **Given** the extractor writes into an existing per-document folder, **When** the run completes, **Then** the extractor writes nothing outside that folder, does not modify `preprocess_output.json`, and does not overwrite or create any of the reserved downstream filenames (`routing_decision.json`, `final_structured_payload.json`, `evaluation_document.json`).

### User Story 2 - Every Extracted Field Is Grounded In The Preprocessing Evidence Packet (Priority: P1)

A pipeline developer relies on the extractor's output being *traceable*: every claim the model makes about the document must reference concrete block or line identifiers from `preprocess_output.json`, not hallucinated or free-form locations. Evidence IDs that don't resolve in the packet must be dropped, and fields whose evidence array ends up empty must have their `present` / `inferred` semantics adjusted so a reader never mistakes a guess for a grounded observation.

**Why this priority**: Evidence-first design is a constitutional non-negotiable. Without it, extractor output is indistinguishable from model guessing, routing cannot trust what it receives, and downstream evaluation becomes a string-match game. This story is what turns raw model output into an auditable extraction artifact.

**Independent Test**: Stage a per-document folder with a known `preprocess_output.json`. Run the extractor. Verify every `evidence` string anywhere in the output exists as a `block_id` or `line_id` in the input packet (at the same `p{N}_b{n}` / `p{N}_l{n}` identifier the packet published). Then run the extractor against a fixture where the model is coaxed to emit an evidence ID that doesn't exist in the packet (e.g., a lint-check or a seeded malformed response); verify the extractor filters the bogus ID out of the final `evidence` array, emits a warning naming the dropped ID, and downgrades the affected field per the grounding rules in US3.

**Acceptance Scenarios**:

1. **Given** any successfully extracted document, **When** a reviewer walks every `evidence` array in the output, **Then** every string in those arrays matches the `^p\d+_[bl]\d+$` pattern and resolves to a real `block_id` or `line_id` in the corresponding `preprocess_output.json`.
2. **Given** a field where the model proposed an evidence ID that does not exist in `preprocess_output.json`, **When** the extractor reconciles model output against the packet, **Then** the bogus ID is removed from the final `evidence` array, a human-readable entry is appended to `warnings` naming the field and the dropped ID, and the surviving evidence (if any) determines grounding for that field.
3. **Given** a field whose final `evidence` array is empty after reconciliation, **When** the extractor assigns `value` / `confidence` / `present` / `inferred`, **Then** scalar string fields (address components, tax IDs, website, phone, email) retain the model-proposed `value` but cap or downgrade `confidence` per a documented reconciliation rule; no ungrounded claim can present itself as high-confidence grounded evidence.
4. **Given** the evidence array for `company_name` ends up empty after reconciliation, **When** `company_name.present` and `company_name.inferred` are set, **Then** `present == false` and `inferred == true`, regardless of how strongly the model claimed the name is explicit. This is the evidence-first correction path that feeds into US3.
5. **Given** a reviewer inspects the extraction notes for any document, **When** reading `extraction_notes`, **Then** any field whose evidence was reconciled away (IDs dropped or evidence ended empty) is represented there or in `warnings` so the adjustment is discoverable from the artifact alone.

### User Story 3 - Missing-Name Invariants Are Enforced At The Extractor Level (Priority: P2)

The pipeline processes documents where no explicit company name appears on the page (the 5 `missing_name` documents in the corpus, plus any real-world document the model genuinely cannot ground). The extractor itself — not a later routing layer — must enforce the provenance invariants: if no grounded evidence supports an explicit name, the extractor stores a best-guess `value` but sets `company_name.present = false` and `company_name.inferred = true`. This is the Principle-IV provenance rule applied at the producer, so the routing slice (006) can trust what it receives.

**Why this priority**: The constitution makes this non-negotiable. Leaving the fix to downstream routing means every routing/consensus/evaluation stage has to re-derive grounding, and the shape of `edge_extraction_output.json` would be inconsistent across voters when ensemble mode arrives. Enforcing at the extractor keeps provenance attached to the artifact that owns it.

**Independent Test**: Run the extractor against a fixture where the input `preprocess_output.json` contains no block or line whose text plausibly supports an explicit company name (e.g., a missing-name corpus document). Verify the output has `company_name.present == false`, `company_name.inferred == true`, a best-guess `value` (possibly `null`), and `confidence` consistent with an inferred guess. Then run the same extractor against a fixture where the company name IS explicitly on the page with grounded evidence; verify `present == true`, `inferred == false`, and a non-empty `evidence` array for `company_name`.

**Acceptance Scenarios**:

1. **Given** a document whose `preprocess_output.json` plausibly contains explicit company-name text and the model grounds `company_name` to at least one real block or line, **When** the extractor runs, **Then** `company_name.value` holds the grounded string, `company_name.present == true`, `company_name.inferred == false`, and `company_name.evidence` is non-empty.
2. **Given** a document where no block or line in `preprocess_output.json` supports an explicit company name and the model still emits a best guess, **When** the extractor runs, **Then** `company_name.value` holds the best guess (or `null` if the model cannot commit), `company_name.present == false`, and `company_name.inferred == true`.
3. **Given** a document where the model incorrectly claims `present == true` but the reconciliation in US2 leaves `company_name.evidence` empty, **When** the extractor finalizes the output, **Then** `present` is deterministically set to `false` and `inferred` is deterministically set to `true`, overriding the model's claim. A note explaining the override is added to `extraction_notes` or `warnings`.
4. **Given** any output where `company_name.present == false` AND `company_name.inferred == true`, **When** the downstream routing layer reads the artifact, **Then** routing (006) has sufficient provenance to deterministically set `manual_review_required = true` without re-running the extractor — this story does not implement routing, but it produces the artifact shape routing will rely on.
5. **Given** any extraction output, **When** both invariants are evaluated jointly, **Then** the combination `present == true` AND `inferred == true` never appears, and the combination `present == false` AND `inferred == false` never appears for `company_name`. Exactly one of "explicit (present/not-inferred)" or "inferred (not-present/inferred)" holds.

### User Story 4 - The Voter Framework Is Pluggable And Architecture-Ready For The Three-Vote Ensemble (Priority: P2)

The stage 1 full-workstation slot is filled by one voter (Gemma 4 E4B running through host Ollama), but the longer-term architecture runs three independent voters (Qwen-family, Gemma-family, Phi-4 Mini) against the same `preprocess_output.json`. The code must be organized so adding the second and third voters later, or selecting the Gemma 4 E2B edge-fast voter through a runtime profile, requires only voter configuration and a corresponding prompt/model adapter — not a rewrite of the input contract, the output shape, the reconciliation loop, or the evidence-grounding rules. `vote_metadata` on the stage 1 artifact identifies which voter produced it so per-voter outputs can coexist in the future `votes/` subdirectory reserved by the folder contract.

**Why this priority**: Reshaping the extractor later is both higher-risk and higher-cost than designing for the multi-voter case on day one. The contract already carries `vote_metadata` and the folder contract already reserves `votes/` — honouring those now is cheap; violating them means paying for the reshape later.

**Independent Test**: Invoke the extractor twice against the same per-document folder using two different voter configurations (e.g., the full-workstation Gemma 4 E4B slot and a simulated Qwen adapter, or the Jetson Gemma 4 E2B config). Verify each invocation produces a schema-valid `edge_extraction_output.json` whose `vote_metadata.voter_id` and `model_runtime` fields differ according to the configured voter, while `document_id`, the evidence packet identifiers, and the overall artifact shape are identical. Confirm that nothing in the extractor's own interface (input signature, output path convention, reconciliation behavior) changes between the two invocations.

**Acceptance Scenarios**:

1. **Given** the stage 1 Gemma 4 E4B voter is configured, **When** the extractor runs, **Then** `model_runtime.provider` identifies the inference provider (host Ollama for the full-workstation path), `model_runtime.model_name` names the configured Gemma slot, `model_runtime.model_version` identifies the pinned version, and `model_runtime.runtime` identifies the runtime (the host Ollama path); all four are non-empty strings.
2. **Given** stage 1 operates in single-voter mode, **When** the extractor populates `vote_metadata`, **Then** `voter_id` is a non-empty string naming the voter instance, `voter_role == "primary_extractor"`, and `consensus_mode == "single_voter_baseline"`. No other consensus_mode value is valid in the v1.0.0 contract.
3. **Given** a future configuration change swaps the configured Gemma slot for a Qwen edge slot (or adds a Phi-4 Mini verifier), **When** the extractor runs with the new configuration, **Then** no change to the extractor's input contract (`preprocess_output.json` shape), output contract (`edge_extraction_output.schema.json` at `contract_set_version = "1.0.0"`), reconciliation logic, or folder layout is required — only the voter configuration and its prompt/adapter change.
4. **Given** a future run configures multiple voters to execute against the same preprocess packet, **When** those runs complete, **Then** each voter's artifact can be stored side-by-side under the reserved `votes/` subdirectory without filename collision, discriminable by `vote_metadata.voter_id`. This feature does not implement multi-voter orchestration; it ensures the single-voter shape does not block it.
5. **Given** any extraction output, **When** `voter_role` is inspected, **Then** it is drawn from the enum `primary_extractor | secondary_extractor | verifier`. Stage 1 only ever emits `primary_extractor`; the other values are reserved for future voters without reshaping this feature.

### User Story 5 - Graceful Degradation On Model, Network, And Parsing Failures (Priority: P3)

Real extraction runs encounter flaky Ollama endpoints, malformed model JSON, responses missing required fields, and transient timeouts. The extractor must surface these conditions clearly and predictably: hard failures (Ollama unreachable, input packet missing or schema-invalid, model returned nothing usable) exit non-zero with no partial artifact written; soft failures (some fields extracted, some missing; model JSON needed repair; evidence IDs had to be dropped) produce a schema-valid artifact with `status` set to `"partial"` or `"failure"` and human-readable `warnings` that identify what broke.

**Why this priority**: Silent failure modes are more expensive than loud ones. A developer investigating a regression needs the artifact to tell them whether the pipeline had a bad day or the model got worse at its job. This story makes that distinction visible without requiring log archaeology.

**Independent Test**: Run the extractor against (a) a normal case (expect `status == "success"`, empty `warnings`); (b) a case where the configured Ollama endpoint is unreachable (expect non-zero exit, no `edge_extraction_output.json` written, clear error message to standard error); (c) a case where the model returns malformed JSON that the extractor must repair (expect `status == "partial"`, `warnings` names the repair); (d) a case where the model returns valid JSON but one required sub-field is missing from the response (expect the missing sub-field to default to `{value: null, confidence: 0.0, evidence: []}` with a `warnings` entry naming the field); (e) a case where the input `preprocess_output.json` is schema-invalid (expect non-zero exit, no output written).

**Acceptance Scenarios**:

1. **Given** the configured Ollama endpoint is unreachable (connection refused, DNS failure, timeout) or the input `preprocess_output.json` is missing or schema-invalid, **When** the extractor runs, **Then** no `edge_extraction_output.json` is written, the extractor exits non-zero, and a human-readable error message names the specific failure cause.
2. **Given** the model returns JSON that requires repair (malformed, truncated, or wrapped in prose) but the repair succeeds, **When** the extractor finishes, **Then** `status == "partial"`, `warnings` includes an entry describing the repair, and the rest of the artifact is schema-valid.
3. **Given** the model response is valid JSON but a required scalar sub-field is absent, **When** the extractor fills the artifact, **Then** the missing sub-field is defaulted to `{value: null, confidence: 0.0, evidence: []}` (or `{value: null, currency: null, confidence: 0.0, evidence: []}` for `total_amount`), `warnings` names the defaulted field, and `status` is set to `"partial"`.
4. **Given** the model returns no usable content at all (empty response, unparseable content that cannot be repaired, explicit refusal), **When** the extractor finishes, **Then** either (a) `edge_extraction_output.json` is written with `status == "failure"`, all field values `null`, all confidences `0.0`, all evidence arrays empty, and `warnings` explaining the cause, OR (b) the extractor exits non-zero with no artifact — the chosen convention must be consistent and documented, and the artifact-with-failure-status path is preferred so downstream consumers can see the failure without log archaeology. See Edge Cases §"Hard-failure vs. status=failure split (US5 AC#4)" for the deterministic tie-break: failures that prevent reconciliation from running (unreachable endpoint, input contract drift, unrepairable JSON, voter config invalid, folder-write error) take path (b) with a non-zero exit per `research.md` §R-011; failures that surface *after* reconciliation runs (blank packet, total evidence drop, all values null) take path (a) with exit code `0`.
5. **Given** any soft-failure output (`status == "partial"` or `status == "failure"`), **When** `warnings` is inspected, **Then** every warning is a non-empty, human-readable string that names what went wrong and where (field name, page, or stage).
6. **Given** any run that writes `edge_extraction_output.json`, **When** the file's schema validity is checked, **Then** validation passes regardless of `status`. A failing extraction still produces a schema-valid artifact; `status == "failure"` is a reported outcome, not a schema violation.

### Edge Cases

- **Input `preprocess_output.json` reports its own partial/failed ingestion (FR-023)**: When `preprocess_output.json` reports per-ingestion-source `status == "failure"` or a non-empty top-level `warnings` array, the extractor proceeds best-effort, uses whatever block/line evidence is present, and MUST record the input-side partiality in its own `extraction_notes` (descriptive) or `warnings` (conditioning signal). It does not refuse to run on a partial-but-schema-valid packet. Input-side partiality does not by itself force `status` below `"success"` — it contributes to the narrative so the operator can see that the input was already degraded.
- **`preprocess_output.json` has zero blocks and zero OCR lines on every page** (blank document): The extractor writes a schema-valid output with `status == "failure"` or `status == "partial"`, all `vendor_candidate` and `invoice_header_fields` defaulted to null values with empty evidence, and a warning explaining the empty input.
- **Document appears not to be an invoice**: `document_type.value` is restricted to `"invoice"` by the v1.0.0 schema. If the model's best judgment is "not an invoice", the extractor still emits `document_type.value == "invoice"` (the enum forces it), lowers `document_type.confidence`, and adds an `extraction_notes` entry describing the mismatch. Stage 1 does not try to classify non-invoice documents; that is out of scope for this feature.
- **Multi-page document with strong vendor signals on page 2 and noise on page 1**: The extractor's evidence IDs include the page prefix (`p2_b7`), so grounding to later pages is explicit and unambiguous. No page-1 preference is baked in.
- **Document contains two plausible vendors (multi-entity header, remit-to block)**: The extractor picks one (ideally the billing entity) and grounds its decision in evidence. The `remit_to_differs_from_vendor` concern is evaluated by the test harness through `challenge_tags`, not by this extractor at run time.
- **Currency on `total_amount` is ambiguous** (e.g., a bare "$" that could be USD or CAD): `total_amount.currency` may be `null` and `confidence` should reflect the uncertainty. Currency is not inferred from the vendor address by this layer; evidence-first.
- **Two invocations against the same folder**: The second invocation overwrites the prior `edge_extraction_output.json`. The extractor does not hold history; version control does. (Re-running with a different voter configuration is the US4 path; that writes the same canonical filename unless ensemble mode is enabled later, at which point voter-specific files go under `votes/`.)
- **`preprocess_output.json` claims `contract_set_version != "1.0.0"`**: The extractor refuses to run, exits non-zero, and names the drift. Extraction is pinned to the frozen contract set.
- **Model returns evidence IDs with correct format but referring to a DIFFERENT document's blocks**: Since the extractor only has access to one `preprocess_output.json` at a time, any ID that doesn't resolve in *this* packet is filtered out per US2 — the extractor does not cross-check against other documents.
- **Host Ollama is running but does not have the configured model pulled**: This is a hard failure (model unavailable); the extractor exits non-zero with a clear error naming the missing model. The extractor does not attempt to pull models on behalf of the operator.
- **Low-determinism behavior from the model**: Two extractions of the same document against the same model/version may produce different string values or confidences. The extractor does not attempt to force bit-exact model output. What *is* deterministic: the input-packet reading, the evidence-reconciliation logic, the schema-fill defaults, and the `status` derivation given a fixed model response.
- **Model returns valid JSON with extra keys not defined in the output schema**: The extractor MUST ignore unknown top-level or sub-field keys emitted by the model (they do not appear in the emitted artifact) and MUST NOT treat their presence as an error. The pre-persist schema validation from FR-002 enforces that only schema-defined keys reach disk. Unknown keys are silently dropped; no `warnings` entry is required for this case because the schema contract is what downstream consumers rely on, not the model's inventive extensions.
- **Hard-failure vs. status=failure split (US5 AC#4)**: The extractor distinguishes failures that prevent reconciliation from running at all (Ollama unreachable, input contract drift, unrepairable model JSON, voter config invalid, folder-write error) from failures that surface after reconciliation runs (blank packet, total evidence drop, every `value` null). The former exit non-zero per the exit-code table (`research.md` §R-011) with no artifact written. The latter produce a schema-valid artifact with `status == "failure"`, every `value` null, every `confidence` `0.0`, every `evidence` empty, an explanatory `warnings` entry, and exit code `0`. This is the preferred convention from US5 AC#4 — "the run happened, the result failed" is discoverable from the artifact alone.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The extractor MUST accept one per-document folder as input, read that folder's `preprocess_output.json`, call the configured voter through host Ollama over HTTP, and write `edge_extraction_output.json` into the same folder.
- **FR-002**: Every `edge_extraction_output.json` the extractor writes MUST validate against `contracts/stage1_vendor_identity/v1.0.0/edge_extraction_output.schema.json` and MUST set `contract_set_version` to `"1.0.0"`.
- **FR-003**: The extractor MUST refuse to run when the input `preprocess_output.json` reports `contract_set_version != "1.0.0"`, when `preprocess_output.json` is missing or unreadable, or when it fails its own schema validation. In all three cases it exits non-zero with a clear error and writes no output.
- **FR-004**: `document_id` in the output MUST equal `document_id` in the input `preprocess_output.json`. The two MUST NOT diverge.
- **FR-005**: `model_runtime` MUST be populated with non-empty `provider`, `model_name`, `model_version`, and `runtime`, together identifying the inference endpoint, the model, its version, and its runtime context. For this feature's full-workstation path the provider is host Ollama, the model is Gemma 4 E4B, the `runtime` identifies the host Ollama / ROCm path, and `model_version` pins the specific variant.
- **FR-006**: `vote_metadata` MUST be populated with a non-empty `voter_id`, `voter_role == "primary_extractor"`, and `consensus_mode == "single_voter_baseline"`. The extractor MUST NOT emit any other `consensus_mode` value in stage 1.
- **FR-007**: `vendor_candidate` MUST populate every required sub-field (`company_name`, the 6 address components, the 4 tax-ID slots, `website`, `phone`, `email`) with `{value, confidence, evidence}` keys per the schema. Missing observations use `value = null`, not empty strings.
- **FR-008**: `invoice_header_fields` MUST populate `invoice_number`, `invoice_date`, and `total_amount`. `total_amount` uses the expanded shape `{value, currency, confidence, evidence}` where `value` is a number-or-null and `currency` is a string-or-null.
- **FR-009**: `document_type` MUST be populated with `value == "invoice"` and a confidence in `[0.0, 1.0]`. Stage 1 does not classify non-invoice documents; when the model's judgment is that the document is not an invoice, the extractor still emits `"invoice"` and lowers the confidence, adding an `extraction_notes` entry.
- **FR-010**: Every `evidence` array in the output MUST contain only strings matching `^p\d+_[bl]\d+$` that also resolve to a real `block_id` or `line_id` in the corresponding `preprocess_output.json`. Unresolvable IDs MUST be filtered out before the artifact is written, and each drop MUST produce a `warnings` entry naming the field and the dropped ID. Surviving evidence IDs MUST be preserved in first-seen order and deduplicated; the same ordering and deduplication rule applies uniformly to every `evidence` array in the output, and to `warnings` and `extraction_notes` entries (first-seen order, no duplicates) so that SC-009's reconciliation-determinism claim holds at the byte level modulo `processed_at` / `pipeline_version`.
- **FR-011**: When a field's final `evidence` array is empty after reconciliation, the extractor MUST retain the model-proposed `value` and MUST apply a hard confidence cap: `confidence = min(confidence, UNGROUNDED_CONFIDENCE_CAP)` where `UNGROUNDED_CONFIDENCE_CAP` is a fixed constant pinned by configuration. The cap MUST be applied deterministically after evidence reconciliation and before the artifact is written. Its numeric value is pinned at `0.30` in the stage-1 gemma-edge voter config (`contracts/voter-config.md`, `research.md` §R-003); the shape (a hard ceiling, not a multiplicative scale) is fixed here.
- **FR-012**: For `company_name`, if the final `evidence` array is empty after reconciliation, the extractor MUST deterministically set `company_name.present = false` and `company_name.inferred = true`, regardless of what the model claimed. An `extraction_notes` or `warnings` entry MUST record the override.
- **FR-013**: The extractor MUST NEVER emit `company_name.present == true` AND `company_name.inferred == true`. It MUST NEVER emit `company_name.present == false` AND `company_name.inferred == false`. Exactly one of "explicit" or "inferred" holds for every document.
- **FR-014**: `status` MUST be `"success"` when extraction produced a meaningful artifact with no non-fatal warnings; `"partial"` when the artifact was produced but at least one field defaulted to null-on-missing, JSON required repair, or an evidence ID was dropped; and `"failure"` when the extractor could not produce a meaningful result and writes a defaulted artifact. The distinction among the three values MUST be deterministic given a fixed model response.
- **FR-015**: When the Ollama endpoint is unreachable (connection refused, DNS failure, or the request exceeds the configured timeout), the configured model is not available on the endpoint, or the model returns content that cannot be repaired into JSON, the extractor MUST exit non-zero and write no `edge_extraction_output.json`. The extractor MUST use a single bounded request timeout (pinned at 180 s read / 10 s connect in the stage-1 gemma-edge voter config per `research.md` §R-002, overridable per-voter) and MUST NOT retry internally — retry policy is an orchestrator concern. Hard failures that prevent reconciliation from running at all (unreachable endpoint, input contract drift, unrepairable model response) surface through the process exit, not through a partial artifact. Failures that are detected *after* reconciliation runs (e.g., reconciliation produced a fully-null artifact) surface as `status == "failure"` on a schema-valid artifact with exit code `0` — see Edge Cases.
- **FR-016**: When the model returns valid JSON but a required sub-field is absent — or the model supplies a value whose type cannot satisfy the schema for that sub-field (e.g., a string where a number is required, an object where a scalar is required) — the extractor MUST default the sub-field to `{value: null, confidence: 0.0, evidence: []}` (or `{value: null, currency: null, confidence: 0.0, evidence: []}` for `total_amount`), record the default in `warnings` naming the sub-field and distinguishing "missing" from "wrong-type", and set `status` to `"partial"`. Wrong-type defaulting is a soft failure, not a hard failure — the policy is default-and-warn, not exit-non-zero.
- **FR-017**: The extractor MUST be pluggable-voter-ready: swapping the configured Gemma 4 E4B slot for another voter (Gemma 4 E2B, Qwen-family, Phi-4 Mini, etc.) MUST require only voter configuration and a corresponding prompt/adapter, not changes to the input contract, the output contract, the evidence-reconciliation behavior, the folder layout, or the extractor's public invocation shape. Voter configuration MUST live in a per-voter YAML config file selected at invocation time by a `--voter <name>` CLI flag and MUST pin at minimum: model tag, `voter_id`, prompt/adapter reference, sampling config, and the `UNGROUNDED_CONFIDENCE_CAP` from FR-011. The Ollama endpoint URL is a separate, host-level concern sourced from the `OLLAMA_BASE_URL` environment variable and is NOT part of the voter config.
- **FR-018**: The extractor MUST honor the folder contract's reserved names: it writes `edge_extraction_output.json` into the per-document folder and MUST NOT write `preprocess_output.json`, `routing_decision.json`, `final_structured_payload.json`, `evaluation_document.json`, `consensus_output.json`, or anything inside `votes/` during a stage 1 single-voter run.
- **FR-019**: The extractor MUST NOT modify `preprocess_output.json`, `expected.json`, `notes.md`, `source.pdf`, or any other file it did not create. Inputs are read-only.
- **FR-020**: The extractor MUST NOT implement or invoke routing logic, consensus comparison, final-payload assembly, or evaluation. It is a pure extraction stage; downstream slices (006 routing, 007 final payload, 007/008 evaluator) consume its output.
- **FR-021**: The extractor MUST NOT attempt cloud escalation, line-item extraction, latency-based gating, or multi-voter orchestration. Those are explicitly out of stage 1 scope.
- **FR-022**: `processed_at` MUST be a valid ISO-8601 date-time in UTC. `pipeline_version` MUST be a non-empty string identifying the build that produced the artifact.
- **FR-023**: When `preprocess_output.json` itself reports `warnings` or a per-ingestion-source `status == "failure"`, the extractor MUST proceed best-effort and MUST record the input-side partiality in its own `extraction_notes` or `warnings`. It MUST NOT refuse to run purely because the input packet was partial-but-schema-valid.
- **FR-024**: The shape of `edge_extraction_output.json` MUST be identical across voter configurations. Only `model_runtime`, `vote_metadata.voter_id`, and the model-dependent scalar values / confidences / evidence selections are allowed to vary between voters.
- **FR-025**: The extractor MUST be invokable as `python -m dartwing_ocr.extract --folder <path> --voter <name>`, where `<path>` is a per-document folder containing a schema-valid `preprocess_output.json` and `<name>` selects a voter config file. This mirrors the existing `python -m dartwing_ocr.validator` submodule pattern. The `--folder` and `--voter` flags are required; the Ollama endpoint URL is sourced from the `OLLAMA_BASE_URL` environment variable (see FR-017). An optional `--voter-config <path>` flag MAY override the packaged voter config resolution for ad-hoc test fixtures and local experimentation; when supplied, `<path>` points at a YAML file on disk and bypasses the `DARTWING_VOTER_CONFIG_DIR` + packaged-config resolution order documented in `contracts/cli-contract.md`. The override does not change the required flag surface or any other extractor behavior.

### Key Entities

- **Per-document folder**: One corpus document's on-disk home. Holds `source.pdf`, `expected.json`, optional `notes.md`, `preprocess_output.json` (input to this feature), and `edge_extraction_output.json` (output of this feature).
- **Preprocessing packet (`preprocess_output.json`)**: The frozen v1.0.0 input artifact this extractor consumes. Read-only. Supplies `document_id`, per-page blocks with `block_id` and text, per-page OCR lines with `line_id` and text, document-level quality signals, `ingestion_sources` status flags, and `document_text`.
- **Edge extraction artifact (`edge_extraction_output.json`)**: The frozen v1.0.0 output artifact this extractor produces. Conforms to `edge_extraction_output.schema.json`. Keys include `contract_set_version`, `pipeline_version`, `document_id`, `processed_at`, `model_runtime`, `vote_metadata`, `document_type`, `vendor_candidate`, `invoice_header_fields`, `extraction_notes`, `warnings`, and `status`.
- **Voter**: One model configuration that produces an `edge_extraction_output.json`. In this feature's default full-workstation path there is exactly one voter (Gemma 4 E4B through host Ollama, `voter_role = "primary_extractor"`). Runtime-profile work adds the smaller Gemma 4 E2B config for the Jetson edge-fast stack without changing this artifact contract. The target architecture runs three voters; this feature keeps that path open without implementing it.
- **Vote metadata (`vote_metadata`)**: Identifies which voter produced this artifact (`voter_id`), what role it played (`voter_role`), and what consensus mode the run operated under (`consensus_mode`, pinned to `"single_voter_baseline"` in v1.0.0).
- **Model runtime (`model_runtime`)**: Identifies the inference provider, model, model version, and runtime context. For this feature's default path this pins the host Ollama path plus Gemma 4 E4B.
- **Evidence ID**: A string matching `^p\d+_[bl]\d+$` that references a block or OCR line in the input preprocessing packet. Every extracted field's `evidence` array is a list of these IDs.
- **Reconciliation step**: The deterministic post-model pass that filters unresolvable evidence IDs, defaults missing sub-fields, enforces the company-name provenance invariants, derives the `status` value, and fills `warnings`. The model does not own this step; code does.
- **Invocation status (`status`)**: One of `"success"`, `"partial"`, `"failure"`, reflecting whether extraction finished cleanly, finished with non-fatal issues, or could not produce a meaningful result.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Running the extractor against one valid per-document folder produces a schema-valid `edge_extraction_output.json` that passes `contracts/stage1_vendor_identity/v1.0.0/edge_extraction_output.schema.json` validation 100% of the time, across all 20 corpus documents, for the stage 1 Gemma 4 E4B voter configuration.
- **SC-002**: On the 5 missing-name documents in the corpus, 100% of extractor outputs satisfy `company_name.present == false` AND `company_name.inferred == true` AND exactly one of the two invariants from FR-013 (never both true, never both false). No document in the missing-name bucket can produce an output that claims an explicit name.
- **SC-003**: 100% of `evidence` arrays in any extractor output resolve fully against the corresponding `preprocess_output.json`. Zero outputs contain an evidence ID that does not exist in the input packet after reconciliation.
- **SC-004**: Replacing the stage 1 Gemma 4 E4B voter with a different configured voter (even a stub/mock voter for testing) produces a schema-valid output whose `model_runtime` and `vote_metadata.voter_id` differ, while `document_id`, the overall artifact shape, the evidence-reconciliation behavior, and the folder layout are identical. Zero code changes outside the voter configuration are required.
- **SC-005**: On hard failures (Ollama unreachable, input packet missing or schema-invalid, `contract_set_version` drift, configured model not available on the endpoint), the extractor exits non-zero 100% of the time, writes no `edge_extraction_output.json`, and emits a human-readable error naming the failure cause.
- **SC-006**: On soft failures (JSON repair needed, dropped evidence IDs, defaulted missing sub-fields), the extractor produces a schema-valid artifact with `status` in `{"partial", "failure"}` and at least one human-readable `warnings` entry naming the condition. Reviewer can identify the condition from the artifact alone without consulting logs.
- **SC-007**: The extractor's total wall-clock time on one document, excluding the model call itself, is under 2 seconds on the `pipeline-dev` devcontainer (CPU-only, Python 3.12 — the constitutionally-pinned execution surface for pipeline code). (The model call itself is outside the extractor's control and is not a release gate in stage 1.)
- **SC-008**: A developer swapping the configured Gemma slot for the eventual Qwen edge slot can do so by changing configuration without editing the extractor's input parser, output writer, reconciliation logic, or folder-write behavior. Only the voter-adapter/prompt module changes.
- **SC-009**: Given the same `preprocess_output.json` and a fixed model response (e.g., a recorded fixture), the extractor's reconciliation logic, `warnings`, `status`, `vendor_candidate.company_name.present`/`.inferred`, and overall artifact shape are deterministic across invocations. Only `processed_at` and potentially `pipeline_version` are allowed to vary.
- **SC-010**: The artifact alone is sufficient input for the 006 routing slice: no routing-relevant information (company-name provenance, per-field confidence, per-field evidence, missing-name posture) lives outside `edge_extraction_output.json` and therefore no downstream slice must re-read `preprocess_output.json` to determine provenance.

## Assumptions

- Stage 1 operates in single-voter baseline mode. The multi-voter ensemble and its consensus logic are forward-compatible obligations captured by `vote_metadata` and the reserved `votes/` subdirectory, but are out of scope for this feature.
- Host Ollama on this workstation is the only GPU-capable inference path. The optional WSL container path is CPU-only and not production-representative; this feature targets the host path. Native Linux ROCm containerization is the production lane and is explicitly out of scope here.
- Gemma 4 E4B is the stage 1 full-workstation Gemma slot per `implementation-plan.md` and `prd-model-pipeline.md`. The Jetson edge-fast stack uses the smaller Gemma 4 E2B voter config through the runtime-profile feature; selecting the exact model tag/variant remains a configuration concern pinned by implementation plans, not a schema-level decision.
- `preprocess_output.json` at `contract_set_version = "1.0.0"` is the only supported input shape. The extractor does not accept legacy preprocessing artifacts.
- `edge_extraction_output.json` at `contract_set_version = "1.0.0"` is the only supported output shape. Amendments to the contract require the governance path in `contracts/stage1_vendor_identity/AMENDMENTS.md` and are out of scope for this feature.
- LLMs are not bit-exact deterministic even at temperature zero. Stage 1 voter configs default to temperature = 0 and a fixed seed where Ollama and the selected model support seeded sampling, and per-voter configs MAY override both. What the extractor contractually guarantees is schema-shape determinism, reconciliation determinism, status-derivation determinism, and provenance-invariant determinism — not identical value strings across runs. Value determinism is best-effort under temp-0 + seed, not a release gate.
- The extractor is artifact-to-artifact from an orchestration perspective: it consumes one preprocessing artifact and produces one extraction artifact per invocation. Corpus-level orchestration (running across all 20 documents) lives in the harness and is not defined by this feature.
- Routing (006), final-payload assembly (007), and evaluation (008 / 007-evaluator) consume the extractor's output read-only. This feature does not implement or invoke any of them.
- The `invoice_header_fields` block (`invoice_number`, `invoice_date`, `total_amount`) is emitted even though stage 1 evaluation focuses on vendor identity. The schema requires it, and producing it now keeps future slices from needing a second extractor pass.
- Prompt engineering and model output schema-nudging techniques (system prompts, structured-output directives, JSON grammar constraints) are implementation concerns delegated to the plan and implement phases. This spec does not prescribe a prompt.
- The initial Qwen stage 1 variant (open question #2 in `prd-model-pipeline.md`) is not required to be answered by this feature. This feature delivers a Gemma-voter-only baseline with a pluggable interface; Qwen selection is a later configuration decision that the interface is designed to accept.
