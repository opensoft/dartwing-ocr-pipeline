# Implementation Plan: GPU Engine Reuse And Phase Timing

**Branch**: `015-gpu-engine-reuse-timing` | **Date**: 2026-05-07 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/015-gpu-engine-reuse-timing/spec.md`

## Summary

Optimize the proven `ppstructurev3@gpu` preprocessing path by collapsing the duplicated PPStructureV3 init that currently fires once during `classify()` (step 6) and again during runtime `_get_engine(device="gpu:0")`, while adding the FR-013 phase timings to the existing `kind: "run_summary"` stdout line so the remaining latency is data-driven. The fix is two-part: (1) classify's PPStructureV3 probe persists its constructed engine into the runtime singleton (`ocr._ENGINE` / `_ENGINE_DEVICE`) instead of destroying it, so step 6 *is* the runtime engine; (2) timing instrumentation around Paddle import, GPU bind probe, engine init, rasterization, per-page inference, and artifact write is collected into a structured `phase_timings` object plus a `per_page_inference` array on each per-document run_summary entry, with a `schema_version` patch bump (0.1.1 → 0.1.2). Optional MIOpen/COMGR warmup is reserved as a phase only (Clarification Q2 — no synthetic warmup). CPU and stub paths remain GPU-cost-free (FR-017–FR-019).

**Structure Decision**: single Python package, mutating five existing modules and adding three test modules. No new top-level subpackage. The phase_timings + per_page_inference contract lives entirely under `pipeline/timing.py` (the `RunSummary` dataclass) — this keeps the run_summary schema as the single source of truth for run-level observability, consistent with feature 011's establishment of the `kind: "run_summary"` final stdout line.
