# Feature Specification: PPStructureV3 Preprocessing Migration

**Feature Branch**: `010-pp-structurev3-preprocessing`
**Created**: 2026-04-22
**Status**: Draft
**Input**: User description: "Migrate stage 1 PDF preprocessing from PaddleOCR 2.10 (PPStructure + PP-OCRv4) to PaddleOCR 3.5 (PPStructureV3 + PP-OCRv5) so layout detection works on invoice-style documents instead of silently returning zero regions. Authoritative context: docs/stage1-vendor-identity/prd-ppstructurev3-migration.md."

## Background

Authoritative context: `docs/stage1-vendor-identity/prd-ppstructurev3-migration.md`. That PRD captures the problem statement, goal, scope boundaries, risks, and fallback strategy. This spec restates only what is necessary to express user stories, requirements, and measurable success criteria. Where this spec and the PRD disagree, the PRD wins and this spec must be updated.

## Clarifications

### Session 2026-04-22

- Q: When engine init fails because model weights cannot be downloaded or cached, what does preprocessing do? → A: Hard-fail — non-zero exit, no `preprocess_output.json` written, error message names the missing model and the upstream hoster.
- Q: Is the PRD's PaddleOCR 2.10 + CDLA fallback delivered as code in this slice? → A: Doc-only — fallback decision and trigger criteria recorded in `research.md`; no 2.10 code path ships in this slice.
- Q: When a page has ≥ 2 OCR lines but only a single layout block, what happens? → A: Emit a "suspicious layout: single block covers multi-line page" warning naming the page; do not downgrade `ingestion_sources.paddleocr_vl.status`.
- Q: Does FR-002's "≥1 block per legible page, non-empty `document_text`" rule apply to the missing-name subset (`company_name.present == false, inferred == true`)? → A: Uniform — FR-002 applies to every corpus document regardless of vendor-identity label polarity.
- Q: What form do the FR-010 OCR-text delta notes take in the regeneration commit? → A: Per-document summary in the commit body — one line per regenerated doc with a nonzero OCR-text diff, classifying the kind of shift (e.g., `inv_003: ampersand→"and" (PP-OCRv5 tokenizer)`).
- Q: What happens when the layout pass succeeds (`blocks > 0`) but the engine's built-in OCR returns zero lines on a page that has ≥ 1 text-type block? → A: Symmetric to FR-003 — emit a per-page warning and downgrade `ingestion_sources.paddleocr_vl.status` to `"failure"`. Evidence-first reasoning applies equally on either axis.
- Q: Does hard-fail init behavior apply only to weight-download failures, or to any engine-init failure? → A: Umbrella — any failure during engine initialization (weight download, paddle exception, oneDNN bug re-firing, import error) triggers hard-fail with non-zero exit and no artifact. The error message names the underlying cause; FR-016's hoster detail applies only when the cause is weight-related.
- Q: Are warning-category prefixes pinned in the spec for grep testability? → A: Yes — each warning category gets a bracketed token prefix in a fixed format (`[silent_empty_layout]`, `[silent_empty_ocr]`, `[suspicious_single_block]`, `[unknown_layout_label]`), placed immediately after the `page N:` prefix. This pins SC-002's grep pattern and makes categories machine-distinguishable without parsing prose.
- Q: During the FR-010 corpus regeneration sweep, what happens if engine init fails on document K of N? → A: Halt immediately — no partial baselines committed, the sweep is re-run after the env is fixed. Init failure is environmental and regenerating the remainder would produce an inconsistent / potentially mixed-engine baseline.
- Q: How is FR-002's "page has legible text" operationalized? → A: A page "has legible text" iff `len(raw_ocr_lines) > 0` on that page. FR-002 is the positive inverse of FR-003's violation trigger; no separate legibility detector or concept enters the artifact.
- Q: What match semantics does SC-001's "`document_text` contains at least one vendor-identity token" use? → A: Case-insensitive substring match — both sides lowercased before `in`. Handles PP-OCRv5 casing shifts (all-caps ↔ mixed-case), works on multi-word vendor names without a tokenizer, no Unicode normalization needed for the ASCII-dominant US-invoice corpus.
- Q: Is FR-010's per-document shift classification in the regeneration commit body a closed vocabulary or free-form prose? → A: Free-form prose per line. The commit body is read once during regeneration review; no scripted consumers. FR-020's bracketed-token vocabulary stays scoped to the artifact's `warnings` array where grep-testability matters.
- Q: Where is SC-005's first-run wall-clock time + hardware context recorded? → A: `specs/010-pp-structurev3-preprocessing/research.md` under a "Baseline timings" heading. Already the canonical ops-notes home for this slice (FR-011, FR-012, FR-017, SC-007); keeps related context discoverable in one file and survives past the landing commit.
- Q: What `pipeline_version` scheme does FR-008 adopt? → A: Bump both axes: `stage1-preprocess-v0.2.0+paddleocr3.5.0.<sha>.dpi300`. The preprocessing portion bumps from `v0.1.0` to `v0.2.0` to signal the material silent→loud / blocks-absent→blocks-present behavior change; the engine portion reflects the new upstream version. Downstream consumers can gate on either axis independently.
- Q: How does preprocessing handle multi-page PDFs now that PPStructureV3 has a much larger memory footprint? → A: Rasterization and inference stream one page at a time. Preprocessing does not materialize every page image for the document before OCR/layout begins; each page is rendered, processed, and released before the next page is rasterized.
- Q: Does preprocessing need previous/next page header or footer context to OCR the current page correctly? → A: No — OCR/layout stays page-local. Cross-page header/footer reconciliation is a later post-processing concern, not part of stage 1 preprocessing.
- Q: How are low-confidence OCR lines filtered under PP-OCRv5's built-in recognizer? → A: Use the engine's default recognition confidence threshold without override; the exact default value (as emitted by the pinned engine version) is recorded in `specs/010-pp-structurev3-preprocessing/research.md`, so a future engine bump that moves the default is caught during review.
- Q: Does the artifact's `tables[]` field get populated from PPStructureV3's table recognizer, or left empty for this slice? → A: Populate `tables[]` from PPStructureV3, projected into the v1.0.0 schema shape; any richer HTML / cell-level structure that the engine emits beyond the schema is discarded at the persistence boundary, consistent with the existing Assumptions rule for richer per-block content.
- Q: How is the `confidence` field on each block and each OCR line sourced under PPStructureV3 / PP-OCRv5? → A: Persist the engine-emitted confidence verbatim (float as returned, no clamping, no normalization); when the engine emits no confidence for a given block or line, record `null` (never `0.0`, never empty). Future engine-version shifts in confidence semantics are caught by FR-010 baseline regeneration review.
- Q: What is the emission policy for debug `page_*.png` images — default vs. opt-in, committed vs. local, and are they covered by FR-004 determinism? → A: Opt-in only (via an explicit CLI flag), never committed to the corpus, and explicitly outside FR-004's byte-identical determinism guarantee. PNGs are a developer-facing investigation tool; FR-004 applies to `preprocess_output.json` alone.

- Q: Which CLI exit codes trigger the FR-010 corpus-sweep halt — only FR-016 engine-init (`3`), or any non-zero exit? → A: Any non-zero exit (`1` unexpected, `2` input_rejected, `3` internal_error). Matches the quickstart §5 `set -e` bash loop already prescribed. Halt rule is about baseline integrity — any non-zero means a document's artifact failed to land, and proceeding would leave the corpus with a partial/inconsistent baseline. This also covers the encrypted-PDF edge case (exit `2`) without a separate rule.
- Q: When a future AMENDMENTS entry adds optional fields to the v1.0.0 `tables[]` / cell schema, does FR-021's projection auto-pick-them-up or require a matching code change? → A: Strict-current-shape. FR-021 projects into the exact set of `tables[]` / cell fields defined by the v1.0.0 schema **as of 010's landing commit**. Future AMENDMENTS entries that widen the schema (e.g., adding optional `cell_confidence`) require a matching preprocessing code change to start populating the new field; silent schema-widening with no code change is prohibited. Avoids a drift where the schema accepts more than preprocessing emits.
- Q: A page with `len(raw_ocr_lines) > 0 AND len(blocks) > 0` but zero geometric overlap (no block's bbox contains any OCR line) — does any FR fire? → A: Out-of-scope for this slice. The condition is rare on invoice PDFs and none of FR-003/FR-018/FR-019 fires today. An Edge Case note is added so future readers don't re-discover the gap. If the corpus surfaces the condition in practice, a follow-up slice adds a fifth warning category (`[orphan_ocr_lines]` or similar) via an FR-020 vocabulary extension + AMENDMENTS entry. No defensive code lands in this slice.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Preprocessing a Real Invoice Produces Usable Layout Evidence (Priority: P1)

A pipeline developer runs stage 1 preprocessing against an invoice PDF from the labeled corpus. Today, preprocessing silently produces an artifact with populated `raw_ocr_lines` but zero `blocks` and an empty `document_text`. After this change, the same invocation produces an artifact with multiple layout blocks, non-empty `document_text`, and `ingestion_sources.paddleocr_vl.status = "success"` — meaning the evidence-packet, extractor, and router stages downstream can actually do their jobs against real layout evidence.

**Why this priority**: This is the blocker. Every downstream stage 1 slice (evidence packet, extraction, routing, evaluator) assumes populated `blocks` and `document_text`. Shipping the pipeline on top of the current silent-zero-blocks output would produce confident vendor-identity payloads unsupported by layout evidence, directly violating the evidence-first rule in `.specify/memory/constitution.md`. Without this story, nothing past preprocessing can legitimately move off stubs.

**Independent Test**: Run preprocessing against `tests/stage1_vendor_identity/inv_001_easy/source.pdf`. Open the resulting `preprocess_output.json` and verify (a) `pages[0].blocks` has at least three entries with valid `block_type`, `bbox`, `reading_order`, and non-empty `text`; (b) `document_text` is non-empty and contains the vendor-identity token `"DESERT DIECUTTING"` (or its V3-OCR-equivalent spelling); (c) `ingestion_sources.paddleocr_vl` reports `enabled == true` and `status == "success"`; (d) the artifact validates against `contracts/stage1_vendor_identity/v1.0.0/preprocess_output.schema.json`.

**Acceptance Scenarios**:

1. **Given** the corpus invoice `inv_001_easy/source.pdf` and preprocessing configured per this spec, **When** preprocessing runs, **Then** `preprocess_output.json` is written to the same folder, validates against the frozen v1.0.0 contract, carries `page_count == 1`, has `pages[0].blocks` with length `>= 3`, and `document_text` contains at least one token from the document's `expected.json` vendor-identity fields.
2. **Given** any invoice PDF in `tests/stage1_vendor_identity/inv_XXX_<difficulty>/` that today produces zero blocks, **When** preprocessing runs under the new engine, **Then** the same document produces a non-empty `blocks` array and a non-empty `document_text`, and no block carries an unknown or unmapped `block_type`.
3. **Given** a multi-page invoice PDF, **When** preprocessing runs, **Then** every page that contains legible text produces both OCR lines and at least one layout block, with page-scoped `block_id` (`p{page}_b{n}`) and `line_id` (`p{page}_l{n}`) remaining deterministic across reruns, and rasterization/inference proceeds one page at a time rather than requiring whole-document raster materialization.

### User Story 2 - Silent Layout Failures Become Visible (Priority: P1)

When a page still produces zero layout blocks despite the page having OCR lines — because a future engine regression, a blank or near-blank page, or an unseen document format — preprocessing surfaces the condition loudly instead of swallowing it. The artifact's `warnings` array carries a per-page warning identifying the page, and `ingestion_sources.paddleocr_vl.status` is downgraded to `"failure"` so downstream stages can gate on that signal.

**Why this priority**: Equal weight with Story 1 because the whole reason Story 1 exists is that today's code fails silently. Fixing the engine without fixing the silent-failure path only delays the next time we miss a regression. This defensive behavior must land regardless of which engine we run — it is also the core of the PRD's fallback path.

**Independent Test**: Stage a synthetic preprocessing invocation where the layout engine is stubbed to return no regions while OCR lines are still produced. Run preprocessing. Verify the output contains a warning of the form `"page N: layout returned zero blocks while OCR produced K lines"` and `ingestion_sources.paddleocr_vl.status == "failure"`. The artifact must still validate against the v1.0.0 contract.

**Acceptance Scenarios**:

1. **Given** a page where the layout engine returns zero regions and OCR returns at least one line, **When** preprocessing assembles the artifact, **Then** `warnings` contains a human-readable entry naming the affected page and the number of OCR lines present, and `ingestion_sources.paddleocr_vl.status` is `"failure"`.
2. **Given** a page that is legitimately blank (zero OCR lines and zero layout blocks), **When** preprocessing assembles the artifact, **Then** no silent-empty warning is emitted for that page, because the "lines exist but blocks don't" condition is absent. The existing "paddleocr_vl: failure (all pages failed)" aggregate warning continues to apply when every page is empty.
3. **Given** a document where at least one page produces healthy blocks and one page hits the silent-empty condition, **When** preprocessing completes, **Then** the healthy page's blocks are preserved, the silent-empty page carries its own warning, and `status == "failure"` at the document level — no mixed-status is emitted because the contract's status enum has no "degraded" value.

---

### User Story 3 - Corpus Baselines Regenerate Deterministically (Priority: P2)

A developer running the full stage 1 corpus through preprocessing (`inv_001..inv_020`) produces a full set of `preprocess_output.json` artifacts whose contents are byte-identical on reruns. The regenerated set becomes the new committed baseline, and future preprocessing changes are reviewed as diffs against it.

**Why this priority**: Reproducibility is what makes the evaluator meaningful. Without determinism, two runs of the same invoice produce different `preprocess_output.json`, which cascades into non-deterministic `edge_extraction_output.json` and nondifferentiable evaluation summaries. P2 rather than P1 because this story depends on Story 1 and Story 2 being in place first.

**Independent Test**: Run preprocessing across the full corpus root, sha256 each `preprocess_output.json`, rerun preprocessing across the same corpus, and confirm every digest matches. The corpus validator (`python -m ledgerlinc_ocr.validator validate corpus tests/stage1_vendor_identity`) passes with zero artifact errors.

**Acceptance Scenarios**:

1. **Given** a corpus where every `preprocess_output.json` has been regenerated under this spec, **When** preprocessing runs a second time, **Then** each resulting artifact is byte-identical to the first run.
2. **Given** a corpus regenerated under this spec, **When** the corpus validator runs, **Then** it reports zero contract violations across the set.
3. **Given** a regenerated corpus and the existing `expected.json` labels unchanged, **When** the extractor and evaluator run downstream on the new baselines, **Then** any field-level deltas relative to the previous baseline are traceable to OCR-text differences (not layout ordering, block id changes, or path-dependent behavior) and are recorded as notes in the regeneration commit.

### Edge Cases

- First-run model weight download fails or is interrupted. Expectation: preprocessing hard-fails — it exits non-zero, writes no `preprocess_output.json` (not even a `status=failure` stub), surfaces an error message naming the missing model and the upstream hoster, and does not silently fall back to an older engine. See FR-016.
- Layout pass succeeds (blocks > 0) but built-in OCR returns zero lines on a page that has ≥ 1 text-type block. Expectation: symmetric to the silent-empty-layout case — warning is emitted, `ingestion_sources.paddleocr_vl.status` is downgraded to `"failure"`, and the artifact is still written. See FR-019.
- Page is legitimately blank (e.g., a trailing blank page in a multi-page PDF): zero OCR lines and zero layout blocks. Expectation: no silent-empty warning for that page; `pages[n].blocks == []` and `raw_ocr_lines == []` are valid outputs; the aggregate all-pages-empty warning still applies when every page matches this condition.
- The layout engine returns a label that is not in the current `{text, title, table, figure, header, footer}` set (e.g., a V3-specific class not yet mapped). Expectation: the unknown label is mapped to `"text"` and a warning is recorded naming the unknown label and the affected page — matching the current 2.10 behavior.
- The paddle 3.3.1 PIR/oneDNN bug fires on a specific document and the `enable_mkldnn=False` workaround is insufficient (e.g., a future patch re-enables oneDNN unexpectedly). Expectation: the engine raises and preprocessing emits a clear `layout extraction failed` warning per the existing `except` branch, `status` is downgraded to `failure`, and the artifact still validates.
- A corpus PDF rasterizes successfully but the V3 engine returns a single giant block covering the whole page (pathological case). Expectation: FR gates below still pass (≥ 3 blocks is the success criterion for inv_001; single-block pages with ≥ 2 OCR lines emit a "suspicious layout" warning per FR-018 but do not downgrade `ingestion_sources.paddleocr_vl.status` and do not block the artifact from being written).
- A multi-page PDF would exceed available workstation memory if every page raster stayed resident until the whole document finished. Expectation: preprocessing still completes because rasterization and inference stream one page at a time; OCR/layout quality stays page-local and does not depend on adjacent-page header/footer context.
- Concurrent preprocessing runs (two processes on the same document folder). Expectation: out of scope — preprocessing is a single-writer tool today and remains so; no file-locking is introduced in this slice.
- A page produces both OCR lines and layout blocks but none of the blocks' bboxes contain (or sufficiently overlap) any OCR line's bbox. Result: every block's `text` field is empty (space-join of zero inclusions) while `raw_ocr_lines[]` is populated; none of FR-003 / FR-018 / FR-019 fires because both counts are > 0. Expectation: out of scope for this slice — the artifact is still schema-valid and is written as-is. If the corpus surfaces this condition in practice, a follow-up slice introduces a fifth warning category (e.g., `[orphan_ocr_lines]`) via an FR-020 vocabulary extension and a matching AMENDMENTS entry.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Preprocessing MUST produce a `preprocess_output.json` that validates against the latest `preprocess_output.schema.json` in `contracts/stage1_vendor_identity/`. Preprocessing's emitted `contract_set_version` stamp stays at `"1.0.0"` (see `src/ledgerlinc_ocr/preprocessing/version.py:CONTRACT_SET_VERSION`); it remains valid under the latest contract set via the validator's major-equal compatibility rule. The only schema change this slice introduces is the v1.2.0 AMENDMENTS entry widening `block.confidence` and `ocr_line.confidence` to accept `null` when the engine omits a score (FR-004 / research R-013); see `contracts/stage1_vendor_identity/AMENDMENTS.md`. No other schema, cross-artifact rule, or validator-rule change is introduced.
- **FR-002**: For every invoice PDF in `tests/stage1_vendor_identity/inv_XXX_<difficulty>/`, including the missing-name subset where `company_name.present == false` and `company_name.inferred == true`, the regenerated `preprocess_output.json` MUST contain `pages[*].blocks` with at least one block for every page that has `len(raw_ocr_lines) > 0` (the operational definition of "page has legible text"), and `document_text` MUST be non-empty. FR-002 is the positive inverse of FR-003's violation trigger: any page where FR-002 holds cannot also fire FR-003, and vice versa. Preprocessing quality is independent of downstream vendor-identity label polarity; the missing-name subset still needs usable layout evidence so the extractor can legitimately conclude "no explicit company name found."
- **FR-003**: When a page has `len(raw_ocr_lines) > 0 AND len(blocks) == 0`, preprocessing MUST append a warning to `warnings` in the form `"page N: [silent_empty_layout] OCR produced K lines but layout returned zero blocks"` (with `N` the 1-based page number and `K` the OCR-line count), and MUST set `ingestion_sources.paddleocr_vl.status` to `"failure"` for the document.
- **FR-004**: Preprocessing MUST be deterministic: running twice on the same input PDF with the same code and dependency versions MUST produce a byte-identical `preprocess_output.json`, including ordering of `blocks`, `raw_ocr_lines`, `reading_order` values, identifiers, bbox values, `document_text`, `warnings` (per FR-020), and the `quality`, `tables`, and `ingestion_sources` blocks. Numeric and encoding stability rules:
    - bbox integer coordinates MUST be produced by `floor` on min-axes (`x0`, `y0`) and `ceil` on max-axes (`x1`, `y1`), clipped to `[0, width]` / `[0, height]`.
    - `text` and `document_text` fields MUST be persisted verbatim from engine output — no Unicode normalization (neither NFC nor NFD) is applied, so glyph-level output is a direct function of the pinned engine version.
    - `confidence` on each block and each OCR line MUST be persisted verbatim from engine output as a float — no clamping to `[0.0, 1.0]`, no renormalization, no sigmoid/min-max remapping. When the engine emits no confidence for a block or line, preprocessing MUST write `null` (never `0.0`, never an empty value), consistent with the constitution's "missing fields use null" rule. A future engine-version shift in confidence semantics surfaces as a diff during FR-010 baseline regeneration review.
- **FR-005**: Preprocessing MUST continue to run CPU-only and single-threaded (`cpu_threads=1`, no multiprocessing), with `paddle.seed(0)` invoked once before first engine construction. The following `PPStructureV3` constructor flags MUST be set to disable the corresponding modules: `use_doc_orientation_classify=False`, `use_doc_unwarping=False`, `use_textline_orientation=False`, `use_formula_recognition=False`, `use_seal_recognition=False`, `use_chart_recognition=False`. `enable_mkldnn=False` MUST also be set on engine construction — both as the workaround for the paddle 3.3.1 PIR/oneDNN bug (per FR-012 and research R-001) and as a determinism axis (oneDNN scratch-buffer layouts are not byte-stable across reruns). No GPU code path is introduced.
- **FR-005a**: Preprocessing MUST rasterize and process documents one page at a time. It MUST NOT require whole-document raster materialization in memory before OCR/layout begins. Each page's raster image MUST be eligible for release once that page's `raw_ocr_lines`, `blocks`, `tables`, and warnings have been derived and copied into artifact-owned data structures. OCR/layout remains page-local in this slice — no previous-page or next-page header/footer context is passed into preprocessing to recognize the current page.
- **FR-006**: Preprocessing MUST map every layout label produced by the new engine onto the existing allowed `block_type` enum `{text, title, table, figure, header, footer}`. Labels without a direct match MUST fall back to `"text"` and MUST produce a per-page warning in the form `"page N: [unknown_layout_label] label=<label_string>"` (with `<label_string>` the unmapped label as emitted by the engine). Unknown-label warnings MUST NOT downgrade `ingestion_sources.paddleocr_vl.status`. This matches current 2.10 behavior.
- **FR-007**: Preprocessing MUST use the new engine's built-in OCR pass as the source of `raw_ocr_lines` rather than running a second, separate OCR engine; the separate `run_ocr_lines()` code path is retired. The engine's default recognition confidence threshold MUST be used without override — no project-specific cutoff is imposed at this slice, so `len(raw_ocr_lines)` (the trigger input for FR-003 and FR-019) reflects the engine's native filtering only. The exact default value, as emitted by the pinned engine version, MUST be recorded in `specs/010-pp-structurev3-preprocessing/research.md`; a future engine bump that moves the default will show up under FR-010 baseline regeneration review.
- **FR-008**: The artifact's `pipeline_version` string MUST reflect the new engine identity. Both axes bump: the preprocessing portion moves from `v0.1.0` to `v0.2.0` to signal the material silent→loud / blocks-absent→blocks-present behavior change, and the engine portion moves to the new upstream version (target shape: `stage1-preprocess-v0.2.0+paddleocr3.5.0.<sha>.dpi300`, previous shape: `stage1-preprocess-v0.1.0+paddleocr2.10.0.0000000.dpi300`). Two preprocessing runs at different engine versions MUST produce different `pipeline_version` strings.
- **FR-009**: Dependency pins MUST be updated: project declaration allows the new engine family; the lockfile pins a single exact engine version. Older engine pins MUST be removed, not left commented out.
- **FR-010**: Every `preprocess_output.json` committed to the corpus MUST be regenerated under this spec before the feature is considered complete. If ANY document in the sweep exits non-zero — regardless of exit-code class (`1` unexpected, `2` input_rejected for malformed/encrypted/zero-page PDFs, or `3` internal_error including FR-016 engine-init) — the sweep MUST halt immediately. No partial baselines are committed, the root cause is fixed, and the sweep is re-run from the top. Mid-sweep skip-and-continue is prohibited for ALL non-zero exits (not only engine-init) to avoid a mixed-engine, mixed-version, or mixed-completion baseline. This also subsumes the encrypted-PDF edge case: an encrypted source.pdf exits `2` and halts the sweep just like any other failure. The commit that lands the regenerated set MUST include a per-document summary in the commit body: one line per regenerated document whose `document_text` differs from the previous baseline, classifying the kind of shift in free-form prose (e.g., `inv_003: ampersand→"and" (PP-OCRv5 tokenizer)`). The example format is illustrative, not normative; no closed vocabulary of shift kinds is imposed — the commit body is read once during regeneration review and has no scripted consumers. FR-020's bracketed-token vocabulary applies to the artifact's `warnings` array only, not to this commit-body prose. Documents with no OCR-text diff are omitted. No separate regeneration-notes file or machine-diffable artifact is required.
- **FR-011**: The following documentation surfaces MUST be updated to reflect the new engine: `docs/stage1-vendor-identity/architecture.md` (processing flow), `docs/stage1-vendor-identity/ollama-runtime.md` (where it references PaddleOCR versions), `specs/003-pdf-preprocessing/research.md` (add a migration decision entry citing this spec and the PRD), and the preprocessing quickstart. Minimum content per surface is captured in the PRD.
- **FR-012**: Any engine-specific workaround applied in this slice (e.g., the PRD-documented PIR/oneDNN flag) MUST be recorded in the feature's `research.md` with a link to the upstream tracking issue, so the workaround can be removed when upstream ships a fix.
- **FR-013**: Integration tests in `tests/integration/preprocessing/` MUST pass unchanged where possible. Tests that fail solely because OCR text shifts under the new recognizer MAY be updated to match new expected strings, but each such change MUST include a free-form-prose comment identifying the OCR-text delta (e.g., `# OCR-text delta: PP-OCRv5 renders "&" as "and"`). The comment format mirrors FR-010's commit-body per-document summary — no closed vocabulary of shift kinds is imposed, since the comment is a permanent in-code audit trail with no scripted consumers. Tests that fail for any other reason MUST be treated as regressions.
- **FR-014**: Contract tests (`tests/contract_tests/`) and pipeline tests (`tests/pipeline_tests/`) MUST continue to pass without substantive rewrites. Pipeline tests use default stubs and do not exercise the real engine; they are unaffected by the engine swap.
- **FR-015**: Preprocessing MUST NOT introduce new network dependencies beyond those required for first-run model weight downloads from the existing upstream model hosters referenced in the PRD. After weights are cached, preprocessing MUST run with no network.
- **FR-016**: When engine initialization fails for any reason — including (but not limited to) a required model weight that cannot be downloaded/cached/loaded, a paddle runtime exception (e.g., PIR/oneDNN bug re-firing despite the `enable_mkldnn=False` workaround), an import error in `paddleocr` / `paddlex`, or any exception raised during `PPStructureV3()` construction before the first page is processed — preprocessing MUST exit with a non-zero status AND MUST NOT write any `preprocess_output.json` (including a `status="failure"` stub). The emitted error message MUST identify the underlying cause (exception class + message for runtime exceptions, package + traceback origin for import errors). When the cause is specifically a weight-download failure, the message MUST additionally identify the missing model artifact and the upstream hoster URL referenced in the PRD. This is an environmental failure, not a per-document evidence failure, and is surfaced at the CLI boundary rather than in the artifact.
- **FR-017**: The PRD's PaddleOCR 2.10 + CDLA (`picodet_lcnet_x1_0_fgd_layout_cdla_infer`) fallback MUST be recorded as a documented contingency only. Its trigger criteria (e.g., V3 cannot initialize on-corpus after the oneDNN workaround, or V3 regresses on >1 corpus document) and its pivot cost MUST be captured in `specs/010-pp-structurev3-preprocessing/research.md`. No 2.10 code path, config flag, or runtime auto-fallback ships in this slice. Preprocessing remains single-engine (V3); invoking the fallback is a future slice, not a toggle.
- **FR-018**: When a page has `len(raw_ocr_lines) >= 2 AND len(blocks) == 1`, preprocessing MUST append a warning to `warnings` in the form `"page N: [suspicious_single_block] single block covers K OCR lines"` (with `K` the OCR-line count). This warning MUST NOT downgrade `ingestion_sources.paddleocr_vl.status`; that signal remains reserved for the `lines>0, blocks==0` condition in FR-003 and the symmetric condition in FR-019. The artifact is still written and still validates against the v1.0.0 contract.
- **FR-019**: When a page has `len(blocks) > 0 AND len(raw_ocr_lines) == 0` AND at least one block has `block_type ∈ {text, title, header, footer}`, preprocessing MUST append a warning to `warnings` in the form `"page N: [silent_empty_ocr] OCR returned zero lines despite K text-type blocks"` (with `K` the count of blocks whose `block_type` is text/title/header/footer), and MUST set `ingestion_sources.paddleocr_vl.status = "failure"` for the document. This is the symmetric counterpart to FR-003 — missing evidence on either the layout axis or the OCR axis is equally untrustworthy and downgrades the document. Pages whose only blocks are `figure` or `table` do NOT trigger FR-019 (zero OCR lines on a figure-only page is legitimate).
- **FR-020**: Every categorized warning emitted by preprocessing MUST start with a fixed prefix of the form `"page N: [<category_token>] "`, where `<category_token>` is drawn from the closed vocabulary `{silent_empty_layout, silent_empty_ocr, suspicious_single_block, unknown_layout_label}`. Any future warning category added to preprocessing MUST extend this vocabulary via an AMENDMENTS entry and update SC-002's grep pattern. Ordering of `warnings[]` MUST be:
    1. Page-ascending by page number (outer key).
    2. Within a single page, categorized warnings are emitted in the vocabulary's lexical order (inner key), to keep outputs byte-identical (FR-004).
    3. When two or more warnings share the same `(page, category_token)` pair, insertion order (emission order in `pipeline.py` / `ocr.py`) is the tie-break.
    4. Non-categorized warnings — aggregate strings like `"ingestion_sources.paddleocr_vl: failure (all pages failed)"` and free-form runtime-error messages like `"page N: OCR failed: ..."`, `"page N: layout extraction failed: ..."`, rasterization-failed and rotation-normalized messages — are NOT rewritten into the bracketed vocabulary in this slice and sort AFTER all categorized warnings in their page scope (aggregate / non-page-scoped warnings sort last in the document).
- **FR-021**: Preprocessing MUST populate the artifact's `tables[]` field from PPStructureV3's table recognizer output, projected into the v1.0.0 schema shape **as of 010's landing commit** (strict-current-shape). Any richer table content the engine emits beyond the schema (e.g., full HTML strings, cell-level spans, bbox-per-cell detail) MUST be discarded at the persistence boundary in this slice; capturing it requires an AMENDMENTS entry on `contract_set_version = "1.0.0"`. Future AMENDMENTS entries that widen the schema (e.g., add an optional `cell_confidence` field) DO NOT auto-populate via this projection — a matching preprocessing code change is required to begin emitting the new field, so the schema never silently accepts more than preprocessing emits. `tables[]` remains subject to FR-004 determinism (ordering, bbox encoding, text verbatim) on the same terms as `blocks[]`.
- **FR-022**: Debug `page_*.png` image emission MUST be opt-in only, gated behind the existing `--write-page-images` CLI flag (inherited from the 003-era CLI contract; no new flag is introduced in this slice). When the flag is absent, preprocessing MUST NOT write any `page_*.png` file. Emitted PNGs MUST NOT be committed to the corpus — they are a developer-facing investigation tool, not an artifact downstream stages read. Debug PNGs are explicitly OUTSIDE FR-004's byte-identical determinism guarantee; FR-004 applies to `preprocess_output.json` only. This keeps corpus commits small under FR-010 regeneration and avoids binary-diff churn on engine bumps.

### Key Entities *(include if feature involves data)*

- **preprocess_output.json (v1.0.0 artifact)**: The stable JSON artifact this slice produces. This spec does not change its schema. What changes is which values populate `pages[*].blocks`, `document_text`, `ingestion_sources.paddleocr_vl`, `warnings`, and `pipeline_version`.
- **Layout block**: The unit of layout evidence downstream consumers care about. Block carries `block_id`, `block_type` ∈ `{text, title, table, figure, header, footer}`, `bbox`, `reading_order`, `text`, and `confidence`. The new engine emits richer per-block content; this slice maps that content into the existing shape without schema changes.
- **Raw OCR line**: The unit of text evidence used by the evidence packet. Carries `line_id`, `bbox`, `text`, `confidence`. In this slice the source shifts from a standalone OCR pass to the layout engine's built-in recognizer.
- **Ingestion source status (`paddleocr_vl.status`)**: The signal downstream stages read to decide whether layout evidence is trustworthy. Allowed values are fixed by the frozen contract: `"success" | "failure" | "not_implemented"`. This slice tightens when `success` is legitimate: any page hitting the silent-empty condition downgrades the document to `"failure"`.

## Assumptions

- The PRD at `docs/stage1-vendor-identity/prd-ppstructurev3-migration.md` is the authoritative source for technical context (engine names, config flags, bug citations, fallback). Implementation-time choices that touch engine configuration MUST be consistent with the PRD or the PRD updated alongside.
- The corpus at `tests/stage1_vendor_identity/` is representative enough that an inv_001..inv_020 pass is sufficient to gate this change. If later-labeled documents surface engine regressions, they are treated as follow-up issues rather than blockers.
- The stage 1 target platform is CPU-only in the devcontainer; GPU/ROCm inference is explicitly out of scope for this slice.
- The `preprocess_output.json` contract is amended additively in this slice (v1.2.0 AMENDMENTS, 2026-04-23): `block.confidence` and `ocr_line.confidence` accept `null` in addition to a number in `[0.0, 1.0]`, so preprocessing can persist the engine-missing case verbatim instead of substituting `0.0`. Numeric values remain bounded. No other schema fields change. Richer per-block content produced by the new engine (e.g., Markdown-style block content) is still discarded at the persistence boundary until a future AMENDMENTS entry permits capturing it.
- Model weights (~500 MB added) download on first run from existing upstream hosters. Devcontainer-side prefetch is not in scope; developers accept a one-time warm-up on first preprocessing call.
- Multi-page preprocessing remains page-local. Streaming one page at a time is required to bound peak memory; no cross-page OCR context is needed to recognize the current page.
- The defensive "lines-present-but-blocks-absent → status=failure" downgrade is conservative: a single affected page is enough to flag the whole document as `failure`. This is chosen over a multi-page threshold because the contract enum offers no middle ground and the evidence-first rule argues for early visibility. Revisit if the corpus surfaces false positives.
- Evaluator, extractor, consensus, and routing code are out of scope and will be exercised only indirectly via the end-to-end smoke mentioned in the PRD's success criteria.
