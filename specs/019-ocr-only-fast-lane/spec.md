# Feature Specification: OCR-Only Fast Lane For Vendor Identity

**Feature Branch**: `019-ocr-only-fast-lane`
**Created**: 2026-05-11
**Status**: Draft
**Input**: User description: "Build the next preprocessing optimization slice after feature 018. Features 014-018 established the GPU preprocessing lane, warmup/timing, module/model reduction, and DPI/region-first strategies. Feature 019 should add an OCR-only fast lane for stage 1 vendor identity so documents that do not need full PPStructureV3 layout processing can skip that heavier path, while preserving the existing artifact schemas and deterministic control rules."

## Clarifications

### Session 2026-05-11

- Q: FR-005 disposition shape — primary-preset (a) or candidate-with-fallback (b)? → A: Candidate-with-fallback (b). Harvests latency without silent quality regression, mirrors feature 018's deterministic fallback pattern, and gives a measurable `ocr_only_fallback_count` reliability signal.
- Q: FR-005 eligibility / sufficiency trigger — which preprocessing-pass-derivable signal indicates OCR-only is insufficient? → A: Combined two-threshold check — (i) aggregate OCR-detected non-whitespace token count AND (ii) aggregate PaddleOCR text-detector confidence across detected boxes. Both must be ≥ their configured thresholds for the OCR-only output to be considered sufficient; if either trips, fall back to `ppstructurev3` on that document. Character count alone is too easy to satisfy with junk text; confidence alone can miss thin-but-useful evidence. Threshold values and the confidence aggregation function are set at `/speckit.plan` time.
- Q: `--gpu-warmup` (feature 016) interaction with `--preprocess-strategy=ocr-only-v1` — which engine(s) does the warmup pass exercise? → A: Warm only the engine implied by the selected strategy. On `--preprocess-strategy=ocr-only-v1`, the warmup pass exercises only the OCR-only PaddleOCR engine; PPStructureV3 remains unconstructed at warmup time. If a document later trips the FR-005 trigger and falls back, the PPStructureV3 cold-start (construction + first-predict warmup) cost is included in that document's timed `phase_timings.per_page_inference` / `phase_timings.rasterization` per R-019.15's combined-cost rule — this is the honest measurement; warmup credit is not transferred across engines.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - OCR-only preprocessing candidate on the GPU lane (Priority: P1)

A pipeline engineer wants to stop paying full PPStructureV3 layout cost when stage 1 only needs vendor-identity evidence. They want to evaluate at least one OCR-only preprocessing candidate against the existing GPU lane default on the same fixed small corpus subset, with the candidate selectable per run via explicit configuration. The OCR-only path runs PaddleOCR text detection + recognition directly — no layout module, no table-recognition module, no formula/seal module — and reassembles `preprocess_output.json` from OCR output alone. Each evaluated OCR-only run must produce a `preprocess_output.json` that still validates against the existing JSON Schema, and the per-document `phase_timings.*` from feature 015 must be available for every run so the latency win can be quantified.

**Why this priority**: This is the core deliverable. PPStructureV3's layout/table/formula modules are sized for full document understanding, but stage 1 only consumes vendor-identity evidence; bypassing layout entirely is the largest preprocessing-side latency win still available after the feature 017 module reduction and the feature 018 DPI / region-first work. Without a quantified per-document `phase_timings.*` comparison and a `preprocess_output.json` that still passes the existing schema, "OCR-only is fast enough" is a guess.

**Independent Test**: Pick a fixed small subset of `tests/stage1_vendor_identity/inv_*` (the same subset for every configuration). Run the `ppstructurev3@gpu` lane on that subset under (a) the existing PPStructureV3 strategy and (b) at least one OCR-only candidate strategy. Confirm: (1) every `preprocess_output.json` validates against the existing JSON Schema in the active contract set; (2) per-document `phase_timings.*` (including `phase_timings.total`) is emitted for every run per feature 015; (3) the preprocessing strategy is selected by explicit configuration, not silently changed on the GPU lane; (4) the PPStructureV3 strategy remains an explicitly selectable option; (5) the OCR-only run does not invoke any PPStructureV3 layout / table / formula / seal module.

**Acceptance Scenarios**:

1. **Given** a `ppstructurev3@gpu` run with the existing PPStructureV3 strategy on a fixed vendor-identity fixture, **When** preprocessing completes, **Then** `phase_timings.*`, `phase_timings.total`, and `preprocess_output.json` are emitted unchanged in shape from features 015–018.
2. **Given** the same fixture and the same `ppstructurev3@gpu` profile but with an OCR-only strategy explicitly selected, **When** preprocessing completes, **Then** `phase_timings.*` is recorded for the OCR-only run, the resulting `preprocess_output.json` validates against the existing schema with no field added, removed, renamed, or retyped, and no PPStructureV3 layout / table-recognition / formula / seal module is invoked.
3. **Given** a `ppstructurev3@gpu` run without any new preprocessing-strategy switch set, **When** preprocessing completes, **Then** the active preprocessing strategy is unchanged from feature 018 — the OCR-only candidate MUST NOT become the GPU default in this scenario unless it is explicitly promoted (US6).

### User Story 2 - Active preprocessing strategy is visible in operator-facing output (Priority: P1)

An operator inspecting a `run_summary` line for any preprocessing run can tell which preprocessing strategy the run used by reading a stable identifier field directly from the output — without having to read source code, environment variables, or feature-flag state. The identifier is emitted on every run including default `ppstructurev3@cpu` and stub-adapter runs, so absence of the field is itself a regression signal. This identifier sits alongside (does not replace) feature 018's `raster_profile_id` and `region_strategy_id` and feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked`.

**Why this priority**: An OCR-only strategy is qualitatively different from the existing PPStructureV3 strategy — it skips layout, it reassembles `preprocess_output.json` from a smaller evidence surface, and it can have different quality characteristics. Without an output-visible identifier, two runs that differ only in preprocessing strategy look identical to operators and to anyone diagnosing a quality regression after the fact. P1 because every other story depends on operators being able to attribute observed differences to the configuration that produced them, and because this is the surface promotion decisions (US6) reference.

**Independent Test**: Run the GPU lane twice — (a) PPStructureV3 strategy, (b) OCR-only strategy — on the same fixture. Confirm: (1) the `run_summary` line for each run carries an additive top-level string field naming the active preprocessing strategy; (2) the two runs produce two distinct identifier values; (3) repeating either run produces the same identifier value as before; (4) a `ppstructurev3@cpu` run also carries the field with a value that reflects the CPU default; (5) the field coexists with feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked` and feature 018's `raster_profile_id` / `region_strategy_id` / `region_strategy_fallback_count` without overlap or replacement.

**Acceptance Scenarios**:

1. **Given** a `ppstructurev3@gpu` run with the existing PPStructureV3 strategy, **When** preprocessing completes, **Then** the `run_summary` line carries an additive `preprocess_strategy_id` (names the active preprocessing strategy — for example `"ppstructurev3"` or `"ocr-only-v1"`) alongside (not replacing) `raster_profile_id`, `region_strategy_id`, `region_strategy_fallback_count`, `module_set_id`, `det_rec_variant_id`, and `ppstructure_modules_invoked`.
2. **Given** the same run repeated under an OCR-only strategy, **When** preprocessing completes, **Then** `preprocess_strategy_id` differs from the PPStructureV3 run, the new value matches the explicitly-selected configuration, and no other identifier on the `run_summary` line changes unless an axis besides preprocessing strategy was also changed.
3. **Given** a `ppstructurev3@cpu` run (default profile) without any new configuration switches set, **When** preprocessing completes, **Then** the `run_summary` line is unchanged from feature 018 except for the one additive identifier field whose value reflects the active CPU default (e.g., `ppstructurev3` or `cpu-default`, agreed at `/speckit.plan` time), so absence of the field is itself a regression signal.

### User Story 3 - Deterministic OCR-only sufficiency and fallback rule (Priority: P1)

When an OCR-only run cannot produce enough evidence for stage 1 vendor identity on a given document, the disposition is deterministic and decided in code — not in a model. Per FR-005 (resolved Session 2026-05-11), the OCR-only strategy is shipped as a candidate fast lane that falls back to the `ppstructurev3` strategy on the same document when a deterministic eligibility check fails, mirroring feature 018 FR-007 / FR-009 region-first fallback. The eligibility / sufficiency / fallback rule MUST be derivable from preprocessing-pass inputs alone, MUST NOT depend on extraction or vendor-identity model output, and MUST be operator-visible on `run_summary` per US2.

**Why this priority**: Without an explicit, deterministic disposition rule, an OCR-only strategy that occasionally produces too-thin evidence becomes a silent quality-regression vector. P1 because deterministic control is a non-negotiable constitution rule (see `.specify/memory/constitution.md`) and because feature 018 FR-007 / FR-009 set a precedent: any candidate path that can produce insufficient evidence MUST either fall back deterministically or be combined with an explicit, deterministic acceptance/review handoff to downstream stages.

**Independent Test**: Construct two probe inputs on the same subset — one where the OCR-only path produces clearly sufficient vendor-identity evidence and one where it does not. Run the OCR-only strategy on both. Confirm: (1) the resulting `preprocess_output.json` on each document validates against the existing schema; (2) the disposition (accept OCR-only output / fall back to `ppstructurev3` on that document) is observable from `run_summary` via `preprocess_strategy_id` plus `ocr_only_fallback_count` (US2); (3) re-running the same input produces the same disposition; (4) no extraction, classification, or vendor-identity model output participates in the disposition decision; (5) `ocr_only_fallback_count` follows the same always-emit pattern as feature 018's `region_strategy_fallback_count` (FR-009).

**Acceptance Scenarios**:

1. **Given** a fixture on which the OCR-only strategy produces clearly sufficient vendor-identity evidence, **When** preprocessing completes, **Then** the resulting `preprocess_output.json` is the OCR-only output, validates against the existing schema, and `preprocess_strategy_id` on `run_summary` reflects the OCR-only strategy.
2. **Given** a fixture on which the OCR-only strategy cannot produce sufficient vendor-identity evidence (per the deterministic eligibility / sufficiency rule established by FR-005), **When** preprocessing completes, **Then** the OCR-only path falls back to `ppstructurev3` on that document, the resulting `preprocess_output.json` is the `ppstructurev3` output and validates against the existing schema, `ocr_only_fallback_count` on `run_summary` is incremented, and the disposition is re-derivable from preprocessing-pass inputs alone.
3. **Given** any run of the new binary, **When** preprocessing completes, **Then** `ocr_only_fallback_count` is emitted on every run (always-emit, default `0`) — including `full-page`, `ppstructurev3`, `ppstructurev3@cpu`, and stub-adapter runs — so absence of the field is itself a regression signal.

### User Story 4 - Default CPU profile and CI without GPU stay safe (Priority: P2)

An engineer running the default `ppstructurev3@cpu` profile, or the existing CI without GPU hardware, must not have their behavior changed by this feature beyond the additive identifier fields on `run_summary`. No CPU code path may import GPU-only OCR-only-strategy code; no CPU run may consult or mutate any GPU-only configuration switch this feature introduces.

**Why this priority**: P2 — the risk is regression, not new value. CPU and CI paths already work post-018; this story protects them. Lower than P1 only because the CPU/CI path's correctness is independently verifiable today, and because this feature's CPU surface is purely the additive identifier surface from US2.

**Independent Test**: Run the default `ppstructurev3@cpu` profile and the existing stub-adapter / CPU-only test suites on a host without Paddle GPU, both with and without the new GPU-only configuration switches set in the environment. The suites must pass in both configurations. CPU `preprocess_output.json` outputs must be byte-identical to outputs on `main` before this feature lands.

**Acceptance Scenarios**:

1. **Given** the default `ppstructurev3@cpu` profile on a host without GPU, **When** preprocessing runs, **Then** no GPU-only OCR-only-strategy code path is imported or executed.
2. **Given** the same default CPU profile with new GPU-only configuration switches *explicitly set* in the environment, **When** preprocessing runs, **Then** the run completes normally with no behavior change other than the additive identifier fields on `run_summary` whose values reflect the default CPU configuration.
3. **Given** the existing default test suite on a host without Paddle GPU, **When** the suite runs, **Then** it passes; GPU-only verification of OCR-only behavior is skipped via `@pytest.mark.gpu` rather than failed.

### User Story 5 - Output schema and downstream contracts unchanged (Priority: P2)

A corpus run on the GPU lane under any preprocessing strategy this feature introduces must produce a `preprocess_output.json` that still matches the existing JSON Schema and that the downstream evidence-packet assembler, single-voter extractor, router, final-payload assembler, and evaluator accept without modification.

**Why this priority**: P2 — protects every downstream slice (004 evidence packet, 005 extraction, 008 routing, 009 final payload, 007 evaluator) from leaking a preprocessing-side optimization into their contract surface. Lower than the core P1 stories only because schema-conformance is mechanically checkable.

**Independent Test**: For each evaluated configuration (each preprocessing-strategy candidate plus the PPStructureV3 baseline), run a small corpus subset end-to-end through the existing pipeline (preprocess → evidence packet → extract → route → assemble → evaluate). Confirm: (a) every `preprocess_output.json` validates under `contracts/stage1_vendor_identity/*/preprocess_output.schema.json` of the active contract set; (b) each downstream stage runs to completion against those outputs; (c) `schema_version`, `contract_set_version`, and the four canonical artifact contracts are not modified by this feature.

**Acceptance Scenarios**:

1. **Given** a small corpus subset run end-to-end under a configuration introduced by this feature, **When** every stage completes, **Then** every emitted artifact validates against its existing schema in the active contract set.
2. **Given** the same end-to-end run, **When** the evaluator runs, **Then** it produces `evaluation_document.json` and `evaluation_run_summary.{json,md}` without contract changes.
3. **Given** the active contract set at landing time, **When** this feature lands, **Then** no `schema_version` value, no JSON schema field, and no entry in `contracts/stage1_vendor_identity/AMENDMENTS.md` is changed by this feature except for the additive identifier surface explicitly defined here.

### User Story 6 - Quality-gate guard before any GPU default change (Priority: P3)

If, after running the US1 benchmark and the US3 sufficiency / fallback evaluation, the team chooses to promote the OCR-only strategy (or any combination of OCR-only plus feature 018's DPI / region-strategy choices) to the new `ppstructurev3@gpu` default, the promotion must be gated on vendor-identity quality being preserved against the existing GPU default — measured on the same small corpus the benchmark used. Promotion that fails the gate is rejected; the legacy PPStructureV3 default stays in place. This mirrors feature 017 FR-015 and feature 018 FR-016.

**Why this priority**: P3 — the feature ships value at P1+P2 (OCR-only candidate, sufficiency/fallback rule, identifier visibility, schema preservation, CPU/CI safety) without ever flipping the GPU default. Promotion is a follow-on decision. P3 because skipping the gate would convert this feature from "evaluation slice" to "silent regression vector"; promotion-gating is required only if and when the team chooses to promote.

**Independent Test**: Take a candidate configuration that US1 / US3 evaluated. Compare its vendor-identity quality numbers (from the existing evaluator) against the legacy GPU default's numbers on the same corpus. The promotion gate passes only if the candidate is at parity or better on the agreed quality metrics. If the gate passes, the candidate becomes the new GPU default in this feature; if it fails, the legacy default is kept and the candidate remains an opt-in selection only.

**Acceptance Scenarios**:

1. **Given** a candidate configuration evaluated under US1 / US3, **When** the team considers promoting it to the new `ppstructurev3@gpu` default, **Then** the decision references vendor-identity quality numbers produced by the existing evaluator on the same corpus the benchmark used.
2. **Given** a candidate that passes the quality gate, **When** the GPU default is changed, **Then** the change is recorded in this feature's research artifact and the new default's `preprocess_strategy_id` value (plus any updated `raster_profile_id` / `region_strategy_id` pair if combined) appears in subsequent `run_summary` lines without any opt-in switch needing to be set.
3. **Given** a candidate that fails the quality gate, **When** the promotion decision is made, **Then** the legacy default remains in place and the candidate stays selectable only via explicit configuration.

### Edge Cases

- **Preprocessing-strategy switch combined with `ppstructurev3@cpu`**: A switch that selects a non-default preprocessing strategy on the GPU lane is GPU-only by design. When set with the CPU profile or a stub adapter, the system MUST follow the same warn-and-proceed pattern features 016 / 017 / 018 established: emit a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`, perform no preprocessing-strategy change, and proceed with the run normally. Silent ignore is NOT acceptable.
- **OCR-only candidate fails vendor-identity quality gates**: Treated as a regression of FR-013. The OCR-only candidate is rejected; the PPStructureV3 strategy is kept as the default until the regression is resolved.
- **OCR-only strategy yields no vendor-identity-relevant evidence on a document**: Per FR-005 (candidate-with-fallback, resolved Session 2026-05-11), the deterministic eligibility / sufficiency check trips and the OCR-only path falls back to `ppstructurev3` on that document. The resulting `preprocess_output.json` is the `ppstructurev3` output, validates against the existing schema, and `ocr_only_fallback_count` on `run_summary` is incremented per FR-007. Silent blank or schema-invalid artifacts are forbidden; failing fast on an individual document is NOT permitted.
- **OCR-only strategy alters the `preprocess_output.json` page index, block index, or coordinate system**: Forbidden. Page count, page index, coordinate origin, coordinate units, block index, and the `pages.length == page_count` invariant from feature 018 MUST stay identical to the legacy PPStructureV3 output so downstream evidence-packet assembly does not need to special-case OCR-only runs. Block boundaries derived from OCR-only line clustering MAY differ from layout-derived blocks within the same `blocks[]` shape — this is a content difference, not a schema difference.
- **OCR-only strategy combined with feature 018's `header-first-v1` region strategy**: Supported. The two axes are orthogonal — region strategy decides which page area to rasterize, preprocessing strategy decides whether to invoke layout. An OCR-only run on a `header-first-v1`-targeted region rasterizes only the header band on page 1, runs PaddleOCR (det + rec) on that crop, and emits a schema-valid `preprocess_output.json` with `pages[]` populated per feature 018 Q2 (page 1 carries header-band blocks; pages 2..N are empty records with valid geometry, `blocks: []`, `raw_ocr_lines: []`).
- **OCR-only strategy alters `phase_timings` shape**: Forbidden. Per-document `phase_timings` keys (`paddle_import`, `gpu_bind_probe`, `engine_init`, `rasterization`, `per_page_inference`, `artifact_write`, `total`, and `warmup` from feature 016) MUST NOT be renamed, removed, or have their type changed by this feature. The `per_page_inference` value remains meaningful even though the OCR-only path runs det+rec only — its definition (time spent in model inference on this page) is unchanged.
- **`--gpu-warmup` combined with `--preprocess-strategy=ocr-only-v1`**: Per Clarifications Session 2026-05-11 Q3, the warmup pass exercises only the engine implied by the selected strategy. On `--preprocess-strategy=ocr-only-v1`, the warmup pass exercises only the OCR-only PaddleOCR engine (`_OCR_ENGINE`); PPStructureV3 (`_ENGINE`) remains unconstructed at warmup time. `phase_timings.warmup` measures the single warmed engine. If a document later trips the FR-005 trigger and falls back to `ppstructurev3`, the PPStructureV3 cold-start (construction + first-predict) cost is included in that document's `phase_timings.per_page_inference` and `phase_timings.rasterization` per R-019.15's combined-cost rule. Warmup credit is not transferred across engines — fallback documents on an `ocr-only-v1` warmup run pay the honest first-engine-invocation cost.
- **GPU bind failure on an OCR-only candidate configuration**: Run MUST fail fast (preserving feature 015 FR-008 / feature 017 FR-007 / feature 018 — no silent CPU fallback after `ppstructurev3@gpu` is selected). The exit reason MUST identify the active `preprocess_strategy_id` (and the `(raster_profile_id, region_strategy_id)` pair) so operators can diagnose without re-instrumentation.
- **Operator overrides the new GPU default back to the legacy default**: MUST be supported by the same explicit configuration switches this feature introduces — a default change MUST NOT remove the operator's ability to select the legacy `preprocess_strategy_id` value by explicit selection.
- **GPU verification deferred to a follow-up**: When workstation GPU hardware is unavailable at landing time, GPU-marked tests (`@pytest.mark.gpu`) and benchmark verification MAY be deferred and tracked as a follow-up issue/task without blocking the CPU-safe implementation from merging (per feature 016 FR-014 / feature 017 FR-024 / feature 018 FR-025). The deferral MUST be captured in this feature's `tasks.md` and quickstart so the verification cannot be quietly skipped.
- **Conditions under which the legacy GPU configuration is preserved as the default** (collated for review traceability): (a) FR-013 quality-gate failure for the OCR-only candidate; (b) deterministic-sufficiency / fallback regression from the OCR-only strategy; (c) downstream-contract conflict where OCR-only would alter `preprocess_output.json` in a way any downstream stage rejects; (d) GPU bind failure on the OCR-only configuration; (e) the team makes no promotion decision at landing. In all cases the legacy PPStructureV3 configuration remains both the default and an explicitly selectable option.

#### Out of Scope

Documented here so future failures are recognized as known gaps rather than regressions:

- **Schema or `schema_version` changes to the four canonical stage 1 artifacts**: Out of scope. This feature is configuration-only on the runtime side and additive-only on the `run_summary` side.
- **Promoting a CPU-side default change**: Out of scope. This feature only considers GPU-side defaults; CPU defaults stay as they are unless an explicit follow-up amendment promotes one.
- **Adding a new persisted benchmark artifact**: Out of scope unless `/speckit.clarify` or `/speckit.plan` produces evidence that `run_summary` plus the existing harness/evaluator outputs are insufficient to record the benchmark. If introduced later, name/location/schema/lifecycle MUST be specified in `data-model.md` + `research.md` and the contract set updated under `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- **Regenerating committed corpus baselines**: Out of scope. Any baseline change MUST go through the established dataset/baseline flow defined in `docs/stage1-vendor-identity/dataset-layout.md` and `labeling-guide.md`, not through this feature's PR.
- **Model-runtime / provider / orchestration changes outside preprocessing**: Out of scope. Extraction, routing, final-payload assembly, and the host Ollama / cloud-workstation / edge-fast runtime selection are unchanged by this feature.
- **Remote / cloud routing changes**: Out of scope. The feature 008 deterministic routing surface is unchanged. The `preprocess_strategy_id` and `ocr_only_fallback_count` identifiers this feature adds are consumed by operators; they are NOT new routing inputs. No new routing scores, no new routing decisions, no remote/cloud escalation.
- **Non-vendor-identity extraction scope**: Out of scope. Line items, totals, dates, and all other stage 2+ extraction surfaces are not touched. `preprocess_output.json` continues to be vendor-identity-evidence-focused on this feature's stage 1 subset.
- **Replacing PPStructureV3 entirely**: Out of scope. PPStructureV3 remains a selectable strategy under `preprocess_strategy_id`. This feature adds an OCR-only path as a sibling, not as a replacement; the PPStructureV3 strategy remains the GPU default unless US6's quality gate passes.

## Requirements *(mandatory)*

### Functional Requirements

**OCR-only preprocessing strategy**

- **FR-001**: System MUST provide an explicit configuration mechanism on the live `ppstructurev3@gpu` path that selects a named preprocessing-strategy preset for a given run. Preset selection is the ONLY user-facing surface for preprocessing-strategy choice — the feature MUST NOT expose free-form module selection on the runtime path. The feature ships at least two presets at landing: `ppstructurev3` (the strategy active on `main` at landing time of feature 018) and at least one OCR-only preset (e.g., `ocr-only-v1`). `preprocess_strategy_id` is drawn from this closed vocabulary; adding a future preset is a code change plus a new `preprocess_strategy_id` value, not a runtime module-set override.
- **FR-002**: An OCR-only preset on the `ppstructurev3@gpu` profile MUST invoke PaddleOCR text detection and text recognition only. It MUST NOT invoke PPStructureV3's layout-detection, table-recognition, formula-recognition, or seal-recognition modules. Blocks in the resulting `preprocess_output.json` MAY be derived from OCR-only line clustering — they are NOT layout-derived in this strategy — but the `blocks[]` shape and required keys are unchanged from the existing schema.
- **FR-003**: An OCR-only run MUST produce a `preprocess_output.json` that validates against the existing JSON Schema for that artifact in the active contract set, with no field added, removed, renamed, or retyped. Page count, page index, coordinate origin, coordinate units, block-index ordering rules, and the `pages.length == page_count` invariant from feature 018 MUST stay identical to a PPStructureV3 run on the same fixture.
- **FR-004**: The OCR-only preset MUST be selectable per-run on the `ppstructurev3@gpu` profile via explicit configuration; the `ppstructurev3` preset MUST remain a valid selection.

**Deterministic sufficiency / fallback rule**

- **FR-005**: System MUST adopt the **candidate-with-fallback** disposition for OCR-only output insufficiency (resolved at `/speckit.clarify` Session 2026-05-11). The OCR-only strategy falls back to the `ppstructurev3` strategy on a document when a deterministic eligibility / sufficiency check fails. The disposition MUST be recorded on `run_summary` via an additive integer field `ocr_only_fallback_count` on every run with the always-emit pattern from feature 018 FR-009. The eligibility / sufficiency check MUST be derivable from preprocessing-pass inputs alone (page geometry, rasterized page metadata, OCR-only detector / recognizer output), MUST NOT depend on extraction or vendor-identity model output, and MUST be re-derivable from the inputs so the same input always yields the same disposition. The trigger is a **combined two-threshold check** (resolved at `/speckit.clarify` Session 2026-05-11): (i) the aggregate OCR-detected non-whitespace token count across the document's targeted region(s) MUST be ≥ a configured integer threshold AND (ii) the aggregate of PaddleOCR text-detector confidence across detected boxes (specific aggregation function — mean / weighted-mean / other — set at `/speckit.plan`) MUST be ≥ a configured float threshold. The OCR-only path is considered sufficient only when BOTH thresholds hold; if either trips, the OCR-only path falls back to `ppstructurev3` for that document. The two threshold values and the confidence aggregation function are set at `/speckit.plan` time and recorded in this feature's research artifact alongside the candidate's `preprocess_strategy_id` value.
- **FR-006**: Whichever FR-005 disposition is chosen, the disposition decision MUST be derivable from `preprocess_output.json` inputs alone, MUST NOT depend on extraction or vendor-identity model output, and MUST be re-derivable from the inputs so two runs of the same strategy on the same input produce the same disposition.
- **FR-007**: Per the FR-005 candidate-with-fallback disposition, the disposition MUST be operator-visible on `run_summary` via `preprocess_strategy_id` plus the additive integer field `ocr_only_fallback_count` emitted on every run of the new binary — including `ppstructurev3` runs, `ppstructurev3@cpu` runs, and stub-adapter runs — with the always-emit pattern from feature 018 FR-009 (default `0`, value equals the number of documents that fell back). Silent disposition is NOT acceptable; absence of either field on a run of the new binary is itself a regression signal.

**Operator-facing visibility**

- **FR-008**: The `run_summary` line MUST carry an additive top-level string field `preprocess_strategy_id` that identifies the active preprocessing strategy for the run. The value MUST be drawn from the FR-001 closed vocabulary (`ppstructurev3`, `ocr-only-v1`, and any future preset added by code change). The field MUST be a human-readable string, not an opaque numeric hash. It MUST coexist with — not replace — feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked` and feature 018's `raster_profile_id` / `region_strategy_id` / `region_strategy_fallback_count`.
- **FR-009**: The fields introduced by FR-007 / FR-008 MUST be additive only on `run_summary`. No existing `run_summary` field, no `phase_timings.*` key, no `preprocess_output.json` field, and no field introduced by feature 017 (`module_set_id`, `det_rec_variant_id`, `ppstructure_modules_invoked`) or feature 018 (`raster_profile_id`, `region_strategy_id`, `region_strategy_fallback_count`) may be renamed, removed, or retyped by this feature.
- **FR-010**: `preprocess_strategy_id` MUST be emitted on every run of the new binary, including default `ppstructurev3@cpu` runs and stub-adapter runs (so absence of the field is itself a regression signal). On those non-GPU runs the field value MUST reflect the active default configuration of that profile (e.g., `ppstructurev3` or `cpu-default`, agreed at `/speckit.plan` time).

**Profile defaults and CPU/stub isolation**

- **FR-011**: `ppstructurev3@cpu` MUST remain the default preprocessing profile.
- **FR-012**: `ppstructurev3@gpu` MUST remain explicit / opt-in.
- **FR-013**: When any GPU-only configuration switch this feature introduces is set on `ppstructurev3@cpu` or a stub adapter, the system MUST: (a) emit a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`; (b) perform no preprocessing-strategy change; (c) proceed with the run normally and exit with the same status it would have produced without the switch. Silent ignore and rejection are both NOT acceptable. (Mirrors feature 016 FR-010 / feature 017 FR-013 / feature 018 FR-014.)
- **FR-014**: CPU and stub adapter execution paths MUST NOT import, reference, or trigger any GPU-only OCR-only-strategy code path this feature introduces. Imports MUST be guarded so a host without Paddle GPU can run the default suite.

**Benchmark**

- **FR-015**: System MUST exercise at least one OCR-only preset on the same fixed small stage 1 vendor-identity corpus subset used for benchmarking the `ppstructurev3` strategy under feature 018 FR-005, and MUST record per-document `phase_timings.*` plus the existing evaluator's vendor-identity quality numbers for each evaluated configuration. The benchmark records at minimum: PPStructureV3 baseline and at least one OCR-only candidate, on the same subset.

**Quality-gate before promotion**

- **FR-016**: An OCR-only preset MUST NOT be promoted to the new `ppstructurev3@gpu` default until BOTH of the following quality-gate metrics, computed on the same small corpus subset used for benchmarking, are at parity with or better than the legacy default's values on the same subset: (1) the per-corpus aggregate vendor-identity field score read from `evaluation_run_summary.json`, and (2) the per-document pass count on that subset (per the pass criterion in `docs/stage1-vendor-identity/scoring.md`). "Parity" means `candidate_metric >= legacy_metric` for each of (1) and (2). Both metrics MUST come from the existing evaluator outputs; no new metric is introduced by this feature. (Mirrors feature 017 FR-015 / feature 018 FR-016.)
- **FR-017**: Quality-gate evidence MUST be recorded in this feature's research artifact alongside the candidate's `preprocess_strategy_id` value, so a future reader can re-derive the promotion decision from documented numbers.
- **FR-018**: Promotion of a new GPU default MUST NOT remove the legacy `preprocess_strategy_id = ppstructurev3` configuration as a selectable option; the operator MUST still be able to invoke the legacy configuration by explicit selection.

**Non-regression and contract preservation**

- **FR-019**: This feature MUST NOT regenerate any committed corpus baseline (`tests/stage1_vendor_identity/*/preprocess_output.json`, `expected.json`, evaluator outputs, etc.). Any baseline regeneration MUST go through the established dataset/baseline flow defined in `docs/stage1-vendor-identity/dataset-layout.md` and `labeling-guide.md`, not through this feature's PR.
- **FR-020**: The four canonical stage 1 artifact schemas (`preprocess_output`, `edge_extraction_output`, `routing_decision`, `final_structured_payload`), the active `contract_set_version`, and the `pipeline_version` shape established in features 014/015/016/017/018 MUST NOT be changed by this feature.
- **FR-021**: This feature MUST NOT introduce a new persisted benchmark artifact unless `/speckit.clarify` or `/speckit.plan` produces evidence that the existing `kind: "run_summary"` stdout shape plus the existing harness/evaluator outputs are insufficient. If introduced, its name, location, schema, and lifecycle MUST be specified in `data-model.md` + `research.md` and the contract set updated under `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- **FR-022**: All feature 014 / 015 / 016 / 017 / 018 guarantees MUST continue to hold: PPStructureV3 constructed exactly once per process when used (015 FR-001), GPU readiness probed at most once per process (015 FR-004), single-device-per-process guard (015 FR-006), no silent CPU fallback after `ppstructurev3@gpu` is selected (015 FR-008), `pipeline_version` continues to end in `.gpu0` for GPU runs / `.cpu0` for CPU runs, warmup pass mechanics unchanged (016 FR-001 through FR-020 — cache, env-default, fixture loader, clock-anomaly check, exit code 15 on failure), `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked` semantics unchanged (017 FR-001, FR-008, FR-010), `raster_profile_id` / `region_strategy_id` / `region_strategy_fallback_count` semantics unchanged (018 FR-008, FR-009, FR-011). When `preprocess_strategy_id = ocr-only-v1`, the PPStructureV3 engine MAY remain unconstructed for the run — the 015 FR-001 "exactly once per process" guarantee applies *to* PPStructureV3 *when* it is invoked, not as a requirement to invoke it. The `--gpu-warmup` pass binds the engine implied by the selected `preprocess_strategy_id` only (Clarifications Session 2026-05-11 Q3): on `ocr-only-v1` it warms the OCR-only PaddleOCR engine; on `ppstructurev3` it warms PPStructureV3. Warmup credit is not transferred across engines — a fallback document on an `ocr-only-v1` warmup run pays the PPStructureV3 cold-start cost on its own `phase_timings` budget per R-019.15.

**CI safety and verification gating**

- **FR-023**: All tests that require Paddle GPU, ROCm, or live `ppstructurev3@gpu` runtime introspection of OCR-only behavior MUST be marked `@pytest.mark.gpu` so they are deselected in the default CI configuration.
- **FR-024**: The default test suite MUST pass on a host without Paddle GPU and without ROCm. CPU profile and stub adapter coverage MUST exercise the warn-and-proceed path from FR-013.
- **FR-025**: If workstation GPU verification cannot be performed before merge, GPU-marked tests, the FR-015 benchmark, and any OCR-only quality measurement MAY be deferred and tracked as a follow-up issue or task per feature 016 FR-014 / feature 017 FR-024 / feature 018 FR-025. Deferral MUST NOT block landing the CPU-safe implementation; the deferred items MUST be captured in this feature's `tasks.md` and quickstart so the verification cannot be quietly skipped.

**Boundary with adjacent features**

- **FR-026**: This feature MUST NOT change the disposition of feature 018's region-first fallback (`region_strategy_fallback_count`) or the feature 008 deterministic routing surface. When OCR-only is combined with feature 018's `header-first-v1` region strategy, the two axes compose orthogonally: region strategy decides which page area to rasterize, preprocessing strategy decides whether to invoke layout. Each axis emits its own deterministic disposition on `run_summary` independently.
- **FR-027**: This feature MUST NOT introduce a remote/cloud OCR engine or any non-Paddle OCR runtime. The OCR-only preset uses the same PaddleOCR text-detection / text-recognition variants already exposed by features 014–018 (the `det_rec_variant_id` from feature 017 continues to identify those variants; OCR-only does not introduce a new `det_rec_variant_id` value).

### Key Entities

- **Preprocessing-strategy preset**: A named preset that fixes which preprocessing pipeline the `ppstructurev3@gpu` profile runs. The feature ships at least `ppstructurev3` (the strategy active on `main` at landing time of feature 018) and at least one OCR-only preset (e.g., `ocr-only-v1`). The OCR-only preset invokes PaddleOCR text-detection + text-recognition only — no layout, no table, no formula, no seal modules. Selection is by preset name only; per-run free-form module selection is not exposed on the runtime path. New presets are added by code change plus a new `preprocess_strategy_id` value.
- **Configuration identifier (preprocessing-strategy axis)**: An additive, human-readable string field `preprocess_strategy_id` emitted on every `run_summary` line. Operators attribute observed runtime / quality differences to the configuration that produced them by reading this field together with feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked` and feature 018's `raster_profile_id` / `region_strategy_id` / `region_strategy_fallback_count`. Stable across runs of the same configuration on this axis; changes when this axis changes. Coexists with the existing identifier surface without overlap or replacement.
- **OCR-only disposition record**: An additive `run_summary` field `ocr_only_fallback_count` (integer, always emitted, default `0`) that records, per run, the number of documents on which the OCR-only strategy fell back to the `ppstructurev3` strategy. Modeled on feature 018's `region_strategy_fallback_count`. Used by operators to distinguish "OCR-only ran clean" from "OCR-only nominally selected but mostly fell back" without inspecting per-document logs.
- **OCR-only eligibility / sufficiency rule**: A deterministic per-document check derived from preprocessing-pass outputs alone, used to decide whether OCR-only output is sufficient or the document falls back to `ppstructurev3`. The rule is a combined two-threshold check (FR-005, resolved Session 2026-05-11): (i) aggregate OCR-detected non-whitespace token count across the document's targeted region(s) ≥ integer threshold AND (ii) aggregate of PaddleOCR text-detector confidence across detected boxes ≥ float threshold. Threshold values and the confidence aggregation function are set at `/speckit.plan` time and recorded in this feature's research artifact. The rule MUST NOT depend on extraction or vendor-identity model output and MUST be re-derivable from the same inputs.
- **Quality-gate evidence**: Vendor-identity quality numbers (per the existing evaluator) for each evaluated `preprocess_strategy_id` configuration on the same small corpus subset, recorded in this feature's research artifact, used as the gating evidence for any GPU-default promotion under FR-016.

## Success Criteria *(mandatory)*

- **SC-005**: A `ppstructurev3@cpu` run with any GPU-only configuration switch this feature introduces *explicitly set* in the environment produces a `run_summary` line with the CPU-default identifier value, performs no preprocessing-strategy change, emits a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`, and exits with the same status it would have produced without the switch.

- The "small stage 1 vendor identity corpus subset" used for benchmarking is the same fixed subset feature 018 used for its four-corner matrix, so feature 018's and feature 019's results are directly comparable. The subset is referenced at `/speckit.plan` time.

Identifier shape is one additive top-level string field on `run_summary` — `preprocess_strategy_id` — emitted on every run regardless of profile, alongside (not replacing) the existing identifier surface. The exact CPU-default and legacy GPU-default string values (e.g., `cpu-default`, `ppstructurev3`) are agreed at `/speckit.plan` time.
- The FR-005 disposition was resolved to **candidate-with-fallback** at `/speckit.clarify` Session 2026-05-11. The eligibility / sufficiency trigger was also resolved Session 2026-05-11 to a **combined two-threshold check**: (i) OCR-detected non-whitespace token count and (ii) PaddleOCR text-detector confidence aggregate, both required to be at or above their thresholds for the OCR-only output to be considered sufficient. The two threshold values (integer for token count, float for confidence aggregate) and the specific aggregation function for the confidence side (mean / weighted-mean / other) are set at `/speckit.plan` time.
- The activation mechanism for the preprocessing-strategy selector follows the same CLI-flag-with-env-var-fallback pattern features 016 / 017 / 018 established. Exact flag name is resolved at `/speckit.plan`.
- Workstation GPU verification of FR-015 / FR-016 / FR-025 is best-effort at landing time. If GPU hardware is unavailable, those verifications are tracked as follow-ups under FR-025 rather than blocking merge of CPU-safe code; the deferral is captured in `tasks.md`.
- No new persisted benchmark artifact is needed at landing time. The benchmark numbers from FR-015 / FR-017 land in this feature's `research.md` (and/or quickstart) under FR-021. If `/speckit.plan` later finds `run_summary` + harness outputs insufficient, FR-021's escape hatch applies.
