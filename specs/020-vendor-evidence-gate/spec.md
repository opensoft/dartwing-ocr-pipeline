## User Scenarios & Testing *(mandatory)*

### User Story 1 - Deterministic vendor-identity evidence signals derived from `preprocess_output.json` (Priority: P1)

A pipeline engineer wants a small, reproducible set of vendor-identity evidence signals computed directly from `preprocess_output.json` content — without consulting any extraction, classification, or vendor-identity model output. Examples include: presence of telephone-shaped tokens, presence of email-shaped tokens, presence of postal-address-shaped tokens, presence of business-suffix tokens (e.g., `LLC`, `Inc`, `Ltd`, `GmbH`, `S.A.`), presence of tax-id-shaped tokens (e.g., EIN, VAT), header-band token density, and aggregate OCR-detection confidence on the targeted region. The signal set is code-owned, frozen for the run, re-derivable from the same `preprocess_output.json` on any host, and exposed to operators so they can attribute a gate decision (US2) to the specific signals that produced it.

**Why this priority**: This is the foundation deliverable. The early-accept gate (US2) is just a deterministic function over these signals — without a fixed, reproducible signal set the gate decision is unauditable and the project's "deterministic control stays in code" constitution rule cannot be enforced. P1 because every other user story in this feature depends on this signal surface existing and being stable across runs.

**Independent Test**: Pick a fixed small subset of `tests/stage1_vendor_identity/inv_*` and run preprocessing on each fixture twice on the same host, then on a different host (or a fresh container). For every fixture, confirm: (1) the signal set is computed and recorded by the new binary; (2) two runs on the same `preprocess_output.json` produce byte-identical signal values; (3) no extraction, routing, classification, or vendor-identity model output participates in producing any signal; (4) the signal set is observable on `run_summary` (per US3) or on an equivalent operator-facing surface that exists today; (5) the signal-set definition is documented in this feature's research / data-model artifact so a future reader can re-derive it from `preprocess_output.json` alone.

**Acceptance Scenarios**:

1. **Given** a fixed `preprocess_output.json` for a vendor-identity fixture, **When** the new binary computes the signal set, **Then** every signal value is derivable from `preprocess_output.json` content alone, the computation does not call any extraction or vendor-identity model, and a second run on the same artifact yields byte-identical signal values.
2. **Given** the same `preprocess_output.json` run on a different host or container with no GPU available, **When** the signal set is computed, **Then** the computed signal values are byte-identical to the values produced on the original host.
3. **Given** a `preprocess_output.json` produced by the OCR-only fast lane (feature 019) and the same fixture's `preprocess_output.json` produced by the PPStructureV3 strategy, **When** the signal set is computed on each, **Then** the signal set is computed successfully on both (the signals do not require layout-derived blocks), and any signal-value difference between the two outputs is attributable to a measurable content difference in `preprocess_output.json` — not to the strategy identifier.

### User Story 2 - Three-state early-sufficiency gate decision (Priority: P1)

A pipeline engineer wants a deterministic gate over the US1 signal set that classifies each document into exactly one of three states — `sufficient`, `borderline`, or `insufficient` — for stage 1 vendor identity. The gate rule is code-owned, expressed as a small explicit decision table (or equivalent boolean expression) over the US1 signals, frozen for the run, and re-derivable from the same `preprocess_output.json` on any host. The three-state vocabulary is closed; adding a fourth state is a code change plus a new explicit state value, not a runtime parameter. The gate decision is operator-visible per US3 and provides a stable handle for the optional behavioral effect resolved in US4.

**Why this priority**: The signal set (US1) alone is observability without leverage; the three-state gate is what makes the signals actionable. P1 because the project's deterministic-control constitution rule mandates that any accept/reject-shaped decision be in code, not in model output, and because the gate is what every downstream consumer of this feature (US3 visibility, US4 behavioral effect, US7 quality gate) reads.

**Independent Test**: Construct three probe inputs on the same fixed corpus subset — one obviously sufficient (clear vendor name + address + business suffix on page 1 header band), one borderline (partial header content), one obviously insufficient (e.g., a corrupted or near-blank page). Run the gate on each. Confirm: (1) the gate produces exactly one of `sufficient`, `borderline`, or `insufficient` for each input; (2) re-running the gate on the same `preprocess_output.json` produces the same decision; (3) the decision is observable per US3; (4) the decision is re-derivable from the recorded signals (US1) and the documented decision table alone — without re-running any model; (5) the gate decision does not appear inside `preprocess_output.json` (which is schema-frozen by FR-019).

**Acceptance Scenarios**:

1. **Given** a `preprocess_output.json` with clearly sufficient vendor-identity evidence, **When** the gate runs, **Then** the gate decision is `sufficient`, the decision is recorded per US3, and the decision is reproducible from the recorded signals plus the documented decision table.
2. **Given** the same fixture with thin or partial evidence, **When** the gate runs, **Then** the gate decision is `borderline`, recorded and reproducible per US3.
3. **Given** a fixture with no vendor-identity evidence (e.g., the OCR-only fast lane fell back per feature 019 FR-005, OR preprocessing yielded near-blank output), **When** the gate runs, **Then** the gate decision is `insufficient`, recorded and reproducible per US3.
4. **Given** any of the three states recorded on a run, **When** an operator re-derives the decision from the recorded signal values plus the documented decision table, **Then** the re-derived decision matches the recorded decision exactly.

### User Story 3 - Gate decision and signal set are visible in operator-facing output (Priority: P1)

An operator inspecting a `run_summary` line for any preprocessing run can tell which gate decision the run reached and, at the document level, which signals drove that decision — by reading stable additive fields directly from the output. The identifier and the signal record sit alongside (do not replace) the feature 017–019 identifier surface (`module_set_id`, `det_rec_variant_id`, `ppstructure_modules_invoked`, `raster_profile_id`, `region_strategy_id`, `region_strategy_fallback_count`, `preprocess_strategy_id`, `ocr_only_fallback_count`). The fields are always emitted on every run of the new binary, including default `ppstructurev3@cpu` runs and stub-adapter runs, so absence of any of them is itself a regression signal.

**Why this priority**: An invisible deterministic gate is the worst kind — operators can't tell why a document was classified the way it was, and any regression hides until extraction or routing produces a visible quality drop. P1 because every other story depends on operators being able to attribute observed runtime / quality differences to gate decisions and signal values. Mirrors the operator-visibility pattern from feature 017 FR-008 / feature 018 FR-008 / feature 019 FR-008.

**Independent Test**: Run the GPU lane on the same fixed corpus subset under (a) the existing PPStructureV3 strategy and (b) the feature 019 OCR-only strategy. Confirm: (1) the `run_summary` line carries an additive top-level string field naming the gate-rule preset (e.g., `evidence_gate_id`) plus a record of the per-document gate decisions (counts or per-document table; exact shape resolved at `/speckit.plan`); (2) a `ppstructurev3@cpu` run also carries the field and the per-document record with values reflecting the CPU default; (3) the fields coexist with all feature 017 / 018 / 019 identifiers without overlap or replacement; (4) repeating the same run produces the same field values; (5) absence of any of these fields on a run of the new binary is treated as a regression.

**Acceptance Scenarios**:

1. **Given** a `ppstructurev3@gpu` run on a fixture, **When** preprocessing completes, **Then** the `run_summary` line carries an additive `evidence_gate_id` string (names the active gate rule — for example `"v1"`), an additive `evidence_gate_state_counts` object with default-zero integer fields for each of `sufficient` / `borderline` / `insufficient`, and an additive `evidence_gate_documents` array with one record per document (`document_id`, `decision`, and the recorded values for each of FR-001's five signals).
2. **Given** the same run repeated on the same input, **When** preprocessing completes, **Then** the gate identifier and the decision record are byte-identical to the previous run.
3. **Given** a `ppstructurev3@cpu` run (default profile) on the same fixture, **When** preprocessing completes, **Then** the `run_summary` line carries the same additive fields with values that reflect the active CPU default — absence of any of these fields on a run of the new binary is itself a regression signal.
4. **Given** the recorded signal-set surface (US1) on `run_summary` and the documented decision table, **When** an operator wants to know why a document was rated `sufficient` / `borderline` / `insufficient`, **Then** the answer is re-derivable from the operator-facing record alone, without re-running the binary and without reading source code.

### User Story 4 - Skip-fallback behavior for OCR-only `sufficient` runs (Priority: P1)

A pipeline engineer wants the gate to harvest latency on the OCR-only fast lane (feature 019) when the gate has independently vouched that the OCR-only output already carries enough vendor-identity evidence. When the gate decision is `sufficient` on a document being processed by the feature 019 OCR-only fast lane AND the feature 019 FR-005 deterministic fallback trigger would otherwise fire, this feature suppresses that fallback for that document — the OCR-only `preprocess_output.json` is the artifact downstream stages consume, and the PPStructureV3 retry is skipped. The behavior MUST be deterministic, code-owned, re-derivable from `preprocess_output.json` and the recorded signal set alone, and operator-visible per US3. The behavior is opt-in via a CLI flag (with env-var fallback per the feature 016–019 activation pattern) and defaults to off on the GPU lane until promoted under FR-016.

**Why this priority**: Shape (b) skip-fallback is the load-bearing behavioral surface for the feature. It directly extends feature 019's OCR-only fast lane (which is the most recent latency lever shipped in the pipeline), it provides measurable latency-harvest value at opt-in time, and it does NOT modify feature 008's deterministic routing surface — preserving the project's "consensus and routing are never delegated to a model" constitutional rule. P1 because the operator-visible `evidence_gate_suppressed_fallback_count` counter and the suppression decision must be testable and reviewable independently of the rest of the pipeline. (Alternative shapes (a) observability-only and (c) routing-input were considered and rejected at `/speckit.clarify` — see Clarifications.)

**Independent Test**: Take one fixture on which the OCR-only fast lane runs, the FR-005 trigger would fire, AND the gate decision is `sufficient`. Take one fixture on which the OCR-only fast lane runs, the FR-005 trigger would fire, AND the gate decision is `borderline` or `insufficient`. With the skip-fallback opt-in flag set, run preprocessing → extraction → routing → final payload → evaluation on both. Confirm: (1) on the first fixture the FR-005 fallback to PPStructureV3 is suppressed, the suppression increments `evidence_gate_suppressed_fallback_count`, and the OCR-only `preprocess_output.json` is what downstream stages consume; (2) on the second fixture the FR-005 fallback runs unchanged and the counter does not increment; (3) the disposition on each fixture is re-derivable from the recorded signal-set values plus the documented decision table plus the FR-005 trigger inputs; (4) with the opt-in flag unset, behavior on both fixtures is identical to a feature-019 run (no suppression, counter remains at default `0`); (5) `preprocess_output.json`, `edge_extraction_output.json`, `routing_decision.json`, and `final_structured_payload.json` continue to validate against their existing schemas in both fixtures and both flag states.

**Acceptance Scenarios**:

1. **Given** the gate decision `sufficient` on an OCR-only run, the feature 019 FR-005 fallback trigger would otherwise fire, and the skip-fallback opt-in flag is set, **When** preprocessing runs, **Then** the OCR-only-to-PPStructureV3 fallback is suppressed for that document, `evidence_gate_suppressed_fallback_count` on `run_summary` increments by one for the run, the suppression is operator-visible per US3, and the downstream pipeline accepts the OCR-only `preprocess_output.json` unchanged.
2. **Given** the gate decision `borderline` or `insufficient` on an OCR-only run with the skip-fallback opt-in flag set, **When** the feature 019 FR-005 fallback trigger would otherwise fire, **Then** the fallback to PPStructureV3 runs unchanged, `evidence_gate_suppressed_fallback_count` does not increment, and the existing feature 019 behavior is preserved.
3. **Given** the gate decision `sufficient` on an OCR-only run AND the skip-fallback opt-in flag is unset, **When** the feature 019 FR-005 fallback trigger would otherwise fire, **Then** the fallback runs unchanged exactly as in feature 019, `evidence_gate_suppressed_fallback_count` stays at default `0`, and the gate decision is observable on `run_summary` per US3 with no behavioral side effect.
4. **Given** any gate decision (`sufficient` / `borderline` / `insufficient`) on a run that is NOT the OCR-only fast lane (i.e., the run already used PPStructureV3 directly), **When** preprocessing completes, **Then** no fallback suppression takes effect (the FR-005 trigger is OCR-only-specific), `evidence_gate_suppressed_fallback_count` stays at default `0`, and the existing pipeline behavior is preserved.

### User Story 5 - Default CPU profile and CI without GPU stay safe (Priority: P2)

An engineer running the default `ppstructurev3@cpu` profile, or the existing CI without GPU hardware, must not have their behavior changed by this feature beyond the additive operator-visible fields on `run_summary`. No CPU code path may import GPU-only gate or behavioral-shape code; no CPU run may consult or mutate any GPU-only configuration switch this feature introduces. The signal set (US1) and the gate decision (US2) MAY be computed on CPU runs — they are pure functions over `preprocess_output.json` and do not require GPU — but any GPU-only-side behavior-shape switch from US4 MUST follow the warn-and-proceed pattern established in features 016 / 017 / 018 / 019.

**Why this priority**: P2 — the risk is regression, not new value. CPU and CI paths already work post-019; this story protects them. Lower than P1 only because the CPU/CI path's correctness is independently verifiable today, and because this feature's CPU surface is purely the additive operator-visible surface from US1 / US2 / US3.

**Independent Test**: Run the default `ppstructurev3@cpu` profile and the existing stub-adapter / CPU-only test suites on a host without Paddle GPU, both with and without any new GPU-only configuration switches set in the environment. The suites must pass in both configurations. CPU `preprocess_output.json` outputs must be byte-identical to outputs on `main` before this feature lands. CPU runs MUST also compute and emit the US1 / US2 / US3 surface — the gate is not GPU-only — but their values on CPU runs reflect the CPU default configuration.

**Acceptance Scenarios**:

1. **Given** the default `ppstructurev3@cpu` profile on a host without GPU, **When** preprocessing runs, **Then** no GPU-only gate behavior-shape code path is imported or executed; the signal set and gate decision ARE computed and emitted per US1 / US2 / US3.
2. **Given** the same default CPU profile with any new GPU-only configuration switch this feature introduces *explicitly set* in the environment, **When** preprocessing runs, **Then** the run completes normally with no GPU-only behavior change and no silent ignore — a clear stderr warning is emitted that the switch was ignored because the active profile is not `ppstructurev3@gpu`, and the run exits with the same status it would have produced without the switch.
3. **Given** the existing default test suite on a host without Paddle GPU, **When** the suite runs, **Then** it passes; GPU-only verification of any US4 behavioral shape is skipped via `@pytest.mark.gpu` rather than failed; signal-set and gate-decision unit tests run on CPU.

**Acceptance Scenarios**:

### User Story 7 - Quality-gate guard before any behavioral default change (Priority: P3)

If, after running the US1 / US2 / US3 evaluation and the US4 skip-fallback evaluation, the team chooses to promote the skip-fallback behavior to the new default on the GPU lane (i.e., turning the FR-007 opt-in on by default), the promotion must be gated on vendor-identity quality being preserved against the existing default — measured on the same small corpus the benchmark used. Promotion that fails the gate is rejected; the legacy non-behaving default (opt-in off) stays in place. This mirrors feature 017 FR-015 / feature 018 FR-016 / feature 019 FR-016.

**Why this priority**: P3 — the feature ships value at P1+P2 (signal set, gate decision, operator visibility, schema preservation, CPU/CI safety) without ever flipping a default. Promotion is a follow-on decision. P3 because skipping the gate would convert this feature from "evaluation slice" to "silent regression vector"; promotion-gating is required only if and when the team chooses to promote.

**Independent Test**: Take a candidate behavioral configuration that US4 evaluated. Compare its vendor-identity quality numbers (from the existing evaluator) against the legacy default's numbers on the same corpus. The promotion gate passes only if the candidate is at parity or better on the agreed quality metrics. If the gate passes, the candidate becomes the new default in this feature; if it fails, the legacy default is kept and the candidate remains an opt-in selection only.

**Acceptance Scenarios**:

1. **Given** a candidate behavioral configuration evaluated under US4, **When** the team considers promoting it to the new default, **Then** the decision references vendor-identity quality numbers produced by the existing evaluator on the same corpus the benchmark used.
2. **Given** a candidate that passes the quality gate, **When** the default is changed, **Then** the change is recorded in this feature's research artifact and the new default's `evidence_gate_id` (plus the active US4 shape identifier, if any) appears in subsequent `run_summary` lines without any opt-in switch needing to be set.
3. **Given** a candidate that fails the quality gate, **When** the promotion decision is made, **Then** the legacy default remains in place and the candidate stays selectable only via explicit configuration.

### Edge Cases

- **Gate or behavioral-shape switch combined with `ppstructurev3@cpu`**: Signal-set and gate-decision computation are NOT GPU-only — they run on CPU runs and stub-adapter runs and emit values per US3. A behavioral-shape switch (US4) that selects a non-default behavior on the GPU lane IS GPU-only by design. When the GPU-only behavior switch is set with the CPU profile or a stub adapter, the system MUST follow the same warn-and-proceed pattern features 016 / 017 / 018 / 019 established: emit a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`, perform no behavior change, and proceed with the run normally. Silent ignore is NOT acceptable.
- **Gate candidate fails vendor-identity quality gates**: Treated as a regression of FR-012. The gate candidate is rejected; the legacy behavior is kept as the default until the regression is resolved.
- **Gate decision conflicts with `region_strategy_fallback_count` or `ocr_only_fallback_count`**: Both prior counters describe what preprocessing actually did; the gate decision describes what the evidence supports. The two surfaces are independent and additive — the gate decision MUST NOT change or mask either counter, and either counter MUST NOT change the gate decision. When the OCR-only fast lane fell back (feature 019), the gate runs on the resulting PPStructureV3 `preprocess_output.json` and emits whatever decision the signals imply.
- **Gate decision changes per-document `phase_timings` shape**: Forbidden. Per-document `phase_timings` keys (`paddle_import`, `gpu_bind_probe`, `engine_init`, `rasterization`, `per_page_inference`, `artifact_write`, `total`, and `warmup` from feature 016) MUST NOT be renamed, removed, or have their type changed by this feature.
- **Gate decision alters the `preprocess_output.json` page index, block index, or coordinate system**: Forbidden. Page count, page index, coordinate origin, coordinate units, block index, and the `pages.length == page_count` invariant from feature 018 MUST stay identical to existing outputs. The gate is a pure read over `preprocess_output.json`; it does not mutate or rewrite the artifact.
- **Gate decision lands inside `preprocess_output.json` or any other canonical artifact**: Forbidden. The decision lives on `run_summary` or an equivalent existing operator-facing surface, never inside any of the four canonical stage 1 artifacts (which are schema-frozen by FR-019).
- **Borderline gate decision triggers behavioral effect**: Forbidden. Only the `sufficient` state MAY trip the optional US4 behavior-shape effect. `borderline` and `insufficient` MUST preserve the existing pipeline behavior so no document is accepted early on weak evidence. (This rule is unconditional regardless of which US4 shape `/speckit.clarify` selects.)
- **GPU bind failure when a US4 behavioral shape is selected**: Run MUST fail fast (preserving feature 015 FR-008 / feature 017 FR-007 / feature 018 / feature 019 — no silent CPU fallback after `ppstructurev3@gpu` is selected). The exit reason MUST identify the active `evidence_gate_id` and the active US4 shape identifier so operators can diagnose without re-instrumentation.
- **Operator overrides a promoted behavioral default back to the legacy behavior**: MUST be supported by the same explicit configuration switches this feature introduces — a default change MUST NOT remove the operator's ability to select the legacy behavior by explicit configuration.
- **GPU verification deferred to a follow-up**: When workstation GPU hardware is unavailable at landing time, GPU-marked tests (`@pytest.mark.gpu`) and benchmark verification for any US4 GPU-side behavioral shape MAY be deferred and tracked as a follow-up issue/task without blocking the CPU-safe implementation from merging (per feature 016 FR-014 / feature 017 FR-024 / feature 018 FR-025 / feature 019 FR-025). The deferral MUST be captured in this feature's `tasks.md` and quickstart so the verification cannot be quietly skipped. Signal-set and gate-decision unit tests run on CPU and MUST pass before merge.
- **Conditions under which the legacy default is preserved** (collated for review traceability): (a) FR-012 quality-gate failure for the behavioral candidate; (b) gate decision becomes non-deterministic or non-re-derivable from `preprocess_output.json` alone; (c) downstream-contract conflict where the gate or its behavioral effect would alter `preprocess_output.json` or any canonical artifact in a way any downstream stage rejects; (d) GPU bind failure on the behavioral-shape configuration; (e) the team makes no promotion decision at landing. In all cases the legacy non-behaving default remains both the default and an explicitly selectable option.

#### Out of Scope

Documented here so future failures are recognized as known gaps rather than regressions:

- **Schema or `schema_version` changes to the four canonical stage 1 artifacts**: Out of scope. This feature is read-only on the canonical artifacts and additive-only on the operator-visible surface.
- **Replacing deterministic routing or consensus with model judgment**: Out of scope. The feature 008 deterministic-routing rules and the future consensus surface remain code-owned. This feature's selected FR-007 shape (skip-fallback) does not feed routing in any way; feature 008's routing inputs and `routing_decision.json` shape are unchanged by this feature.
- **Cloud / remote routing changes**: Out of scope. No new escalation surface, no new remote model call, no new external API.
- **Non-vendor-identity extraction scope**: Out of scope. Line items, totals, dates, and all other stage 2+ extraction surfaces are not touched. The signal set is vendor-identity-specific.
- **Promoting a CPU-side default change**: Out of scope. Signal-set and gate-decision computation are added to CPU runs as observability; their values reflect the CPU default configuration. Any new behavioral effect under US4 is GPU-only by design.
- **Adding a new persisted artifact**: Out of scope unless `/speckit.clarify` or `/speckit.plan` produces evidence that the existing `kind: "run_summary"` stdout shape plus the existing harness/evaluator outputs are insufficient to record the signal set and gate decisions. If introduced, its name, location, schema, and lifecycle MUST be specified in `data-model.md` + `research.md` and the contract set updated under `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- **Regenerating committed corpus baselines**: Out of scope. Any baseline change MUST go through the established dataset/baseline flow defined in `docs/stage1-vendor-identity/dataset-layout.md` and `labeling-guide.md`, not through this feature's PR.
- **Adding a learned or ML-derived signal**: Out of scope. Every signal MUST be a deterministic function over `preprocess_output.json` text/token/geometry/confidence content — no learned classifiers, no statistical models, no extraction-model inputs. Future ML-derived signals are a separate feature and a separate constitutional review.
- **Replacing feature 019's OCR-only fallback trigger with the gate decision**: Out of scope here. Feature 019's FR-005 trigger is preserved unchanged. Any interaction with the gate is opt-in via US4 shape (b) (skip-fallback) and is conditional on a `sufficient` decision; the underlying feature 019 trigger logic is not removed.

## Requirements *(mandatory)*

### Functional Requirements

**Deterministic signal set**

- **FR-001**: System MUST compute a code-owned signal set derived exclusively from `preprocess_output.json` content for each document. Signals MUST be deterministic, MUST be re-derivable from the same `preprocess_output.json` on any host, and MUST NOT consult any extraction, classification, routing, or vendor-identity model output. The signal set is closed; adding a future signal is a code change plus a new entry, not a runtime parameter. At landing the signal set comprises exactly five signals (resolved at `/speckit.clarify` — see Clarifications): (1) a vendor-name-candidate-token signal, (2) a header-band token-density signal, (3) an OCR-detection aggregate-confidence signal, (4) a business-suffix-presence signal (presence of tokens like `LLC`, `Inc`, `Ltd`, `GmbH`, `S.A.`), and (5) a tax-id-shaped-token-presence signal (presence of EIN-shaped or VAT-shaped patterns). All five signals MUST be computed over a single uniform coordinate scope — the page-1 header band, defined as tokens whose y-coordinate falls in the top fraction of page 1 (default y-threshold `0.25` of page-1 height, exact value resolved at `/speckit.plan`) — applied via a coordinate filter over `preprocess_output.json` regardless of which region strategy produced the file. Footer-only vendor identity, multi-page-only vendor identity, and tokens outside the page-1 header band are explicitly out of this feature's signal scope; they may surface a `borderline` or `insufficient` decision and fall through to the legacy feature-019 behavior. Telephone-shaped, email-shaped, and postal-address-shaped tokens are also out of scope and are NOT computed or emitted by this feature.
- **FR-002**: The signal set MUST be computable on the output of any preprocessing strategy in scope today — feature 018's `full-page` and `header-first-v1` region strategies and feature 019's `ppstructurev3` and `ocr-only-v1` preprocessing strategies. The signals MUST NOT require layout-derived blocks (so OCR-only outputs are first-class inputs) and MUST NOT require any feature-018 region-strategy-specific shape (so full-page outputs are first-class inputs).
- **FR-003**: The signal values for every document MUST be observable on the existing single `kind: "run_summary"` stdout line as an additive top-level `evidence_gate_documents` array (resolved at `/speckit.clarify` — see Clarifications). Each array element MUST carry a stable `document_id`, the document's gate decision (`sufficient` / `borderline` / `insufficient`), and the recorded values for each of FR-001's five signals. The shape MUST be sufficient for an operator to re-derive the gate decision (FR-004) from the recorded signal values plus the documented decision table without re-running the binary.

**Gate decision**

- **FR-004**: System MUST compute, for each document, a gate decision drawn from a closed three-state vocabulary — `sufficient`, `borderline`, `insufficient`. The decision MUST be a deterministic function over the FR-001 signal set, MUST be re-derivable from the recorded signal values plus the documented decision table, MUST NOT depend on any extraction or vendor-identity model output, and MUST be expressed in code as an explicit decision table or equivalent boolean expression. Adding a fourth state is a code change plus a new explicit state value, not a runtime parameter.
- **FR-005**: The gate-rule body (the decision table or boolean expression that maps signals → state) MUST be versioned and selectable via an `evidence_gate_id` preset. At landing time the feature ships at least one preset (e.g., `v1`); future iterations of the rule add new preset values, not runtime parameter knobs.
- **FR-006**: The gate decision MUST be operator-visible on the existing single `kind: "run_summary"` stdout line per FR-008 via two additive top-level fields (resolved at `/speckit.clarify` — see Clarifications): (a) `evidence_gate_state_counts` — an object with default-zero integer counts for each of `sufficient`, `borderline`, and `insufficient` across the run; AND (b) `evidence_gate_documents` — the per-document array defined in FR-003. Both fields MUST be present on every run of the new binary (default-zero / empty-array semantics when no documents reached the gate). The shape MUST allow both aggregate-level observation and per-document attribution from a single recorded `run_summary` line.

**Behavioral effect of the gate**

- **FR-007**: System MUST adopt the **skip-fallback for OCR-only `sufficient` runs** behavioral shape (resolved at `/speckit.clarify` — see Clarifications). When the gate decision is `sufficient` on a document being processed by feature 019's OCR-only fast lane AND the skip-fallback opt-in is active for the run, the feature 019 FR-005 deterministic fallback to PPStructureV3 on that document MUST be suppressed — even if the FR-005 trigger would otherwise fire. The suppression MUST be operator-visible per FR-008 via an additive `evidence_gate_suppressed_fallback_count` integer counter on `run_summary` with the same always-emit pattern as feature 018 FR-009 / feature 019 FR-007 (default `0`, present on every run of the new binary including `ppstructurev3@cpu` runs and stub-adapter runs). The gate decision and the FR-005 trigger inputs together MUST deterministically and unambiguously decide whether the document falls back. `borderline` and `insufficient` MUST preserve the feature 019 fallback unchanged. The skip-fallback behavior is opt-in via a CLI flag (with env-var fallback per the feature 016–019 activation pattern); it defaults to off on the GPU lane per FR-012 until promoted under FR-016.
- **FR-008**: Whichever FR-007 shape is chosen, the disposition (including any new counter that shape introduces) MUST be operator-visible on `run_summary` and MUST follow the always-emit pattern established by feature 018 FR-009 / feature 019 FR-007 (counter fields default `0` and are present on every run of the new binary, including `ppstructurev3@cpu` runs and stub-adapter runs).
- **FR-009**: Whichever FR-007 shape is chosen, only the gate state `sufficient` MAY trip the optional behavioral effect. `borderline` and `insufficient` MUST preserve the existing pipeline behavior unchanged.

**Operator-facing visibility**

- **FR-010**: The `run_summary` line MUST carry an additive top-level string field `evidence_gate_id` that identifies the active gate rule for the run. The value MUST be drawn from the FR-005 closed vocabulary (`v1` at landing, plus any future preset added by code change). The field MUST be a human-readable string, not an opaque numeric hash. It MUST coexist with — not replace — feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked`, feature 018's `raster_profile_id` / `region_strategy_id` / `region_strategy_fallback_count`, and feature 019's `preprocess_strategy_id` / `ocr_only_fallback_count`.
- **FR-011**: The fields introduced by FR-003 / FR-006 / FR-008 / FR-010 MUST be additive only on `run_summary`. No existing `run_summary` field, no `phase_timings.*` key, no field inside any of the four canonical stage 1 artifacts, and no field introduced by features 017–019 may be renamed, removed, or retyped by this feature.

**Profile defaults and CPU/stub isolation**

- **FR-012**: `ppstructurev3@cpu` MUST remain the default preprocessing profile, with the signal set, gate decision, and operator-visible surface running on CPU as observability. Any FR-007 behavioral shape that introduces a GPU-only switch MUST default to "off" on the GPU lane until explicitly promoted via the FR-013 quality gate.
- **FR-013**: When any GPU-only configuration switch this feature introduces (e.g., a US4 behavioral-shape switch under FR-007) is set on `ppstructurev3@cpu` or a stub adapter, the system MUST: (a) emit a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`; (b) perform no behavior change; (c) proceed with the run normally and exit with the same status it would have produced without the switch. Silent ignore and rejection are both NOT acceptable. (Mirrors feature 016 FR-010 / feature 017 FR-013 / feature 018 FR-014 / feature 019 FR-013.)

### Key Entities

- **Vendor-identity evidence signal**: A code-owned, deterministic value derived from `preprocess_output.json` content for a single document — for example, a count of vendor-name-candidate tokens in the header band, an aggregate OCR detection confidence over the targeted region, the presence-of-business-suffix boolean, or a postal-code-pattern presence boolean. Each signal is a pure function over `preprocess_output.json` and is computed without any extraction or vendor-identity model in the loop. The signal set is closed at code level; new signals are added by code change plus a new closed-vocabulary entry. The exact signal list is resolved at `/speckit.plan`.
- **Evidence-gate preset**: A named preset that fixes the gate rule (the decision table or boolean expression that maps the FR-001 signal set into one of the three states `sufficient` / `borderline` / `insufficient`). Identified on `run_summary` by `evidence_gate_id` (e.g., `v1`). Closed vocabulary at code level; new presets are added by code change. The gate rule is documented in this feature's `research.md` / `data-model.md` so the decision is re-derivable from the recorded signals.
- **Gate decision**: The three-state outcome of the gate for a single document — `sufficient`, `borderline`, or `insufficient`. Stored on the operator-visible surface (`run_summary` or equivalent), not inside any canonical artifact. The decision is deterministic and re-derivable from the recorded signal values plus the documented decision table.
- **Skip-fallback suppression counter**: An additive `run_summary` integer field `evidence_gate_suppressed_fallback_count` (default `0`, always emitted) that records how many OCR-only-fast-lane documents had their feature 019 FR-005 fallback suppressed by the gate on this run (per FR-007 / FR-008). Increments only when the gate decision is `sufficient` AND the FR-005 trigger would otherwise fire AND the skip-fallback opt-in is active.
- **Quality-gate evidence**: Vendor-identity quality numbers (per the existing evaluator) for each evaluated `evidence_gate_id` + FR-007 shape combination on the same small corpus subset, recorded in this feature's research artifact, used as the gating evidence for any default promotion under FR-016.
