## Summary

Add a deterministic vendor-identity evidence gate over `preprocess_output.json` content. The gate computes a closed-vocabulary set of **five signals** over the page-1 header band (top fraction of page 1 by y-coordinate, default `Y_THRESHOLD_FRACTION = 0.25` — R-020.5) regardless of which region strategy produced the file: (1) vendor-name-candidate-token count, (2) header-band token-density, (3) OCR-detection aggregate confidence, (4) business-suffix-presence (presence of any of `LLC`, `Inc`, `Incorporated`, `Ltd`, `Limited`, `GmbH`, `S.A.`, `S.A.S.`, `Corp`, `Corporation`, `Co.` — R-020.4), and (5) tax-id-shaped-token-presence (EIN `XX-XXXXXXX` or VAT-like `[A-Z]{2}[A-Z0-9]{2,12}` regex — R-020.4). These five signals are mapped deterministically to one of three states (`sufficient` / `borderline` / `insufficient`) by the **v1 explicit decision table** (R-020.6): `sufficient` requires `vendor_name_candidate_count >= 1` AND `header_band_token_density >= 8` AND `ocr_detection_confidence_mean >= 0.70` AND (`business_suffix_present` OR `tax_id_shaped_present`); `insufficient` requires all five signals at their negative level (no candidate name AND density `< 8` AND confidence `< 0.70` AND no business suffix AND no tax-id); `borderline` is the residual. The gate is identified on `run_summary` by `evidence_gate_id = "v1"` (closed vocabulary of size one at landing — R-020.2). Feature 020 adopts FR-007 **shape (b) skip-fallback** (resolved at `/speckit.clarify`): when the gate decision over an OCR-only **candidate** `preprocess_output.json` is `sufficient` AND the operator opt-in is active AND feature 019's FR-005 fallback trigger would otherwise fire, the fallback to PPStructureV3 is suppressed and the OCR-only candidate becomes the document's final `preprocess_output.json`; otherwise feature 019's existing fallback behavior runs unchanged (R-020.7 / R-020.8). The opt-in is `--evidence-gate-skip-fallback` (boolean, off-by-default) on both `python -m ledgerlinc_ocr.preprocessing` and `python -m ledgerlinc_ocr.pipeline` with env-var fallback `LEDGERLINC_EVIDENCE_GATE_SKIP_FALLBACK` (R-020.1; same precedence rule as features 016/017/018/019 — CLI wins, empty string env = unset). The feature ships **four additive top-level fields on `run_summary`** (resolved at `/speckit.clarify` Q3 — single line carrying aggregate counters AND per-document table): `evidence_gate_id: str` (always `"v1"` at landing), `evidence_gate_state_counts: {sufficient: int, borderline: int, insufficient: int}` (default zeros, always present), `evidence_gate_documents: list[EvidenceGateDocumentRecord]` (default `[]`, one record per document carrying `document_id` + `decision` + the five signal values), and `evidence_gate_suppressed_fallback_count: int` (default `0`, increments only when shape (b) suppression actually fires); the codebase-level `RunSummary.SCHEMA_VERSION` patches **0.1.6 → 0.1.7** for the four additive top-level fields (R-020.9); the four canonical stage 1 artifact schemas, `contract_set_version`, and the `pipeline_version` shape are unchanged (FR-020 / SC-007 / SC-010). Combining `--evidence-gate-skip-fallback` with `ppstructurev3@cpu` or any stub adapter emits the FR-013 warn-and-proceed stderr line containing the literal `--evidence-gate-skip-fallback ignored:` (R-020.12, identical structure to feature 016/017/018/019 precedent) and produces an otherwise identical run. No new exit code is introduced — the gate is a closed read over `preprocess_output.json`, never a CLI-time selectable preset (no `--evidence-gate <id>` flag at landing because the registry has size one; future presets land that flag), so `UnknownPresetError` is **not** extended by this feature. The signal-set + gate-decision computation is **pure Python over `preprocess_output.json` content** — no Paddle import, no GPU, no model call — and runs on CPU profiles, stub-adapter runs, and the GPU lane uniformly (FR-014 / FR-024 / SC-005). The gate may evaluate at most **twice per document** when shape (b) is engaged and a fallback fires (once on the OCR-only candidate to decide suppression, once on the post-fallback PPStructureV3 output for the recorded decision); otherwise the gate evaluates exactly once per document (R-020.7). The skip-fallback suppression and feature 019's FR-005 trigger together MUST deterministically and unambiguously decide whether the document falls back, and only the `sufficient` gate state MAY trip the suppression (FR-009 / SC-011). All feature 014 / 015 / 016 / 017 / 018 / 019 guarantees carry over unchanged (FR-022 / SC-009): PPStructureV3 constructed at most once per process when used, GPU readiness probed at most once per process, single-device-per-process guard, no silent CPU fallback after `ppstructurev3@gpu` is selected, warmup behavior unchanged, `pipeline_version` ends in `.gpu0` / `.cpu0`, feature 017/018/019 identifier surfaces unchanged. Corpus baselines and `preprocess_output.json` shape are byte-identical to the pre-feature legacy GPU configuration on every fixture (FR-019 / SC-006 / SC-007). The FR-015 benchmark — the legacy default (no skip-fallback opt-in) vs. the skip-fallback opt-in candidate — runs over the **same fixed 5-doc subset features 017, 018, and 019 used** (R-020.13) and lands its numbers in this feature's `quickstart.md` Appendix A. Quality-gate evidence (FR-016 / FR-017) — both metrics from the existing evaluator (per-corpus aggregate vendor-identity field score from `evaluation_run_summary.json` AND per-document pass count per `docs/stage1-vendor-identity/scoring.md`) — lands in this feature's `research.md` Appendix B alongside the candidate's `evidence_gate_id` value. GPU verification of FR-015 / FR-016 / GPU-marked tests may be deferred per FR-026 (R-020.15, feature 016/017/018/019 precedent); the deferral is captured in `tasks.md` and `quickstart.md` Appendix B so the verification cannot be quietly skipped. The signal-set and gate-decision unit tests run on CPU and MUST pass before merge.

Writes `preprocess_output.json` into the same per-document folder unchanged in shape (FR-020). The four new `run_summary` fields live exclusively in the existing single `kind: "run_summary"` stdout line per feature 014/015/016/017/018/019 lineage and per Clarifications Q3 — single line, aggregate counters AND per-document table together; **no new persisted artifact** (FR-021 / Out of Scope / SC-007). The FR-015 benchmark numbers and FR-016 quality-gate evidence land in this feature's `quickstart.md` Appendix A (benchmark numbers) and `research.md` Appendix B (quality-gate evidence) at landing time; both are Markdown documents under `specs/020-vendor-evidence-gate/`, not under `contracts/` and not under `tests/stage1_vendor_identity/`.
**Testing**: pytest. Existing markers `gpu` (deselected without GPU per FR-024) and `live` carry over. New tests under `tests/unit/preprocessing/` and `tests/pipeline_tests/` (matching feature 016/017/018/019's directory convention; `tasks.md` is normative for exact file paths). Existing `tests/contract_tests/` continue to pass unchanged (FR-020). Stub-adapter and CPU-only suites must continue to pass without GPU (FR-014 / FR-024 / SC-005). The warn-and-proceed path for the new switch is covered on the default (no-GPU) suite per FR-024 / R-020.12. Signal-set and gate-decision unit tests run on CPU (FR-014).
**Target Platform**: Linux (devcontainer + workstation WSL with native ROCm `gfx1151` via host Ollama / `.venv-paddle-rocm`). CPU profile and stub adapter work on any Linux host. Production CI exercises CPU + stub only.
**Project Type**: single Python package (`ledgerlinc-ocr`) with a pluggable evidence-gate layer over `preprocess_output.json` content. **Two new modules across the stacked-PR delivery** (`preprocessing/evidence_gate.py` on PR #38, `preprocessing/evidence_gate_optin.py` on stacked PR #40), **zero new exception classes**, **zero new exit codes** (no `UnknownPresetError` extension; the closed vocabulary at landing has size one), and **surgical edits to seven existing modules** (`preprocessing/pipeline.py`, `preprocessing/cli.py`, `preprocessing/identifiers.py`, `pipeline/timing.py`, `pipeline/corpus_run.py`, `pipeline/runner.py`, `pipeline/cli.py`).
**Performance Goals**: no numeric latency target (Constitution: "no latency target as a release gate"; spec Assumptions). Outcomes are observability + measurable latency-harvest on shape (b) skip-fallback runs when gate decision is `sufficient` — measurable as (a) `evidence_gate_suppressed_fallback_count >= 1` on the FR-015 benchmark for at least one fixture with the opt-in active (SC-003 / FR-015); (b) the FR-015 benchmark is recorded with both quality metrics on the same 5-doc subset (FR-015 / FR-016 / SC-008); (c) `evidence_gate_id`, `evidence_gate_state_counts`, `evidence_gate_documents`, and `evidence_gate_suppressed_fallback_count` are present on every run_summary line and stable across reruns of the same configuration on the same input (SC-001 / SC-002 / SC-003); (d) signal-set values + the documented decision table re-derive the recorded decision exactly (SC-012). **Gate cost characterization**: per-document gate evaluation is `O(T)` in `T = len(tokens on pages[0])` after the y-coordinate filter — each token is checked against the stop-word `frozenset` (O(1) membership), the vendor-name heuristic (O(1) per token), the compiled `BUSINESS_SUFFIX_RE`, and the two compiled tax-id regexes (all bounded-repetition patterns, R-020.4). Confidence-mean aggregation is `O(B)` in `B = len(detection boxes in band)`. The three regex patterns are compiled ONCE at module load (data-model.md §6). Worst case per document is two evaluations when shape (b) is engaged and fallback fires (R-020.7). **Memory cost characterization**: `evidence_gate_documents` accumulates one `EvidenceGateDocumentRecord` dict per document on the run-level `RunSummary` (worst-case `O(N)` in corpus size, `N = 20` on the stage-1 corpus). No in-process mutable globals; the gate module is stateless at module level (data-model.md §10). No new persisted artifact (FR-021) — `run_summary` carries the entire surface in-line. **Latency-harvest noise floor**: per FR-015 measurement discipline, latency deltas below the host's run-to-run jitter band (established by two legacy runs on the same fixture) are reported but not treated as harvest. **Gate evaluation cost accounting in `phase_timings.total`**: when the gate evaluates twice per document (candidate + post-fallback per R-020.7), both evaluations are pure-Python work and are accounted for within `phase_timings.total` as part of the preprocessing pass — they are NOT separately timed (forbidden per run-summary-schema.md § Forbidden surface changes — no `phase_timings.evidence_gate` key) and are NOT subtracted from any feature-019 `phase_timings.per_page_inference` value. The second-evaluation overhead is O(T) in `pages[0]` token count of the post-fallback `preprocess_output.json` and is bounded by the per-document cost characterization above; on the 5-doc benchmark subset this is < 5ms per document of pure-Python work, well below the host's jitter band.

**Structure Decision**: single Python package, **two new modules across the stacked-PR delivery** (`preprocessing/evidence_gate.py` on PR #38, `preprocessing/evidence_gate_optin.py` on stacked PR #40), **zero new exception classes**, **zero new exit codes** (the gate has no CLI-time preset selection at landing because the closed vocabulary has size one; future presets will land their own `--evidence-gate <id>` flag and reuse the existing `UNKNOWN_PRESET = 16` exit code via the existing `UnknownPresetError` machinery), **seven touched modules** (`preprocessing/pipeline.py`, `preprocessing/cli.py`, `preprocessing/identifiers.py`, `pipeline/timing.py`, `pipeline/corpus_run.py`, `pipeline/runner.py`, `pipeline/cli.py`). **No new top-level subpackage.** The evidence-gate axis contract lives entirely under `preprocessing/evidence_gate.py` (signal-set + decision-table on PR #38) and `preprocessing/evidence_gate_optin.py` (CLI/env-var opt-in resolution on PR #40), keeping the run_summary schema as the single source of truth for run-level observability per Clarifications Q3. The `--evidence-gate-skip-fallback` opt-in lives in the existing preprocess CLI and warm-corpus CLI rather than a new entry point, mirroring how features 014–019 added their orthogonal switches rather than spinning up separate CLIs.
