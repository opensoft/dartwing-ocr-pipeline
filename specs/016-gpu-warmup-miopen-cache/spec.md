# Feature Specification: GPU Warmup And MIOpen Cache Stabilization

**Feature Branch**: `016-gpu-warmup-miopen-cache`
**Created**: 2026-05-07
**Status**: Draft
**Input**: User description: "Build the next GPU optimization slice after feature 015. Add an explicit, opt-in GPU warmup path for `ppstructurev3@gpu` so MIOpen/COMGR tuning cost can be paid before timed corpus documents and reported separately from document OCR time."

## Clarifications

### Session 2026-05-07

- Q: When the explicit warmup pass itself raises a MIOpen/COMGR/Paddle error, what is the contract — fail-fast, record-and-proceed, or warn-and-skip? → A: **Fail-fast.** The process exits non-zero before any document is timed, with a reason of the form `warmup failed: <cause>`. No `phase_timings.warmup` is emitted (preserving feature 015 FR-016 "absent phases are omitted, not zeroed"). All `phase_timings.*` entries remain shaped `{seconds: <float>}` only — warmup-failure details are reported outside `phase_timings`, via stderr and the process exit reason, mirroring how feature 015 surfaces GPU-prerequisite failures. Resolved inline during `/speckit.specify`.

### Session 2026-05-08

- Q: When the warmup opt-in is set but the active profile is not `ppstructurev3@gpu` (e.g., `ppstructurev3@cpu` or a stub adapter), what is the contract — reject with a configuration error, silent no-op, or warn-and-proceed? → A: **Warn-and-proceed.** The system emits a clear stderr warning that warmup was ignored because the active preprocess profile is not `ppstructurev3@gpu`, performs no warmup, emits no `phase_timings.warmup`, makes no MIOpen/COMGR env var mutation, and performs no `~/.cache/miopen` or `~/.cache/comgr` access. The run then proceeds normally and exits with the same status it would have produced without the opt-in. Replaces the earlier "either reject or silently no-op" OR in FR-010, US3 acceptance #3, the Edge Cases entry, and SC-007.
- Q: Should the `schema_version` patch bump in FR-008 be codebase-level (all runs of the new binary) or per-run conditional (only when warmup actually ran)? → A: **Codebase-level.** This feature ships one bumped `run_summary` `schema_version` (X.Y.Z → X.Y.(Z+1)) that applies to *all* runs of the new binary. The bumped schema permits `phase_timings.warmup`, but the `warmup` key is absent in the emitted run_summary unless the warmup pass actually completed successfully (per feature 015 FR-016 "absent phases are omitted, not zeroed"). Updates FR-008 and SC-010.
- Q: How should MIOpen/COMGR runtime workspace warnings observed during warmup be handled — document only, eliminate by config, or both? → A: **Hybrid (eliminate where possible, document the residual).** Where a safe default configuration (env vars and/or cache directory layout shipped by this feature) can suppress a warning without changing observable warmup behavior, this feature MUST adopt that configuration as its default. Any warnings that remain after the default configuration is applied MUST be catalogued in this feature's documentation as known runtime diagnostics, with their meaning and operator guidance. Both lists — "addressed by default config" (with the exact env vars/settings used) and "residual / known diagnostic" (with meaning and operator guidance) — MUST appear in `research.md` and the docs deliverable referenced by US4. Replaces the OR in FR-016.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Opt-in warmup pass with separately reported timing (Priority: P1)

A pipeline engineer wants to pay the MIOpen/COMGR kernel-tuning cost up front, before any corpus document is timed, so that the per-document inference numbers in `run_summary.phase_timings` reflect steady-state OCR cost and not first-call kernel selection. They invoke the existing `ppstructurev3@gpu` preprocessing or corpus command with an explicit warmup opt-in, observe a single warmup pass run after PPStructureV3 engine construction and before the first timed document, and read its duration as a distinct `phase_timings.warmup` entry in the existing per-document `run_summary` line. Default GPU runs without the opt-in MUST behave identically to feature 015 — no warmup, no `warmup` key.

**Why this priority**: This is the headline of the feature. Every other story exists to protect or measure this behavior. Without it, MIOpen first-call latency keeps inflating `per_page_inference` and `total`, which undermines feature 015's reason for existing (data-driven latency analysis on the GPU path). It is also a prerequisite for distinguishing cold-cache from warmed-cache behavior (US2).

**Independent Test**: A single warmup-enabled `ppstructurev3@gpu` run on `inv_001_easy/source.pdf` is sufficient: invoke the warmup-enabled command, assert that exactly one warmup pass executes after engine construction and before any document inference, that `phase_timings.warmup` is present in the per-document `run_summary` entry that carries the other one-time GPU phases, and that `phase_timings.per_page_inference` and `phase_timings.total` for that document do NOT include warmup time.

**Acceptance Scenarios**:

1. **Given** a fresh process selecting `ppstructurev3@gpu` and the warmup opt-in on `inv_001_easy/source.pdf`, **When** preprocessing completes successfully, **Then** the per-document `run_summary` entry includes `phase_timings.warmup` as a `{seconds: <float>}` record, and the same entry's `phase_timings.total` and `phase_timings.per_page_inference` durations do NOT include the warmup time.
2. **Given** the same warmup-enabled single-document run, **When** preprocessing completes, **Then** PPStructureV3 was constructed exactly once (preserving feature 015's FR-001/SC-001), the warmup pass ran exactly once, the warmup pass executed strictly after engine construction and strictly before the first timed document inference, and the resulting `preprocess_output.json` is byte-identical to what the same `ppstructurev3@gpu` run produces without warmup.
3. **Given** a fresh process selecting `ppstructurev3@gpu` *without* the warmup opt-in, **When** preprocessing completes, **Then** no warmup pass executes and the per-document `run_summary` entry contains no `warmup` key (preserving feature 015's FR-016 "absent phases are omitted, not zeroed").
4. **Given** a warm corpus run with the warmup opt-in over at least two documents, **When** the run completes, **Then** the warmup pass ran exactly once across the entire run and `phase_timings.warmup` appears only on the first successfully processed per-document entry (alongside `paddle_import`, `gpu_bind_probe`, `engine_init` per feature 015 FR-015).

### User Story 2 - Cold-cache vs warmed-cache observability (Priority: P1)

A workstation operator runs the warmup-enabled GPU preprocessing command twice on the same fixture: once after clearing `~/.cache/miopen` and `~/.cache/comgr` (cold cache), and once with those caches populated by the previous run (warm cache). They expect `phase_timings.warmup` to be measurably larger on the cold-cache run than on the warm-cache run, so that they can tell from `run_summary` alone whether MIOpen kernel selection was performed or served from cache.

**Why this priority**: The whole point of paying warmup cost up front is to push variance out of `per_page_inference`. That guarantee is only useful if operators can confirm the cache is doing its job. P1 because the feature's value proposition collapses if the warmup phase looks the same regardless of cache state — operators would have no way to detect a corrupt or cleared cache from telemetry.

**Independent Test**: Run the warmup-enabled GPU command twice on the same fixture in two consecutive processes (cold then warm), capture both `run_summary` lines, and confirm that `phase_timings.warmup.seconds` on the cold-cache run exceeds the warm-cache run by an operator-detectable margin (see SC-003).

**Acceptance Scenarios**:

1. **Given** an empty `~/.cache/miopen` and `~/.cache/comgr` and a warmup-enabled `ppstructurev3@gpu` run on a fixed fixture, **When** the run completes, **Then** `phase_timings.warmup.seconds` reflects cold-cache MIOpen kernel selection cost.
2. **Given** the same fixture run a second time without clearing caches, **When** the run completes, **Then** `phase_timings.warmup.seconds` is measurably lower than the cold-cache value (per SC-003) while the rest of `phase_timings` (engine_init, per_page_inference, total) remains in the same order of magnitude.
3. **Given** a warmed-cache run, **When** the operator clears only `~/.cache/comgr` and runs again, **Then** `phase_timings.warmup.seconds` rises again, allowing the operator to attribute the change to cache state without rerunning instrumentation.

### User Story 3 - CPU and stub paths pay no warmup cost (Priority: P2)

An engineer running the default `ppstructurev3@cpu` profile, or a stub adapter in CI, must not trigger any warmup logic, MIOpen environment-variable mutation, or `~/.cache/miopen` interaction — even if the warmup opt-in is set in their environment. CI runs on hosts without Paddle GPU and without ROCm; warmup logic that runs unconditionally would either crash or contaminate CPU timing.

**Why this priority**: P2 — important but lower than the GPU stories because the risk is regression, not new value. CPU and stub paths already work today (post-015); this story protects them.

**Independent Test**: Run the default `ppstructurev3@cpu` profile and the existing stub-adapter test suites on a host without Paddle GPU, with the warmup opt-in both unset and explicitly set. The suite must pass in both configurations and the run output must contain no `warmup` key, no MIOpen/COMGR environment variable mutations, and no GPU phase timings.

**Acceptance Scenarios**:

1. **Given** `ppstructurev3@cpu` (the default profile) selected on a host without GPU, **When** preprocessing runs, **Then** no warmup pass executes, no `phase_timings.warmup` is emitted, no MIOpen/COMGR env var is set or read, and no `~/.cache/miopen` or `~/.cache/comgr` access occurs.
2. **Given** the existing CPU profile and stub adapter test suites with the warmup opt-in *explicitly* set in the environment, **When** the suites run on a host without GPU, **Then** they pass without modification and produce no `warmup` key.
3. **Given** the warmup opt-in is requested with `ppstructurev3@cpu`, **When** the CLI is invoked, **Then** the system emits a clear stderr warning that warmup was ignored because the active preprocess profile is not `ppstructurev3@gpu`, proceeds with the run normally, exits with the same status it would have produced without the opt-in, performs no warmup pass, sets no MIOpen/COMGR env var, and reads or writes no MIOpen/COMGR cache directory.

### User Story 4 - Workstation cache and diagnostics are documented (Priority: P3)

A workstation operator new to this feature needs to know: where MIOpen and COMGR persist their tuning artifacts, how to clear them deliberately, what `MIOPEN_FIND_MODE=2` does and why this feature defaults to it, and what the runtime warnings about MIOpen/COMGR workspaces mean (and whether they need to act). Without this, "warmup is fast on the second run" looks like magic and operators cannot triage cache-state regressions.

**Why this priority**: P3 — the feature can ship and be valuable to its author without docs, but the feature cannot be operated by anyone else on the team without them. Documentation is a release-gate item, not an MVP gate.

**Independent Test**: Open the documentation produced by this feature (quickstart and/or known-issues note under `docs/stage1-vendor-identity/`) and confirm it answers, in plain language: (a) cache locations for MIOpen and COMGR, (b) how to clear them, (c) the default `MIOPEN_FIND_MODE` value and rationale, (d) what each observed MIOpen/COMGR workspace warning means and whether it indicates a problem, (e) how to read `phase_timings.warmup` to detect cold vs warm cache state.

**Acceptance Scenarios**:

1. **Given** a workstation operator new to GPU warmup, **When** they read this feature's documentation, **Then** they can locate the cache directories, clear them, run a cold-cache warmup, and verify the result without further help.
2. **Given** the same operator observing a MIOpen or COMGR workspace warning during a warmup run, **When** they consult the documentation, **Then** the warning is either explained as a known runtime diagnostic with operator guidance, or the documentation describes a safe configuration that eliminates it (and which configuration this feature ships as the default).

### Edge Cases

- **Warmup opt-in selected without `ppstructurev3@gpu`**: Combined with `ppstructurev3@cpu` or a stub adapter, the system MUST emit a clear stderr warning that warmup was ignored because the active preprocess profile is not `ppstructurev3@gpu`, then proceed with the run normally with no warmup pass, no MIOpen/COMGR env var mutation, and no `~/.cache/miopen` or `~/.cache/comgr` access. Silent ignore is NOT acceptable (FR-010, US3 #3, SC-007).
- **Warmup pass itself fails**: When the explicit warmup pass raises a MIOpen/COMGR/Paddle error, the run MUST fail-fast: exit non-zero before any document is timed, with a reason of the form `warmup failed: <cause>`. No `phase_timings.warmup` is emitted; failure details are reported outside `phase_timings` (stderr and the process exit reason). The run MUST NOT silently fall back to a no-warmup run after warmup was opted in (preserving feature 015 FR-008 "no silent CPU fallback" precedent). See FR-007 and SC-011.
- **MIOpen cache exists but is invalid**: e.g., `~/.cache/miopen` populated under a different ROCm or driver version. Handling is left to MIOpen's own runtime; this feature does not detect or pre-validate cache freshness, but the documentation (US4) MUST describe how operators clear the cache when they suspect this.
- **Workstation MIOpen/COMGR workspace warnings**: Handled with a hybrid policy (FR-016): each observed warning is either suppressed by the default configuration this feature ships (with the exact env var/setting documented) or catalogued as a known runtime diagnostic with operator guidance in `research.md` and the docs deliverable. Silent suppression without documentation is NOT acceptable.
- **GPU verification deferred to a follow-up**: When workstation GPU hardware is unavailable at landing time, GPU-marked tests MAY be deferred and tracked as a follow-up issue/task without blocking the CPU-safe implementation from merging (FR-014).
- **Warmup requested for a corpus run already in progress**: Warmup is one-time-per-process and runs strictly between engine construction and the first timed document; it MUST NOT be re-triggered mid-corpus.
- **Engine reuse violated by warmup**: Warmup MUST use the already-constructed PPStructureV3 engine (preserving feature 015's "construct exactly once" guarantee). Warmup MUST NOT instantiate a second engine even if the first one's caches appear cold.

#### Out of Scope (intentional gaps surfaced by `/speckit.checklist`)

The following edge cases are **explicitly out of scope** for stage 1's narrow vendor-identity slice. They are documented here so a future failure mode is recognized as a known gap rather than a regression. Each is a follow-up candidate, not a blocker.

- **Read-only `$HOME` / `~/.cache/miopen` not writable**: Out of scope. The Assumptions section pins `$HOME/.cache/miopen` and `$HOME/.cache/comgr` as writable. If MIOpen/COMGR raise during warmup because the cache cannot be created or written, the failure surfaces as `WarmupError` with `cause_class = MIOpenError` or `UnknownError` (whichever module the underlying exception originated in) — i.e., the fail-fast contract still holds, but the pipeline does NOT detect read-only filesystems pre-emptively.
- **Disk-full / filesystem error during cache write**: Out of scope. Same disposition as read-only `$HOME` — surfaces as `WarmupError` via the underlying exception's module.
- **Two parallel processes writing the same `~/.cache/miopen`**: Out of scope. MIOpen's own internal locking may or may not be sufficient depending on ROCm version; this feature does not document or enforce a parallel-process contract. Operators running multiple warmup-enabled processes concurrently are advised to use distinct `MIOPEN_USER_DB_PATH` values per process if they observe corruption.
- **`KeyboardInterrupt` (Ctrl+C) mid-warmup**: Out of scope for explicit handling. Python's default `KeyboardInterrupt` propagation applies: the process exits with the standard SIGINT exit code (typically 130), the cache may be partially populated, and no `phase_timings.warmup` is emitted (the run did not complete). Operators clearing partially-warmed caches should `rm -rf ~/.cache/miopen ~/.cache/comgr` per the docs deliverable's clearance procedure.
- **Cache state after `WarmupError`**: Unspecified. MIOpen may have written partial kernel-database entries before the underlying exception was raised; the feature does not attempt to clean up or roll back. Operators retrying after a `WarmupError` should clear caches if the underlying cause looks cache-related (e.g., `MIOpenError` referencing kernel database corruption); this guidance lands in the docs deliverable per FR-017 / T024.
- **Per-document entry with `status: "success"` but partial `phase_timings`** (e.g., `artifact_write` missing): Out of scope as a distinct case. The runner emits `status: "success"` only when all stages including `artifact_write` complete; if `artifact_write` raises, the entry is rebuilt via `build_per_document_failure(...)` with `status: "failure"`. So this case does not occur in practice; documenting here only because the `gpu-observability.md` checklist asked.

## Requirements *(mandatory)*

### Functional Requirements

**Warmup behavior and ordering**

- **FR-001**: When the warmup opt-in is set and the active profile is `ppstructurev3@gpu`, the system MUST execute exactly one PPStructureV3 warmup inference pass after PPStructureV3 engine construction and before the first timed document's preprocessing.
- **FR-002**: GPU warmup MUST be explicit and opt-in. Default `ppstructurev3@gpu` runs (warmup opt-in absent) MUST NOT perform warmup and MUST NOT emit `phase_timings.warmup`.
- **FR-003**: The warmup pass MUST use the already-constructed PPStructureV3 engine. Warmup MUST NOT construct, replace, or rebind a second engine, preserving feature 015's FR-001 ("construct PPStructureV3 no more than once") and the single-device-per-process guard (feature 015 FR-006).
- **FR-004**: Warmup MUST run at most once per process, even when the same process processes a multi-document corpus.
- **FR-005**: The warmup pass MUST be deterministic **across runs** — every run of every process MUST use the same fixture bytes, the same page count for the fixture, and the same OCR/layout code path — so that cold-cache vs warm-cache `phase_timings.warmup` differences are attributable to MIOpen/COMGR cache state rather than warmup-input variance. The warmup fixture's page count does NOT need to match the page count of the timed documents in the active run: the warmup fixture is a fixed reference shape (per `research.md` R-016.2: page 1 of `tests/stage1_vendor_identity/inv_001_easy/source.pdf`, single-page) used to populate MIOpen kernel-selection and COMGR compilation caches; subsequent multi-page timed documents reuse those caches even though their page count differs.

**Phase timing emission**

- **FR-006**: Warmup duration MUST be measured from a monotonic clock (e.g., `time.perf_counter()`) and emitted as `phase_timings.warmup` shaped `{seconds: <float>}`, attached to the same per-document `run_summary` entry that carries the other one-time GPU phases (`paddle_import`, `gpu_bind_probe`, `engine_init`) per feature 015 FR-015 — i.e., the first per-document entry whose `status == "success"`.
- **FR-007**: Warmup time MUST NOT be folded into any per-document phase. Specifically, the first document's `phase_timings.total`, `phase_timings.rasterization`, `phase_timings.per_page_inference`, and `phase_timings.artifact_write` MUST NOT include warmup time. When the explicit warmup pass itself raises a MIOpen/COMGR/Paddle error, the process MUST exit with **exit code 15** (the warmup-failed code, immediately following feature 014's preflight 10–14 range) before any document is timed, with a stderr reason of the form `error: warmup failed: <cause-class>: <message>` (literal prefix `error: warmup failed:` is part of the contract — see `contracts/cli-contract.md` §3–§4); no `phase_timings.warmup` MUST be emitted (preserving feature 015 FR-016); all `phase_timings.*` entries MUST remain shaped `{seconds: <float>}` only — warmup-failure details MUST be reported outside `phase_timings` (stderr line + process exit code 15), mirroring feature 015's GPU-prerequisite fail-fast surface. The run MUST NOT silently fall back to a no-warmup run after warmup was opted in.
- **FR-008**: This feature MUST ship a single codebase-level `schema_version` patch bump (X.Y.Z → X.Y.(Z+1)) per feature 015 FR-014's additive-only rule. The bumped `schema_version` MUST be emitted on the `run_summary` line for *every* run of the new binary, regardless of whether warmup was opted in, performed, skipped on CPU/stub, or failed. The bumped schema MUST permit a `warmup` key under `phase_timings`; the `warmup` key MUST be absent in the emitted run_summary unless the warmup pass actually completed successfully (preserving feature 015 FR-016 "absent phases are omitted, not zeroed"). Existing `phase_timings` keys (`paddle_import`, `gpu_bind_probe`, `engine_init`, `rasterization`, `per_page_inference`, `artifact_write`, `total`) MUST NOT be renamed, removed, or have their type changed.
- **FR-009**: Legacy flat keys from feature 014 (`stages.preprocess.{total_seconds, gpu_init_seconds, gpu_inference_seconds}`) MUST NOT include warmup time. `gpu_init_seconds` continues to mean `paddle_import + gpu_bind_probe + engine_init` only; warmup is reported only via `phase_timings.warmup`. Specifically, **warmup time MUST NOT inflate `gpu_init_seconds`, `gpu_inference_seconds`, or `total_seconds`**; the legacy flat-key emission for a warmup-enabled run MUST be byte-identical to the same run without the warmup opt-in (preserving the feature 014 → feature 015 → feature 016 additive-only schema lineage).

**Profile defaults and CPU/stub isolation**

- **FR-010**: `ppstructurev3@cpu` MUST remain the default preprocessing profile. When the warmup opt-in is combined with `ppstructurev3@cpu` or any stub adapter, the system MUST: (a) emit a clear stderr warning that warmup was ignored because the active preprocess profile is not `ppstructurev3@gpu`; (b) perform no warmup pass; (c) make no MIOpen/COMGR env var mutation; (d) read or write nothing under `~/.cache/miopen` or `~/.cache/comgr`; and (e) continue the run normally and exit with the same status it would have produced without the opt-in. The system MUST NOT silently ignore the opt-in and MUST NOT reject the run.
- **FR-011**: CPU and stub adapter execution paths MUST NOT import, reference, or trigger any MIOpen/COMGR-specific code path that this feature introduces. Imports of GPU-only modules MUST be guarded so a host without Paddle GPU can run the default suite.

**CI safety and verification gating**

- **FR-012**: All tests that require Paddle GPU, ROCm, or a populated/cleared MIOpen/COMGR cache MUST be marked `@pytest.mark.gpu` so they are deselected in the default CI configuration.
- **FR-013**: The default test suite MUST pass on a host without Paddle GPU and without ROCm. CPU profile and stub adapter coverage MUST exercise the warmup opt-in's no-op path on CPU/stub.
- **FR-014**: If workstation GPU verification cannot be performed before merge, the GPU-marked tests and any other GPU-only verification steps MAY be deferred and tracked as a follow-up issue or task. Deferral MUST NOT block landing the CPU-safe implementation; the deferred items MUST be captured in the feature's tasks/quickstart so the verification cannot be quietly skipped.

**Cache and environment defaults**

- **FR-015**: `MIOPEN_FIND_MODE=2` MUST be the default fast-find mode set by this feature for warmup runs. **Operator override wins**: if the operator has already exported a different value for `MIOPEN_FIND_MODE` (or any of the four feature-shipped MIOpen env vars under FR-016 / `data-model.md` §"Default env-var configuration"), the operator's value MUST be preserved and the feature default MUST NOT clobber it. If implementation evidence in `/speckit.plan` or `research.md` measures and justifies a different default value (safer or faster), the new default and rationale MUST be documented in this feature's research artifact and quickstart, and this requirement MUST be amended to record the change before implementation.
- **FR-016**: MIOpen and COMGR workspace warnings observed during warmup MUST be handled with a hybrid policy: (a) where a safe default configuration (env vars and/or cache directory layout shipped by this feature) can suppress a warning without altering observable warmup behavior, that configuration MUST be adopted as the default this feature ships; and (b) any warnings that persist after the default configuration is applied MUST be catalogued as known runtime diagnostics with their meaning and operator guidance in this feature's documentation. Both lists — "addressed by default config" (with the exact env vars/settings used) and "residual / known diagnostic" (with meaning and operator guidance) — MUST appear in `research.md` and in the operator-facing docs referenced by US4. Silent suppression of warnings without documentation is NOT acceptable.
- **FR-017**: This feature's documentation MUST describe (a) `~/.cache/miopen` and `~/.cache/comgr` cache locations, (b) how to clear them deliberately, (c) how to confirm cold vs warm cache state from `phase_timings.warmup`, and (d) the rationale for the chosen `MIOPEN_FIND_MODE` default. **Together with FR-016** (which mandates the workspace-warning hybrid dual list — "addressed by default config" + "residual / known diagnostic" — in the same docs deliverable), FR-017 + FR-016 collectively cover all five US4 Independent Test items per SC-009: (a) cache locations, (b) how to clear, (c) cold-vs-warm reading, (d) `MIOPEN_FIND_MODE` rationale, (e) workspace-warning meaning + operator guidance (FR-016).

**Non-regression**

- **FR-018**: Committed corpus baselines (`tests/stage1_vendor_identity/*/preprocess_output.json`) MUST NOT be regenerated by this feature. The warmup opt-in's only observable effects on `preprocess_output.json` MUST be no effect: a warmup-enabled run MUST produce a `preprocess_output.json` byte-identical to the same `ppstructurev3@gpu` run without warmup.
- **FR-019**: This feature MUST NOT introduce a new persisted benchmark artifact unless `/speckit.clarify` or `/speckit.plan` produces evidence that the existing `kind: "run_summary"` stdout shape is insufficient. If a new artifact is introduced, its name, location, schema, and lifecycle MUST be specified in this feature's `data-model.md` and `research.md` and the contract set updated under `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- **FR-020**: All feature 015 guarantees MUST continue to hold under warmup-enabled runs: PPStructureV3 constructed exactly once per process, GPU readiness probed at most once per process, single-device-per-process guard enforced, no silent CPU fallback after `ppstructurev3@gpu` is selected, and `pipeline_version` continues to end in `.gpu0` for GPU runs (`.cpu0` for CPU runs).

### Key Entities

- **Warmup pass**: A single, deterministic PPStructureV3 inference invocation performed after engine construction and before the first timed document. Same input shape and code path as a real document inference. Its purpose is side-effect: populating MIOpen kernel selection caches and COMGR compilation caches so downstream document inferences hit warm caches.
- **`phase_timings.warmup` entry**: An additive `{seconds: <float>}` record inside the existing per-document `phase_timings` object on the per-document `run_summary` entry that carries the other one-time GPU phases (per feature 015 FR-015). Emitted only when warmup actually runs (per feature 015 FR-016 "absent phases are omitted, not zeroed"). Excluded from `total`, `per_page_inference`, `rasterization`, `artifact_write`.
- **MIOpen cache state**: Two on-disk directories — `~/.cache/miopen` (kernel database / find-mode tuning artifacts) and `~/.cache/comgr` (HIP/ROCm compiler cache). "Cold" means absent or empty for the active ROCm/driver/PPStructureV3 configuration; "warm" means populated by a prior compatible run. **Binding rule for production code**: cache state is detected from telemetry magnitude — high `phase_timings.warmup.seconds` (cold) vs low `phase_timings.warmup.seconds` (warm) — NOT from filesystem inspection (filesystem inspection is operator-side triage only and is the basis for the verification procedure in `quickstart.md` §1–§3, not a production-code code path).
- **Warmup opt-in**: The explicit signal a developer or operator gives to enable warmup for a given process. Mechanism resolved in `/speckit.plan` R-016.1 → CLI flag `--gpu-warmup` (canonical) with env-var fallback `LEDGERLINC_GPU_WARMUP=1` (truthiness whitelist `{"1", "true", "yes"}`, case-insensitive; CLI flag wins when both are present) — see `contracts/cli-contract.md` §1. The opt-in is explicit, off-by-default (FR-002), and orthogonal to the existing `--preprocess-profile` selector.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A warmup-enabled `ppstructurev3@gpu` preprocessing run on `inv_001_easy/source.pdf` produces a `run_summary` entry whose `phase_timings.warmup.seconds` is a positive number greater than zero, attached to the same per-document entry that carries `paddle_import`, `gpu_bind_probe`, and `engine_init`.
- **SC-002**: A `ppstructurev3@gpu` preprocessing run on the same fixture *without* the warmup opt-in produces a `run_summary` entry that contains no `warmup` key under `phase_timings` (per feature 015 FR-016).
- **SC-003**: Two consecutive warmup-enabled GPU runs on the same fixture in distinct processes — the first preceded by clearing `~/.cache/miopen` and `~/.cache/comgr`, the second with those caches left populated by the first run — produce `phase_timings.warmup.seconds` values where the cold-cache value exceeds the warm-cache value by at least 2x. The 2x threshold is a verification criterion; if real workstation measurements during `/speckit.plan` show this is too lax or too strict, the threshold MUST be tuned in this feature's research artifact before implementation.
- **SC-004**: In any warmup-enabled run, the first document's `phase_timings.total`, `phase_timings.rasterization`, `phase_timings.per_page_inference[*].seconds`, and `phase_timings.artifact_write` are each strictly less than `phase_timings.total + phase_timings.warmup` and do not include the warmup duration.
- **SC-005**: A warm corpus run (≥ 2 documents) with the warmup opt-in enabled emits `phase_timings.warmup` on exactly one per-document entry — the first successfully processed document — and on no other entry.
- **SC-006**: The default test suite passes on a host without Paddle GPU. All warmup-related GPU verification tests are skipped via `@pytest.mark.gpu` rather than failed.
- **SC-007**: A `ppstructurev3@cpu` run (default profile) with the warmup opt-in *explicitly* set in the environment produces a `run_summary` entry with no `warmup` key, performs no MIOpen/COMGR env var mutations, accesses no MIOpen/COMGR cache directories, and emits a clear stderr warning that warmup was ignored because the active preprocess profile is not `ppstructurev3@gpu`. The exit status MUST equal the status the same run would produce without the opt-in (success in normal cases). A runtime crash referencing GPU/MIOpen/COMGR, a non-zero exit attributable to the opt-in, or the absence of the stderr warning is a failure of this criterion.
- **SC-008**: A warmup-enabled GPU run produces a `preprocess_output.json` byte-identical to the same run without warmup (FR-018). Verified by running both, computing `sha256` of each, and asserting equality.
- **SC-009**: This feature's documentation, accessed from the project's stage 1 docs index, answers all five questions from US4's Independent Test (cache locations, how to clear, `MIOPEN_FIND_MODE` default and rationale, workspace-warning meaning and disposition, how to detect cold vs warm cache from `phase_timings.warmup`).

- **SC-011**: On a warmup-enabled `ppstructurev3@gpu` run where the explicit warmup pass raises a MIOpen/COMGR/Paddle error, the following forbidden states ALL hold: (a) the process exits with **exit code 15** (the warmup-failed code; non-zero); (b) stderr contains the literal prefix `error: warmup failed:` followed by the cause-class name and underlying message; (c) **no overall `run_summary` line is emitted on stdout** (a header-only run_summary with `documents_total = 0` is also forbidden — the entire stdout `kind: "run_summary"` JSON line is absent); (d) no per-document `run_summary` entry is emitted for any document that would have been timed after the failed warmup; (e) no `phase_timings.warmup` key appears in any output (because no run_summary is emitted at all); (f) no `preprocess_output.json` is written for any document that would have been timed after the failed warmup; (g) the run MUST NOT silently downgrade to a no-warmup run.

## Assumptions

- This feature builds directly on feature 015. The single-engine-construction guarantee, `phase_timings` schema, `kind: "run_summary"` stdout shape, and `@pytest.mark.gpu` test-marker convention are treated as established infrastructure, not as work to redo.
- The workstation ROCm Paddle path used for verification is the host WSL `.venv-paddle-rocm` environment with `paddlepaddle-dcu` bound to `gpu:0`, as established in features 014 and 015. CI continues to run CPU and stub paths only.
- `phase_timings.warmup` is shaped `{seconds: <float>}` to match the rest of the scalar `phase_timings` entries from feature 015. It is NOT shaped as an array, dict-of-stages, or aggregated bundle.
- The active stage 1 contract set at landing time accepts an additive `warmup` key inside `phase_timings` (per feature 015 FR-014's additive-only rule) without requiring a contract-set version bump beyond a `schema_version` patch increment.
- Cold-cache verification is performed by deleting `~/.cache/miopen` and `~/.cache/comgr` on the workstation between runs. A fresh container or fresh user account is an equivalent cold-cache setup. The 2x cold-vs-warm threshold in SC-003 remains a placeholder pending workstation measurement at landing time per `research.md` R-016.3 / FR-014; if observed numbers warrant a different threshold, SC-003 and R-016.3 are amended before merge.
- "Warmup pass content" — resolved in `/speckit.plan` R-016.2: page 1 of `tests/stage1_vendor_identity/inv_001_easy/source.pdf`, rasterized through `preprocessing.rasterize.rasterize_page(...)` at the same DPI the active preprocess profile uses (300 DPI for `ppstructurev3@gpu`). The fixture sha256 is captured in `WarmupResult` for diagnostics (`data-model.md` §WarmupResult) but does not appear in `run_summary`.
- "Warmup activation mechanism" — resolved in `/speckit.plan` R-016.1 + /speckit.clarify Q1: CLI flag `--gpu-warmup` (canonical) with env-var fallback `LEDGERLINC_GPU_WARMUP=1` (truthiness whitelist `{"1", "true", "yes"}`, case-insensitive; CLI flag wins when both are present). Off by default per FR-002, orthogonal to `--preprocess-profile`. CPU/stub disposition resolved per /speckit.clarify Q1: warn-and-proceed (FR-010, SC-007). FR-016 hybrid workspace-warning policy resolved per /speckit.clarify Q3.
- Workstation GPU verification of FR-001 / FR-002 / SC-001 / SC-003 is best-effort at landing time. If GPU hardware is unavailable, those verifications are tracked as follow-ups under FR-014 rather than blocking merge of CPU-safe code; the deferral is captured in `tasks.md` T020 / T026 / T032.
- The default warmup fixture (`tests/stage1_vendor_identity/inv_001_easy/source.pdf`, page 1) is a **hard dependency** of `preprocessing.warmup.run_warmup()` per `research.md` R-016.2 / `contracts/module-invariants.md` I-8. If the fixture is renamed, removed, or content-changed, `run_warmup` raises `WarmupError` with `cause_class = FixtureLoadError` (per `data-model.md` §WarmupError taxonomy) — the failure is loud, not silent. Future corpus refactors that rename `inv_001_easy` MUST update R-016.2's fixture path + `_DEFAULT_FIXTURE_PATH` in `preprocessing/warmup.py` + the byte-identity baseline expected by `tests/pipeline/test_warmup_engine_reuse.py`.
- The workstation home directory (`$HOME`) is writable; specifically `$HOME/.cache/miopen` and `$HOME/.cache/comgr` are creatable / writable by the process running warmup. Read-only `$HOME` and disk-full conditions are out of scope (see §Edge Cases > "Out of Scope").

## Definitions

- **Warmup pass**: A single PPStructureV3 inference invocation whose only purpose is to populate MIOpen and COMGR caches with the kernels/binaries that subsequent document inferences will use. Counts as "one warmup pass" per FR-001 / FR-004 regardless of how many internal kernels it triggers; a "pass" is one `predict(...)` call (or equivalent), not one kernel.
- **Cold cache / warm cache**: The on-disk state of `~/.cache/miopen` and `~/.cache/comgr` at the moment the warmup pass starts. "Cold" = both directories absent or empty for the active ROCm + driver + PPStructureV3 configuration. "Warm" = both directories populated by a prior run with a compatible configuration. **Production code MUST detect cache state from `phase_timings.warmup.seconds` magnitude only** (per SC-003). Filesystem inspection of these directories is operator-side triage only — used by the verification procedure in `quickstart.md` §1–§3 and by ad-hoc operator triage; production-code paths MUST NOT inspect filesystem state to decide behavior.
- **Warmup opt-in**: The explicit, off-by-default signal that enables warmup for a given process. User-facing surface resolved per `/speckit.plan` R-016.1: CLI flag `--gpu-warmup` (canonical) and env-var fallback `LEDGERLINC_GPU_WARMUP=1` (truthiness whitelist `{"1", "true", "yes"}`, case-insensitive; CLI wins when both are present). See `contracts/cli-contract.md` §1 for the activation truth table.
- **`phase_timings.warmup`**: The additive `{seconds: <float>}` entry under `phase_timings` in the per-document `run_summary` line, attached to the first successfully processed document per feature 015 FR-015. Omitted entirely when warmup did not run (feature 015 FR-016).
- **Construct PPStructureV3 / construction count**: Same definition as feature 015 — an invocation of the `paddleocr.PPStructureV3(...)` constructor. Warmup MUST NOT increment this count (FR-003 / FR-020).
