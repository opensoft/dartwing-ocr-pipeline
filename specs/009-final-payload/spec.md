# Feature Specification: Final Structured Payload Assembly (Stage 1 Vendor-Identity)

**Feature Branch**: `009-final-payload`
**Created**: 2026-04-21
**Status**: Draft
**Input**: User description: "Final structured payload assembly. Call this 009-final-payload. Read one document's edge_extraction_output.json (005) AND routing_decision.json (008) from the same per-document folder, and emit final_structured_payload.json conforming to the frozen v1.0.0 contract. Flattens {value, confidence, evidence} into {value, confidence} (no evidence in the downstream payload), copies review_status verbatim from routing (including the canonical review_reason string), emits a quality_summary roll-up, and populates the trace block with relative paths to the three upstream artifacts. Artifact-to-artifact, deterministic, no model calls."

## Clarifications

### Session 2026-04-21

- Q: How should the assembler surface an upstream contract violation where routing's `decision == "edge_accept"` but `review_status.manual_review_required == true` (FR-016)? → A: Hard failure — exit non-zero, write no `final_structured_payload.json`, error names the contradiction. The schema has no in-artifact warnings slot, so a "soft" defensive propagation would hide the violation from downstream consumers; treating it as a cross-input invariant is consistent with the other hard-fail rules in US6/FR-003–FR-005.
- Q: How should the assembler's policy version (pinning for the `overall_vendor_confidence` formula and `secondary_identifiers_found` ordering per FR-019/SC-008) be represented, given the frozen v1.0.0 schema has no `policy_version` slot? → A: Encode it inside `pipeline_version` as `"009-final-payload@<semver>"` (e.g., `"009-final-payload@0.1.0"`). Bumping the formula or ordering bumps the semver. No contract amendment needed; downstream consumers can parse the string to discriminate policy generations.
- Q: What exact ordering must `quality_summary.secondary_identifiers_found` follow (FR-020 currently says `"e.g., schema enum order"`)? → A: Pin exactly to the schema enum's declared order: `["address", "ein", "state_tax_id", "vat_id", "other_tax_id", "website", "phone", "email"]`. Keeps ordering tied to the frozen v1.0.0 contract, machine-checkable, and removes the evaluator/assembler-drift risk left by the `e.g.` hedge.
- Q: What exact CLI subcommand should the assembler expose (FR-026)? → A: `python -m dartwing_ocr.assembler` with module path `src/dartwing_ocr/assembler/`. Matches the in-spec term "assembler", parallels the existing `dartwing_ocr.validator` precedent (001/002), and gives downstream orchestration (the 007 evaluator, harness scripts) a stable entry point to depend on.
- Q: Should the `quality_summary.overall_vendor_confidence` formula be pinned in the spec, or deferred to the plan (per Assumption 4)? → A: Pin it in the spec as the stage 1 starter formula (policy `0.1.0`): `overall_vendor_confidence = clip(0.5 * company_name.confidence + 0.5 * mean(secondary_identifier_confidences, default 0.0 when no secondaries), 0.0, 1.0)`. The secondary set is exactly the confidences of the fields named in `secondary_identifiers_found` (address uses the mean of `city`, `state`, `postal_code` confidences; tax-ids/website/phone/email use their own confidence). Any future tuning of weights, aggregation shape, or secondary derivation bumps the `<semver>` segment of `pipeline_version` per FR-007. Gives the 007 evaluator and reviewers a concrete, testable semantic at stage 1; reduces cleanly to 0.0 on the all-null spam-gate case (US4 AS-6).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Emit A Schema-Valid `final_structured_payload.json` For One Document (Priority: P1)

A pipeline developer (or downstream accounting/CRM integration) has a per-document folder containing a valid `edge_extraction_output.json` (from 005) and `routing_decision.json` (from 008). They need a single deterministic command to read both artifacts, assemble the clean downstream payload, and write `final_structured_payload.json` into the same folder. Every downstream consumer — the evaluator (007), any future accounting/CRM handoff, any future human-facing viewer — reads this artifact, so it must be schema-valid and self-sufficient.

**Why this priority**: Without a schema-valid final payload, the evaluator has no real pipeline output to score, the end-to-end one-document run is incomplete, and the pipeline cannot be demonstrated as usable. This is the last critical-path slice before the stage 1 pipeline is runnable end to end.

**Independent Test**: Stage a per-document folder with a schema-valid `edge_extraction_output.json` fixture AND a schema-valid `routing_decision.json` fixture referencing the same `document_id`. Run the assembler against that folder. Verify `final_structured_payload.json` is written next to the inputs, validates against `contracts/stage1_vendor_identity/v1.0.0/final_structured_payload.schema.json`, reports `contract_set_version == "1.0.0"`, carries the same `document_id` as both inputs, sets `document_type == "invoice"`, populates `vendor_candidate`, `review_status`, `quality_summary`, and `trace` per the schema, and writes no other files. Two invocations against the same pair of inputs produce byte-identical outputs except for `processed_at`.

**Acceptance Scenarios**:

1. **Given** a per-document folder containing a valid `edge_extraction_output.json` and a valid `routing_decision.json` referencing the same `document_id`, **When** the assembler runs against that folder, **Then** `final_structured_payload.json` is written next to the inputs and validates against the frozen v1.0.0 schema.
2. **Given** the assembler writes the artifact, **When** its contents are inspected, **Then** `document_id` equals the one in both inputs, `contract_set_version == "1.0.0"`, `processed_at` is a valid ISO-8601 date-time in UTC, `pipeline_version` is a non-empty build identifier for the assembler itself (not copied from an input), and `document_type == "invoice"` (the v1.0.0 enum allows no other value).
3. **Given** the assembler runs successfully, **When** its output is inspected, **Then** every required top-level key (`contract_set_version`, `pipeline_version`, `document_id`, `processed_at`, `document_type`, `vendor_candidate`, `review_status`, `quality_summary`, `trace`) is present and non-empty. No optional key is silently omitted.
4. **Given** the same input pair is assembled twice with no configuration change, **When** the two outputs are compared, **Then** every field except `processed_at` is byte-identical: the flattened vendor_candidate values and confidences, the review_status block, the quality_summary, and the trace block are all deterministic.
5. **Given** the assembler runs in a per-document folder, **When** the run completes, **Then** it writes nothing outside the target folder, does not modify either input, and does not create or overwrite any of the other reserved filenames (`preprocess_output.json`, `evaluation_document.json`, `consensus_output.json`, or anything inside `votes/`).
6. **Given** the assembler runs successfully, **When** downstream consumers (the evaluator, any CRM integration) read `final_structured_payload.json`, **Then** every routing-relevant, vendor-identity-relevant, and provenance-relevant piece of information they need is present in the payload — they never need to re-open `edge_extraction_output.json` or `routing_decision.json` for routine reads.

### User Story 2 - Flatten Evidence While Preserving Provenance And Confidence (Priority: P1)

The extractor's output carries `{value, confidence, evidence}` per scalar field because evidence-first design is a stage 1 non-negotiable for the extractor. The final payload is the *downstream handoff*: evidence pointers back into `preprocess_output.json` are not useful to an accounting system, a CRM, or an evaluator — they are an internal diagnostic. The assembler must strip evidence arrays out while preserving `value`, `confidence`, `company_name.present`, and `company_name.inferred` exactly. Consumers learn *what* the pipeline extracted and *how confident it was*, but do not re-reason about where the model grounded its claims.

**Why this priority**: If evidence leaks into the final payload, downstream systems become entangled with the Trijunction evidence packet and any future contract change to evidence IDs breaks those consumers. Conversely, if confidence or provenance (present/inferred) is dropped, the evaluator cannot distinguish grounded vs inferred cases, which violates the constitution's Principle IV on provenance and review safety. The flattening must preserve the right things and strip the right things — no improvisation.

**Independent Test**: Run the assembler against a fixture whose `edge_extraction_output.json` has populated `{value, confidence, evidence}` blocks for several fields (company_name with present/inferred flags set, two populated address components, one tax ID, website, email) and null blocks for everything else. Verify that in the output: every present field has `value` and `confidence` copied exactly from the input; `company_name.present` and `.inferred` are copied exactly (not recomputed); no `evidence` key appears anywhere in `final_structured_payload.json`; null fields are retained as `{value: null, confidence: <number>}` per schema. Validate the output against the frozen v1.0.0 schema.

**Acceptance Scenarios**:

1. **Given** a populated scalar field in `edge_extraction_output.json` (e.g., `vendor_candidate.address.city = {value: "Oakland", confidence: 0.82, evidence: ["p1_b7", "p1_l14"]}`), **When** the assembler writes that field in `final_structured_payload.json`, **Then** it emits `{value: "Oakland", confidence: 0.82}` — value and confidence copied exactly, evidence key absent.
2. **Given** a null scalar field in `edge_extraction_output.json` (e.g., `tax_ids.vat_id = {value: null, confidence: 0.0, evidence: []}`), **When** the assembler writes that field, **Then** it emits `{value: null, confidence: 0.0}` — the null survives, the evidence array does not.
3. **Given** the extractor's `company_name` block carries `{value: "Acme Widgets Inc.", present: true, inferred: false, confidence: 0.94, evidence: [...]}`, **When** the assembler writes `company_name` in the final payload, **Then** it emits `{value: "Acme Widgets Inc.", present: true, inferred: false, confidence: 0.94}` — the four non-evidence keys are copied exactly; `present` and `inferred` are never recomputed by this layer.
4. **Given** the extractor's `invoice_header_fields` block (with `invoice_number`, `invoice_date`, `total_amount` including a currency), **When** the assembler writes the final payload, **Then** `invoice_header_fields` is NOT included in the output — it is not a `vendor_candidate` component and the v1.0.0 `final_structured_payload.schema.json` does not accept it. Invoice header data is preserved for downstream work in `edge_extraction_output.json` via the `trace` block, not re-emitted in the final payload.
5. **Given** any output the assembler writes, **When** a reader inspects it for `evidence` keys at any nesting depth, **Then** none are found. Evidence has been fully flattened out.
6. **Given** the extractor reports a reconciled `company_name.present == false` AND `company_name.inferred == true` (the missing-name provenance rule from 005 FR-012/FR-013), **When** the assembler writes the final payload, **Then** both booleans are propagated exactly as emitted by the extractor. The assembler does not second-guess provenance.

### User Story 3 - Review Status Propagates Verbatim From Routing (Priority: P2)

A downstream consumer reading `final_structured_payload.json:review_status` must see exactly what routing decided — including the canonical review_reason string `"company_name_inferred"` when the document went to review for missing/inferred name. This is the signal that tells every consumer (the evaluator's `review_routing_passed` gate, any future accounting system, any future human reviewer queue) whether the document is safe to accept. The assembler does not re-derive review status from the extractor's output; it copies routing's decision verbatim.

**Why this priority**: The canonical string `"company_name_inferred"` is load-bearing across the pipeline: 005's reconciliation sets `company_name.inferred`, 008 emits `review_reason = "company_name_inferred"`, 007-evaluator's US4 matches on the exact string. If the assembler re-derives, paraphrases, or drops this string, the evaluator's missing-name gate fails and the stage 1 quality claim collapses on the missing-name corpus subset. The safest behavior is verbatim copy with no transformation.

**Independent Test**: Run the assembler against three fixtures. Fixture A: `routing_decision.json` with `review_status = {manual_review_required: true, review_reason: "company_name_inferred"}`. Fixture B: routing with `{manual_review_required: true, review_reason: "secondary_identifiers_insufficient"}`. Fixture C: routing with `{manual_review_required: false, review_reason: null}`. Verify that in each case, `final_structured_payload.json:review_status` is byte-identical to `routing_decision.json:review_status` — both fields copied exactly, no transformation.

**Acceptance Scenarios**:

1. **Given** `routing_decision.json:review_status.manual_review_required == true` and `routing_decision.json:review_status.review_reason == "company_name_inferred"`, **When** the assembler writes the final payload, **Then** `final_structured_payload.json:review_status.manual_review_required == true` and `review_reason == "company_name_inferred"` — exact-string match, no normalization, no aliasing.
2. **Given** `routing_decision.json:review_status.manual_review_required == false` and `review_reason == null`, **When** the assembler writes the final payload, **Then** `final_structured_payload.json:review_status` is `{manual_review_required: false, review_reason: null}` — null survives, no default string substituted.
3. **Given** routing's canonical reason string is one of the stage 1 policy values (`"company_name_inferred"`, `"post_extraction_spam_gate_failed"`, `"secondary_identifiers_insufficient"`, `"upstream_extraction_failed"`), **When** the assembler writes the final payload, **Then** the string is propagated verbatim. The assembler does not have its own vocabulary for `review_reason` and does not rewrite values it doesn't recognize.
4. **Given** routing's `decision` was `"edge_accept"`, **When** the assembler writes the final payload, **Then** `review_status.manual_review_required == false` AND `review_reason == null` — consistent with the accept decision. This is verified, not re-derived: the two inputs are expected to agree, and the assembler propagates the agreed value.
5. **Given** routing's `decision` and `review_status` are inconsistent (e.g., `decision == "edge_accept"` but `manual_review_required == true`), **When** the assembler runs, **Then** the assembler treats it as a hard upstream contract violation: no `final_structured_payload.json` is written, the assembler exits non-zero, and the error names both `decision` and the conflicting `review_status` fields. The assembler never silently accepts, rewrites, or defensively propagates contradictory routing output, because the frozen v1.0.0 schema has no channel for surfacing the violation to downstream consumers.

### User Story 4 - Quality Summary Is Computed Deterministically From Inputs (Priority: P2)

A downstream consumer (evaluator, CRM integration, future dashboard) reads `quality_summary` to quickly understand *how good* a vendor-identity extraction was, without having to open the extractor's or routing's outputs. The summary has four fields — `overall_vendor_confidence`, `explicit_name_found`, `consensus_level`, `secondary_identifiers_found` — each derived by deterministic code from the two inputs. This feature pins how each field is derived so the summary means the same thing on every document.

**Why this priority**: Without a deterministic quality summary, downstream consumers either re-compute their own roll-up (leaking internal knowledge) or rely on inconsistent signals across documents. Pinning the derivation here is what makes `quality_summary` a portable signal.

**Independent Test**: Run the assembler against a fixture with known-good inputs where company_name is grounded explicit, address has city+state+postal grounded, one tax_id is grounded, email is grounded. Verify: `quality_summary.overall_vendor_confidence` is in `[0.0, 1.0]` and computed deterministically per the pinned formula (re-running the assembler against the same inputs reproduces the same value exactly); `explicit_name_found == true`; `consensus_level == "single_voter_baseline"`; `secondary_identifiers_found` contains exactly `"address"`, the relevant tax-ID string, and `"email"`, emitted in the schema enum's declared order `["address", "ein", "state_tax_id", "vat_id", "other_tax_id", "website", "phone", "email"]` (absent identifiers skipped).

**Acceptance Scenarios**:

1. **Given** any assembled payload, **When** `quality_summary.consensus_level` is inspected, **Then** it is exactly `"single_voter_baseline"` in stage 1. No other value appears until a future amendment enables multi-voter consensus.
2. **Given** the extractor's `company_name.present == true` AND `company_name.inferred == false`, **When** the assembler runs, **Then** `quality_summary.explicit_name_found == true`. Given either `present == false` OR `inferred == true`, `explicit_name_found == false`. The boolean is a direct function of the two extractor flags; no evidence inspection needed.
3. **Given** a populated payload, **When** `quality_summary.overall_vendor_confidence` is inspected, **Then** it is a number in `[0.0, 1.0]`, derived deterministically from the input confidences and structural grounding. The exact formula is pinned in the policy version (bumping the formula requires a policy bump), and the value is reproducible across runs given the same inputs.
4. **Given** a populated payload, **When** `quality_summary.secondary_identifiers_found` is inspected, **Then** it is an array of strings drawn from the frozen enum `{"address", "ein", "state_tax_id", "vat_id", "other_tax_id", "website", "phone", "email"}`, contains `"address"` iff the extractor's address has `city`, `state`, AND `postal_code` all non-null with non-empty evidence (matching routing's `address_has_minimum_components` rule from 008 FR-010), contains each tax-ID string iff the corresponding tax-ID slot has a non-null value AND non-empty evidence, and contains `"website"`, `"phone"`, or `"email"` iff each respective field has a non-null value AND non-empty evidence. No other strings appear.
5. **Given** a populated payload, **When** `secondary_identifiers_found` is compared across two assembler runs on the same input pair, **Then** the array is byte-identical — same items, same order. Ordering matches the schema enum's declared order exactly (`["address", "ein", "state_tax_id", "vat_id", "other_tax_id", "website", "phone", "email"]`); absent identifiers are skipped, included identifiers appear in that order.
6. **Given** a payload for an all-null extraction (the 008 spam-gate case), **When** `quality_summary` is inspected, **Then** `overall_vendor_confidence == 0.0`, `explicit_name_found == false`, `consensus_level == "single_voter_baseline"`, and `secondary_identifiers_found == []` (empty array, not omitted).

### User Story 5 - Trace Block References The Three Upstream Artifacts (Priority: P3)

A developer debugging a downstream consumer's behavior against a specific `final_structured_payload.json` needs to quickly locate the upstream artifacts that produced it: the source PDF, the preprocessing output, the extraction output, and the routing decision. The `trace` block names each by a relative path anchored at the per-document folder, so any consumer with access to the folder can open them directly without guesswork.

**Why this priority**: Cheap to do, invaluable when debugging. Without the trace block, a reviewer who picks up a suspect `final_structured_payload.json` has no direct link back to the evidence that produced it. With it, diagnostic investigation is a two-click path.

**Independent Test**: Run the assembler against a per-document folder with the standard four files (`source.pdf`, `preprocess_output.json`, `edge_extraction_output.json`, `routing_decision.json`). Verify `trace` in the output contains: `source_file == "source.pdf"`, `preprocess_output_file == "preprocess_output.json"`, `edge_extraction_output_file == "edge_extraction_output.json"`, `routing_decision_file == "routing_decision.json"`. All four relative paths resolve to existing files when opened from the per-document folder.

**Acceptance Scenarios**:

1. **Given** a per-document folder containing the standard upstream artifacts, **When** the assembler writes `final_structured_payload.json`, **Then** `trace.source_file` is a relative path that resolves to the document's PDF from the per-document folder.
2. **Given** the same folder, **When** `trace` is inspected, **Then** `trace.preprocess_output_file`, `trace.edge_extraction_output_file`, and `trace.routing_decision_file` each resolve to existing files in the per-document folder.
3. **Given** any assembled payload, **When** `trace` is inspected, **Then** every string in `trace` is a relative path (not absolute), so the payload remains portable if the folder is moved or shared across environments.
4. **Given** a per-document folder that is missing one of the upstream artifacts at assembly time (should never happen if 003/005/008 ran cleanly, but could happen if a file was deleted mid-run), **When** the assembler runs, **Then** it fails hard per the US6 rules — no partial payload with a broken trace reference is ever written.
5. **Given** any assembled payload, **When** `trace` is compared against the actual filesystem of the per-document folder, **Then** every file named in `trace` exists. The assembler writes no reference to a file that is not actually there.

### User Story 6 - Hard Failures On Contract Drift, Document Mismatch, And Missing Inputs (Priority: P3)

The assembler must refuse to produce a payload when the two inputs do not agree on `document_id`, when either input reports `contract_set_version != "1.0.0"`, when either input is missing or unreadable, or when either input fails its own schema validation. In those cases, no `final_structured_payload.json` is written, the assembler exits non-zero, and the error message names the specific failure cause.

**Why this priority**: A final payload with a wrong `document_id`, cross-contaminated fields, or stale schema assumptions is worse than no payload at all — it will silently poison every downstream consumer. Loud failures surface the bug immediately; silent defaults propagate it.

**Independent Test**: Run the assembler against six failure fixtures: (a) `edge_extraction_output.json` missing; (b) `routing_decision.json` missing; (c) both present but `document_id` in extractor output doesn't match `document_id` in routing output; (d) one input reports `contract_set_version == "1.1.0"` (not the frozen value); (e) one input is present but fails its own schema validation; (f) `routing_decision.json:decision == "edge_accept"` but `routing_decision.json:review_status.manual_review_required == true` (FR-016 contradiction). In all six cases verify: no `final_structured_payload.json` is written, the assembler exits non-zero, and the error message names the specific failure cause.

**Acceptance Scenarios**:

1. **Given** `edge_extraction_output.json` is missing from the per-document folder, **When** the assembler runs, **Then** no `final_structured_payload.json` is written, the assembler exits non-zero, and a human-readable error names the missing file.
2. **Given** `routing_decision.json` is missing from the per-document folder, **When** the assembler runs, **Then** no output is written, the assembler exits non-zero, and the error names the missing file.
3. **Given** both inputs are present but `edge_extraction_output.json:document_id == "inv_005"` while `routing_decision.json:document_id == "inv_006"`, **When** the assembler runs, **Then** no output is written, the assembler exits non-zero, and the error names both document_ids and the mismatch.
4. **Given** one input reports `contract_set_version == "1.1.0"` (drifted from the frozen `1.0.0`), **When** the assembler runs, **Then** no output is written, the assembler exits non-zero, and the error names the drifting file and its contract_set_version.
5. **Given** one input is present but fails its own schema validation (e.g., an extra key, a missing required field), **When** the assembler runs, **Then** no output is written, the assembler exits non-zero, and the error names the failing file and a short validation diagnostic.
6. **Given** any upstream-status propagation: both inputs validate AND their `document_id`s match AND their `contract_set_version`s are `"1.0.0"`, but one input reports its own `status == "failure"`, **When** the assembler runs, **Then** it still produces a valid `final_structured_payload.json` (the upstream failure is surfaced in routing's `review_status` and was already a review_required gate; the assembler does not itself treat upstream `status == "failure"` as a hard error because the pipeline has already handled it). This clarifies that `status` fields flow through the logic of each stage, while `contract_set_version` drift and `document_id` mismatch are cross-input invariants the assembler enforces.

### Edge Cases

- **Extractor evidence is empty for a field but `value` is non-null**: This is the 005 FR-011 case (ungrounded value retained with capped confidence). The assembler flattens to `{value, confidence}` as usual; the capped confidence is preserved verbatim. The assembler does not re-apply the cap.
- **Routing `decision == "edge_accept"` and extractor has strong identity but empty `review_reason`**: Expected and valid. `review_status == {manual_review_required: false, review_reason: null}` propagates verbatim.
- **Routing emits a `review_reason` string the assembler has never seen before**: The assembler propagates verbatim. It does not maintain its own canonical-reason list; routing owns that vocabulary.
- **Extractor reports `invoice_header_fields` (invoice_number, invoice_date, total_amount with currency)**: Not emitted in the final payload. The v1.0.0 `final_structured_payload.schema.json` has no slot for invoice header fields; they remain discoverable via the `trace` block's reference to `edge_extraction_output.json`.
- **Extractor reports `document_type.value == "invoice"` with low confidence**: The final payload's `document_type` is a bare string enum `["invoice"]`; confidence is not representable. The extractor's document_type.confidence is dropped. (Future amendments could add a document-type confidence to the final payload if needed; for stage 1 it is scope-out.)
- **The per-document folder already contains a prior `final_structured_payload.json`**: The new assembly overwrites it. The assembler does not version or timestamp-name its output file; git history is the audit trail.
- **`source.pdf` is missing from the folder but the three JSON artifacts are present**: The trace block's `source_file` names `"source.pdf"` anyway (it's a logical reference to where the PDF should be). The assembler does not independently verify `source.pdf` exists — that's the test harness's concern per 006-corpus-labeling. If downstream consumers need PDF access, they see the missing file themselves.
- **Two assembler runs against the same inputs, but `pipeline_version` is bumped between them** (e.g., a new assembler build): `pipeline_version` differs in the two outputs. That is allowed; it's the identifier of the assembler build. Everything else is still byte-identical.
- **One input reports its own `status == "partial"`**: Assembler still produces the final payload. Upstream partiality is surfaced in `routing_decision.json`'s `status` and `reasons` fields (visible via trace) and, when relevant, in `review_status` from routing. The assembler does not itself recompute an aggregate status.
- **Extractor reports `vote_metadata.consensus_mode != "single_voter_baseline"`**: Should not happen in stage 1 (extractor's schema enum only allows that value), but if it did, the assembler would propagate that signal only through routing — the final payload's `consensus_level` is pinned to `"single_voter_baseline"` by its own schema enum, and the assembler emits only that value.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The assembler MUST accept one per-document folder as input, read that folder's `edge_extraction_output.json` and `routing_decision.json`, and write `final_structured_payload.json` into the same folder.
- **FR-002**: Every `final_structured_payload.json` the assembler writes MUST validate against `contracts/stage1_vendor_identity/v1.0.0/final_structured_payload.schema.json` and MUST set `contract_set_version` to `"1.0.0"`.
- **FR-003**: The assembler MUST refuse to run when either `edge_extraction_output.json` or `routing_decision.json` has any of the following defects. In all cases it exits non-zero with a human-readable error and writes no output. The three kinds are distinguished so downstream orchestrators and tests can target each precisely:
  - **FR-003a (missing input)**: either file is absent from the per-document folder. The error names the missing filename.
  - **FR-003b (unreadable input)**: either file is present but cannot be opened or JSON-parsed. The error names the file and a short parse diagnostic.
  - **FR-003c (schema-invalid input)**: either file parses but fails its own v1.0.0 schema. The error names the file and a short schema-validation diagnostic.
- **FR-004**: The assembler MUST refuse to run when either input reports `contract_set_version != "1.0.0"`. It exits non-zero, names the drifting file, and writes no output.
- **FR-005**: The assembler MUST refuse to run when the two inputs disagree on `document_id`. It exits non-zero, names both `document_id` values, and writes no output.
- **FR-006**: `document_id` in the output MUST equal `document_id` in both inputs (already guaranteed to agree by FR-005).
- **FR-007**: `pipeline_version` MUST identify the assembler build AND the assembler's policy generation, using the structured format `"009-final-payload@<semver>"` (e.g., `"009-final-payload@0.1.0"`). The feature-branch prefix (`"009-final-payload"`) is fixed; the `<semver>` segment bumps whenever the `overall_vendor_confidence` formula or the `secondary_identifiers_found` ordering changes (cf. FR-019, FR-020, SC-008). It is a fresh string generated by this feature; it is NOT copied from either input's `pipeline_version` field (which identifies the upstream stage). `processed_at` MUST be a fresh ISO-8601 UTC date-time reflecting when the assembly ran.
- **FR-008**: `document_type` MUST be the bare string `"invoice"` (the only v1.0.0 enum value). Stage 1 does not classify non-invoice documents.
- **FR-009**: `vendor_candidate.company_name` MUST copy `value`, `present`, `inferred`, and `confidence` verbatim from `edge_extraction_output.json:vendor_candidate.company_name`. The `evidence` key MUST NOT appear in the output.
- **FR-010**: `vendor_candidate.address` MUST copy `value` and `confidence` for each of `street_1`, `street_2`, `city`, `state`, `postal_code`, `country` verbatim from the extractor's `vendor_candidate.address`. The `evidence` key MUST NOT appear in any sub-field of the output.
- **FR-011**: `vendor_candidate.tax_ids` MUST copy `value` and `confidence` for each of `ein`, `state_tax_id`, `vat_id`, `other_tax_id` verbatim from the extractor's `vendor_candidate.tax_ids`. The `evidence` key MUST NOT appear in any sub-field of the output.
- **FR-012**: `vendor_candidate.website`, `vendor_candidate.phone`, and `vendor_candidate.email` MUST each copy `value` and `confidence` verbatim from the extractor's corresponding fields. The `evidence` key MUST NOT appear in the output.
- **FR-013**: The assembler MUST NOT include `invoice_header_fields` (invoice_number, invoice_date, total_amount) in the output. The v1.0.0 `final_structured_payload.schema.json` has no slot for them; invoice header data is preserved via the `trace` block's reference to `edge_extraction_output.json`.
- **FR-014**: The assembler MUST NOT emit any `evidence` key anywhere in the output at any nesting depth. Evidence is an extractor-internal concern and is fully flattened out of the downstream handoff.
- **FR-015**: `review_status.manual_review_required` and `review_status.review_reason` MUST be copied verbatim from `routing_decision.json:review_status`. The assembler does not re-derive, normalize, rewrite, or substitute defaults for these values. In particular, the canonical string `"company_name_inferred"` (from 008 FR-008) MUST propagate exact-string.
- **FR-016**: If routing's `decision` and `review_status` are inconsistent (e.g., `decision == "edge_accept"` but `manual_review_required == true`, or any other mismatch between the decision and the review flags), the assembler MUST treat it as a hard upstream contract violation: exit non-zero, write no `final_structured_payload.json`, and emit a human-readable error that names both `routing_decision.json:decision` and the conflicting `review_status` fields. The frozen v1.0.0 schema has no in-artifact channel for surfacing a contradiction, and silently accepting or defensively rewriting a broken routing signal would hide the violation from every downstream consumer; therefore contradictory routing joins FR-003/FR-004/FR-005 as a cross-input invariant that blocks assembly.
- **FR-017**: `quality_summary.consensus_level` MUST be `"single_voter_baseline"` in stage 1. No other value appears until a future amendment enables multi-voter consensus.
- **FR-018**: `quality_summary.explicit_name_found` MUST be `true` iff the extractor's `company_name.present == true` AND `company_name.inferred == false`; otherwise `false`. This boolean is a direct function of two extractor flags and is not re-derived from evidence.
- **FR-019**: `quality_summary.overall_vendor_confidence` MUST be a number in `[0.0, 1.0]` derived deterministically from the two inputs by the stage 1 starter formula (policy `0.1.0`): `overall_vendor_confidence = clip(0.5 * company_name.confidence + 0.5 * mean(secondary_identifier_confidences, default 0.0 when no secondaries), 0.0, 1.0)`. The secondary confidence set is drawn exactly from the fields named in `quality_summary.secondary_identifiers_found` (FR-020): `"address"` contributes the mean of the extractor's `address.city.confidence`, `address.state.confidence`, and `address.postal_code.confidence`; each present tax-ID string contributes its own `tax_ids.<slot>.confidence`; `"website"`, `"phone"`, and `"email"` contribute their respective top-level confidences. When `secondary_identifiers_found` is empty, the secondary term defaults to 0.0 (not dropped). When `company_name` is null/missing, `company_name.confidence` is used as-is from the extractor (stage 1 schema guarantees it exists). Given the same inputs and the same policy version, two assembler runs MUST produce the same value exactly. Any change to this formula — weights, aggregation shape, secondary derivation, or clipping behavior — requires a bump of the `<semver>` segment of `pipeline_version` per FR-007 and SC-008; the formula above is policy `0.1.0`.
- **FR-020**: `quality_summary.secondary_identifiers_found` MUST be an array of strings drawn from the frozen enum `{"address", "ein", "state_tax_id", "vat_id", "other_tax_id", "website", "phone", "email"}`, containing `"address"` iff the extractor's address has `city`, `state`, AND `postal_code` all non-null with non-empty evidence (matching 008 FR-010's `address_has_minimum_components` rule); containing each tax-ID string iff the corresponding tax-ID slot has a non-null value AND non-empty evidence; and containing `"website"`, `"phone"`, or `"email"` iff each respective field has a non-null value AND non-empty evidence. The ordering MUST match the schema enum's declared order exactly: `["address", "ein", "state_tax_id", "vat_id", "other_tax_id", "website", "phone", "email"]` — included identifiers appear in that order, absent identifiers are skipped. No other ordering is permitted.
- **FR-021**: `trace.source_file`, `trace.preprocess_output_file`, `trace.edge_extraction_output_file`, and `trace.routing_decision_file` MUST be relative paths (not absolute) anchored at the per-document folder. In stage 1 they are `"source.pdf"`, `"preprocess_output.json"`, `"edge_extraction_output.json"`, and `"routing_decision.json"` respectively.
- **FR-022**: Given identical inputs and identical assembler build, the assembler MUST produce byte-identical `final_structured_payload.json` outputs except for `processed_at`. All vendor_candidate values, confidences, review_status, quality_summary, and trace fields MUST be deterministic.
- **FR-023**: The assembler MUST NOT call any model, perform OCR, re-read `preprocess_output.json` for content, or re-run routing logic. It consumes exactly two JSON files (`edge_extraction_output.json`, `routing_decision.json`) and emits exactly one JSON file (`final_structured_payload.json`). The trace block references `preprocess_output.json` but does not read it.
- **FR-024**: The assembler MUST NOT modify `edge_extraction_output.json`, `routing_decision.json`, `preprocess_output.json`, `expected.json`, `notes.md`, `source.pdf`, or any other file it did not create. Inputs are read-only.
- **FR-025**: The assembler MUST NOT implement or invoke evaluation, consensus logic, ensemble reconciliation, line-item extraction, cloud escalation, or multi-document orchestration. It is a pure assembly stage; the evaluator (007) consumes its output.
- **FR-026**: The assembler MUST be invokable as `python -m dartwing_ocr.assembler` with its implementation under `src/dartwing_ocr/assembler/`, in a one-document mode that takes a per-document folder path as input (e.g., `python -m dartwing_ocr.assembler --document-folder tests/stage1_vendor_identity/inv_017_medium/`). This parallels the existing `python -m dartwing_ocr.validator` pattern (001/002) and gives downstream orchestration (the 007 evaluator, harness scripts) a stable entry point. The exact flag names are pinned in `contracts/cli-contract.md` (`--document-folder` is required; `--pipeline-version` is an optional test-only override); the module name and one-folder-per-invocation contract are pinned here.

### Key Entities

- **Per-document folder**: One corpus document's on-disk home. Holds `source.pdf`, `expected.json`, optional `notes.md`, `preprocess_output.json` (003), `edge_extraction_output.json` (005), `routing_decision.json` (008), and `final_structured_payload.json` (output of this feature).
- **Extraction artifact (`edge_extraction_output.json`)**: The v1.0.0 input #1. Read-only. Supplies `vendor_candidate` (with per-field value/confidence/evidence and company_name present/inferred) plus `status` / `warnings`. Its `invoice_header_fields` block is intentionally not propagated to the final payload in stage 1.
- **Routing artifact (`routing_decision.json`)**: The v1.0.0 input #2. Read-only. Supplies `review_status` (manual_review_required + canonical review_reason) and `consensus_summary` (single_voter_baseline in stage 1). The assembler copies `review_status` verbatim.
- **Final payload artifact (`final_structured_payload.json`)**: The v1.0.0 output. Conforms to `final_structured_payload.schema.json`. Keys: `contract_set_version`, `pipeline_version`, `document_id`, `processed_at`, `document_type`, `vendor_candidate` (flattened — no evidence), `review_status` (verbatim from routing), `quality_summary` (derived), `trace` (relative paths to upstreams).
- **Flattened vendor candidate**: The final payload's `vendor_candidate` shape. Each scalar field has `{value, confidence}` (no evidence). `company_name` additionally has `present` and `inferred` booleans propagated verbatim from the extractor. Address, tax_ids, website, phone, email follow the same `{value, confidence}` pattern.
- **Quality summary**: Four-field roll-up (`overall_vendor_confidence`, `explicit_name_found`, `consensus_level`, `secondary_identifiers_found`) derived deterministically from the two inputs. Pinned by the assembler's policy version.
- **Trace block**: Four relative paths (`source_file`, `preprocess_output_file`, `edge_extraction_output_file`, `routing_decision_file`) anchored at the per-document folder. Lets any downstream consumer open the upstream artifacts without guesswork.
- **Verbatim propagation**: Copying a field from an input to the output exactly, with no transformation. Applies to `document_id`, `vendor_candidate` values/confidences, `company_name.present`, `company_name.inferred`, and `review_status` (both sub-fields).
- **Cross-input invariant**: A condition that must hold between the two inputs. Stage 1 enforces two: `contract_set_version == "1.0.0"` on both (FR-004) and `document_id` agreement (FR-005). Failures are hard errors.
- **Policy version (assembler-local)**: The `<semver>` segment of `pipeline_version` (formatted as `"009-final-payload@<semver>"` per FR-007). It pins the `overall_vendor_confidence` formula and the `secondary_identifiers_found` ordering. Any change to either bumps the semver so downstream consumers reading a `final_structured_payload.json` can tell output generations apart without opening source control.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Running the assembler against one valid per-document folder produces a schema-valid `final_structured_payload.json` in ≤ 200 ms of wall-clock time on a developer workstation (pure deterministic code, two JSON reads and one write). Across all 20 corpus documents, 100% of runs pass schema validation given valid inputs.
- **SC-002**: For every input pair where `routing_decision.json:review_status.review_reason == "company_name_inferred"`, the assembled `final_structured_payload.json:review_status.review_reason` is byte-identical (exact-string match). This feature introduces zero string variants, zero normalization, and zero default substitutions for the canonical missing-name string. The aggregate claim that all 5 labeled missing-name corpus documents carry this exact string end-to-end is the 007 evaluator's release gate (it runs over the corpus); this feature's contribution is the per-invocation verbatim-propagation guarantee, verified via the `missing_name_inferred/` fixture.
- **SC-003**: Across any valid input pair, zero `evidence` keys appear in `final_structured_payload.json` at any nesting depth. The flattening is complete.
- **SC-004**: For any valid input pair, two consecutive assembler runs produce byte-identical outputs except for `processed_at`. No drift in vendor_candidate values, confidences, review_status, quality_summary, or trace — including `secondary_identifiers_found` ordering.
- **SC-005**: On hard failures (missing input, schema-invalid input, `contract_set_version` drift, `document_id` mismatch, routing-internal contradiction per FR-016), the assembler exits non-zero 100% of the time, writes no `final_structured_payload.json`, and emits a human-readable error naming the failure cause.
- **SC-006**: A downstream consumer (the 007 evaluator, a future CRM integration) reading a single `final_structured_payload.json` can answer, without opening any upstream artifact: (a) what values the pipeline extracted for vendor identity, (b) whether the pipeline flagged the document for review and why (via `review_status`), (c) how confident the pipeline was overall (via `quality_summary`), and (d) where to find the upstream artifacts if deeper investigation is needed (via `trace`).
- **SC-007**: A reviewer who picks up a `final_structured_payload.json` alongside the 007 evaluator's `evaluation_document.json` for the same document can reconstruct why each field scored the way it did, tracing from evaluator verdict → final payload value → (via trace) extractor value/evidence. The final payload is sufficient to close the loop between pipeline output and evaluator scoring.
- **SC-008**: Changes to the `overall_vendor_confidence` formula or the `secondary_identifiers_found` ordering are visible through a bump of the `<semver>` segment inside `pipeline_version` (formatted as `"009-final-payload@<semver>"` per FR-007). Zero formula/ordering changes ship without a coordinated semver bump, and every `final_structured_payload.json` carries the policy generation that produced it.
- **SC-009**: The assembler is artifact-to-artifact: it can be executed against any pair of schema-valid fixtures without requiring a real extractor, router, model, or Ollama endpoint. This enables unit and regression testing independent of the rest of the pipeline.
- **SC-010**: This feature delivers the fourth and final stage 1 artifact so that a harness-composed chain of 003 + 005 + 008 + 009 produces all four stage 1 artifacts (`preprocess_output.json`, `edge_extraction_output.json`, `routing_decision.json`, `final_structured_payload.json`) ready for the 007 evaluator to score. Multi-stage orchestration itself is the harness's responsibility (per plan §Assumptions); this feature's contribution is a per-document CLI that any such harness can invoke as its final step.

## Assumptions

- The v1.0.0 `final_structured_payload.schema.json` contract is stable for the life of this feature. Any change to the schema blocks this feature and requires the governance path in `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- The v1.0.0 `edge_extraction_output.json` and `routing_decision.json` shapes produced by 005 and 008 are stable. The assembler relies on their invariants (005 FR-012/FR-013 for company-name provenance, 008 FR-008 for the canonical `"company_name_inferred"` string, 008 FR-010 for `address_has_minimum_components` definition) being upheld.
- Stage 1 operates in single-voter baseline mode. `quality_summary.consensus_level == "single_voter_baseline"` is hard-coded in this feature; multi-voter consensus ships with its own policy bump.
- The `overall_vendor_confidence` formula is pinned in FR-019 as the stage 1 starter formula (policy `0.1.0`): `clip(0.5 * company_name.confidence + 0.5 * mean(secondary_identifier_confidences, default 0.0), 0.0, 1.0)`. Any future change to weights, aggregation shape, secondary derivation, or clipping behavior is a policy change, not a contract change: it bumps the `<semver>` segment of `pipeline_version` (FR-007, SC-008) and leaves the schema untouched.
- The final payload does not carry invoice header fields (`invoice_number`, `invoice_date`, `total_amount`) because the v1.0.0 schema has no slot for them. If a future downstream consumer requires those fields in the final payload, a contract amendment is required. For stage 1, invoice header data remains accessible via the `trace` block's link to `edge_extraction_output.json`.
- The final payload does not carry `document_type.confidence`. The extractor emits it; the final payload flattens `document_type` to the bare string `"invoice"` per the v1.0.0 schema enum. If downstream consumers need the confidence, a contract amendment is required.
- The assembler is artifact-to-artifact from an orchestration perspective: one invocation per document, two JSON reads, one JSON write. Corpus-level orchestration (running across all 20 documents) lives in the harness and is not defined by this feature.
- The 003-pdf-preprocessing, 005-single-voter-extraction, and 008-routing features produce the inputs this feature consumes. The 006-corpus-labeling feature provides the labeled corpus against which 007-evaluator will score this feature's outputs. None of those contracts are reshaped by this feature.
- Cloud escalation, ensemble consensus, line-item extraction, and non-invoice document types are out of scope. They will be separate features with their own contract amendments.
