# Feature Specification: Deterministic Routing (Stage 1 Vendor-Identity)

**Feature Branch**: `008-routing`
**Created**: 2026-04-21
**Status**: Draft
**Input**: User description: "Deterministic routing. Call this 008-routing. Read one document's edge_extraction_output.json and emit routing_decision.json conforming to the frozen v1.0.0 contract. The decision is edge_accept or edge_review_required, derived entirely from rule-based code — the model never decides routing."

## Clarifications

### Session 2026-04-21

- Q: Should scores incorporate the input's `confidence` values (e.g., down-weighting a weakly-evidenced field)? → A: No — scores are pure structural grounding fractions. Confidence is never used in score computation. FR-018 is tightened accordingly: confidence MUST NOT affect scores or decisions.
- Q: What are the canonical formulas for the five scores? → A: Per-category grounding fractions with equal-weight overall. `company_name_score` = 1.0 iff `present==true AND inferred==false AND evidence non-empty`, else 0.0. `address_score` = (grounded components among {street_1, city, state, postal_code, country}) / 5. `street_2` does not contribute. `tax_id_score` = (grounded among {ein, state_tax_id, vat_id, other_tax_id}) / 4. `contact_score` = (grounded among {website, phone, email}) / 3. `overall_vendor_identity_score` = arithmetic mean of the four per-category scores. "Grounded" = non-null value AND non-empty evidence array.
- Q: In what order are entries emitted in the `reasons` array? → A: Pinned to the FR-015 rule-priority order: (1) missing-name, (2) spam-gate failure, (3) secondary-identifier deficit, (4) upstream-failure propagation, then any `edge_accept` affirmative entries, then any informational notes (e.g., input `status == "partial"`, contract-violation notes). Byte-identical across repeat runs.
- Q: What CLI module path and subcommand name does the router use? → A: `python -m dartwing_ocr.router route <folder>`. Module `router`, subcommand `route`. Parallel to `python -m dartwing_ocr.validator validate …`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Emit A Schema-Valid Deterministic `routing_decision.json` For One Document (Priority: P1)

A pipeline developer has `edge_extraction_output.json` sitting in a per-document folder (produced by 005) and needs a single deterministic command to read that artifact, apply the stage 1 routing rules, and write `routing_decision.json` into the same folder. Every claim the artifact makes about the document's acceptability must be traceable to a concrete rule and a concrete observation in the extractor's output — not to a model judgment or a confidence threshold.

**Why this priority**: Without a schema-valid routing artifact, the final-payload assembly (007/future) cannot proceed, the evaluator (007-evaluator) has nothing to score against `expected_review`, and the stage 1 pipeline is one slice short of end-to-end runnable. Routing is also the load-bearing deterministic gate between "what the model proposed" and "what the downstream system accepts" — without it, the constitution's Principle III is empty.

**Independent Test**: Stage a per-document folder containing a schema-valid `edge_extraction_output.json` fixture. Run the router against that folder. Verify `routing_decision.json` is written next to the input, validates against `contracts/stage1_vendor_identity/v1.0.0/routing_decision.schema.json`, reports `contract_set_version == "1.0.0"`, carries the same `document_id` as the input, populates every required top-level key (including `policy_version`, `consensus_summary`, `scores`, `checks`, `review_status`, `reasons`), and reports a `decision` that matches the rules applied against the fixture. Two invocations against the same fixture produce byte-identical outputs except for `processed_at`.

**Acceptance Scenarios**:

1. **Given** a per-document folder containing a valid `edge_extraction_output.json`, **When** the router runs against that folder, **Then** `routing_decision.json` is written next to the input and validates against the frozen schema.
2. **Given** the router writes the artifact, **When** its contents are inspected, **Then** `document_id` equals the one in `edge_extraction_output.json`, `contract_set_version == "1.0.0"`, `processed_at` is a valid ISO-8601 date-time in UTC with the literal `Z` suffix and second precision (e.g., `"2026-04-21T17:03:22Z"`; no sub-second fractional component, no `+00:00` offset form), `pipeline_version` is a non-empty build identifier, and `policy_version` is a non-empty identifier pinning the rule set applied (bumped whenever the routing rules themselves change).
3. **Given** the router writes the artifact, **When** `consensus_summary` is inspected, **Then** `mode == "single_voter_baseline"` and `agreement_level == "not_applicable"`; no other values are emitted in stage 1.
4. **Given** any run, **When** `decision` is inspected, **Then** it is exactly one of `"edge_accept"` or `"edge_review_required"`, and is consistent with `review_status`: `decision == "edge_accept"` iff `review_status.manual_review_required == false` AND `review_status.review_reason == null`; `decision == "edge_review_required"` iff `manual_review_required == true` AND `review_reason` is a non-empty canonical string.
5. **Given** the router writes the artifact, **When** `reasons` is inspected, **Then** it is an array of human-readable strings naming every rule that fired against the document — including "everything green" rules for an `edge_accept` so a reviewer can see *why* the document was accepted. For an `edge_review_required` decision, `review_status.review_reason` equals the highest-priority entry in `reasons` per a documented priority order.
6. **Given** the same fixture is routed twice with no configuration change, **When** the two outputs are compared, **Then** `decision`, `review_status`, `checks`, `scores`, `reasons` contents, and the overall artifact shape are byte-identical. Only `processed_at` is allowed to vary.
7. **Given** the router runs in a per-document folder, **When** the run completes, **Then** it writes nothing outside the target folder, does not modify `edge_extraction_output.json`, and does not create or overwrite any of the reserved downstream filenames (`final_structured_payload.json`, `evaluation_document.json`) or the reserved `votes/` subdirectory.

### User Story 2 - Missing-Name Invariant Routes To Review With The Canonical Reason (Priority: P1)

A pipeline developer processing a missing-name document relies on routing to enforce the constitutional invariant: any `edge_extraction_output.json` reporting `company_name.inferred == true` (or `company_name.present == false`) must route to `edge_review_required` with a review reason that exactly matches the evaluator's pinned canonical string `"company_name_inferred"`. This is the one rule with zero flexibility — the entire missing-name corpus's pass/fail behavior depends on routing emitting this exact string.

**Why this priority**: The constitution (Principle IV) and the evaluator's US4 clarification both anchor behavior to the exact string `"company_name_inferred"`. If routing emits a different string, 5 of 20 corpus documents silently fail the `review_routing_passed` gate at evaluation time, and the stage 1 quality claim collapses on the hardest 25% of the corpus. No amount of secondary-identifier strength can override this rule.

**Independent Test**: Run the router against two fixtures. Fixture A: `company_name.present == false` AND `company_name.inferred == true` (canonical missing-name shape). Fixture B: `company_name.present == true` AND `company_name.inferred == false` with a grounded evidence array. Verify Fixture A produces `decision == "edge_review_required"`, `review_status.manual_review_required == true`, and `review_status.review_reason == "company_name_inferred"` exactly (no variants like `"name_inferred"` or `"vendor_name_inferred"`). Verify Fixture B is NOT forced to `edge_review_required` by the missing-name rule (other rules may still force review on Fixture B; the missing-name rule specifically does not).

**Acceptance Scenarios**:

1. **Given** an `edge_extraction_output.json` where `company_name.inferred == true`, **When** the router runs, **Then** `decision == "edge_review_required"`, `review_status.manual_review_required == true`, `review_status.review_reason == "company_name_inferred"` exactly, and `reasons` contains an entry matching that reason.
2. **Given** an `edge_extraction_output.json` where `company_name.present == false` (regardless of the `inferred` flag), **When** the router runs, **Then** `decision == "edge_review_required"` with the canonical `"company_name_inferred"` reason in `review_status.review_reason`. The two signals (present and inferred) are treated as the same gate because the extractor's reconciliation (005 FR-012, FR-013) guarantees they co-move; the router enforces both independently as defense-in-depth.
3. **Given** the missing-name rule fires, **When** `checks` is inspected, **Then** `company_name_present == false` (reflecting the extractor's reconciled value) AND `company_name_inferred == true`. Both boolean checks are populated from the input regardless of which rule carried the decision.
4. **Given** the missing-name rule fires AND the document also has strong secondary identifiers (two or more grounded), **When** the router runs, **Then** `decision == "edge_review_required"` stands. Secondary-identifier strength does not override the missing-name gate.
5. **Given** any `edge_accept` decision the router emits, **When** its provenance is inspected, **Then** `company_name_present == true` AND `company_name_inferred == false` in `checks`. The router never accepts a document whose company name is inferred or missing.

### User Story 3 - Secondary Identifier Floor Forces Review When Vendor Grounding Is Thin (Priority: P2)

A pipeline developer needs routing to reject documents where the extractor found an explicit company name but essentially nothing else: no address, no tax IDs, no website, no phone, no email. Those documents cannot be safely auto-accepted because the company name alone is not enough provenance. Routing applies a "secondary identifier floor": at least 2 of the 4 floor slots must be grounded (non-null value AND non-empty evidence) in the input artifact, or the document routes to `edge_review_required`. The 4 floor slots are pinned by FR-014: (1) `address_has_minimum_components` (city + state + postal_code jointly grounded), (2) `at_least_one_tax_id_present`, (3) `website_or_email_present` (website and email count together as one slot, not two), (4) phone-grounded as an independent slot.

**Why this priority**: This mirrors the evaluator's `vendor_identity_passed` gate, which itself mirrors real invoice-handling practice — a name by itself does not identify a vendor. Without this rule, routing would be over-permissive and the evaluator's review_routing_passed rate would diverge from the document_score rate in ways that hide real quality issues. Deferring this rule to evaluation would also mean every auto-accepted document silently bypasses a check the evaluator will enforce anyway.

**Independent Test**: Run the router against three fixtures with an explicit grounded company name but varying secondary-identifier strength. Fixture A: zero grounded secondary identifiers — expect `edge_review_required` with a secondary-identifier-insufficient reason. Fixture B: exactly 1 grounded secondary identifier (e.g., only website) — expect `edge_review_required`. Fixture C: exactly 2 grounded secondary identifiers (e.g., address AND email) — expect `edge_accept` (assuming no other rule fires). Verify `checks` booleans (`address_has_minimum_components`, `at_least_one_tax_id_present`, `website_or_email_present`) reflect the inputs faithfully in all three cases.

**Acceptance Scenarios**:

1. **Given** an `edge_extraction_output.json` with an explicit grounded `company_name`, zero grounded address components, zero grounded tax IDs, and no grounded website/phone/email, **When** the router runs, **Then** `decision == "edge_review_required"`, `review_status.review_reason` is the canonical `"secondary_identifiers_insufficient"` string (or an equivalent constant pinned in the policy), and `reasons` names the deficit.
2. **Given** the same shape but with exactly 1 grounded secondary identifier (e.g., only a website), **When** the router runs, **Then** `decision == "edge_review_required"` with the secondary-identifier deficit reason. One grounded secondary identifier is not enough.
3. **Given** the same shape with 2 or more grounded secondary identifiers from the 4-slot floor pinned by FR-014 — `{address_has_minimum_components, at_least_one_tax_id_present, website_or_email_present, phone-grounded}` — **When** the router runs and no other rule fires, **Then** `decision == "edge_accept"`, `review_status.manual_review_required == false`, and `review_reason == null`.
4. **Given** the address check is being evaluated, **When** `checks.address_has_minimum_components` is populated, **Then** it is `true` iff the input address has grounded non-null values for at least `city`, `state`, and `postal_code` (the evaluator's pinned definition of "address counts as one matching secondary identifier"). Street or country alone does not qualify.
5. **Given** the tax-ID check is being evaluated, **When** `checks.at_least_one_tax_id_present` is populated, **Then** it is `true` iff at least one of `ein`, `state_tax_id`, `vat_id`, or `other_tax_id` has a non-null value AND a non-empty evidence array. Unevidenced tax IDs do not count.
6. **Given** multiple review-forcing rules fire on the same document (e.g., missing-name AND secondary-identifier deficit), **When** the router writes `reasons`, **Then** all firing reasons appear in `reasons`, but `review_status.review_reason` carries only the highest-priority canonical reason per the documented priority order (missing-name outranks secondary-identifier deficit).

### User Story 4 - Post-Extraction Spam Gate Catches All-Noise Documents (Priority: P2)

A pipeline developer needs routing to have one last defensive check against documents the extractor ran on but that are not meaningfully invoices at all: pages that are nearly empty, obviously spam, or otherwise produce an `edge_extraction_output.json` with no grounded fields of any kind. The schema's `checks.post_extraction_spam_gate_passed` is routing's slot for that check. It is deterministic, runs purely against the extractor's output, and does not re-OCR or call a model.

**Why this priority**: Falcon OCR's pre-extraction spam gate (per the architecture doc) is not yet wired up in stage 1. Until it is, the post-extraction spam gate is the only defensive layer between "garbage in" and "accepted vendor identity out". The rule is cheap (pure inspection of already-computed booleans) and catches a failure mode that no other stage 1 rule addresses.

**Independent Test**: Run the router against a fixture representing an all-noise document: `edge_extraction_output.json` with `vendor_candidate.company_name.value == null`, every address component null, every tax ID null, website/phone/email all null, and `extraction_notes`/`warnings` noting the empty page. Verify `checks.post_extraction_spam_gate_passed == false`, `decision == "edge_review_required"`, and `review_status.review_reason` is a canonical spam-gate reason (e.g., `"post_extraction_spam_gate_failed"`). Then run against a normal invoice fixture; verify `post_extraction_spam_gate_passed == true` and the spam gate contributes no entries to `reasons`.

**Acceptance Scenarios**:

1. **Given** an `edge_extraction_output.json` where `vendor_candidate.company_name.value == null`, every address component is null, every tax ID is null, `website == null`, `phone == null`, and `email == null`, **When** the router runs, **Then** `checks.post_extraction_spam_gate_passed == false` and `decision == "edge_review_required"` with a canonical spam-gate reason in `review_status.review_reason` and an entry in `reasons`.
2. **Given** a normal invoice fixture with at least one grounded vendor-candidate field, **When** the router runs, **Then** `checks.post_extraction_spam_gate_passed == true` and the spam gate contributes no entry to `reasons` (other rules may still fire).
3. **Given** the spam gate's exact threshold is pinned in the policy, **When** `policy_version` is inspected, **Then** changing the threshold requires a `policy_version` bump, even if no other routing rule changed. The spam-gate threshold is part of the routing policy.
4. **Given** multiple review-forcing rules fire on the same document (e.g., spam gate AND missing name), **When** `review_status.review_reason` is inspected, **Then** the canonical missing-name reason `"company_name_inferred"` wins over the spam-gate reason per the priority order; spam-gate still appears in `reasons` for traceability.
5. **Given** the spam gate fires, **When** `scores` is inspected, **Then** `overall_vendor_identity_score` is `0.0` or near-zero, consistent with the spam-gate conclusion that the document has no useful vendor identity signal.

### User Story 5 - Graceful Degradation Honors Input Status And Surfaces Hard Errors (Priority: P3)

A pipeline developer processing a corpus will occasionally feed routing an `edge_extraction_output.json` where the extractor itself reported `status == "partial"` or `"failure"`. Routing must still emit a schema-valid `routing_decision.json` in those cases, carry the input's partiality forward in its own `status`, and surface the input's failure cause in `reasons`. Hard errors (missing input, schema-invalid input, contract-version drift) exit non-zero with no artifact written.

**Why this priority**: Silent failure modes on the routing layer are costly to debug. Making input-status propagation explicit, schema-shape determinism hold even on bad inputs, and hard errors loud-and-visible means a developer looking at a failing document in the evaluator can trace back to routing and see what routing knew. This story is pure defensive behavior — it adds no new decisions but ensures the existing decisions are legible.

**Independent Test**: Run the router against (a) a clean `edge_extraction_output.json` with `status == "success"` — expect routing `status == "success"`. (b) An `edge_extraction_output.json` with `status == "partial"` — expect routing `status == "partial"` with a `reasons` entry carrying the input's `warnings`. (c) An `edge_extraction_output.json` with `status == "failure"` — expect routing `status == "partial"` or `"failure"`, a cautious `decision == "edge_review_required"`, and a `reasons` entry naming the upstream failure. (d) A missing or schema-invalid `edge_extraction_output.json` — expect non-zero exit, no `routing_decision.json` written, a human-readable error. (e) An input reporting `contract_set_version != "1.0.0"` — expect non-zero exit with a version-drift error.

**Acceptance Scenarios**:

1. **Given** the input `edge_extraction_output.json` reports `status == "success"` and validates against its schema, **When** the router runs, **Then** the output's `status == "success"` unless the router's own computation flagged a non-fatal issue.
2. **Given** the input's `status == "partial"`, **When** the router runs, **Then** the output's `status == "partial"`, the decision is still computed using the rules in US2–US4, and `reasons` includes an entry indicating the input was partial.
3. **Given** the input's `status == "failure"`, **When** the router runs, **Then** the output's `status` is `"partial"` or `"failure"`, `decision == "edge_review_required"` (defensive default), and `reasons` names the upstream failure. Routing does not try to guess a meaningful decision from a failed extraction.
4. **Given** the input `edge_extraction_output.json` is missing, unreadable, fails its own schema validation, or reports `contract_set_version != "1.0.0"`, **When** the router runs, **Then** no `routing_decision.json` is written, the router exits non-zero, and a human-readable error names the specific failure cause.
5. **Given** any `routing_decision.json` the router writes, **When** its schema validity is checked, **Then** validation passes regardless of `status`. A failing upstream extraction still produces a schema-valid routing artifact; `status == "failure"` is a reported outcome, not a schema violation.
6. **Given** any routing run, **When** the reasons for the decision are reconstructed from `checks`, `scores`, and the documented rule set, **Then** the `decision` the router emitted matches the reconstruction. There is no routing decision a developer cannot reproduce by reading the artifact alone (traceability is complete).

### Edge Cases

- **Input reports both `present == true` AND `inferred == true`**: This combination is forbidden by extractor FR-013, so it should never occur. If it does, routing treats it as a contract violation, emits `status == "partial"` with a `reasons` entry naming the violation, and defensively routes to `edge_review_required`. Routing does not attempt to silently "correct" a contract violation in the input.
- **Input reports `present == false` AND `inferred == false`**: Also forbidden by FR-013. Treated identically to the above — defensive review-required with a reasons entry.
- **Company name is grounded but looks like noise (e.g., "INVOICE" or a numeric string)**: Not routing's job. The extractor is responsible for realistic value selection; routing only checks present/inferred/evidence-grounding and structural validity.
- **Input evidence arrays reference IDs the extractor claims it reconciled**: Routing does not re-verify evidence against `preprocess_output.json`. The extractor (005 FR-010, FR-011) owns that invariant. Routing trusts the extractor's reconciliation.
- **Phone present as the only secondary identifier**: Per FR-014's 4-slot floor (`address_has_minimum_components`, `at_least_one_tax_id_present`, `website_or_email_present`, phone-grounded), phone occupies one independent slot. A document with only a grounded phone satisfies exactly 1 of 4 floor slots and routes to `edge_review_required` with the secondary-identifier-insufficient reason.
- **Address is populated but below the minimum-components bar** (e.g., only `country` is set): `address_has_minimum_components == false`, address does NOT count toward the secondary-identifier floor. The documented definition is `city AND state AND postal_code` all grounded; incomplete addresses do not count.
- **Multiple tax IDs populated (e.g., both `ein` and `state_tax_id`)**: `at_least_one_tax_id_present == true`; this counts as exactly one secondary identifier toward the floor, not two. The floor counts *kinds* of identifiers, not *instances*.
- **`website` and `email` are both populated**: `website_or_email_present == true`; this counts as one secondary identifier (per the schema's aggregate boolean), not two. Routing does NOT split them.
- **A review-forcing rule and `edge_accept`-permitting signals both exist**: Any review-forcing rule forces `edge_review_required`. Permissive signals never override a forcing rule.
- **Zero review-forcing rules fire AND `post_extraction_spam_gate_passed == true` AND the secondary-identifier floor is met AND `company_name_present == true` AND `company_name_inferred == false`**: The document routes to `edge_accept`. All four conditions must co-occur; missing any one produces review-required.
- **Policy version bump mid-corpus**: Each document's `routing_decision.json` records the `policy_version` in effect at its routing time. If the policy changes mid-corpus (unusual), documents routed before and after the change carry different policy versions and can be reconciled forensically. Routing does not retroactively re-route older documents.
- **Input's `warnings` or `extraction_notes` mention issues the router can't act on** (e.g., dropped evidence IDs, JSON repair): Routing's decision is based on the structural shape of the extractor's output, not the narrative in warnings. The warnings are surfaced in `reasons` for traceability but do not drive the decision by themselves.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The router MUST accept one per-document folder as input, read that folder's `edge_extraction_output.json`, apply the stage 1 routing rules, and write `routing_decision.json` into the same folder. On a successful run, the router MUST overwrite any existing `routing_decision.json` in the target folder with the newly computed artifact; no merging or diffing against a previous artifact is performed.
- **FR-002**: Every `routing_decision.json` the router writes MUST validate against `contracts/stage1_vendor_identity/v1.0.0/routing_decision.schema.json` and MUST set `contract_set_version` to `"1.0.0"`. The artifact MUST be persisted atomically (write to a temporary file in the target folder, then rename into place); a failed or interrupted write MUST NOT leave a partial or dangling `routing_decision.json`. The `checks` block MUST be emitted in the schema's `required` key order; the `scores` block MUST likewise be emitted in the schema's `required` key order. Implementation-dependent key ordering is forbidden so byte-identity across reruns is well-defined.
- **FR-003**: The router MUST refuse to run when the input `edge_extraction_output.json` is missing, unreadable, fails its own schema validation, or reports `contract_set_version != "1.0.0"`. In all four cases it exits non-zero with a human-readable error written to **stderr** (stdout remains reserved for structured output in future versions) and writes no `routing_decision.json`. Exit codes are split by cause: exit `2` for "bad input" (external cause — the four hard-error conditions above, i.e. malformed input or contract-version drift), exit `3` for "bad policy" or "bad routing code" (internal cause — assembled output fails schema validation, or an internal invariant is violated), exit `1` for any unexpected exception (stack trace on stderr). Exit `0` is reserved for a successful write. The canonical exit-code taxonomy is documented in the CLI contract.
- **FR-004**: `document_id` in the output MUST equal `document_id` in the input. The two MUST NOT diverge.
- **FR-005**: `pipeline_version` MUST identify the router build. `policy_version` MUST identify the routing rule set. Both MUST be non-empty strings. A change to the routing rules themselves (including rule addition, rule removal, threshold change, canonical reason-string change, or spam-gate threshold change) MUST bump `policy_version`. The bump is a PR-review gate, not a runtime check: any PR touching `src/dartwing_ocr/router/rules.py`, `checks.py`, `reasons.py`, or the canonical-string constants MUST include a corresponding change to `version.POLICY_VERSION`. A PR that modifies rule-layer code without bumping `POLICY_VERSION` MUST be rejected at review.
- **FR-006**: `consensus_summary.mode` MUST be `"single_voter_baseline"` and `consensus_summary.agreement_level` MUST be `"not_applicable"` in stage 1. No other values are emitted.
- **FR-007**: `decision` MUST be exactly one of `"edge_accept"` or `"edge_review_required"`. `decision == "edge_accept"` iff `review_status.manual_review_required == false` AND `review_status.review_reason == null`; `decision == "edge_review_required"` iff `manual_review_required == true` AND `review_reason` is a non-empty canonical string. The two fields cannot disagree.
- **FR-008**: If the input reports `company_name.inferred == true` OR `company_name.present == false`, the router MUST set `decision = "edge_review_required"` AND `review_status.review_reason = "company_name_inferred"` exactly (matching the evaluator's pinned canonical string). No value variation — not `"name_inferred"`, not `"vendor_name_inferred"`, not any other spelling.
- **FR-009**: The router MUST compute `checks.company_name_present` and `checks.company_name_inferred` by direct copy from the input's `vendor_candidate.company_name.present` and `.inferred` booleans. It MUST NOT re-derive these values from evidence arrays; the extractor (005) owns provenance.
- **FR-010**: The router MUST compute `checks.address_has_minimum_components` as `true` iff the input's `vendor_candidate.address` has non-null values AND non-empty evidence arrays for `city`, `state`, AND `postal_code` jointly. Street-only, country-only, or any two-of-three subset returns `false`.
- **FR-011**: The router MUST compute `checks.at_least_one_tax_id_present` as `true` iff at least one of `ein`, `state_tax_id`, `vat_id`, `other_tax_id` in `vendor_candidate.tax_ids` has a non-null value AND a non-empty evidence array.
- **FR-012**: The router MUST compute `checks.website_or_email_present` as `true` iff at least one of `vendor_candidate.website` or `vendor_candidate.email` has a non-null value AND a non-empty evidence array.
- **FR-013**: The router MUST compute `checks.post_extraction_spam_gate_passed` as `false` iff the input's `vendor_candidate.company_name.value == null` AND every address component value is null AND every tax-ID value is null AND `website == null` AND `phone == null` AND `email == null`. Otherwise the gate passes. (The specific threshold is part of `policy_version`; relaxing or tightening this rule requires a policy bump.)
- **FR-014**: The router MUST apply the secondary-identifier floor: if the aggregate count of `true` values across `{checks.address_has_minimum_components, checks.at_least_one_tax_id_present, checks.website_or_email_present, phone-grounded}` is fewer than 2, AND no higher-priority rule has fired, the decision is `edge_review_required` with a canonical `"secondary_identifiers_insufficient"` reason string. (Phone-grounded is inspected as an additional identifier independently of the schema's aggregate boolean since `phone` has its own field in `vendor_candidate`.)
- **FR-015**: When multiple review-forcing rules fire, the router MUST apply this priority order to `review_status.review_reason` (highest wins): (1) missing-name (`"company_name_inferred"`), (2) spam-gate failure (`"post_extraction_spam_gate_failed"`), (3) secondary-identifier deficit (`"secondary_identifiers_insufficient"`), (4) upstream-failure propagation (`"upstream_extraction_failed"`). All firing rules MUST still appear in `reasons` regardless of which one carried `review_reason`. The `reasons` array itself MUST be emitted in this same priority order (1→2→3→4), followed by any `edge_accept` affirmative entries (when applicable), followed by any informational entries (e.g., input-status-partial note, contract-violation note). Ordering is deterministic and byte-identical across repeat runs.
- **FR-016**: For an `edge_accept` decision, the router MUST still populate `reasons` with at least one human-readable entry that names the affirmative conditions met (e.g., "explicit company name grounded", "secondary identifier floor met with address + email"). `edge_accept` decisions are traceable, not silent. The exact affirmative string set (e.g., `"company_name_explicit"`, `"secondary_identifier_floor_met"`) and the exact informational string set (e.g., `"upstream_status_partial"`, `"contract_violation_detected"`) are part of the routing policy: their spellings are pinned by `policy_version` and changing any of them MUST bump `policy_version` per FR-005. Initial spellings are fixed by the plan/research document (see research.md Decisions 9 and 10 and the CLI contract's canonical vocabulary section), not by this spec, so the spec can add affirmative/informational categories in future slices without itself requiring amendment.
- **FR-017**: The router MUST compute `scores` deterministically from the input's structural booleans and evidence arrays — not from the input's confidence values. All five values MUST lie in `[0.0, 1.0]`. The canonical formulas are pinned by `policy_version` as follows: "grounded" means a non-null value AND a non-empty evidence array.
  - `company_name_score` = `1.0` iff `company_name.present == true` AND `company_name.inferred == false` AND `company_name.evidence` is non-empty; otherwise `0.0`.
  - `address_score` = (count of grounded components among `{street_1, city, state, postal_code, country}`) / `5`. `street_2` does not contribute to the score; the extractor's `street_2` field is informational only.
  - `tax_id_score` = (count of grounded slots among `{ein, state_tax_id, vat_id, other_tax_id}`) / `4`.
  - `contact_score` = (count of grounded fields among `{website, phone, email}`) / `3`.
  - `overall_vendor_identity_score` = arithmetic mean of the four per-category scores above (equal weight).
- **FR-018**: The router MUST NOT use the input's `confidence` numbers in any gate, check, or score. Scores are pure structural grounding fractions computed per FR-017; confidence values are read-only signals that MAY be surfaced in human-readable `reasons` entries for traceability, but MUST NOT enter any numeric computation the router emits. Provenance (present/inferred) and grounding (evidence arrays) alone drive routing.
- **FR-019**: The router MUST NOT call any model, perform OCR, re-read `preprocess_output.json`, or otherwise bypass the extractor's output as its sole information source. Routing is artifact-to-artifact: `edge_extraction_output.json` in, `routing_decision.json` out.
- **FR-020**: When the input's `status == "partial"`, the output's `status` MUST be `"partial"` and `reasons` MUST include an entry naming that the upstream was partial; the per-rule logic in FR-008, FR-013, FR-014 still evaluates normally because a partial extractor run is trustworthy enough for its structural booleans to be read. When the input's `status == "failure"`, the output's `status` MUST be `"partial"` (the router itself succeeded at producing a schema-valid artifact; see research Decision 11), `decision` MUST be `"edge_review_required"`, `review_status.review_reason` MUST be `"upstream_extraction_failed"` exactly, and `reasons` MUST be exactly the single-entry array `["upstream_extraction_failed"]`. Per research Decision 11, **no other rule evaluates on a failure input** — the extractor's structural booleans are untrustworthy, so FR-008 / FR-013 / FR-014 / FR-024 are all suppressed, and no lower-priority forcing reason may preempt the upstream-failure signal in `review_reason` via FR-015 priority ordering. Affirmatives (`"upstream_extraction_ok"`, etc.) and the `"upstream_status_partial"` informational entry are also suppressed on a failure input.
- **FR-021**: Given identical inputs, the router MUST produce byte-identical `routing_decision.json` outputs except for `processed_at`. `decision`, `review_status`, `checks`, `scores`, `reasons` content, and artifact shape MUST be deterministic. `processed_at` MUST be an ISO-8601 UTC date-time with the literal `Z` suffix and second precision (e.g., `"2026-04-21T17:03:22Z"`); sub-second fractional components and `+00:00` offset forms are forbidden so the only legitimate drift between reruns is the second-precision wall clock.
- **FR-022**: The router MUST NOT modify `edge_extraction_output.json`, `preprocess_output.json`, `expected.json`, `notes.md`, `source.pdf`, or any other file it did not create. Inputs are read-only.
- **FR-023**: The router MUST NOT implement or invoke final-payload assembly, evaluation, consensus comparison, ensemble reconciliation, or cloud escalation logic. It is a pure routing stage; downstream slices (007/final-payload, 007-evaluator) consume its output.
- **FR-024**: If the input violates an extractor invariant (e.g., `company_name.present == true` AND `company_name.inferred == true`, or `company_name.present == false` AND `company_name.inferred == false`, both forbidden by extractor FR-013), the router MUST treat this as a contract violation, set `status == "partial"`, include a `reasons` entry naming the violation with the canonical informational string `"contract_violation_detected"` (part of `policy_version`; renaming requires a policy bump), and defensively set `decision == "edge_review_required"`. The router does NOT silently correct extractor violations.
- **FR-025**: The router MUST be invokable from the stage 1 CLI as `python -m dartwing_ocr.router route <per-document-folder>` — module `router`, subcommand `route` — in a one-document mode, parallel to the existing `python -m dartwing_ocr.validator validate …` pattern. Additional subcommands (e.g., corpus orchestration) are out of scope for this feature.

### Key Entities

- **Per-document folder**: One corpus document's on-disk home. Holds `source.pdf`, `expected.json`, optional `notes.md`, `preprocess_output.json` (003), `edge_extraction_output.json` (005 — input to this feature), and `routing_decision.json` (output of this feature).
- **Extraction artifact (`edge_extraction_output.json`)**: The frozen v1.0.0 input. Read-only. Supplies `vendor_candidate` (company_name + address + tax_ids + website + phone + email, each with value/confidence/evidence), `invoice_header_fields`, `status`, and `warnings`.
- **Routing artifact (`routing_decision.json`)**: The frozen v1.0.0 output. Conforms to `routing_decision.schema.json`. Keys: `contract_set_version`, `pipeline_version`, `policy_version`, `document_id`, `processed_at`, `status`, `decision`, `consensus_summary`, `scores`, `checks`, `review_status`, `reasons`.
- **Decision**: One of `"edge_accept"` or `"edge_review_required"`. The stage 1 vocabulary is fixed; future ensemble decisions require a contract-set amendment.
- **Policy version (`policy_version`)**: Identifier for the rule set applied. Bumps whenever any routing rule, threshold, or canonical reason string changes. Lets a reviewer tell apart two `routing_decision.json` files that differ only because the rules changed between runs.
- **Checks**: Six booleans the router publishes for traceability: `company_name_present`, `company_name_inferred`, `address_has_minimum_components`, `at_least_one_tax_id_present`, `website_or_email_present`, `post_extraction_spam_gate_passed`. All are derived from the input's structural shape, not from the input's confidence numbers. Phone-grounding (the 4th FR-014 floor slot) is **not** a `checks.*` field — the frozen v1.0.0 schema has no `phone_present` boolean, so the router computes phone grounding inline from `vendor_candidate.phone` when evaluating the secondary-identifier floor (research Decision 6). Adding a `checks.phone_present` key would require a contract-set amendment.
- **Scores**: Five numeric roll-ups in `[0.0, 1.0]`: `company_name_score`, `address_score`, `tax_id_score`, `contact_score`, `overall_vendor_identity_score`. Advisory signals for downstream consumers; not used by routing's own gates.
- **Review status (`review_status`)**: Two fields — `manual_review_required` (boolean) and `review_reason` (canonical string or null). The definitive statement of what the downstream system should do with this document.
- **Reasons**: Array of human-readable strings naming every rule that contributed to the decision, including affirmative reasons for `edge_accept`. For `edge_review_required`, `review_status.review_reason` equals the highest-priority entry in `reasons` per the documented priority order.
- **Canonical reason strings**: Stage 1 pins two classes of canonical strings, both part of `policy_version` (changing any of them requires a policy bump per FR-005 / SC-010):
  - **Forcing-rule strings** (drive `review_status.review_reason` per FR-015 priority): `"company_name_inferred"`, `"post_extraction_spam_gate_failed"`, `"secondary_identifiers_insufficient"`, `"upstream_extraction_failed"`.
  - **Informational strings** (appear in `reasons` but never supply `review_reason`): `"contract_violation_detected"` (FR-024), `"upstream_status_partial"` (FR-020 partial case), and the affirmative strings named by FR-016 (see research.md Decision 9 and the CLI contract's canonical-vocabulary section for the pinned affirmative spellings `"company_name_explicit"`, `"spam_gate_passed"`, `"secondary_identifier_floor_met"`, `"upstream_extraction_ok"`). Exact spellings for affirmative and informational strings are pinned by the plan/research document, not by this spec; the spec pins only that these strings exist and are governed by `policy_version`.
- **Priority order** (for resolving `review_reason` when multiple rules fire): (1) missing-name, (2) spam-gate failure, (3) secondary-identifier deficit, (4) upstream-failure propagation.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Running the router against one valid per-document folder produces a schema-valid `routing_decision.json` in ≤ 200 ms of wall-clock time on a developer workstation (pure deterministic code, no I/O beyond two JSON files). Across all 20 corpus documents, 100% of runs pass schema validation.
- **SC-002**: 100% of inputs where `company_name.inferred == true` OR `company_name.present == false` produce `decision == "edge_review_required"` AND `review_status.review_reason == "company_name_inferred"` exactly. Zero variants. This is the hardest invariant; the entire missing-name corpus's `review_routing_passed` rate depends on it.
- **SC-003**: 100% of inputs where the four affirmative conditions co-occur (`company_name_present == true` AND `company_name_inferred == false` AND `post_extraction_spam_gate_passed == true` AND secondary-identifier floor met) produce `decision == "edge_accept"`. No other rule silently overrides.
- **SC-004**: Given identical inputs, two consecutive router invocations produce byte-identical outputs except for `processed_at`. No drift in `decision`, `review_status`, `checks`, `scores`, `reasons` content, or ordering.
- **SC-005**: For every document routed, the `decision` can be reconstructed by a reviewer using only the `routing_decision.json` artifact and the documented rule set pinned at `policy_version`. No routing decision requires access to logs, the input, or external state to explain.
- **SC-006**: On hard failures (missing input, schema-invalid input, contract-version drift), the router exits non-zero 100% of the time, writes no `routing_decision.json`, and emits a human-readable error naming the failure cause.
- **SC-007**: When the input's `status` is `"partial"` or `"failure"`, the router produces a schema-valid `routing_decision.json` with its own `status` reflecting the upstream condition and `reasons` naming the upstream partiality/failure. Upstream issues are always visible in the artifact, never silent.
- **SC-008**: The router's decisions match the evaluator's expectations for `review_routing_passed` on 100% of the 5 missing-name corpus documents. If any missing-name document fails `review_routing_passed` at evaluation time, the cause is in the extractor or the labels, not in routing.
- **SC-009**: A reviewer can read any `routing_decision.json` and, without consulting the input, determine (a) what decision was made, (b) why it was made (via `reasons` and `review_status.review_reason`), (c) the structural condition of the input's vendor identity (via `checks` and `scores`), and (d) which rule set was applied (via `policy_version`).
- **SC-010**: Adding a new routing rule, removing a rule, changing a threshold, or changing a canonical reason string forces a `policy_version` bump. Zero routing rule changes ship without a corresponding `policy_version` change. Enforced at PR review per FR-005: a PR that edits rule-layer modules (`rules.py`, `checks.py`, `reasons.py`, canonical-string constants) without editing `version.POLICY_VERSION` is treated as a quality-gate failure, not a style nit.

## Assumptions

- The v1.0.0 routing contract (`routing_decision.schema.json`) is stable for the life of this feature. Any change to the schema blocks this feature and requires the governance path in `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- `edge_extraction_output.json` shape produced by 005 is stable at `contract_set_version = "1.0.0"`. The extractor owns the invariants named in 005's FR-012 and FR-013 (company-name provenance), so this router treats those booleans as trustworthy and does not re-derive them.
- Stage 1 operates in single-voter baseline mode. `consensus_summary.mode == "single_voter_baseline"` is hard-coded in this feature; multi-voter consensus is a separate future slice that will ship with its own policy bump.
- The pre-extraction spam gate (Falcon OCR) is not yet wired up in stage 1. This feature's `post_extraction_spam_gate_passed` check is the only spam defense active in the stage 1 pipeline and is intentionally conservative.
- The canonical review reasons pinned by this feature (`"company_name_inferred"`, `"post_extraction_spam_gate_failed"`, `"secondary_identifiers_insufficient"`, `"upstream_extraction_failed"`) are part of the stage 1 routing policy. The `"company_name_inferred"` string specifically is load-bearing across the evaluator (007's US4) and MUST NOT change without a coordinated evaluator-side amendment.
- Scores are advisory signals for downstream consumers (final-payload quality summary, evaluator calibration tracking, human reviewers). Routing's own gates are driven by structural booleans, not by scores. Scores that happen to be low on an `edge_accept` document are a signal to downstream review, not an override.
- Routing is artifact-to-artifact: one input JSON, one output JSON, same folder. Corpus-level orchestration (running across all 20 documents) lives in the harness and is not defined by this feature.
- The 003-pdf-preprocessing, 005-single-voter-extraction, 006-corpus-labeling (parallel workstream), and 007-evaluator features produce and consume the artifacts this feature sits between. This feature does not reshape any of their contracts.
- Cloud escalation, ensemble consensus, and line-item routing are out of scope. They will be separate features with their own policy bumps.
