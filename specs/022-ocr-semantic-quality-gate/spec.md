# Feature Specification: OCR Semantic Quality Gate

**Feature Branch**: `022-ocr-semantic-quality-gate`
**Created**: 2026-05-22
**Status**: Draft
**Input**: User description: "Create feature 022-ocr-semantic-quality-gate. Add deterministic semantic/table OCR quality evaluation for degraded invoice body/table rows, governed by the OpenSpec change `add-ocr-semantic-quality-gate` (the capability spec is the source of truth). Add an optional authored `semantic_table_truth.json` sidecar; keep `expected.json` as the vendor-identity truth file; evaluate from `preprocess_output.json` + the sidecar; no model judgment, network calls, or OCR confidence as proof of correctness; record concrete failed checks; expose semantic table quality separately from vendor-identity metrics; preserve features 019/020/021 behavior and `document_pass_fail.vendor_identity_passed`; treat degraded-body samples as fixtures first."

---

> **Governing input**: This spec is derived from and subordinate to the OpenSpec change `openspec/changes/add-ocr-semantic-quality-gate/` — its capability spec `specs/ocr-semantic-quality-gate/spec.md` is the **source of truth for feature behavior**. The prior OpenSpec change `govern-ocr-semantic-quality-gap/` only documented the as-built limitation; this feature is the implementation work. Supporting context: `docs/stage1-vendor-identity/prd-ocr-semantic-quality-gate.md` (draft PRD seed) and `docs/stage1-vendor-identity/ocr-semantic-quality-observations.md` (the `inv_024_hard_degraded_body` GPU calibration finding).

> **Scope discipline**: This feature is an **evaluator/harness-owned** validation slice. It adds table/body OCR quality evaluation — it does NOT add line-item extraction, does NOT rewrite features 019/020/021 in place, and does NOT change pipeline preprocessing/extraction/routing/final-payload behavior at landing. The gate is deterministic and code-owned: no learned classifier, no new model runtime, no remote service, no network call, no prompt-owned routing decision. Specs and code stay aligned — no active functional requirement ships without covering implementation tasks and tests.

## Clarifications

### Session 2026-05-22

- **Q1 — Fixture corpus home** (FR-026, FR-027): Q: Should canonical degraded-body fixtures live under `tests/stage1_vendor_identity/`, or should this feature introduce a separate semantic-quality corpus root? → A: A **separate semantic-quality corpus root**. `tests/stage1_vendor_identity/` remains the stable 20-document vendor-identity MVP baseline and is NOT extended with degraded-body fixtures. The new corpus root may reuse the same per-document folder discipline where useful, but it is canonical for semantic/table-quality evaluation only — not for the vendor-identity MVP baseline.
- **Q2 — Minimum sidecar row shape** (FR-002): Q: What is the minimum `semantic_table_truth.json` row shape for the first gate — required values only, required values plus row text, or required values plus approximate row-region anchors? → A: **Required values plus row text.** Required values alone are too weak to test text coverage and row alignment; approximate row-region anchors are too brittle and remain optional future metadata. The first required row shape supports `row_id`, `quantity`, `description`, `unit_price`, `amount`, and expected/required row text (or required text fragments).
- **Q3 — Runtime integration boundary** (Out of Scope, FR-033): Q: Should runtime fallback/review integration remain out of scope and be deferred until evaluator-only evidence is stable? → A: **Yes — out of scope, deferred.** This feature implements evaluator/harness evidence first. It MAY report that whole-invoice/table-quality failed or would require review, but it MUST NOT alter feature 019 fallback behavior, feature 020 vendor-identity skip-fallback behavior, `routing_decision.json`, or runtime review policy. Runtime integration is a later feature, after evaluator evidence is stable.
- **Q4 — Verdict aggregation rule** (FR-016): Q: How is the per-document verdict decided between `passed` and `failed`? → A: **Any-fail rule.** A document is `failed` if any row records any failed check; it is `passed` only when zero failed checks are recorded across all rows. No per-category severity tiers and no weighted/threshold score.
- **Q5 — Text-match normalization** (FR-009, FR-011, FR-012): Q: What normalization is applied before comparing sidecar text/values to observed body OCR? → A: **Normalized exact match.** Apply Unicode NFKC normalization, case-folding, whitespace collapse, and punctuation stripping to both sides, then test exact token / substring containment. No fuzzy similarity or edit-distance threshold.
- **Q6 — Row-text-coverage gap definition** (FR-011): Q: What counts as "covers only part" of a row's expected text? → A: **Binary.** Any required/expected text token absent from the observed body OCR is a row-text-coverage gap; no numeric coverage threshold. A coverage ratio MAY be recorded as supporting evidence but is not the trigger.
- **Q7 — Row-to-OCR association method** (FR-012): Q: How are sidecar rows anchored to observed OCR for row-alignment? → A: **Text-anchored.** Locate each row by the best normalized match of its description / row text, then verify required values are present, in order, and not split. When candidate anchors tie, break the tie deterministically by earliest observed-OCR position, then by sidecar declaration order.
- **Q8 — Required vs optional row fields** (FR-002, FR-004): Q: Which sidecar row fields are mandatory? → A: **`row_id` and row text mandatory.** `quantity`, `description`, `unit_price`, and `amount` are optional, and every field that IS present becomes a required-content check for that row.
- **Q9 — Currency representation in the sidecar** (FR-002, FR-010): Q: How are `unit_price` / `amount` stored? → A: **Normalized decimal strings without a currency symbol** (e.g. `"21.00"`) — not JSON numbers and not symbol-prefixed strings.
- **Q10 — Malformed currency-shape definition** (FR-010): Q: How is "malformed currency shape" defined? → A: **Regex.** A currency-position token is malformed when it fails the canonical money regex `^\$?\d{1,3}(,\d{3})*\.\d{2}$` — this flags colon-for-decimal (`$21:00`) and truncated values (`$22:`) without enumerating every defect.
- **Q11 — `row_id` format and uniqueness** (FR-002, FR-004): Q: What constrains `row_id`? → A: **Non-empty string, unique within the sidecar.**
- **Q12 — Whole-invoice claim report surface** (FR-024, FR-025): Q: Where is the whole-invoice/table-quality claim represented in the reports? → A: A new **`document_pass_fail.semantic_table_quality_passed`** field, added alongside the unchanged `vendor_identity_passed`.
- **Q13 — Gate invocation** (FR-007): Q: Does the gate run automatically inside the evaluator, or behind an opt-in? → A: **Automatic.** The gate runs inside the existing evaluator whenever `semantic_table_truth.json` is present; the sidecar's presence is the opt-in and no new CLI flag is introduced.
- **Q14 — Contract-set membership of the sidecar schema** (FR-031): Q: Where does the `semantic_table_truth.json` JSON Schema live? → A: **Added to the governed contract set** under `contracts/stage1_vendor_identity/`, advancing `contract_set_version` by a minor bump from `1.2.0` to `1.3.0` with a corresponding `AMENDMENTS.md` entry.
- **Q15 — Semantic-quality corpus root path** (FR-026, FR-027): Q: What is the path of the separate semantic-quality corpus root? → A: **`tests/stage1_semantic_quality/`** (parallel to `tests/stage1_vendor_identity/`).
- **Q16 — Raw currency-token evaluation order** (FR-009, FR-010): Q: Does FR-010 run before or after punctuation-stripping normalization? → A: **Before normalization.** Currency-shape checks operate on raw observed OCR token text from `preprocess_output.json` before FR-009 punctuation stripping. FR-009 normalization remains the comparison rule for missing-content, row-text coverage, and row anchoring.
- **Q17 — Check ordering and short-circuiting** (FR-014, FR-015, FR-016): Q: Can the gate stop after the first failed check? → A: **No short-circuiting.** For every sidecar row, the gate evaluates every applicable check and records failures in deterministic order: `malformed-currency-shape`, `missing-required-content`, `row-text-coverage-gap`, then `row-alignment-failure`.
- **Q18 — Failed-check category boundaries** (FR-009, FR-011, FR-012, FR-015): Q: How are overlapping row defects attributed? → A: **Predicate-based attribution.** Missing-required-content means an authored cell value is absent from the full observed body OCR after normalization; row-text-coverage-gap means authored required row-text tokens are absent from the full observed body OCR after normalization; row-alignment-failure means required content is present somewhere but cannot be reconstructed in the row's anchored span, order, or grouping; malformed-currency-shape means a raw currency-position token exists but fails the canonical money regex. A row may record more than one failed category when more than one predicate is true.
- **Q19 — Aggregate semantic metrics** (FR-018): Q: Which run-summary metrics are required? → A: **Enumerated namespace.** New reports carry a `semantic_table_quality_metrics` object with integer counts for applicable, not-applicable, evaluable, passed, failed, and unevaluable documents; a nullable pass rate over evaluable documents; and failed-check counts by category. They also carry per-document semantic status entries for the run scope.
- **Q20 — `semantic_table_quality_passed` value domain** (FR-025): Q: What does the field contain for failed, unevaluable, and not-applicable cases? → A: **Boolean or null.** `document_pass_fail.semantic_table_quality_passed` is `true` only for semantic status `passed`, `false` for `failed` and `unevaluable`, and `null` for `not applicable`. The string status is reported separately as `semantic_table_quality.status` and in run-summary per-document entries.
- **Q21 — Degraded-body fixture status** (FR-026): Q: Is `inv_024_hard_degraded_body` promoted as committed scored corpus data in this feature? → A: **No.** The named degraded-body folders remain calibration evidence only. US2 uses a committed synthetic semantic-quality fixture under `tests/stage1_semantic_quality/`, derived from the observed failure pattern, unless a later dataset-amendment change explicitly promotes real degraded-body samples.
- **Q22 — Observed body-OCR selection rule** (FR-007, FR-009, FR-010, FR-011, FR-012): Q: Which subset of `preprocess_output.json` counts as the "observed body OCR evidence" the gate searches? → A: **All page OCR text minus the page-1 header band.** "Observed body OCR evidence" is every OCR line and token on every page of `preprocess_output.json` EXCEPT the feature-020 page-1 header-band region. This selection is lane-robust — it applies identically to OCR-only-lane and PPStructureV3 `preprocess_output.json` artifacts and does NOT depend on table-block detection (which is unreliable on the degraded invoices the gate targets).
- **Q23 — Noncanonical-folder recognition rule** (FR-027, US5, SC-009): Q: How does the validator decide a folder is calibration vs a scored corpus folder? → A: **Canonical-pattern allowlist.** A folder is a scored corpus folder ONLY when its name fully matches the canonical `inv_NNN_<difficulty>` pattern (`^inv_\d{3}_(easy|medium|hard)$`, using the closed difficulty vocabulary defined in `dataset-layout.md`). Every non-matching name — including any extra suffix such as `inv_024_hard_degraded_body` — is calibration / test-fixture material. The rule is default-exclude: an unrecognized name is never silently scored.
- **Q24 — "Earliest observed-OCR position" definition** (FR-012, FR-014): Q: What ordering does the FR-012 row-anchor tie-break "earliest observed-OCR position" refer to? → A: **`preprocess_output.json` serialization order.** "Earliest" is the lowest index in the artifact's own ordering — page array order, then line/token array order within each page, exactly as serialized in `preprocess_output.json`. No geometry computation and no coordinate tolerance is used.
- **Q25 — Synthetic US2 fixture composition** (FR-026, US2): Q: What does the committed synthetic US2 fixture folder under `tests/stage1_semantic_quality/` contain? → A: **Hand-authored `preprocess_output.json` + `semantic_table_truth.json`, no `source.pdf`.** The fixture folder commits a hand-authored, schema-valid `preprocess_output.json` that reproduces the degraded-body pattern (high mean detector confidence, materially wrong rows) and the matching authored sidecar. It contains NO `source.pdf` and is NOT generated by running the preprocessing pipeline — keeping the fixture deterministic, CPU-only, and free of any Paddle/GPU dependency.
- **Q26 — Verdict status enum string values** (FR-016, FR-017, FR-018, FR-025): Q: What are the canonical JSON string values for the verdict status set? → A: **snake_case.** The four canonical JSON enum values are `passed`, `failed`, `not_applicable`, and `unevaluable`, used verbatim wherever a semantic status is serialized (`semantic_table_quality.status` and the run-summary per-document `semantic_table_quality_status`). This matches the repo's existing status/decision enum precedent (`edge_accept` / `edge_review_required` in `routing_decision.json`). The four failed-check category labels remain kebab-case as already fixed by Clarifications Q17/Q18 (`malformed-currency-shape`, `missing-required-content`, `row-text-coverage-gap`, `row-alignment-failure`).

### Session 2026-05-23

- **Q27 — Sidecar top-level envelope shape** (FR-002): Q: What is the top-level shape of `semantic_table_truth.json`? → A: **`{document_id, rows[], schema_version?}`.** `schema_version` is an optional string (e.g. `"1.3.0"`); when absent, the governed contract set remains authoritative.
- **Q28 — Row-text representation** (FR-002, FR-011): Q: Is the row-text field a single string or an array of fragments? → A: **Array.** Required row text is represented as a non-empty array field `required_row_text_tokens`, each item a non-empty string. These tokens drive the FR-011 binary row-text-coverage check.
- **Q29 — `failed_checks` vs `row_reasons` structural relationship** (FR-015, FR-017): Q: How are the two keys related? → A: **Two-view.** `failed_checks` is the flat ordered array of full failed-check records (FR-015 fields, FR-015 ordering) and remains the source of truth. `row_reasons` is a per-row aggregation keyed by `row_id`, derived from `failed_checks`, containing that row's failed-category set plus a short human-readable reason. Both are required when status is `failed`. (Field names pinned at landing per the 2026-05-23 F1+F2 remediation: `row_reasons` is a JSON object keyed by `row_id` whose values are `{categories, reason}` — see FR-017 and `contracts/module-invariants.md` MI-14.)
- **Q30 — OCR-confidence placement in the report** (FR-013, FR-017): Q: Where in the JSON do OCR confidence values live? → A: **Document-aggregate only.** Confidence is recorded only on `semantic_table_quality.supporting_evidence` as the closed shape `{body_confidence_mean, body_confidence_min, body_line_count, body_token_count, header_band_excluded}`. No per-row or per-failed-check confidence field is added.
- **Q31 — `unevaluable` cause vocabulary** (FR-016, FR-017): Q: Is the `unevaluable` cause a closed enum or free text? → A: **Closed enum + free-text detail.** The semantic_table_quality object carries a `cause` field constrained to the closed enum {`preprocess_output_missing`, `preprocess_output_invalid_json`, `preprocess_output_schema_invalid`, `body_ocr_unreadable`} and an optional free-text `cause_detail` string. Required when `status == unevaluable`.
- **Q32 — FR-009 punctuation-stripping Unicode category set** (FR-009): Q: Which Unicode categories does FR-009 strip? → A: **All `P*` categories.** After NFKC normalization, strip every code point whose Unicode general category begins with `P`: `Pc`, `Pd`, `Pe`, `Pf`, `Pi`, `Po`, and `Ps`.
- **Q33 — Comparison granularity** (FR-009, FR-011, FR-012): Q: Does the gate match per-line or against a single concatenation? → A: **Single normalized concatenation.** Build one body-OCR search string by joining every body-OCR line on every page in `preprocess_output.json` serialization order (Q24) with a single ASCII space, then apply the FR-009 normalization pipeline once. All "found anywhere" checks operate against that one normalized string.
- **Q34 — Byte-identical serialization conventions** (FR-014, SC-007): Q: What JSON serialization conventions are locked? → A: **Sorted keys + fixed-precision numeric floats.** Sorted keys at every nesting level; UTF-8 encoding; LF line endings; trailing newline at EOF; no trailing whitespace. Derived ratios/confidence values are rounded to 6 decimal places using round-half-to-even and emitted as **fixed-precision JSON numbers (not strings)**, preserving numeric schema types. Integer counts remain JSON numbers.
- **Q35 — Currency-position-token identification** (FR-010): Q: How does the gate locate the candidate raw token for the currency-shape check? → A: **Digit-sequence match per declared field.** Within the row's anchored OCR span, scan raw tokens in Q24 order for the first unmatched token whose digit sequence equals the expected `unit_price` or `amount` digit sequence after removing punctuation and currency symbols. Evaluate the canonical money regex against THAT raw token. If no candidate exists for a declared currency field, the failure is `missing-required-content`, NOT `malformed-currency-shape`. Per-field digit-sequence matching prevents misclassifying quantity tokens as currency tokens.
- **Q36 — `semantic_table_quality_metrics` location** (FR-018): Q: Where does the new metrics namespace sit in the run summary? → A: **Top-level sibling** in `evaluation_run_summary.json`, parallel to existing vendor-identity / feature-020 fields.
- **Q37 — `supporting_evidence` shape pinned** (FR-017): Q: Is the `supporting_evidence` shape pinned at landing? → A: **Yes, closed shape.** `{body_confidence_mean: float, body_confidence_min: float, body_line_count: int, body_token_count: int, header_band_excluded: bool}` (numeric confidence values, integer counts, boolean header-band flag).
- **Q38 — Explicit Out-of-Scope additions** (Out of Scope): Q: Are the absences of performance and configuration requirements intentional? → A: **Yes — explicitly out of scope.** Add two Out-of-Scope bullets: (a) Performance / latency / throughput targets — the gate is a deterministic in-memory comparison with no NFR target this feature; (b) New configuration surface — no CLI flags, environment variables, config files, or tunable thresholds (consistent with Clarifications Q13).
- **Q39 — Sidecar handling for calibration folders** (FR-027, FR-018): Q: What does the gate do when a noncanonical (calibration) folder has a sidecar? → A: **Gate runs, scored aggregation excludes.** The gate runs on the sidecar and writes per-document `semantic_table_quality` plus per-document semantic status; however the document is EXCLUDED from `semantic_table_quality_metrics` aggregation in `evaluation_run_summary.json`.
- **Q40 — Semantic-quality corpus subfolder pattern** (FR-026): Q: What is the canonical subfolder name pattern under the new corpus root? → A: **Same `inv_NNN_<difficulty>` pattern** as `tests/stage1_vendor_identity/`, with the closed difficulty vocabulary `easy`/`medium`/`hard`. The Q23 allowlist (`^inv_\d{3}_(easy|medium|hard)$`) applies uniformly to both roots; the synthetic US2 fixture lands at e.g. `tests/stage1_semantic_quality/inv_001_hard/`.
- **Q41 — Validator error message content** (FR-003, FR-004): Q: Is the validator's error content pinned? → A: **Yes.** A `document_id`-mismatch error MUST name both the declared `document_id` and the containing folder basename. A row-violation error MUST name the offending `row_id` (or the row-array index when `row_id` cannot be parsed), the specific failed field, and a one-line machine-readable reason.
- **Q42 — Validator-time vs gate-time error boundary** (FR-016): Q: A sidecar that passes the validator but produces an invariant violation at gate-time — hard error or `unevaluable`? → A: **Hard error.** Gate-time invariant violations cause the run to fail; semantic status is NOT recorded as `unevaluable` (which is reserved for unreadable INPUT files) and the document is excluded from semantic metrics.
- **Q43 — Pre-feature `document_pass_fail` reading** (FR-019): Q: How is an absent `document_pass_fail.semantic_table_quality_passed` field interpreted when reading a pre-feature `evaluation_document.json`? → A: **Treated as `null`.** Absence means "the semantic gate did not run on this document"; the artifact remains valid against the post-feature schema (FR-019 read-tolerance).
- **Q44 — PII screening applicability to the new corpus root** (FR-026): Q: Does `labeling-guide.md`'s PII / license pre-inclusion screening apply to `tests/stage1_semantic_quality/`? → A: **Yes — identical screening.** The same `labeling-guide.md` PII/license pre-inclusion screening applies to both corpus roots. The Q25 synthetic fixture carries no real PII by construction, but any future committed fixture under `tests/stage1_semantic_quality/` MUST pass the same screening.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Author and validate the semantic table truth sidecar (Priority: P1)

A fixture author has a degraded invoice document whose table body OCR is known to be unreliable. They author an optional `semantic_table_truth.json` file in that document's per-document folder, recording the true table/body row content. The validator accepts the sidecar only when it is internally consistent — its `document_id` matches the folder, and every row conforms to the semantic table truth contract. The sidecar is independent of `expected.json`: `expected.json` keeps its current vendor-identity-only meaning, and a folder without a sidecar continues to validate and evaluate exactly as it does today.

**Why this priority**: The sidecar is the authored truth surface every other part of the feature consumes. Without a validated truth contract, the gate has nothing deterministic to compare observed OCR against. It is foundational and independently testable.

**Independent Test**: Author a `semantic_table_truth.json` for one degraded-body fixture; run the validator and confirm it accepts a well-formed sidecar, rejects one whose `document_id` mismatches the folder, and rejects one whose rows violate the contract. Confirm a folder with no sidecar still validates under the existing `expected.json` contract with no new requirement.

**Acceptance Scenarios**:

1. **Given** a per-document folder that contains a well-formed `semantic_table_truth.json` whose `document_id` matches the folder, **When** the validator runs, **Then** the sidecar is accepted and its rows are available to the semantic quality gate.
2. **Given** a per-document folder whose `semantic_table_truth.json` declares a `document_id` that does not match the folder name, **When** the validator runs, **Then** the sidecar is rejected with an error naming the mismatch.
3. **Given** a per-document folder whose `semantic_table_truth.json` contains a row that violates the row-truth contract, **When** the validator runs, **Then** the sidecar is rejected with an error identifying the offending row.
4. **Given** a per-document folder with no `semantic_table_truth.json`, **When** the validator runs, **Then** vendor-identity validation continues under the existing `expected.json` contract and no table/body truth is required.
5. **Given** any per-document folder, **When** the feature lands, **Then** `expected.json` retains its current vendor-identity-only shape and meaning — table/body truth is never written into `expected.json`.

### User Story 2 - Deterministically evaluate semantic/table OCR quality (Priority: P1)

An evaluation owner runs the semantic quality gate against a document that has a `semantic_table_truth.json` sidecar. The gate reads the observed body OCR from `preprocess_output.json` and the authored row truth from the sidecar, and produces a deterministic verdict. It records concrete failed checks — a required row value that cannot be found in the observed body OCR, a malformed currency shape such as `$21:00` where `$21.00` is expected, a row text coverage gap, and row-alignment failure evidence. OCR detector confidence is recorded only as supporting evidence; a high-confidence row that fails a content check still fails. The same inputs always produce the same verdict.

**Why this priority**: This is the core of the feature — the deterministic gate that catches confidently-wrong table/body OCR that features 019/020/021 do not detect. It is the reason the feature exists.

**Independent Test**: Run the gate on a committed synthetic semantic-quality fixture under `tests/stage1_semantic_quality/` — a hand-authored, schema-valid `preprocess_output.json` plus its matching `semantic_table_truth.json`, with no `source.pdf` and not produced by a preprocessing run — whose `preprocess_output.json` reproduces the degraded-body failure pattern: high mean OCR confidence (the `inv_024_hard_degraded_body` calibration evidence shows body confidence mean ≈ 0.97) but materially wrong table rows. Confirm the verdict is "failed", that it names at least one concrete failed check, and that re-running on the same inputs yields a byte-identical semantic verdict object. The named `inv_024_hard_degraded_body` sample remains calibration evidence only unless separately promoted through the corpus amendment path.

**Acceptance Scenarios**:

1. **Given** a sidecar row whose expected amount is decimal currency `$21.00` and observed body OCR that contains `$21:00`, **When** the gate runs, **Then** the verdict records a failed currency-shape check for that row even though OCR confidence is high.
2. **Given** a sidecar row that declares required quantity, description, unit-price, or amount content that cannot be found in the observed body OCR evidence, **When** the gate runs, **Then** the verdict records a failed missing-required-content check naming that row.
3. **Given** observed body OCR that omits, shifts, or splits a row's values such that the row cannot be deterministically reconstructed against the sidecar, **When** the gate runs, **Then** the verdict records row-alignment failure evidence for that row.
4. **Given** a row whose expected text is only partially present in the observed body OCR, **When** the gate runs, **Then** the verdict records a failed row-text-coverage check for that row.
5. **Given** observed body OCR with high mean detector confidence but failing row content checks, **When** the gate runs, **Then** the verdict remains "failed" and OCR confidence is recorded only as supporting evidence — it cannot make a failing row pass.
6. **Given** identical `preprocess_output.json` and `semantic_table_truth.json` inputs, **When** the gate runs twice, **Then** both runs produce a byte-identical verdict, failed-check set, and row-level reasons.
7. **Given** any gate run, **When** the verdict is produced, **Then** no model is called, no network I/O is performed, and the verdict depends only on the two input files.

### User Story 3 - Surface semantic table quality in evaluator reports (Priority: P2)

A reviewer reads the evaluator output to understand a corpus run. For each document that has semantic table truth, the per-document `evaluation_document.json` carries a `semantic_table_quality` object with the verdict status, the failed checks, and row-level reasons. The run-level `evaluation_run_summary.json` carries aggregate semantic-quality metrics and per-document semantic status. These fields are distinct from vendor-identity scoring — they never change the meaning or values of existing vendor-identity metrics. Existing evaluation reports that predate this feature remain readable: the new fields are optional and additive.

**Why this priority**: Without a report surface, the gate's verdict is not visible to a reviewer and cannot inform a whole-invoice/table-quality claim. It depends on US2 producing a verdict.

**Independent Test**: Run the evaluator over a corpus containing at least one document with a sidecar and at least one without. Confirm `evaluation_document.json` for the sidecar document includes `semantic_table_quality` with status + failed checks + row reasons; confirm the document without a sidecar reports semantic status `not_applicable`; confirm `evaluation_run_summary.json` includes the enumerated aggregate semantic metrics and per-document semantic status entries; confirm an existing pre-feature report still loads without error.

**Acceptance Scenarios**:

1. **Given** the evaluator processes a document that has `semantic_table_truth.json`, **When** the per-document report is written, **Then** `evaluation_document.json` includes a `semantic_table_quality` object with the verdict status, failed checks, and row-level reasons.
2. **Given** the evaluator processes a corpus where only some documents have semantic table truth, **When** the run summary is written, **Then** `evaluation_run_summary.json` reports semantic quality metrics for the applicable documents and leaves vendor-identity pass rates comparable to prior runs.
3. **Given** an `evaluation_document.json` or `evaluation_run_summary.json` produced before this feature (without semantic fields), **When** the report schema validates it, **Then** the report is still accepted as valid.
4. **Given** any evaluator run, **When** semantic quality fields are written, **Then** the meaning and values of existing vendor-identity metrics — including `document_pass_fail.vendor_identity_passed` — are unchanged.

### User Story 4 - Preserve vendor-identity behavior and gate whole-invoice claims (Priority: P1)

A pipeline developer must be certain that adding the semantic gate does not regress the shipped MVP. Feature 019 OCR-only fallback behavior, feature 020 vendor-identity evidence-gate behavior and run-summary fields, feature 021 GPU MVP promotion criteria, and `document_pass_fail.vendor_identity_passed` all behave exactly as before. Separately, when a document has semantic truth and the semantic gate fails, any whole-invoice or table-quality pass claim must fail or require review even if vendor identity passed. When a document has no semantic truth, semantic table quality is reported as "not applicable" — never inferred as a pass from vendor-identity metrics.

**Why this priority**: Non-regression of the shipped vendor-identity MVP is a hard release gate. A feature that silently alters feature 019/020/021 behavior is unacceptable regardless of how good the new gate is.

**Independent Test**: Run the existing 20-document vendor-identity corpus before and after the feature lands; confirm vendor-identity pass/fail, feature 020 run-summary fields, and `vendor_identity_passed` values are identical. Separately, confirm a document with a failing semantic gate but passing vendor identity reports `document_pass_fail.semantic_table_quality_passed: false`, and a document with no sidecar reports semantic status `not_applicable` with `document_pass_fail.semantic_table_quality_passed: null`.

**Acceptance Scenarios**:

5. **Given** a document with no `semantic_table_truth.json`, **When** the evaluator reports semantic table quality, **Then** it reports "not applicable" and never infers a semantic pass from vendor-identity metrics.
6. **Given** feature 019 OCR-only fallback (FR-005) and feature 021 GPU MVP promotion criteria, **When** the feature lands, **Then** neither is rewritten in place and both behave as before.

### Edge Cases

- **Sidecar present but `preprocess_output.json` missing or unreadable**: the gate cannot evaluate; it records semantic status "unevaluable" with a named cause rather than silently passing or silently failing, and `document_pass_fail.semantic_table_quality_passed` is `false`.
- **Sidecar present but observed body OCR is empty**: every required-content check fails; the verdict is "failed" with missing-required-content reasons for all rows — empty OCR is not a pass.
- **Sidecar declares zero rows**: treated as a contract violation by the validator (a semantic truth sidecar with no row truth has no purpose); the validator rejects it.
- **Currency value with a genuinely correct decimal point** (`$21.00` observed for `$21.00` expected): the currency-shape check passes for that row — the check flags malformed shapes, not all currency.
- **A row's expected text legitimately appears in the OCR but in a different reading order**: row-alignment evidence must distinguish "present but unaligned" from "absent" so the failed-check category is accurate.
- **A currency token looks malformed only before normalization**: the currency-shape check uses the raw observed OCR token before punctuation stripping; normalized matching cannot erase a colon-for-decimal or truncated-cents failure.
- **Document has both a sidecar AND insufficient vendor-identity evidence**: the two verdicts are independent — vendor identity may fail and semantic quality may also fail; neither overrides the other.
- **Semantic gate fails but the run is explicitly a vendor-identity-only run**: vendor-identity acceptance is not blocked; the semantic failure is reported on its own surface (it does not retroactively fail vendor identity).
- **An existing v1.2 evaluation report is re-read after the feature lands**: it remains valid; absence of `semantic_table_quality` is interpreted as "semantic gate did not run", not as a failure.
- **A noncanonical degraded-body folder is accidentally pointed at a scored corpus run**: the validator/docs treat it as calibration material and exclude it from scored aggregation rather than scoring it.

## Requirements *(mandatory)*

### Functional Requirements

**Semantic table truth sidecar contract**

- **FR-001**: The system MUST support an optional per-document `semantic_table_truth.json` file, authored by a fixture author, that is separate from `expected.json` and carries the table/body row truth consumed by the semantic quality gate.
- **FR-002**: The system MUST define a row-truth contract for `semantic_table_truth.json`. The sidecar's top-level shape is `{document_id, rows[], schema_version?}` where `schema_version` is an optional string (e.g. `"1.3.0"`); when absent, the governed contract set remains authoritative (Clarifications Q27). The minimum row shape for the first gate is **required values plus row text** (Clarifications Q2): each row MUST support `row_id`, `quantity`, `description`, `unit_price`, `amount`, and `required_row_text_tokens` — a non-empty array of non-empty token strings used by the FR-011 binary row-text-coverage check (Clarifications Q28). Of these, **only `row_id` and `required_row_text_tokens` are mandatory** in every row; `quantity`, `description`, `unit_price`, and `amount` are optional, and every one of those fields that IS present becomes a required-content check for that row (Clarifications Q8). `row_id` MUST be a non-empty string and MUST be unique within the sidecar (Clarifications Q11). Additionally, `row_id` MUST match the safety pattern `^[A-Za-z0-9_-]{1,64}$` (per security-clarify Q-SEC-2/B) — alphanumeric + dash/underscore, ≤64 chars; the pattern rejects path-traversal sequences, control characters, whitespace, punctuation-heavy PII-style labels, and runaway identifier lengths without being onerous to authors. `unit_price` and `amount`, when present, MUST be authored as **normalized decimal strings without a currency symbol** — e.g. `"21.00"` (Clarifications Q9). Approximate row-region anchors are explicitly NOT part of the first required row shape — they remain optional future metadata and MUST NOT be required by the validator for the first gate.
- **FR-003**: The `semantic_table_truth.json` sidecar MUST declare a `document_id`, and the validator MUST accept the sidecar only when that `document_id` matches the per-document folder it lives in. When the validator rejects a sidecar for a `document_id` mismatch, the error message MUST name both the declared `document_id` value and the containing folder basename (Clarifications Q41). Additionally, `document_id` MUST match the safety pattern `^[A-Za-z0-9_-]{1,64}$` (per security-clarify Q-SEC-2/B); the canonical fixture-folder pattern `^inv_\d{3}_(easy|medium|hard)$` (Q23 / MI-21) is a strict subset of this safety pattern, so existing names are unaffected.
- **FR-004**: The validator MUST accept a `semantic_table_truth.json` sidecar only when every row conforms to the row-truth contract and all `row_id` values in the sidecar are unique, and MUST reject it with a row-identifying error otherwise. Row-violation errors MUST name the offending `row_id` (or the row-array index when `row_id` cannot be parsed), the specific failed field, and a one-line machine-readable reason (Clarifications Q41).
- **FR-005**: When a per-document folder contains no `semantic_table_truth.json`, vendor-identity validation and evaluation MUST continue under the existing `expected.json` contract with no new requirement.
- **FR-006**: `expected.json` MUST remain the vendor-identity truth file with its current shape and meaning. Table/body truth MUST NOT be written into `expected.json` unless a later clarification explicitly changes that decision.

**Deterministic semantic quality checks**

- **FR-007**: The system MUST evaluate semantic table quality deterministically from `preprocess_output.json` and `semantic_table_truth.json` when the sidecar is present. The gate MUST run automatically inside the existing evaluator whenever a per-document folder contains `semantic_table_truth.json` — the sidecar's presence is itself the opt-in, and no new CLI flag or separate command is introduced (Clarifications Q13). The gate's input from `preprocess_output.json` is the **observed body OCR evidence**: every OCR line and token on every page EXCEPT the feature-020 page-1 header-band region. This selection MUST be lane-robust — it applies identically to OCR-only-lane and PPStructureV3 `preprocess_output.json` artifacts and MUST NOT depend on table-block detection (Clarifications Q22).
- **FR-008**: The semantic gate MUST NOT call a model, MUST NOT perform network I/O, and MUST NOT use OCR detector confidence as proof of correctness.
- **FR-009**: The semantic gate MUST record a failed missing-required-content check for a row when a required value declared by the sidecar cannot be found anywhere in the **normalized body-OCR search string**. The body-OCR search string is constructed once per document by joining every body-OCR line on every page in `preprocess_output.json` serialization order (Clarifications Q24) with a single ASCII space, then applying the FR-009 normalization pipeline once; all "found anywhere" checks (FR-009, FR-011, FR-012) operate against that one normalized string (Clarifications Q33). "Found" MUST be determined by a **normalized exact comparison**: Unicode NFKC normalization, Python `str.casefold()` case-folding, collapse of all Unicode whitespace to a single ASCII space, and stripping of all Unicode punctuation — every code point whose Unicode general category begins with `P` (`Pc`, `Pd`, `Pe`, `Pf`, `Pi`, `Po`, `Ps`) after NFKC — applied identically to both the sidecar value and the body-OCR search string (Clarifications Q32). For scalar cell values, exact containment means the full normalized sidecar value appears as a contiguous substring in the normalized body-OCR search string. For `required_row_text_tokens`, exact containment means every required normalized token appears as a substring in the normalized body-OCR search string. No fuzzy similarity or edit-distance threshold is used (Clarifications Q5, Q16, Q18, Q32, Q33).
- **FR-010**: The semantic gate MUST record a failed currency-shape check for a row when an expected decimal currency value appears in the observed body OCR as a malformed shape. Currency-shape evaluation MUST use the **raw observed OCR token text before FR-009 punctuation stripping or other comparison normalization**. A currency-position token is evaluated only for rows that declare `unit_price` or `amount`. For each declared currency field, the candidate raw token MUST be identified by scanning raw tokens within the row's anchored OCR span in `preprocess_output.json` serialization order (Clarifications Q24) and selecting the first not-yet-matched raw token whose **digit sequence** — its raw text with all punctuation and currency symbols removed — equals the expected field's digit sequence (with punctuation and symbols similarly removed). Per-field digit-sequence matching prevents misclassifying a quantity token as a currency token (Clarifications Q35). If no candidate raw token exists for a declared currency field, the failure category MUST be `missing-required-content`, NOT `malformed-currency-shape`. A matched currency-position token is **malformed when it fails the anchored canonical money regex `^\$?\d{1,3}(,\d{3})*\.\d{2}$`** — this flags colon-for-decimal shapes (e.g. `$21:00`) and truncated values (e.g. `$22:`) while accepting correctly-shaped decimals (Clarifications Q10, Q16, Q18, Q35). Expected `unit_price`/`amount` truth is authored as a normalized decimal string without a currency symbol (FR-002 / Clarifications Q9).
- **FR-011**: The semantic gate MUST record a failed row-text-coverage check for a row when the observed body OCR covers only part of the row's expected text. Coverage is **binary**: any required/expected row-text token absent anywhere from the observed body OCR (under the normalized comparison of FR-009) constitutes a row-text-coverage gap; no numeric coverage threshold is applied. A coverage ratio MAY be recorded as supporting evidence but MUST NOT be the trigger (Clarifications Q6, Q18).
- **FR-012**: The semantic gate MUST record row-alignment failure evidence for a row when required row content is present somewhere in the observed body OCR but is shifted, out of order, or split such that the row cannot be deterministically reconstructed within the row's anchored span. Each sidecar row MUST be anchored to observed body OCR by the **best normalized exact match (FR-009) of its description / row text**; "best" means the candidate containing the most required normalized row-text tokens, not fuzzy edit distance. The gate then verifies the row's required values are present, in order, and not split across incompatible spans. When candidate anchors tie, the tie MUST be broken deterministically by earliest observed-OCR position — defined as the lowest index in `preprocess_output.json`'s own serialization order (page array order, then line/token array order within each page; no geometry computation and no coordinate tolerance) — then by sidecar declaration order (Clarifications Q7, Q18, Q24).
- **FR-013**: The semantic gate MUST record OCR detector confidence as supporting evidence only. A high-confidence row that fails a content check MUST still fail; confidence MUST NOT promote a failing row to a pass. OCR detector confidence MUST be recorded ONLY as document-aggregate supporting evidence on `semantic_table_quality.supporting_evidence`; the gate MUST NOT add per-row or per-failed-check confidence fields (Clarifications Q30).
- **FR-014**: The semantic gate verdict MUST be deterministic and reproducible — identical `preprocess_output.json` and `semantic_table_truth.json` inputs MUST yield a byte-identical semantic verdict object, failed-check set, failed-check ordering, and row-level reasons. Stable JSON serialization for newly written semantic outputs MUST be: sorted keys at every nesting level, UTF-8 encoding, LF line endings, a trailing newline at EOF, and no trailing whitespace. Derived ratios and confidence values MUST be rounded to 6 decimal places using round-half-to-even and emitted as fixed-precision JSON numbers (not strings), preserving numeric schema types. Integer counts remain JSON numbers (Clarifications Q34).
- **FR-015**: Every recorded failed check MUST identify which check category failed and which row it applies to, with enough evidence for a reviewer to understand the cause without re-running the gate. Each failed-check record MUST include `category`, `row_id`, the applicable sidecar field or row-text token, the expected value/text, the observed raw token or normalized absence/alignment finding, and the check predicate that was applied. Failed checks MUST be recorded in sidecar row declaration order, then in this check-category order: `malformed-currency-shape`, `missing-required-content`, `row-text-coverage-gap`, `row-alignment-failure`. The gate MUST NOT short-circuit after the first failure (Clarifications Q17, Q18). The `failed_checks` flat ordered array on `semantic_table_quality` is the source of truth for recorded failures; `row_reasons` is a per-row aggregation derived from it (Clarifications Q29).
- **FR-016**: The semantic gate MUST produce one of a closed set of verdict statuses for a document, serialized as these four canonical lowercase snake_case JSON strings: `passed`, `failed`, `not_applicable` (no sidecar), or `unevaluable` (sidecar present but inputs missing/unreadable). These literal values MUST be used verbatim wherever a semantic status is serialized — `semantic_table_quality.status` and the run-summary per-document `semantic_table_quality_status` (Clarifications Q26). The verdict MUST be aggregated by an **any-fail rule** after all applicable checks have been evaluated: a document is `failed` if any row records any failed check, and `passed` only when zero failed checks are recorded across all rows. `unevaluable` is a separate status for unreadable/missing inputs and is not a passing result. There are no per-category severity tiers and no weighted/threshold score (Clarifications Q4, Q17, Q26). Gate-time invariant violations — a sidecar that passes the validator but produces an internal-invariant violation during gate evaluation — MUST be hard errors: the run fails, the document MUST be excluded from semantic metrics, and the status MUST NOT be recorded as `unevaluable` (which is reserved for unreadable INPUT files) (Clarifications Q42).

**Semantic quality evaluator report surface**

- **FR-017**: Newly written `evaluation_document.json` artifacts MUST include `document_pass_fail.semantic_table_quality_passed` for every processed document. When the document has `semantic_table_truth.json`, `evaluation_document.json` MUST also include a `semantic_table_quality` object whose required keys are: `status` (the Q26 enum value), `failed_checks` (flat ordered array of full failed-check records — FR-015 fields, FR-015 ordering — source of truth), `row_reasons` (JSON **object** keyed by `row_id` — NOT an array — derived from `failed_checks`, where each value is the closed record `{categories: array of kebab-case failed-category labels in the fixed Q17 order, reason: short one-line human-readable summary string}`; required when `status == failed`; pinned by `contracts/evaluator-output-contract.md` §`semantic_table_quality` and `contracts/schema-amendments.md` `evaluation_document.schema.json` `row_reasons` definition), and `supporting_evidence` (the closed shape `{body_confidence_mean: float, body_confidence_min: float, body_line_count: int, body_token_count: int, header_band_excluded: bool}`). When `status == unevaluable`, the object MUST also include `cause` (constrained to the closed enum {`preprocess_output_missing`, `preprocess_output_invalid_json`, `preprocess_output_schema_invalid`, `body_ocr_unreadable`}) and an optional free-text `cause_detail` string (Clarifications Q29, Q30, Q31, Q37). When the sidecar is absent, `semantic_table_quality` MAY be omitted, but semantic status MUST be represented as `not_applicable` in the run-summary per-document status and `document_pass_fail.semantic_table_quality_passed` MUST be `null`.
- **FR-018**: Newly written `evaluation_run_summary.json` artifacts MUST include a distinct `semantic_table_quality_metrics` namespace as a **top-level sibling key** parallel to the existing vendor-identity and feature-020 fields (Clarifications Q36), plus per-document semantic status entries for the current run scope. Documents whose folder is calibration material (FR-027) MUST appear in the per-document semantic status entries but MUST be EXCLUDED from the `semantic_table_quality_metrics` aggregate counts and pass rate (Clarifications Q39). `semantic_table_quality_metrics` MUST include these fields: `semantic_applicable_document_count` (integer count of processed documents with a sidecar), `semantic_not_applicable_document_count` (integer count without a sidecar), `semantic_evaluable_document_count` (integer count of `passed` + `failed` semantic statuses), `semantic_passed_document_count` (integer), `semantic_failed_document_count` (integer), `semantic_unevaluable_document_count` (integer), `semantic_table_quality_pass_rate` (number in [0,1] computed as passed / evaluable, or `null` when evaluable is 0), and `semantic_failed_check_counts` (object with integer counts for `malformed-currency-shape`, `missing-required-content`, `row-text-coverage-gap`, and `row-alignment-failure`). Per-document status entries MUST appear under the top-level sibling key **`semantic_document_statuses`** (a JSON array, parallel to `semantic_table_quality_metrics` — NOT nested inside it; pinned by `contracts/evaluator-output-contract.md` §`semantic_document_statuses` and `contracts/schema-amendments.md` §`evaluation_run_summary.schema.json`). Each entry MUST include `document_id`, `semantic_table_quality_status`, and `semantic_table_quality_passed`, sorted by the evaluator's deterministic run-document order (Clarifications Q19, Q20).
- **FR-019**: The evaluation report schemas MUST remain tolerant of existing reports that do not contain the semantic-quality fields — pre-feature `evaluation_document.json` / `evaluation_run_summary.json` artifacts MUST still validate. This backward-compatibility requirement applies to reading and validating older reports; it does NOT permit the new writer to omit required semantic fields from newly generated reports when the feature is active. When reading a pre-feature `evaluation_document.json`, an absent `document_pass_fail.semantic_table_quality_passed` field MUST be interpreted as `null` — semantically "the semantic gate did not run on this document" (Clarifications Q43).
- **FR-020**: Semantic table quality MUST be exposed separately from vendor-identity scoring. Adding the semantic fields MUST NOT change the meaning or values of any existing vendor-identity metric.

### Key Entities

- **Semantic Table Truth Sidecar** (`semantic_table_truth.json`): an optional, per-document, authored truth file separate from `expected.json`. Top-level shape is `{document_id, rows[], schema_version?}` — `schema_version` is an optional string (e.g. `"1.3.0"`) and the governed contract set remains authoritative when absent (Clarifications Q27). Present only for documents that have authored table/body truth.
- **Semantic Table Row Truth**: one expected table/body row within the sidecar. Per Clarifications Q2 the first-gate row shape supports `row_id`, `quantity`, `description`, `unit_price`, `amount`, and `required_row_text_tokens` (a non-empty array of non-empty token strings — Clarifications Q28). `row_id` (non-empty string, unique within the sidecar) and `required_row_text_tokens` are mandatory; `quantity`, `description`, `unit_price`, and `amount` are optional, and `unit_price`/`amount` are authored as normalized decimal strings without a currency symbol (Clarifications Q8, Q9, Q11). Approximate row-region anchors are optional future metadata and are not part of the first required shape.
- **Observed Body OCR Evidence**: the OCR lines, tokens, and per-line detector confidence read from `preprocess_output.json` for the document under evaluation — specifically every page's OCR content EXCEPT the feature-020 page-1 header-band region (Clarifications Q22). The input the gate compares against the sidecar truth. The selection rule is lane-robust and does not depend on table-block detection.
- **Semantic Quality Verdict**: the per-document result of the gate — a status from the closed set, serialized as one of the four canonical snake_case JSON strings `passed`, `failed`, `not_applicable`, `unevaluable` (Clarifications Q26) — plus the set of failed checks, row-level reasons, and OCR confidence recorded as supporting evidence only. The status is aggregated by an any-fail rule after all checks are evaluated: `failed` if any row records any failed check, `passed` only when zero failed checks are recorded across all rows, and `unevaluable` when required inputs cannot be read (Clarifications Q4, Q17).
- **Failed Check**: one recorded failure, categorized as one of {malformed-currency-shape, missing-required-content, row-text-coverage-gap, row-alignment-failure}, with the row it applies to and the evidence behind it. Category predicates are explicit and may coexist on the same row when multiple defects are present (Clarifications Q18).
- **Semantic Quality Report Fields**: `document_pass_fail.semantic_table_quality_passed` on newly written `evaluation_document.json` artifacts, the `semantic_table_quality` object for sidecar/unevaluable documents (required keys: `status`, `failed_checks`, `row_reasons` [when `failed`], `supporting_evidence` [closed shape: body_confidence_mean, body_confidence_min, body_line_count, body_token_count, header_band_excluded], plus `cause` [closed enum] and optional `cause_detail` when `status == unevaluable` — Clarifications Q29/Q30/Q31/Q37; see **FR-017** for the post-fix pinning that `row_reasons` is a JSON object keyed by `row_id` with `{categories, reason}` values and that `body_confidence_min` is always JSON `number` never `null`), the required `semantic_table_quality_metrics` namespace as a top-level sibling on newly written `evaluation_run_summary.json` artifacts (Clarifications Q36), and per-document semantic status entries serialized under the top-level sibling array key `semantic_document_statuses` (calibration folders appear in per-document entries but are excluded from the aggregate counts — Clarifications Q39; see **FR-018** for the post-fix pinning of the `semantic_document_statuses` key name and the eight metrics field names). `semantic_table_quality_passed` is a sibling of unchanged `vendor_identity_passed` and has value domain `true`, `false`, or `null` (Clarifications Q12, Q19, Q20).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A degraded-body fixture whose observed body OCR has a high mean detector confidence (≥ 0.95, consistent with the `inv_024_hard_degraded_body` calibration evidence of ≈ 0.97) but materially wrong table rows produces a semantic quality verdict of "failed".
- **SC-002**: Every "failed" semantic verdict names at least one concrete failed check from the closed category set {missing-required-content, malformed-currency-shape, row-text-coverage-gap, row-alignment-failure}, with the specific row identified.
- **SC-003**: 100% of malformed-currency rows of the observed calibration shape (e.g. `$21:00`, `$22:` where `$21.00` / `$22.00` is expected) are flagged by the currency-shape check on raw observed OCR tokens before FR-009 punctuation stripping — i.e. any currency-position token failing `^\$?\d{1,3}(,\d{3})*\.\d{2}$`; 0% of correctly-shaped decimal currency values are flagged.
- **SC-004**: A document with semantic table truth present and a failing semantic verdict is reported with `document_pass_fail.semantic_table_quality_passed: false` in 100% of cases, even when its vendor identity passes.
- **SC-005**: A document with no `semantic_table_truth.json` is reported with semantic table quality status `not_applicable` and `document_pass_fail.semantic_table_quality_passed: null` in 100% of cases — zero documents have a semantic pass inferred from vendor-identity metrics.
- **SC-006**: Across the existing 20-document vendor-identity baseline corpus, vendor-identity pass/fail, feature 020 evidence-gate run-summary fields, and `document_pass_fail.vendor_identity_passed` values are identical before and after the feature lands (zero regressions).
- **SC-007**: A reviewer can reproduce any semantic verdict from `preprocess_output.json` plus `semantic_table_truth.json` alone, with no model call and no network access; re-running the gate on the same inputs yields a byte-identical semantic verdict object, failed-check ordering, and row-level reasons.
- **SC-008**: Existing pre-feature `evaluation_document.json` and `evaluation_run_summary.json` artifacts still validate against the report schemas after the feature lands (zero breakage of prior reports).
- **SC-009**: Zero noncanonical degraded-body folders (e.g. `inv_024_hard_degraded_body`) appear in scored stage 1 corpus evaluation output unless promoted through the full dataset/labeling/folder-contract/evaluator-contract amendment path.
- **SC-010**: Every active functional requirement (FR-001 through FR-034) maps to at least one implementation task and at least one test — verified at `/speckit.tasks` and `/speckit.analyze` time.

## Assumptions

- The first implementation of the semantic gate is **evaluator/harness-owned**: it runs during evaluation when a document has semantic table truth, and does NOT alter pipeline preprocessing, extraction, routing, or final-payload generation at landing (per `add-ocr-semantic-quality-gate/design.md` Decision 1). Runtime fallback/review integration is deferred entirely to a later feature (Clarifications Q3, FR-033).
- The existing evaluator (feature 007 surface — `evaluation_document.json`, `evaluation_run_summary.json`) is the integration point for the report surface. This feature extends that surface additively; it does not replace it.
- `preprocess_output.json` already contains the body/table OCR lines, tokens, and per-line detector confidence the gate needs — the `ocr-semantic-quality-observations.md` finding was derived from exactly that artifact (body lines, body token count, body confidence mean/min).
- The existing 20-document vendor-identity baseline corpus under `tests/stage1_vendor_identity/` is NOT mutated by this feature. Degraded-body PDFs (`inv_021_hard_degraded_body` … `inv_024_hard_degraded_body`) exist as calibration evidence and are NOT yet committed scored corpus data. The first semantic-quality independent test uses a committed synthetic fixture under `tests/stage1_semantic_quality/`, not direct promotion of those calibration folders.
- Report schema changes are additive for readers and required for newly written feature-aware reports. Existing v1.2-era evaluation reports remain valid; the feature does not force regeneration of committed baseline artifacts.
- The semantic gate verdict status set is closed at the four canonical snake_case JSON values {`passed`, `failed`, `not_applicable`, `unevaluable`} (Clarifications Q26); `not_applicable` is the status for any document without a sidecar.
- The OpenSpec capability spec `add-ocr-semantic-quality-gate/specs/ocr-semantic-quality-gate/spec.md` governs feature behavior; where this Speckit spec and the OpenSpec capability spec disagree, the OpenSpec capability spec wins and this spec is corrected.

### Out of Scope

- **Runtime pipeline integration** — changing preprocessing, extraction, routing (`routing_decision.json`), final-payload generation, feature 019 fallback behavior, feature-020 skip-fallback suppression, or runtime review policy based on the semantic verdict. Decided out of scope and deferred to a later feature (Clarifications Q3, FR-033); this feature delivers evaluator/harness evidence only. The feature MAY *report* a whole-invoice/table-quality failure or review-needed status, but that report MUST NOT drive runtime behavior.
- **Line-item extraction** — this feature evaluates table/body OCR *quality*; it does not extract structured line items.
- **A learned classifier, a new model runtime, a remote service, a network call, or a prompt-owned routing decision** — explicitly excluded; the gate is deterministic and code-owned.
- **Rewriting features 019, 020, or 021** in place.
- **Regenerating committed corpus baselines** outside the normal dataset amendment flow.
- **Promoting `inv_024_hard_degraded_body` (or sibling degraded-body folders) into scored corpus data** unless this feature also delivers the full dataset/labeling/folder-contract/evaluator-contract amendment set (FR-026).
- **Performance / latency / throughput targets** — the gate is a deterministic in-memory comparison and this feature defines no NFR target: no latency budget, no throughput goal, no runtime envelope. The absence is intentional, not omitted (Clarifications Q38).
- **New configuration surface** — no CLI flags, environment variables, config files, or tunable thresholds are introduced. The gate's behavior is fully fixed by the spec contract and the Clarifications record; there are no runtime knobs to set (Clarifications Q13, Q38).
- **Jetson / edge deployment** concerns.
