# Module Invariants: OCR Semantic Quality Gate

This document records the cross-cutting code invariants that every implementation of the semantic quality gate MUST satisfy. An invariant violation is a design issue, not a style issue: it indicates that the gate no longer behaves as the spec and Clarifications record contract. Gate-time invariant violations are hard errors (MI-19); they are NOT silently absorbed as `unevaluable` verdicts. Each invariant is keyed to the Functional Requirement(s) and Clarification(s) that define it.

---

**MI-1**: The gate MUST NOT import `paddleocr`, `paddlepaddle`, `paddlepaddle-dcu`, or any Paddle-family package, either at module-import time or at gate-run time. It MUST NOT perform network I/O, open sockets, resolve hostnames, or make HTTP requests at any time during a gate evaluation. The constraint is unconditional — no configuration option, environment variable, or runtime flag may cause a Paddle import or a network call. Verified by `test_semantic_quality_module_safety.py`: `import dartwing_ocr.evaluator.semantic_quality` in a process with no Paddle installed MUST succeed. (FR-008, FR-029)

**MI-2**: The gate is fully deterministic. Given byte-identical `preprocess_output.json` content and byte-identical `semantic_table_truth.json` content, the gate MUST produce a byte-identical `SemanticQualityResult` — identical status, identical `failed_checks` array (including element ordering), identical `row_reasons`, identical `supporting_evidence` values — on the same host and across hosts. This means the gate MUST NOT read the clock, generate random values, consult environment variables that affect its output, or depend on Python dict iteration order for any observable output. Byte-identical serialization via `stable_json.dump_stable` is required for newly-written artifacts (Q34). (FR-014, SC-007)

**MI-3**: For every sidecar row (iterated in sidecar declaration order), the gate MUST evaluate all four checks in the following fixed order: `malformed-currency-shape` → `missing-required-content` → `row-text-coverage-gap` → `row-alignment-failure`. The gate MUST NOT short-circuit after recording the first failure on a row: all four applicable check predicates are evaluated to completion for every row, and every failure is appended to `failed_checks` in that fixed category order within the row. The outer iteration is sidecar row declaration order; the inner iteration is this fixed check-category order. Deviating from this order violates the determinism requirement (MI-2) and produces non-comparable reports across runs. (Q17, FR-014, FR-015)

**MI-4**: Failed-check category attribution is predicate-based. Each of the four category predicates is evaluated independently, and a row MAY record failures in more than one category simultaneously when more than one predicate is true. No mutual-exclusion rule exists between categories: a row that simultaneously has a malformed currency token AND a missing required value MUST record both a `malformed-currency-shape` entry and a `missing-required-content` entry in `failed_checks`. Artificially squashing overlapping failures into a single category is a behavioral error, not a conservative choice. (Q18, FR-015)

**MI-5**: OCR detector confidence values MUST be recorded ONLY on the `semantic_table_quality.supporting_evidence` object, as the closed shape `{body_confidence_mean, body_confidence_min, body_line_count, body_token_count, header_band_excluded}`. Confidence values MUST NOT appear in any per-row field, any `failed_checks` entry, or any `row_reasons` value. A high OCR confidence value MUST NOT change the result of any check predicate — a row with body_confidence_mean ≈ 0.97 that fails a content check still fails; confidence is evidence to the reviewer, not decision-making authority for the gate. (Q30, FR-013)

**MI-6**: The body-OCR search string is built ONCE per document, by joining every body-OCR line on every page of `preprocess_output.json` in its own serialization order (page array order, then line/token array order within each page) with a single ASCII space, then applying the FR-009 normalization pipeline exactly once. All four check predicates that perform "found anywhere" searches — missing-required-content (FR-009), row-text-coverage (FR-011), row anchoring (FR-012), and currency-candidate identification within a span (FR-010/Q35) — operate against this single normalized string. The normalization pipeline is not re-applied mid-check. (Q33, FR-009, FR-011, FR-012)

**MI-7**: The Y_THRESHOLD_FRACTION constant used to exclude the page-1 header band from the observed body-OCR evidence MUST be imported from `preprocessing.evidence_gate` (exposed as `EVIDENCE_GATE_Y_THRESHOLD_FRACTION` by that module), not redeclared or hardcoded in the semantic gate modules. A duplicated constant that drifts from the feature-020 value violates the lane-robustness requirement (Q22): the same header-band boundary must apply to both the feature-020 vendor-identity gate and the feature-022 semantic quality gate. (Q22, R-022.4)

**MI-8**: FR-009 normalization (NFKC → casefold → whitespace collapse → punctuation strip) applies to the comparison path for missing-required-content (FR-009), row-text-coverage (FR-011), and row anchoring (FR-012). The FR-010 currency-shape check evaluates the **raw** OCR token text BEFORE any normalization step. The raw token is the string as it appears in `preprocess_output.json`. Running the regex `^\$?\d{1,3}(,\d{3})*\.\d{2}$` against a normalized token would erase the very defect the check is designed to detect (e.g., normalization of `$21:00` could strip the colon). This ordering is non-negotiable. (Q16, FR-010)

**MI-9**: Currency-position-token identification uses per-field digit-sequence matching, not positional heuristics. For each declared currency field (`unit_price` or `amount`), the gate scans raw tokens in the row's anchored span in `preprocess_output.json` serialization order and selects the first not-yet-matched token whose digit-only representation (raw token with all punctuation and currency symbols removed) equals the expected field's digit sequence. This approach prevents quantity tokens (e.g., `21` for a quantity of 21 units) from being misclassified as currency tokens for a `$21.00` amount field. If no candidate token exists, the failure is `missing-required-content`, never `malformed-currency-shape`. (Q35, FR-010)

**MI-10**: The verdict is aggregated by the any-fail rule after ALL applicable checks across ALL rows have been evaluated. A document is `failed` if `len(failed_checks) > 0`; `passed` if `len(failed_checks) == 0`; `unevaluable` if a required input file is missing or unreadable; `not_applicable` if no sidecar is present. There are no per-category severity tiers, no weighted scores, no pass-threshold configurations, and no early-pass escape hatch. The any-fail rule is applied after MI-3's full evaluation loop completes. (Q4, FR-016)

**MI-11**: The closed verdict status set is exactly `{"passed", "failed", "not_applicable", "unevaluable"}` — these four snake_case literal JSON string values and no others. The gate MUST NOT produce `None`, an empty string, a capitalized variant, or any fourth state. Where a semantic status is serialized — `semantic_table_quality.status` on `evaluation_document.json` and `semantic_table_quality_status` in the run-summary per-document entries — these four values MUST appear verbatim. (Q26, FR-016)

**MI-12**: The closed failed-check category label set is exactly `{"malformed-currency-shape", "missing-required-content", "row-text-coverage-gap", "row-alignment-failure"}` — these four kebab-case literal JSON string values and no others. The `category` field in every `failed_checks` entry MUST be one of these four values. The four values are used verbatim in `failed_checks[].category`, in the `row_reasons` derived aggregation, and as the keys of `semantic_failed_check_counts` in the run-summary metrics. (Q17, Q18, FR-015)

**MI-13**: When `semantic_table_quality.status == "unevaluable"`, the object MUST include a `cause` field constrained to the closed enum `{"preprocess_output_missing", "preprocess_output_invalid_json", "preprocess_output_schema_invalid", "body_ocr_unreadable"}`. An optional `cause_detail` free-text string MAY be included for additional diagnostic information. The `cause` field MUST NOT be present when status is anything other than `unevaluable`. Selecting the cause value is deterministic: absence of the file → `preprocess_output_missing`; file present but not valid JSON → `preprocess_output_invalid_json`; file valid JSON but fails schema validation → `preprocess_output_schema_invalid`; file valid and schema-conformant but contains no readable body OCR lines → `body_ocr_unreadable`. (Q31, FR-017)

**MI-14**: `failed_checks` is the flat ordered array that is the single source of truth for all recorded failures. `row_reasons` is a derived, per-row aggregation serialized as a JSON **object keyed by `row_id`** (NOT an array) whose values are the closed record `{categories: array of kebab-case failed-category labels in the fixed Q17 order, reason: short one-line human-readable summary string}` (field names pinned at landing per the 2026-05-23 F1+F2 remediation — see spec.md FR-017 and data-model.md §5). `row_reasons` MUST be derivable by grouping `failed_checks` by `row_id` without any loss of information. Any discrepancy between `failed_checks` and `row_reasons` — e.g., a category present in `row_reasons` but absent from `failed_checks` — is an implementation bug. `row_reasons` is required when `status == "failed"` and MUST be **omitted entirely** when `status != "failed"` (an empty `{}` is NOT a valid alternative — the key is absent, not present-but-empty). (Q29, FR-015, FR-017)

**MI-15**: The `supporting_evidence` object is the pinned closed shape `{body_confidence_mean: float, body_confidence_min: float, body_line_count: int, body_token_count: int, header_band_excluded: bool}`. No other keys may appear in `supporting_evidence`. `body_confidence_mean` and `body_confidence_min` are computed across all body-OCR lines that survived the header-band exclusion filter; `body_line_count` is the count of those lines; `body_token_count` is the total number of raw tokens across those lines; `header_band_excluded` is `true` if at least one page-1 header-band line was filtered out, `false` otherwise. (Q37, FR-017)

**MI-16**: All newly written semantic outputs MUST be serialized using `stable_json.dump_stable`: sorted keys at every nesting level, UTF-8 encoding, LF line endings, a trailing newline at EOF, and no trailing whitespace. Derived ratios and confidence values MUST be rounded to 6 decimal places using `decimal.ROUND_HALF_EVEN` and emitted as fixed-precision JSON numbers (not strings). Integer counts MUST be emitted as JSON integers. This convention applies to `semantic_table_quality` in `evaluation_document.json` and to `semantic_table_quality_metrics` in `evaluation_run_summary.json`. (Q34, FR-014)

**MI-17**: `document_pass_fail.semantic_table_quality_passed` is determined exclusively by the semantic status as follows: `"passed"` → `true`; `"failed"` → `false`; `"unevaluable"` → `false`; `"not_applicable"` → `null`. There are no other inputs to this mapping and no overrides. The field MUST be present on every newly-written `evaluation_document.json`. A document with no sidecar MUST have this field set to `null` (not absent). A document with a failing semantic verdict but a passing vendor-identity verdict MUST have this field set to `false`; the two verdicts are independent and neither overrides the other. (Q20, FR-017, FR-025)

**MI-18**: The gate runs automatically inside the existing evaluator on every per-document folder that contains a `semantic_table_truth.json` file. The sidecar's presence is itself the opt-in mechanism; no new CLI flag, environment variable, configuration file, or command invocation is introduced. A folder without a sidecar continues to evaluate under the existing vendor-identity contract with no behavioral change. This invariant is permanent: a future configuration surface for the gate would require an explicit spec amendment and a new Clarification. (Q13, FR-007)

**MI-19**: Gate-time invariant violations MUST raise `SemanticGateInvariantError`. They MUST NOT be caught and converted to `unevaluable` verdicts. The run fails, the document is excluded from `semantic_table_quality_metrics` aggregate counts, and no `semantic_table_quality` object is written for the affected document. `unevaluable` is reserved exclusively for cases where a required input file is absent, cannot be parsed as JSON, fails schema validation, or contains no readable body OCR. A sidecar that passes the validator but triggers an internal inconsistency during gate computation (e.g., an anchor function returning a span with negative indices) is a hard error, not a recoverable failure. (Q42, FR-016)

**MI-20**: Calibration folders — those whose folder basename does NOT match the canonical pattern `^inv_\d{3}_(easy|medium|hard)$` per MI-21 — are included in the per-document semantic status entries in `evaluation_run_summary.json` but are EXCLUDED from all aggregate counters and from the `semantic_table_quality_pass_rate` computation in `semantic_table_quality_metrics`. When a calibration folder has a sidecar, the gate runs on it, produces a per-document result, and that result appears in the per-document entries; it just does not count toward the scored aggregation. This separation is enforced by `corpus_pattern.is_scored_corpus_folder(folder_basename)`. (Q39, FR-018, FR-027)

**MI-21**: The canonical-pattern allowlist regex `^inv_\d{3}_(easy|medium|hard)$` is the sole authority for determining whether a folder is a scored corpus folder. It is compiled once as a module-level constant in `dartwing_ocr.validator.corpus_pattern` and reused by both the validator and the gate metrics aggregator. No folder with an extra suffix — including `inv_024_hard_degraded_body` or any other non-matching name — may appear in scored corpus evaluation output unless it was explicitly promoted through the full dataset/labeling/folder-contract/evaluator-contract amendment path. The rule is default-exclude: an unrecognized name is never silently scored. (Q23, FR-027, SC-009)

**MI-22**: Vendor-identity fields — `document_pass_fail.vendor_identity_passed`, all feature-020 run-summary fields (`evidence_gate_id`, `evidence_gate_state_counts`, `evidence_gate_documents`, `evidence_gate_suppressed_fallback_count`), and all feature-019/021 fields — MUST be byte-identical before and after this feature lands across the existing 20-document vendor-identity baseline corpus. Adding the semantic gate MUST NOT alter any of these values, their types, their default values, or their serialization order. SC-006 is the measurable enforcement gate. (SC-006, FR-021, FR-022, FR-023, FR-024)

**MI-23**: `expected.json` retains its current vendor-identity-only shape and meaning. Table/body truth is never written into `expected.json`. A folder with no `semantic_table_truth.json` continues to validate and evaluate exactly as it does today. The introduction of the semantic sidecar does not add any new requirement on `expected.json` for any existing or new document folder. (FR-006, FR-023)

**MI-24**: A pre-feature `evaluation_document.json` that was written before this feature landed — and therefore has no `document_pass_fail.semantic_table_quality_passed` field — MUST be read without error. The absent field MUST be interpreted as `null` semantically: "the semantic gate did not run on this document." This backward-compatibility rule applies to reading and schema-validating older reports; it does NOT permit the new writer to omit the field from newly-generated reports when the feature is active. (Q43, FR-019)

**MI-25**: The synthetic US2 test fixture committed under `tests/stage1_semantic_quality/inv_001_hard/` contains exactly a hand-authored `preprocess_output.json` and a hand-authored `semantic_table_truth.json`. It contains no `source.pdf`. It was not produced by running the preprocessing pipeline and MUST NOT require any Paddle, GPU, or model dependency to use. The fixture is a deterministic, CPU-only ground-truth resource; any committed fixture under `tests/stage1_semantic_quality/` that adds `source.pdf` or requires a preprocessing run violates the fixture-isolation contract. (Q25, FR-026)
