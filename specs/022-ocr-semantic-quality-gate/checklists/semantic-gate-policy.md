## Check-Category Definition Completeness

- [x] CHK001 Is the full set of check categories closed and stated in one authoritative list in the spec — {missing-required-content, malformed-currency-shape, row-text-coverage-gap, row-alignment-failure} — so a reader cannot infer additional undocumented categories from the user stories? [Completeness, Spec §Key Entities, Spec §FR-009, Spec §FR-010, Spec §FR-011, Spec §FR-012] — ✓ Key Entities "Failed Check" lists the closed set; FR-015/Q17 fixes the canonical category order; FR-018 enumerates all four in semantic_failed_check_counts
- [x] CHK002 Is the "missing-required-content" check defined to apply only to fields that are present in the sidecar row (per Clarifications Q8 / FR-002), or could it be triggered for fields that are absent from the sidecar but expected by the gate's own logic? [Clarity, Spec §FR-009, Spec §Clarifications Q8] — ✓ Q8/FR-002: "every field that IS present becomes a required-content check for that row"; absent fields impose no check; FR-009 scoped to "a required value declared by the sidecar"
- [x] CHK003 Is the "malformed-currency-shape" check specified to apply only to `unit_price` and `amount` positions, or could it also fire on `quantity` or `description` tokens that happen to contain numeric values? - [x] CHK004 Does the spec define how the gate identifies "currency-position tokens" in the observed body OCR — is it anchored to the sidecar's declared `unit_price`/`amount` column context, or does it scan the entire body OCR for any token that resembles a currency value? [Ambiguity, Spec §FR-010] — ✓ FR-010: "identified from the raw tokens in the row's anchored OCR span for that expected currency field" — anchored to the row's span, not a full-body scan
- [x] CHK005 Is the "row-text-coverage-gap" check defined to operate over the full expected row text / required text fragments, or only over the first non-null text field in the row? [Completeness, Spec §FR-011, Spec §FR-002] — ✓ FR-011: operates over "the row's expected text" (full expected/required text); Q6: "any required/expected text token absent from the observed body OCR"
- [x] CHK006 Is "row-alignment failure" defined to be mutually exclusive with other check categories — i.e., can a row record both a row-alignment-failure AND a missing-required-content check, or does one subsume the other? [Ambiguity, Spec §FR-012, Spec §FR-009] — ✓ Q18/FR-015: predicate-based attribution, "A row may record more than one failed category when more than one predicate is true"; explicitly not mutually exclusive
- [x] CHK007 Is the "row-alignment failure" category specified to apply to the entire row rather than to individual field positions within it, so a reviewer knows the granularity of the evidence? [Clarity, Spec §FR-012, Spec §FR-015] — ⚠ OPEN: FR-012 says the gate verifies "required values are present, in order, and not split" within the anchored span; FR-015 says each record identifies the row; but whether a single row-alignment-failure record covers the whole row or one record per misaligned field is not specified — ✓✓ Data-Model §4: `field` is "string | null — null for row-text-coverage-gap and row-alignment-failure where no single cell applies"; row-alignment-failure records cover the whole row (field=null); granularity is row-level, not per-field; Schema-Amendments §evaluation_document delta confirms `field` may be null for these categories
- [x] CHK008 Are all four check categories traceable to acceptance scenarios — is each of {missing-required-content, malformed-currency-shape, row-text-coverage-gap, row-alignment-failure} covered by at least one US acceptance scenario? [Traceability, Spec §US2 AS1, Spec §US2 AS2, Spec §US2 AS3, Spec §US2 AS4] — ✓ US2 AS1→malformed-currency-shape, AS2→missing-required-content, AS3→row-alignment-failure, AS4→row-text-coverage-gap; all four covered
- [x] CHK009 Does the spec state whether a single row that fails multiple check categories records one failed-check entry per category or one combined failed-check entry for the row? [Completeness, Spec §FR-015, Spec §FR-016, Gap] — ✓ Q18/FR-015: predicate-based, "A row may record more than one failed category when more than one predicate is true" — one entry per category per row

## Trigger-Condition Clarity

- [x] CHK010 Is the trigger condition for "missing-required-content" (FR-009) expressed as a testable binary predicate — "the normalized sidecar value cannot be found in the normalized observed body OCR" — or does it leave room for partial-match or approximate-match interpretations? [Clarity, Spec §FR-009, Spec §Clarifications Q5] — ✓ FR-009: binary — "cannot be found anywhere in the observed body OCR evidence" via normalized exact containment; Q5: "No fuzzy similarity or edit-distance threshold"
- [x] CHK011 Is the trigger condition for "malformed-currency-shape" (FR-010) solely the failure of the regex `^\$?\d{1,3}(,\d{3})*\.\d{2}$`, or are there additional conditions that must also be satisfied — e.g., must the row first pass or fail the missing-content check before the currency check runs? [Completeness, Spec §FR-010, Spec §Clarifications Q10] — ✓ FR-010: malformed when the raw token fails the anchored canonical money regex; if no candidate raw token exists → missing-required-content not currency-shape; Q17/FR-015: no short-circuit, all checks run
- [x] CHK012 Is the evaluation order of the four checks (FR-009, FR-010, FR-011, FR-012) specified — does the gate short-circuit after the first failure, evaluate all checks regardless of prior failures, or leave the order implementation-defined? [Ambiguity, Spec §FR-016, Gap] — ✓ Q17/FR-015: "No short-circuiting. For every sidecar row, the gate evaluates every applicable check and records failures in deterministic order: malformed-currency-shape, missing-required-content, row-text-coverage-gap, then row-alignment-failure"
- [x] CHK013 Is it specified whether the malformed-currency-shape check (FR-010) is triggered when the sidecar's `unit_price`/`amount` is present but the corresponding observed OCR token cannot be found at all — i.e., is "not found" a missing-content check trigger, a currency-shape check trigger, or both? [Clarity, Spec §FR-009, Spec §FR-010] — ✓ FR-010: "If no candidate raw token exists, the defect is missing-required-content rather than currency-shape" — explicitly resolved
- [x] CHK014 Is "covers only part of a row's expected text" (FR-011) defined in terms of the same token set used in FR-009 normalization, so that a reader can derive exactly which token must be absent to trigger the check? [Clarity, Spec §FR-011, Spec §Clarifications Q6] — ✓ FR-011: "any required/expected row-text token absent anywhere from the observed body OCR (under the normalized comparison of FR-009)"; token set = FR-009 normalized tokens
- [x] CHK015 Is the "binary" definition of coverage (Clarifications Q6) reconciled with the "coverage ratio MAY be recorded as supporting evidence" clause — specifically, is it clear that the ratio is never the trigger, and that the absence of any single token is always sufficient? [Consistency, Spec §FR-011, Spec §Clarifications Q6] — ✓ FR-011: "A coverage ratio MAY be recorded as supporting evidence but MUST NOT be the trigger"; "any required/expected row-text token absent … constitutes a row-text-coverage gap; no numeric coverage threshold is applied"
- [x] CHK016 Is the trigger condition for "row-alignment failure" (FR-012) limited to value ordering and splitting, or does it also fire when the description / row text is present but the required numeric values cannot be placed in order within the anchored span? [Completeness, Spec §FR-012] — ✓ FR-012: "required values are present, in order, and not split across incompatible spans" — includes numeric values out of order within the anchored span; Q18: "required content is present somewhere but cannot be reconstructed in the row's anchored span, order, or grouping"
- [x] CHK017 Is there a specified precedence or relationship between the missing-required-content check (FR-009) and the row-alignment-failure check (FR-012) when the same row value is both absent and misaligned — does the spec prevent double-counting or specify that both checks should be recorded? [Conflict, Spec §FR-009, Spec §FR-012] — ✓ Q18 defines mutually exclusive predicates: missing-required-content = absent from full observed body OCR; row-alignment-failure = present somewhere but cannot be reconstructed in span; a value cannot be both simultaneously absent and present — categories are disjoint by definition

## Verdict Aggregation Policy

- [x] CHK018 Is the any-fail rule in FR-016/Clarifications Q4 stated in terms that make it unambiguous — "a document is 'failed' if ANY row records ANY failed check across ALL rows" — so that a single failed check in a single row causes a document-level "failed" verdict? [Clarity, Spec §FR-016, Spec §Clarifications Q4] — ✓ FR-016: "a document is 'failed' if any row records any failed check; it is 'passed' only when zero failed checks are recorded across all rows"; Q4: "Any-fail rule" with identical wording
- [x] CHK019 Is "zero failed checks recorded across all rows" the only condition that produces a "passed" verdict, or are there rows that could be excluded from the aggregation (e.g. rows with no optional fields that therefore have no checkable content beyond row-id and row-text)? [Completeness, Spec §FR-016] — ⚠ OPEN: FR-016 says "passed only when zero failed checks are recorded across all rows"; FR-002/Q8 say a row with only row_id + row-text still has row-text-coverage as a required check; but the spec does not explicitly confirm that all rows participate in aggregation regardless of optional-field presence — ✓✓ MI-3: the gate "MUST evaluate all four checks in the following fixed order" for "every sidecar row"; MI-10: any-fail aggregation applied "after ALL applicable checks across ALL rows have been evaluated"; Data-Model §2 row-text optionality rule: required_row_text_tokens is mandatory, so every row participates in at least the row-text-coverage check
- [x] CHK020 Is the verdict aggregation rule consistent with the "not applicable" status — specifically, does a document with a sidecar that has all rows pass produce "passed", while a document with no sidecar produces "not applicable", with no overlap between these two statuses? [Consistency, Spec §FR-016, Spec §FR-025] — ✓ FR-016: passed/failed from any-fail rule (sidecar present); FR-025: not_applicable when no sidecar; Q26/FR-016 confirm the four values are disjoint
- [x] CHK021 Does the spec state what verdict is produced when the sidecar has zero rows — is this treated as the validator-rejection edge case (FR-004 / Edge Cases) so the verdict is never "passed" for a zero-row sidecar, or could the any-fail rule over an empty check set vacuously produce "passed"? [Edge Case, Spec §FR-016, Spec §Edge Cases] — ✓ Edge Cases: "Sidecar declares zero rows: treated as a contract violation by the validator (a semantic truth sidecar with no row truth has no purpose); the validator rejects it" — vacuous pass eliminated by validator rejection
- [x] CHK022 Is the "no per-category severity tiers" constraint in Clarifications Q4 stated explicitly enough to prevent a future implementer from treating `malformed-currency-shape` as a warning rather than a failure? [Clarity, Spec §FR-016, Spec §Clarifications Q4] — ✓ Q4: "No per-category severity tiers and no weighted/threshold score"; FR-016: any failed check produces "failed" verdict — all categories are equal-weight failures
- [x] CHK023 Is the "no weighted/threshold score" constraint in Clarifications Q4 measurable — is there a test that verifies the verdict cannot be changed from "failed" to "passed" by adjusting any numeric parameter? [Measurability, Spec §Clarifications Q4, Spec §SC-001] — ✓ SC-001: "A degraded-body fixture … but materially wrong table rows produces a semantic quality verdict of 'failed'" — provides measurable anchor; SC-003: 100% of malformed-currency rows flagged regardless of confidence

## Confidence-Handling Policy

- [x] CHK030 Is it stated precisely where in the output the OCR confidence is recorded as "supporting evidence" — in each failed-check record, in the row-level reasons, in a separate top-level field, or all of the above? [Completeness, Spec §FR-013, Spec §FR-015, Spec §FR-017] — ⚠ OPEN: FR-013 says "recorded as supporting evidence only"; FR-017 lists "optional supporting_evidence" in the semantic_table_quality object; FR-015 lists required failed-check fields but does not explicitly place confidence in every failed-check record; exact placement is not pinned — ✓✓ MI-5 + Q30 + Data-Model §6: confidence MUST be recorded ONLY on semantic_table_quality.supporting_evidence as the closed shape {body_confidence_mean, body_confidence_min, body_line_count, body_token_count, header_band_excluded}; MUST NOT appear in any per-row field, failed_checks entry, or row_reasons value; placement is exclusive to the document-aggregate supporting_evidence object
- [x] CHK031 Is the prohibition "confidence MUST NOT promote a failing row to a pass" measurable — is there a success criterion or test that verifies a row with confidence ≥ 0.97 and a failed content check is still reported as "failed"? [Measurability, Spec §FR-013, Spec §SC-001] — ✓ SC-001: "degraded-body fixture … high mean detector confidence (≥ 0.95 … ≈ 0.97) but materially wrong table rows produces a semantic quality verdict of 'failed'" — provides measurable test anchor
- [x] CHK032 Is "OCR detector confidence" defined — does it refer to the per-line `score` field in `preprocess_output.json`, a per-token confidence, a mean across the body, or all three? [Clarity, Spec §FR-013] — ⚠ OPEN: SC-001 references "mean detector confidence" from the calibration evidence; FR-013 says "per-line detector confidence" in the Key Entities definition of Observed Body OCR Evidence; but FR-013 itself just says "OCR detector confidence" without specifying per-line vs per-token vs mean — ✓✓ Data-Model §3 BodyOcrLine: detector_confidence is a per-line float from preprocess_output.json; R-022.12: body_confidence_mean is "arithmetic mean of per-line OCR detector confidence values across all included body-OCR lines"; body_confidence_min is the minimum across the same set; definition is per-line, aggregated to mean/min for supporting_evidence
- [x] CHK033 Is the "supporting evidence" role of OCR confidence required in output — i.e., MUST the gate always record the observed confidence value alongside every failed check, or MAY it omit it? [Completeness, Spec §FR-013, Spec §FR-015] — ⚠ OPEN: FR-017 says supporting_evidence is "optional" in the semantic_table_quality object; FR-013/FR-015 do not say MUST for every failed check; the recording of confidence is optional not required — ✓✓ Data-Model §6 always-emit rule: "supporting_evidence is required when status ∈ {passed, failed, unevaluable}. It MAY be omitted when status == not_applicable"; confidence recording is mandatory for all evaluable and unevaluable cases; FR-017 "optional" refers only to the not_applicable case where no sidecar was present
- [x] CHK034 Is the acceptance scenario US2 AS5 ("confidence is recorded only as supporting evidence — it cannot make a failing row pass") consistent with US2 AS1 which does not explicitly state that confidence was recorded — is recording confidence mandatory or optional in all scenarios? [Consistency, Spec §US2 AS1, Spec §US2 AS5] — ⚠ OPEN: FR-017 "optional supporting_evidence" is consistent with recording being optional; but US2 AS5 says "confidence is recorded only as supporting evidence" in a way that could be read as mandatory recording; the spec does not resolve this tension — ✓✓ Data-Model §6 always-emit rule resolves this: supporting_evidence (including confidence) is REQUIRED when status ∈ {passed, failed, unevaluable}; US2 AS5 refers to the failed case (mandatory); "optional" in FR-017 refers only to status==not_applicable; tension resolved in Data-Model §6
- [x] CHK035 Is it specified whether OCR confidence is read from the body/table region only, or from the full document including the header band — given that the gate is defined over "observed body OCR evidence"? [Clarity, Spec §FR-013, Spec §Key Entities] — ✓ Key Entities "Observed Body OCR Evidence": "every page's OCR content EXCEPT the feature-020 page-1 header-band region" — body only; header band excluded consistently with Q22

## Notes

- The evaluation order of the four check categories (FR-009, FR-010, FR-011, FR-012) is unspecified; for determinism and test coverage this should be fixed either as "all checks run regardless" or as a defined order, since short-circuiting changes the set of recorded failures.
- CHK013 and CHK017 flag a potential overlap between "missing-required-content" and "row-alignment-failure" that could cause different implementations to attribute the same defect to different categories; the spec should clarify whether both can be simultaneously recorded for the same row.
- The "not passed (or requiring review)" phrasing in FR-025 (CHK029) introduces ambiguity about whether two distinct values are legal for `semantic_table_quality_passed`; this should resolve to exactly one value per verdict status before implementation.
