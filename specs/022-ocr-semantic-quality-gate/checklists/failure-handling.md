## Exception / Error Requirements

- [x] CHK003 Is the "named cause" requirement for "error/unevaluable" verdicts (Edge Cases) specified with enough detail to be testable — e.g., does the spec state that the cause string must identify the file involved and the nature of the fault? [Measurability, Spec §FR-015, Spec §Edge Cases] — ⚠ OPEN: Edge Cases says "unevaluable with a named cause"; the spec does not specify what fields the cause record must contain or how a test would verify that the cause is adequately descriptive — ✓✓ MI-13 + Q31 + Data-Model §7: cause is a closed enum {preprocess_output_missing, preprocess_output_invalid_json, preprocess_output_schema_invalid, body_ocr_unreadable}; optional cause_detail free-text string for operator diagnostics; Schema-Amendments §evaluation_document delta and Evaluator-Output-Contract Example C pin the exact JSON shape; testable by asserting cause membership in the closed enum
- [ ] CHK004 Is there a requirement specifying whether the gate raises a Python exception, writes an error to stderr, returns a structured error object, or returns an "unevaluable" verdict with a cause — and whether more than one of these may occur simultaneously? [Completeness, Spec §FR-016, Gap] — ⚠ OPEN: the spec defines "unevaluable" as the verdict status but does not specify whether Python exceptions are raised, whether stderr is written, or the exact error-handling API contract — STILL OPEN at impl-time: Data-Model §13 covers state transitions (unevaluable for unreadable inputs, SemanticGateInvariantError hard-raised for invariant violations) but the question of stderr writing vs structured-only response is not addressed in any artifact
- [x] CHK005 Is the "unevaluable" verdict required to include a failed-check record, or only a top-level cause — and is that distinction stated in FR-015 / FR-016 or elsewhere? [Coverage, Spec §FR-016, Gap] — ⚠ OPEN: the spec does not address multi-document corpus run isolation; no requirement states that one unevaluable document must not abort the run — STILL OPEN at impl-time: not addressed in plan/research/invariants; corpus-run isolation behavior is implementer-defined
