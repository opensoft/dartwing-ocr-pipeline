## Reproducibility Criteria

- [x] CHK008 Does SC-007 specify what "byte-identical verdict" means concretely — same JSON bytes including key ordering, same whitespace, same floating-point serialization — or is it left implementation-defined? [Measurability, Spec §SC-007] — ⚠ OPEN: FR-014 says "byte-identical semantic verdict object … when serialized with the project's stable JSON ordering" but "stable JSON ordering" and floating-point serialization format are not defined in the spec; implementation-defined risk remains — ✓✓ Q34 + R-022.3 + MI-16: sorted keys at every nesting level; UTF-8; LF line endings; trailing newline; 6-dp ROUND_HALF_EVEN floats as JSON numbers; integer counts as JSON integers; implemented by `stable_json.dump_stable`
- [x] CHK009 Is there a requirement that the gate produces the same verdict when run on different host machines (different OS, different Python minor version, different locale) given the same input files? [Coverage, Spec §FR-014, Gap] — ⚠ OPEN: FR-014 requires byte-identical output from identical inputs but does not explicitly address cross-machine or cross-Python-version reproducibility — ✓✓ R-022.2: Python 3.12 ships Unicode 15.0.0 data, pinned for the lifetime of the 3.12 interpreter; MI-1 forbids locale-sensitive imports; MI-2 forbids env-var reads that affect output; `stable_json.dump_stable` uses `sort_keys=True` eliminating dict-order variation; cross-machine byte-identity is achievable on same CPython 3.12 version
- [x] CHK010 Is the reproducibility requirement in US2 AS6 ("both runs produce a byte-identical verdict, failed-check set, and row-level reasons") measurable as a test — i.e., is there a specified comparison method (file diff, JSON diff, or canonical serialization)? [Measurability, Spec §US2 AS6] — ⚠ OPEN: US2 AS6 states the requirement but the spec does not prescribe the comparison method (file diff, JSON diff, canonical serialization); test authoring is left to the implementer — ✓✓ Quickstart Path 2: `sha256sum` comparison of two successive runs; `test_semantic_quality_determinism.py` runs gate twice and hashes outputs (plan.md test list)
- [x] CHK011 Does the spec state whether the `evaluation_document.json` and `evaluation_run_summary.json` outputs must also be byte-identical across runs, or only the semantic verdict object within them? [Completeness, Spec §FR-014, Spec §FR-017, Spec §FR-018] — ⚠ OPEN: FR-014 scopes the byte-identical guarantee to "semantic verdict object"; whether evaluation_document.json or evaluation_run_summary.json as a whole must be byte-identical is not stated — ✓✓ MI-16 + Data-Model §13: "All newly written semantic outputs MUST be serialized using stable_json.dump_stable" — applies to both evaluation_document.json (via evaluation_document_writer.py) and evaluation_run_summary.json (via run_summary_serializer.py); full-file byte-identity is required, not just the verdict object
- [x] CHK012 Is it specified whether a "coverage ratio" recorded as supporting evidence (FR-011) may differ between runs if it is computed from floating-point arithmetic, and whether that is consistent with the byte-identical reproducibility requirement? [Consistency, Spec §FR-011, Spec §FR-014] — ⚠ OPEN: FR-011 says coverage ratio MAY be recorded as supporting evidence; FR-014 requires byte-identical verdict object; interaction with floating-point ratio serialization is unresolved — ✓✓ Q37 + Data-Model §6: supporting_evidence is a pinned closed shape {body_confidence_mean, body_confidence_min, body_line_count, body_token_count, header_band_excluded} — NO coverage_ratio field exists; FR-011's "MAY be recorded" is superseded by Q37's closed-shape pin; conflict eliminated by exclusion of the field
- [x] CHK013 Is there a requirement on the stability of the failed-check ordering when the any-fail rule is triggered by multiple rows — can two runs list the same failures in different orders? [Completeness, Spec §FR-014, Spec §FR-016] — ✓ FR-014 pins "byte-identical … failed-check ordering"; FR-015/Q17 fixes ordering to sidecar row declaration order then category order within each row

## Normalization Specification Clarity

- [x] CHK014 Is the NFKC normalization step in FR-009 scoped to a specific Unicode version or Python `unicodedata` version, so that the output is reproducible if the Unicode standard changes? [Measurability, Spec §FR-009] — ⚠ OPEN: FR-009 names "Unicode NFKC normalization" and "Python str.casefold()" but does not pin a Unicode version or Python unicodedata version — ✓✓ R-022.2: "Python 3.12 ships Unicode 15.0.0 data and that version is fixed for the lifetime of the 3.12 interpreter"; pinned to CPython 3.12 / Unicode 15.0.0 without a separately-installed Unicode database package
- [x] CHK015 Is "case-folding" defined to mean Python `str.casefold()` or Unicode case-folding (which may differ for some locales), and is that distinction documented? [Clarity, Spec §FR-009, Spec §Clarifications Q5] — ✓ FR-009 explicitly pins "Python str.casefold()" / Q5 confirms the same
- [x] CHK016 Is "whitespace collapse" defined — does it collapse only ASCII spaces, or also tabs, non-breaking spaces, and other Unicode whitespace code points? [Clarity, Spec §FR-009, Spec §Clarifications Q5] — ✓ FR-009 says "collapse of all Unicode whitespace to a single ASCII space" — Unicode-wide scope is explicit
- [x] CHK017 Is "punctuation stripping" defined — does it cover only ASCII punctuation, or Unicode general-category punctuation (`\p{P}`)? Is the stripping applied before or after NFKC? Does order matter? [Clarity, Spec §FR-009, Spec §Clarifications Q5] — ⚠ OPEN: FR-009 says "stripping of Unicode punctuation after NFKC" which resolves ordering, but "Unicode punctuation" is not mapped to a specific Unicode general category (P, Po, Pc, etc.); implementation may vary — ✓✓ Q32 + R-022.2 + Data-Model §11: strip every code point whose `unicodedata.category(ch)` starts with "P" (all seven P* sub-categories: Pc, Pd, Pe, Pf, Pi, Po, Ps); applied after NFKC + casefold + whitespace collapse; step 4 in the fixed normalization pipeline; implemented by `unicodedata.category(ch).startswith("P")`
- [x] CHK018 Is the normalization pipeline in FR-009 applied identically to the sidecar value and to the observed OCR — or might one side have been pre-processed differently by the time the gate reads it from `preprocess_output.json`? [Consistency, Spec §FR-009] — ✓ FR-009: "applied identically to both the sidecar value and observed OCR"
- [x] CHK019 Is the term "exact token containment" in FR-009 defined — specifically, does it mean every whitespace-separated token of the sidecar value must appear somewhere in the normalized observed OCR, or that the entire normalized sidecar string must appear as a substring? [Ambiguity, Spec §FR-009, Spec §Clarifications Q5] — ✓ FR-009: "For scalar cell values, exact containment means the full normalized sidecar value appears as a contiguous substring in normalized observed body OCR. For multi-token row text, exact containment means every required normalized token appears in observed body OCR."
- [x] CHK020 Is the term "substring containment" in FR-009 distinguished from "token containment" — and is it specified which applies for each check category (FR-009 missing-required-content, FR-011 coverage check, FR-012 row anchoring)? [Ambiguity, Spec §FR-009, Spec §FR-011, Spec §FR-012] — ✓ FR-009 distinguishes scalar (substring) from multi-token row text (token presence); FR-011 applies to row-text tokens; FR-012 uses "best normalized exact match" of description/row text
- [x] CHK021 Is the normalization for currency comparison (FR-010) specified separately from FR-009 normalization — specifically, is punctuation stripping in FR-009 applied before the canonical money regex in FR-010, which could strip the decimal point and cause every value to fail? [Conflict, Spec §FR-009, Spec §FR-010, Spec §Clarifications Q10] — ✓ Q16/FR-010: currency-shape evaluation uses "raw observed OCR token text BEFORE FR-009 punctuation stripping or other comparison normalization"; conflict resolved
- [x] CHK022 Is the normalization in FR-009 applied to the `unit_price`/`amount` sidecar values authored as normalized decimal strings (e.g. `"21.00"`) before they are compared to observed OCR tokens that may include a currency symbol (e.g. `$21.00`)? Is the interaction with FR-010's regex fully specified? [Completeness, Spec §FR-002, Spec §FR-009, Spec §FR-010] — ⚠ OPEN: FR-010 handles raw-token regex check; FR-009 handles normalized containment for missing-required-content; but the spec does not explicitly state whether FR-009 normalization is applied to the sidecar decimal string `"21.00"` when searching for it as a substring against a raw OCR token `$21.00` that includes a currency symbol — ✓✓ MI-8 + Data-Model §11: FR-010 currency-shape evaluates the RAW OCR token before any normalization; FR-009 missing-required-content applies normalize() to both the sidecar decimal string and the body-OCR search string — punct stripping removes the decimal point making `"21.00"` → `"2100"` and `$21.00` → `2100`, so they match as expected; the two paths (raw for currency-shape, normalized for missing-content) are disjoint by MI-8
- [x] CHK023 Is it specified whether the description / row-text matching in FR-012 uses the same normalization pipeline as FR-009, or a distinct normalization? [Consistency, Spec §FR-012, Spec §Clarifications Q7] — ✓ FR-012: "best normalized exact match (FR-009) of its description / row text" — explicitly references FR-009 pipeline
- [x] CHK024 Does the spec define whether normalization is applied to "observed body OCR" at the line level, the token level, or the full concatenated body text level — and whether that choice affects which tests pass or fail? [Completeness, Spec §FR-009, Gap] — ⚠ OPEN: FR-009 describes the result of normalization (substring/token containment) but does not specify whether observed body OCR is concatenated into a single string or compared line-by-line or token-by-token; this choice affects whether values split across OCR lines are found — ✓✓ Q33 + MI-6 + Data-Model §3: single normalized concatenation — all body-OCR lines joined with a single ASCII space in Q24 serialization order, normalization applied once to the joined string; all "found anywhere" checks operate against this one string; cross-line values are findable

## Tie-Breaking Determinism

- [x] CHK025 Is "earliest observed-OCR position" in FR-012/Clarifications Q7 defined in terms of a specific, stable ordering — e.g., page index then bounding-box top-y then left-x then character offset — rather than a language-runtime iteration order that may vary? [Clarity, Spec §FR-012, Spec §Clarifications Q7] — ✓ Q24/FR-012: "lowest index in preprocess_output.json's own serialization order (page array order, then line/token array order within each page; no geometry computation and no coordinate tolerance)"
- [x] CHK026 Is "sidecar declaration order" in the tie-break defined as the JSON array index of the row in the `semantic_table_truth.json` rows array, making it stable regardless of JSON parser implementation? [Clarity, Spec §Clarifications Q7] — ✓ Q24/FR-012 confirms: "then by sidecar declaration order" and Q24 defines "lowest index in the artifact's own ordering … page array order, then line/token array order" — sidecar declaration order means JSON array index
- [x] CHK027 Is it specified what constitutes a "tie" among candidate anchors — i.e., is the tie defined as identical normalized-match score, and is the match score itself defined? [Ambiguity, Spec §FR-012, Spec §Clarifications Q7] — ✓ FR-012: "best" = "candidate containing the most required normalized row-text tokens"; tie = equal token overlap count; tie-break by earliest serialization-order position then sidecar declaration order
- [x] CHK028 Is there a requirement stating what happens when no anchor candidate exists at all for a sidecar row — is that a row-alignment failure distinct from the tie-break scenario? [Coverage, Spec §FR-012, Spec §Edge Cases] — ✓ FR-010 / FR-009 interaction: if no candidate raw token exists, it is missing-required-content not currency-shape; FR-012 row-alignment handles "present somewhere but cannot be reconstructed"; the row-text-coverage gap (FR-011) handles absent tokens; the three checks together cover no-anchor as missing-required-content/coverage-gap
- [x] CHK029 Is the tie-break specified to apply only within a single document run, or must it also produce the same result across separate process invocations on the same input? [Completeness, Spec §FR-012, Spec §FR-014] — ⚠ OPEN: FR-014 requires byte-identical verdict for identical inputs; tie-break is defined via serialization-order index (stable per-file), so cross-invocation stability follows from FR-014 — but the spec does not explicitly state this extension; safe inference but not explicit — ✓✓ MI-2: "Given byte-identical preprocess_output.json content and byte-identical semantic_table_truth.json content, the gate MUST produce a byte-identical SemanticQualityResult … on the same host and across hosts"; Data-Model §12: tie-break uses preprocess_output.json serialization order (a stable per-file property); cross-invocation stability is explicitly required by MI-2
- [x] CHK030 Is the "best normalized match" concept in FR-012 defined algorithmically — e.g., does "best" mean the longest matching prefix, the highest token overlap count, or the lowest edit distance — so the tie-break rule is only reached when the match scores are provably equal? [Ambiguity, Spec §FR-012, Spec §Clarifications Q7] — ✓ FR-012: "best" means "the candidate containing the most required normalized row-text tokens" (token overlap count); no edit distance involved; tie-break reached only when token counts are equal

[Conflict, Spec §FR-011, Spec §FR-014] — ⚠ OPEN: FR-011 permits coverage ratio as supporting evidence but FR-014 requires byte-identical verdict; the spec does not resolve whether the floating-point ratio must be serialized deterministically or whether it is excluded from the byte-identical guarantee — ✓✓ Q37 + Data-Model §6 + Schema-Amendments §evaluation_document delta: supporting_evidence is a closed shape {body_confidence_mean, body_confidence_min, body_line_count, body_token_count, header_band_excluded} — no coverage_ratio field; FR-011's "MAY be recorded" clause is superseded by Q37's pinned closed shape; conflict resolved by field exclusion

[Ambiguity, Spec §FR-014] — ⚠ OPEN: FR-014 says "byte-identical … failed-check set" and FR-015 says one record per category per row (predicate-based, Q18), but the spec does not explicitly state whether duplicates (same row, same category) are forbidden or merely not expected — ✓✓ MI-4 + Data-Model §4: predicate-based attribution — each category predicate is binary and evaluated independently; a predicate can only be true or false once per row; a row can appear multiple times in failed_checks only with DIFFERENT category values; same-row same-category duplicates are impossible by predicate definition, not merely discouraged
- [x] CHK037 Does FR-009 "no fuzzy similarity or edit-distance threshold" conflict with FR-012's "best normalized match" — specifically, could "best" imply an edit-distance ranking that FR-009 prohibits? - [ ] CHK038 Is SC-007's "no model call and no network access" measurable as a test assertion — i.e., does the spec describe how a test would verify that the gate made zero network calls (e.g. mocking the socket layer, patching httpx, or checking for import of network libraries)? - [x] CHK040 Is the consistency between FR-008 (no OCR confidence as proof) and US2 AS5 ("OCR confidence is recorded only as supporting evidence — it cannot make a failing row pass") sufficient — specifically, is it stated that confidence also cannot influence the per-check triggering condition, not just the final verdict? [Consistency, Spec §FR-008, Spec §FR-013, Spec §US2 AS5] — ✓ FR-013: "confidence MUST NOT promote a failing row to a pass"; US2 AS5 and FR-008 together cover both per-check trigger and verdict; SC-001 provides measurable test anchor

## Notes

- The normalization pipeline in FR-009 / Clarifications Q5 is the single most ambiguity-dense area: the interaction between punctuation stripping, currency regex matching (FR-010), and the "exact token / substring" containment choice should be specified with worked examples to be unambiguous.
- The tie-break rule (FR-012 / Clarifications Q7) references "earliest observed-OCR position" without defining the coordinate system or whether the position is stable across PaddleOCR versions; this is a reproducibility risk across environments.
- CHK021 and CHK022 flag a potential silent conflict where FR-009 punctuation stripping removes the decimal point before FR-010's regex runs, causing all decimal values to appear malformed; this conflict should be resolved in the spec before implementation.
