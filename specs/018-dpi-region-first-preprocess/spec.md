# Feature Specification: DPI Reduction And Region-First Vendor Identity Preprocess

**Feature Branch**: `018-dpi-region-first-preprocess`
**Created**: 2026-05-09
**Status**: Draft
**Input**: User description: "Build the next GPU optimization slice after feature 017. Reduce preprocessing latency further by lowering rasterization cost where safe and by introducing a vendor-identity-focused region-first/header-first preprocessing path, still without changing any persisted stage 1 artifact contracts."

## Clarifications

### Session 2026-05-10

- Q: When a region-first strategy yields no vendor-identity-relevant evidence on a page or document (FR-007 disposition), should the system fall back to the full-page strategy or fail fast? → A: Fall back to the full-page strategy on that document and record the fallback on `run_summary`; never emit a silent blank `preprocess_output.json`.
- Q: For multi-page invoices, how does the header-first preset shape `preprocess_output.json.pages[]`? → A: Header band on page 1 only; pages 2..N appear in `pages[]` as empty records (valid geometry, `blocks: []`, `raw_ocr_lines: []`); `pages.length == page_count` invariant is preserved; pages 2..N do no rasterization or inference.
- Q: What deterministic signal triggers the FR-007 fallback ("no vendor-identity-relevant evidence")? → A: After region-first preprocessing of the targeted region on page 1, trigger fallback when the concatenation of all `blocks[].text` in the targeted region, with whitespace stripped, is empty. Pure deterministic check; no model output, no magic threshold.
- Q: What shape does the `run_summary` fallback field take, and is it always emitted? → A: A single integer field `region_strategy_fallback_count` on `run_summary`, always emitted (0 default) on every run including `full-page`, `ppstructurev3@cpu`, and stub-adapter runs. Per-document attribution is recoverable from `preprocess_output.json.pages[]` shape (a fallen-back document has full-length populated pages while a clean region-first run has pages 2..N empty per Q2).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Reduced-DPI rasterization candidate on the GPU lane (Priority: P1)

A pipeline engineer wants to stop paying full-DPI, full-page rasterization cost when stage 1 only needs vendor-identity evidence. They want to evaluate at least one reduced-DPI rasterization candidate against the existing GPU lane default on the same fixed small corpus subset, with the candidate selectable per run via explicit configuration. Each evaluated DPI must produce a `preprocess_output.json` that still validates against the existing JSON Schema, and the per-document `phase_timings.rasterization` from feature 015 must be available for every run so the latency win can be quantified.

**Why this priority**: This is one of the two core deliverables. Rasterization is currently sized for full-page document understanding, but stage 1 only consumes vendor-identity evidence; lowering DPI is the cheapest preprocessing-side latency win available before touching layout structure. Without a quantified per-document `phase_timings.rasterization` comparison and a `preprocess_output.json` that still passes the existing schema, "reduce DPI" is a guess.

**Independent Test**: Pick a fixed small subset of `tests/stage1_vendor_identity/inv_*` (the same subset for every configuration). Run the `ppstructurev3@gpu` lane on that subset under (a) the legacy DPI default and (b) at least one reduced-DPI candidate. Confirm: (1) every `preprocess_output.json` validates against the existing JSON Schema in the active contract set; (2) per-document `phase_timings.rasterization` and `phase_timings.total` are emitted for every run per feature 015; (3) the DPI configuration is selected by explicit configuration, not silently changed on the GPU lane; (4) the legacy DPI default remains an explicitly selectable option.

**Acceptance Scenarios**:

1. **Given** a `ppstructurev3@gpu` run with the legacy DPI default on a fixed vendor-identity fixture, **When** preprocessing completes, **Then** `phase_timings.rasterization`, `phase_timings.total`, and `preprocess_output.json` are emitted unchanged in shape from features 015–017.
2. **Given** the same fixture and the same `ppstructurev3@gpu` profile but with a reduced-DPI candidate explicitly selected, **When** preprocessing completes, **Then** `phase_timings.rasterization` is recorded for the reduced-DPI run and the resulting `preprocess_output.json` validates against the existing schema with no field added, removed, renamed, or retyped.
3. **Given** a `ppstructurev3@gpu` run without any new DPI switch set, **When** preprocessing completes, **Then** rasterization-DPI behavior is unchanged from feature 017 — the reduced-DPI candidate MUST NOT become the GPU default in this scenario unless it is explicitly promoted (US6).

### User Story 2 - Region-first / header-first preprocessing path for vendor identity (Priority: P1)

An engineer wants an explicit region-first / header-first preprocessing strategy on the `ppstructurev3@gpu` profile that focuses preprocessing work on the page region(s) most likely to carry vendor-identity evidence (typically the document header band on the first page) instead of running the full-page pipeline edge-to-edge on every page. The strategy is selectable per run alongside the existing full-page baseline, produces a `preprocess_output.json` that still passes the existing schema, and exposes its identifier on the `run_summary` line so an operator can attribute observed timing or quality differences to it.

**Why this priority**: This is the second core deliverable and the structurally larger preprocessing win. Even with reduced DPI (US1), running the full PPStructureV3 pipeline edge-to-edge on every page costs more than vendor identity needs. A region-first / header-first strategy concentrates preprocessing on the page area that actually carries vendor identity. Without it, the team cannot evaluate whether the bigger latency win lives in DPI or in region targeting.

**Independent Test**: Run the `ppstructurev3@gpu` lane on the same fixed small corpus subset under (a) the existing full-page baseline and (b) at least one region-first / header-first strategy. Confirm: (1) every `preprocess_output.json` validates against the existing JSON Schema; (2) per-document `phase_timings.*` is recorded for every run; (3) the strategy is selected by explicit configuration; (4) two runs that differ only on the region strategy emit different identifier values in `run_summary` (per US3); (5) the existing harness/evaluator pipeline runs end-to-end against the region-first outputs.

**Acceptance Scenarios**:

1. **Given** a `ppstructurev3@gpu` run with the legacy full-page strategy on a fixed vendor-identity fixture, **When** preprocessing completes, **Then** `preprocess_output.json` and the `run_summary` line are unchanged in shape from feature 017 except for the additive identifier fields defined in US3.
2. **Given** the same fixture and the same `ppstructurev3@gpu` profile but with a region-first / header-first strategy explicitly selected, **When** preprocessing completes, **Then** the resulting `preprocess_output.json` validates against the existing schema, the downstream evidence-packet assembler / extractor / router / final-payload assembler / evaluator complete without contract changes, and `phase_timings.*` is recorded.
3. **Given** a region-first strategy that, on a particular fixture, yields no vendor-identity-relevant text in the targeted region, **When** preprocessing completes, **Then** the system MUST fall back to the full-page strategy on that document, MUST emit a schema-valid `preprocess_output.json` produced by the full-page strategy, and MUST record the fallback on `run_summary` so it is operator-visible. Failing fast is not permitted; silently emitting a blank `preprocess_output.json` remains forbidden.

### User Story 3 - Active rasterization / region strategy is visible in operator-facing output (Priority: P1)

An operator inspecting a `run_summary` line for any preprocessing run can tell which rasterization DPI and which region strategy the run used by reading stable identifier fields directly from the output — without having to read source code, environment variables, or feature-flag state. The identifiers are emitted on every run including default `ppstructurev3@cpu` and stub-adapter runs, so absence of either field is itself a regression signal.

**Why this priority**: Reduced-DPI evaluation (US1) and region-first evaluation (US2) introduce multiple possible preprocessing configurations on the same `ppstructurev3@gpu` profile. Without an output-visible identifier per axis, two runs that differ only in DPI or only in region strategy look identical to operators and to anyone diagnosing a quality regression after the fact. P1 because every other story depends on operators being able to attribute observed differences to the configuration that produced them, and because this is the surface promotion decisions (US6) reference.

**Independent Test**: Run the GPU lane four times — (a) legacy DPI + full-page, (b) reduced-DPI + full-page, (c) legacy DPI + region-first, (d) reduced-DPI + region-first. Confirm: (1) the `run_summary` line for each run carries two additive top-level string fields naming the active rasterization DPI choice and the active region strategy; (2) the four runs produce four distinct identifier-pair values; (3) repeating any one of the four runs produces the same identifier-pair value as before; (4) a `ppstructurev3@cpu` run also carries both fields with values that reflect the CPU default.

**Acceptance Scenarios**:

1. **Given** a `ppstructurev3@gpu` run with the legacy DPI and full-page strategy, **When** preprocessing completes, **Then** the `run_summary` line carries an additive `raster_profile_id` (names the active rasterization DPI choice — for example `"legacy"` or `"reduced-v1"`) and an additive `region_strategy_id` (names the active region strategy — for example `"full-page"` or `"header-first-v1"`).
2. **Given** the same run repeated under a different DPI choice or a different region strategy, **When** preprocessing completes, **Then** at least one of `raster_profile_id` / `region_strategy_id` differs from the legacy run, and the new value matches the explicitly-selected configuration.
3. **Given** a `ppstructurev3@cpu` run (default profile) without any new configuration switches set, **When** preprocessing completes, **Then** the `run_summary` line is unchanged from feature 017 except for the two additive identifier fields whose values reflect the active CPU default (e.g., `cpu-default` for both, or equivalent stable strings agreed at `/speckit.plan` time), so absence of either field is itself a regression signal.
4. **Given** any run on which the region-first strategy fell back to the full-page strategy on one or more documents (per US2 acceptance scenario 3), **When** preprocessing completes, **Then** the fallback is observable from `run_summary` via the additive top-level integer `region_strategy_fallback_count` (always emitted, default `0`, value equal to the number of documents that fell back) without changing the existing `phase_timings.*` keys.

### User Story 4 - Default CPU profile and CI without GPU stay safe (Priority: P2)

An engineer running the default `ppstructurev3@cpu` profile, or the existing CI without GPU hardware, must not have their behavior changed by this feature beyond the additive identifier fields on `run_summary`. No CPU code path may import GPU-only DPI or region-strategy code; no CPU run may consult or mutate any GPU-only configuration switch this feature introduces.

**Why this priority**: P2 — the risk is regression, not new value. CPU and CI paths already work post-017; this story protects them. Lower than P1 only because the CPU/CI path's correctness is independently verifiable today, and because this feature's CPU surface is purely the additive identifier surface from US3.

**Independent Test**: Run the default `ppstructurev3@cpu` profile and the existing stub-adapter / CPU-only test suites on a host without Paddle GPU, both with and without the new GPU-only configuration switches set in the environment. The suites must pass in both configurations. CPU `preprocess_output.json` outputs must be byte-identical to outputs on `main` before this feature lands.

**Acceptance Scenarios**:

1. **Given** the default `ppstructurev3@cpu` profile on a host without GPU, **When** preprocessing runs, **Then** no GPU-only DPI or region-strategy code path is imported or executed.
2. **Given** the same default CPU profile with new GPU-only configuration switches *explicitly set* in the environment, **When** preprocessing runs, **Then** the run completes normally with no behavior change other than the additive identifier fields on `run_summary` whose values reflect the default CPU configuration.
3. **Given** the existing default test suite on a host without Paddle GPU, **When** the suite runs, **Then** it passes; GPU-only verification of reduced-DPI / region-first behavior is skipped via `@pytest.mark.gpu` rather than failed.

### User Story 5 - Output schema and downstream contracts unchanged (Priority: P2)

A corpus run on the GPU lane under any rasterization-DPI choice and any region strategy this feature introduces must produce a `preprocess_output.json` that still matches the existing JSON Schema and that the downstream evidence-packet assembler, single-voter extractor, router, final-payload assembler, and evaluator accept without modification.

**Why this priority**: P2 — protects every downstream slice (004 evidence packet, 005 extraction, 008 routing, 009 final payload, 007 evaluator) from leaking a preprocessing-side optimization into their contract surface. Lower than the core P1 stories only because schema-conformance is mechanically checkable.

**Independent Test**: For each evaluated configuration (each DPI candidate × each region-strategy candidate, plus the legacy baseline), run a small corpus subset end-to-end through the existing pipeline (preprocess → evidence packet → extract → route → assemble → evaluate). Confirm: (a) every `preprocess_output.json` validates under `contracts/stage1_vendor_identity/*/preprocess_output.schema.json` of the active contract set; (b) each downstream stage runs to completion against those outputs; (c) `schema_version`, `contract_set_version`, and the four canonical artifact contracts are not modified by this feature.

**Acceptance Scenarios**:

1. **Given** a small corpus subset run end-to-end under a configuration introduced by this feature, **When** every stage completes, **Then** every emitted artifact validates against its existing schema in the active contract set.
2. **Given** the same end-to-end run, **When** the evaluator runs, **Then** it produces `evaluation_document.json` and `evaluation_run_summary.{json,md}` without contract changes.
3. **Given** the active contract set at landing time, **When** this feature lands, **Then** no `schema_version` value, no JSON schema field, and no entry in `contracts/stage1_vendor_identity/AMENDMENTS.md` is changed by this feature except for the additive identifier surface explicitly defined here.

### User Story 6 - Quality-gate guard before any GPU default change (Priority: P3)

If, after running the US1 + US2 benchmarks, the team chooses to promote a reduced-DPI candidate or a region-first strategy (or any combination) to the new `ppstructurev3@gpu` default, the promotion must be gated on vendor-identity quality being preserved against the existing GPU default — measured on the same small corpus the benchmark used. Promotion that fails the gate is rejected; the legacy default stays in place. This mirrors feature 017's promotion gate (017 FR-015).

**Why this priority**: P3 — the feature ships value at P1+P2 (DPI candidate, region-first candidate, identifier visibility, schema preservation, CPU/CI safety) without ever flipping the GPU default. Promotion is a follow-on decision. P3 because skipping the gate would convert this feature from "evaluation slice" to "silent regression vector"; promotion-gating is required only if and when the team chooses to promote.

**Independent Test**: Take a candidate configuration that US1 / US2 evaluated (a specific `(raster_profile_id, region_strategy_id)` pair). Compare its vendor-identity quality numbers (from the existing evaluator) against the legacy GPU default's numbers on the same corpus. The promotion gate passes only if the candidate is at parity or better on the agreed quality metric. If the gate passes, the candidate becomes the new GPU default in this feature; if it fails, the legacy default is kept and the candidate remains an opt-in selection only.

**Acceptance Scenarios**:

1. **Given** a candidate configuration evaluated under US1 / US2, **When** the team considers promoting it to the new `ppstructurev3@gpu` default, **Then** the decision references vendor-identity quality numbers produced by the existing evaluator on the same corpus the benchmark used.
2. **Given** a candidate that passes the quality gate, **When** the GPU default is changed, **Then** the change is recorded in this feature's research artifact and the new default's `(raster_profile_id, region_strategy_id)` pair appears in subsequent `run_summary` lines without any opt-in switch needing to be set.
3. **Given** a candidate that fails the quality gate, **When** the promotion decision is made, **Then** the legacy default remains in place and the candidate stays selectable only via explicit configuration.

### Edge Cases

- **DPI switch combined with `ppstructurev3@cpu`**: A switch that selects a non-legacy rasterization DPI on the GPU lane is GPU-only by design. When set with the CPU profile or a stub adapter, the system MUST follow the same warn-and-proceed pattern features 016 / 017 established: emit a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`, perform no DPI change, and proceed with the run normally. Silent ignore is NOT acceptable.
- **Region-strategy switch combined with `ppstructurev3@cpu`**: Same disposition as the DPI switch. Warn-and-proceed; no region-targeting; the CPU run uses its existing full-page CPU defaults.
- **Reduced-DPI candidate fails vendor-identity quality gates**: Treated as a regression of FR-015. The reduced-DPI candidate is rejected; the legacy DPI is kept as the default until the regression is resolved.
- **Region-first strategy yields no vendor-identity evidence on a page or document**: The system MUST fall back to the full-page strategy on that document, MUST emit a schema-valid `preprocess_output.json` produced by the full-page strategy, and MUST record the fallback on `run_summary` per US3 / FR-009. Failing fast is not permitted; silently emitting a blank or malformed `preprocess_output.json` remains forbidden. (Disposition resolved 2026-05-10 in `/speckit.clarify` Q1.)
- **Region-first strategy on a multi-page invoice where vendor identity lives only on page 1**: The header-first preset processes the header band on page 1 only. Pages 2..N MUST appear in `preprocess_output.json.pages[]` as empty records — `page_number`, `width`, `height`, and `rotation_detected` derived from the PDF page geometry, with `blocks: []` and `raw_ocr_lines: []`. Pages 2..N MUST NOT be rasterized and MUST NOT be sent to inference. The `pages.length == page_count` invariant MUST be preserved so downstream consumers iterate `pages[]` without surprise. Page coverage decisions MUST be deterministic, MUST NOT depend on model output, and MUST be re-derivable from the inputs alone. (Page-coverage shape resolved 2026-05-10 in `/speckit.clarify` Q2.)
- **Reduced-DPI changes per-document `phase_timings` shape**: Forbidden. Per-document `phase_timings` keys (`paddle_import`, `gpu_bind_probe`, `engine_init`, `rasterization`, `per_page_inference`, `artifact_write`, `total`, and `warmup` from feature 016) MUST NOT be renamed, removed, or have their type changed by this feature.
- **Region-first strategy attempts to alter the `preprocess_output.json` page index, block index, or coordinate system**: Forbidden. Coordinate origin, units, and indexing MUST stay identical to the legacy full-page output so downstream evidence-packet assembly does not need to special-case region-first runs.
- **GPU bind failure on a candidate configuration**: Run MUST fail fast (preserving feature 015 FR-008 / feature 017 FR-007 — no silent CPU fallback after `ppstructurev3@gpu` is selected). The exit reason MUST identify the configuration `(raster_profile_id, region_strategy_id)` that failed so operators can diagnose without re-instrumentation.
- **Operator overrides the new GPU default back to the legacy default**: MUST be supported by the same explicit configuration switches this feature introduces — a default change MUST NOT remove the operator's ability to select the legacy `(raster_profile_id, region_strategy_id)` configuration.
- **GPU verification deferred to a follow-up**: When workstation GPU hardware is unavailable at landing time, GPU-marked tests (`@pytest.mark.gpu`) and benchmark verification MAY be deferred and tracked as a follow-up issue/task without blocking the CPU-safe implementation from merging (per feature 016 FR-014 / feature 017 FR-024). The deferral MUST be captured in this feature's `tasks.md` and quickstart so the verification cannot be quietly skipped.
- **Conditions under which the legacy GPU configuration is preserved as the default** (collated for review traceability): (a) FR-015 quality-gate failure on either metric for the candidate `(raster_profile_id, region_strategy_id)`; (b) deterministic fallback / blank-output regression from a region-first strategy; (c) downstream-contract conflict where reducing DPI or region-targeting would alter `preprocess_output.json` in a way any downstream stage rejects; (d) GPU bind failure on the candidate configuration; (e) the team makes no promotion decision at landing. In all cases the legacy configuration remains both the default and an explicitly selectable option.

#### Out of Scope

Documented here so future failures are recognized as known gaps rather than regressions:

- **OCR-only fast lane that bypasses layout entirely for vendor-identity-only paths**: Reserved for feature 019. Out of scope here.
- **Module-set or detection/recognition variant changes**: Owned by feature 017. This feature MUST NOT alter `module_set_id` or `det_rec_variant_id` semantics introduced there; those identifiers stay alongside the new ones on `run_summary` unchanged.
- **Promoting a CPU-side default change**: Out of scope. This feature only considers GPU-side defaults; CPU defaults stay as they are unless an explicit follow-up amendment promotes one.
- **Adding a new persisted benchmark artifact**: Out of scope unless `/speckit.clarify` or `/speckit.plan` produces evidence that `run_summary` plus the existing harness/evaluator outputs are insufficient to record the benchmark. If introduced later, name/location/schema/lifecycle MUST be specified in `data-model.md` + `research.md` and the contract set updated under `contracts/stage1_vendor_identity/AMENDMENTS.md`.
- **Regenerating committed corpus baselines**: Out of scope. Any baseline change MUST go through the established dataset/baseline flow defined in `docs/stage1-vendor-identity/dataset-layout.md` and `labeling-guide.md`, not through this feature's PR.
- **Schema or `schema_version` changes to the four canonical stage 1 artifacts**: Out of scope. This feature is configuration-only on the runtime side and additive-only on the `run_summary` side.

## Requirements *(mandatory)*

### Functional Requirements

**Reduced-DPI rasterization candidate**

- **FR-001**: System MUST provide an explicit configuration mechanism on the live `ppstructurev3@gpu` path that selects a named rasterization-DPI preset for a given run. Preset selection is the ONLY user-facing surface for DPI choice — the feature MUST NOT expose a free-form numeric DPI knob on the runtime path. The feature ships at least two presets at landing: `legacy` (the rasterization DPI active on `main` at landing time of feature 017) and at least one reduced-DPI preset (e.g., `reduced-v1`) recommended by the FR-005 benchmark. `raster_profile_id` is drawn from this closed vocabulary; adding a future preset is a code change plus a new `raster_profile_id` value, not a runtime numeric override.
- **FR-002**: A `ppstructurev3@gpu` run with a reduced-DPI preset MUST produce a `preprocess_output.json` that validates against the existing JSON Schema for that artifact in the active contract set, with no field added, removed, renamed, or retyped. Coordinate origin, units, page index, and block index in the resulting `preprocess_output.json` MUST stay identical to the legacy DPI run on the same fixture (modulo numerical rasterization differences within rounding tolerance — exact tolerance resolved at `/speckit.plan` time).
- **FR-003**: The reduced-DPI preset MUST be selectable per-run on the `ppstructurev3@gpu` profile via explicit configuration; the legacy DPI preset MUST remain a valid selection.

**Region-first / header-first preprocessing strategy**

- **FR-004**: System MUST provide an explicit configuration mechanism on the live `ppstructurev3@gpu` path that selects a named region strategy for a given run. Preset selection is the ONLY user-facing surface for region-strategy choice — the feature MUST NOT expose free-form region coordinates on the runtime path. The feature ships at least two presets at landing: `full-page` (the legacy strategy active on `main` at landing time of feature 017) and at least one region-first / header-first preset (e.g., `header-first-v1`). `region_strategy_id` is drawn from this closed vocabulary; adding a future preset is a code change plus a new `region_strategy_id` value, not a runtime per-run coordinate override.
- **FR-005**: System MUST exercise at least one reduced-DPI preset and at least one region-first / header-first preset on the same fixed small stage 1 vendor-identity corpus subset used for benchmarking the legacy default, and MUST record per-document `phase_timings.*` plus the existing evaluator's vendor-identity quality numbers for each evaluated configuration. The benchmark records the four corner cases at minimum: legacy DPI × full-page, reduced DPI × full-page, legacy DPI × region-first, reduced DPI × region-first.
- **FR-006**: The region-first strategy's per-page or per-document targeting decisions MUST be deterministic and MUST NOT depend on the output of any extraction, classification, or vendor-identity model. The targeting decision MUST be re-derivable from the inputs (PDF page geometry, page index, layout heuristics) alone so two runs of the same strategy on the same input produce the same targeting.
- **FR-007**: When a region-first strategy yields no vendor-identity-relevant evidence on a document, the system MUST fall back to the full-page strategy on that document, MUST emit a `preprocess_output.json` produced by the full-page strategy (so downstream stages always receive a schema-valid artifact), and MUST record the fallback on `run_summary` per FR-009 so the event is operator-visible. The trigger condition for "no vendor-identity-relevant evidence" is deterministic: after region-first preprocessing of the targeted region on page 1, the concatenation of all `blocks[].text` inside the targeted region, with whitespace stripped, is empty. The trigger condition MUST be re-derivable from `preprocess_output.json` alone and MUST NOT depend on the output of any extraction, classification, or vendor-identity model. Failing fast in this scenario is NOT permitted; silently emitting a blank or schema-invalid `preprocess_output.json` remains forbidden. (Disposition + trigger clarified 2026-05-10.)

**Operator-facing visibility**

- **FR-008**: The `run_summary` line MUST carry two additive top-level string fields that together identify the active preprocessing configuration on this feature's two axes: `raster_profile_id` (names the active rasterization DPI choice — for example `"legacy"`, `"reduced-v1"`) and `region_strategy_id` (names the active region strategy — for example `"full-page"`, `"header-first-v1"`). Both fields MUST be human-readable strings, not opaque numeric hashes.
- **FR-009**: When a region-first strategy falls back to the full-page strategy on one or more documents during a run, the fallback MUST be observable from `run_summary` via an additive top-level integer field `region_strategy_fallback_count` whose value is the number of documents in the run that fell back. This field MUST be emitted on every run of the new binary — including `full-page`, `ppstructurev3@cpu`, and stub-adapter runs (default value `0`) — so absence of the field is itself a regression signal (mirrors FR-011 always-emit pattern). This field MUST NOT change any existing `phase_timings.*` key, and MUST NOT appear inside `preprocess_output.json`. Per-document attribution is recoverable from `preprocess_output.json.pages[]` shape per Q2 (fallen-back documents have full-length populated `pages[]`; clean region-first multi-page documents have pages 2..N empty). (Field name and always-emit policy clarified 2026-05-10.)
- **FR-010**: The fields introduced by FR-008 / FR-009 (`raster_profile_id`, `region_strategy_id`, `region_strategy_fallback_count`) MUST be additive only on `run_summary`. No existing `run_summary` field, no `phase_timings.*` key, no `preprocess_output.json` field, and no field introduced by feature 017 (`module_set_id`, `det_rec_variant_id`, `ppstructure_modules_invoked`) may be renamed, removed, or retyped by this feature.
- **FR-011**: Both `raster_profile_id` and `region_strategy_id` MUST be emitted on every run of the new binary, including default `ppstructurev3@cpu` runs and stub-adapter runs (so absence of either field is itself a regression signal). On those non-GPU runs the field values MUST reflect the active default configuration of that profile (e.g., `cpu-default` for both, or equivalent stable strings agreed at `/speckit.plan` time).

**Profile defaults and CPU/stub isolation**

- **FR-012**: `ppstructurev3@cpu` MUST remain the default preprocessing profile.
- **FR-013**: `ppstructurev3@gpu` MUST remain explicit / opt-in.
- **FR-014**: When any GPU-only configuration switch this feature introduces is set on `ppstructurev3@cpu` or a stub adapter, the system MUST: (a) emit a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`; (b) perform no DPI change and no region targeting; (c) proceed with the run normally and exit with the same status it would have produced without the switch. Silent ignore and rejection are both NOT acceptable. (Mirrors feature 016 FR-010 / feature 017 FR-013.)
- **FR-015**: CPU and stub adapter execution paths MUST NOT import, reference, or trigger any GPU-only DPI or region-strategy code path this feature introduces. Imports MUST be guarded so a host without Paddle GPU can run the default suite.

**Quality-gate before promotion**

- **FR-016**: A reduced-DPI preset, a region-first preset, or any combination MUST NOT be promoted to the new `ppstructurev3@gpu` default until BOTH of the following quality-gate metrics, computed on the same small corpus subset used for benchmarking, are at parity with or better than the legacy default's values on the same subset: (1) the per-corpus aggregate vendor-identity field score read from `evaluation_run_summary.json`, and (2) the per-document pass count on that subset (per the pass criterion in `docs/stage1-vendor-identity/scoring.md`). "Parity" means `candidate_metric >= legacy_metric` for each of (1) and (2). Both metrics MUST come from the existing evaluator outputs; no new metric is introduced by this feature. (Mirrors feature 017 FR-015.)
- **FR-017**: Quality-gate evidence MUST be recorded in this feature's research artifact alongside the candidate's `(raster_profile_id, region_strategy_id)` pair, so a future reader can re-derive the promotion decision from documented numbers.
- **FR-018**: Promotion of a new GPU default MUST NOT remove the legacy `(raster_profile_id, region_strategy_id)` configuration as a selectable option; the operator MUST still be able to invoke the legacy configuration by explicit selection.

**Non-regression and contract preservation**

- **FR-019**: This feature MUST NOT regenerate any committed corpus baseline (`tests/stage1_vendor_identity/*/preprocess_output.json`, `expected.json`, evaluator outputs, etc.). ### Key Entities

- **Rasterization-DPI preset**: A named preset that fixes the rasterization DPI used by the `ppstructurev3@gpu` preprocessing pass. The feature ships at least `legacy` (the DPI active on `main` at landing time of feature 017) and at least one reduced preset (e.g., `reduced-v1`). Selection is by preset name only; per-run free-form numeric DPI is not exposed on the runtime path. New presets are added by code change plus a new `raster_profile_id` value.
- **Region strategy preset**: A named preset that fixes how preprocessing targets page area for vendor-identity evidence. The feature ships at least `full-page` (legacy strategy) and at least one region-first / header-first preset (e.g., `header-first-v1`). For the `header-first-v1`-class preset on multi-page PDFs, the targeting rule is: process the header band on page 1 only; pages 2..N appear in `preprocess_output.json.pages[]` as empty records (valid geometry from PDF, `blocks: []`, `raw_ocr_lines: []`) and are not rasterized or inferred. The `pages.length == page_count` invariant is preserved. Targeting decisions are deterministic and re-derivable from input geometry and page index — they do NOT depend on extraction or vendor-identity model output. Selection is by preset name only; per-run free-form region coordinates are not exposed on the runtime path.
- **Configuration identifier (preprocessing axis)**: A pair of additive, human-readable string fields emitted on every `run_summary` line — `raster_profile_id` for the active DPI preset and `region_strategy_id` for the active region strategy. Operators attribute observed runtime / quality differences to the configuration that produced them by reading these two fields. Both are stable across runs of the same configuration on that axis; either changes when its axis changes. Coexists with feature 017's `module_set_id` and `det_rec_variant_id` without overlapping or replacing them.
- **Region-strategy fallback record**: An additive `run_summary` field `region_strategy_fallback_count` (integer, always emitted, default `0`) that records, per run, the number of documents on which the region-first strategy fell back to the full-page strategy under FR-007. Used by operators to distinguish "region-first ran clean" from "region-first nominally selected but mostly fell back" without inspecting per-document logs. Per-document attribution is independently recoverable from `preprocess_output.json.pages[]` shape (fallen-back documents have full-length populated `pages[]`; clean region-first multi-page runs have pages 2..N empty per the Q2 invariant).
- **Quality-gate evidence**: Vendor-identity quality numbers (per the existing evaluator) for each evaluated `(raster_profile_id, region_strategy_id)` configuration on the same small corpus subset, recorded in this feature's research artifact, used as the gating evidence for any GPU-default promotion under FR-016.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For a fixed vendor-identity fixture, a `ppstructurev3@gpu` run with a reduced-DPI preset produces a `preprocess_output.json` that validates against the same JSON Schema as a run with the legacy DPI preset, with no schema-level diff between the two outputs.
- **SC-002**: For the same fixture, a `ppstructurev3@gpu` run with a region-first / header-first preset produces a `preprocess_output.json` that validates against the same JSON Schema as the legacy full-page run, with no schema-level diff between the two outputs.
- **SC-003**: At least one reduced-DPI preset and at least one region-first / header-first preset are evaluated against the same small stage 1 vendor-identity corpus subset. The four-corner matrix (legacy DPI × full-page, reduced DPI × full-page, legacy DPI × region-first, reduced DPI × region-first) is benchmarked, and each cell's per-document `phase_timings.*` plus the existing evaluator's vendor-identity quality numbers are recorded in this feature's research artifact alongside the cell's `(raster_profile_id, region_strategy_id)` pair.
- **SC-004**: Every `run_summary` line emitted by the new binary carries both additive string fields `raster_profile_id` and `region_strategy_id` per FR-008 / FR-011. Two runs that differ on the rasterization-DPI preset have different `raster_profile_id` values; two runs that differ on the region strategy have different `region_strategy_id` values; two runs with the same configuration on both axes have identical values for both fields.
- **SC-005**: A `ppstructurev3@cpu` run with any GPU-only configuration switch this feature introduces *explicitly set* in the environment produces a `run_summary` line with the CPU-default identifier values, performs no DPI change and no region targeting, emits a clear stderr warning that the switch was ignored because the active profile is not `ppstructurev3@gpu`, and exits with the same status it would have produced without the switch.
- **SC-006**: The default test suite passes on a host without Paddle GPU. All FR-005 / FR-016 verifications that require GPU are skipped via `@pytest.mark.gpu` rather than failed.
- **SC-007**: No committed corpus baseline file under `tests/stage1_vendor_identity/` is modified by this feature outside the established dataset/baseline flow. Verified by checking the diff of this feature's PR against `main` for those paths.
- **SC-008**: For every evaluated configuration, end-to-end pipeline runs on a small corpus subset (preprocess → evidence packet → extract → route → assemble → evaluate) complete with every emitted artifact validating against its existing schema in the active contract set.
- **SC-009**: If a `(raster_profile_id, region_strategy_id)` candidate is promoted to the new `ppstructurev3@gpu` default, BOTH (a) the per-corpus aggregate vendor-identity field score from `evaluation_run_summary.json` and (b) the per-document pass count on the small corpus subset (per `docs/stage1-vendor-identity/scoring.md`) are ≥ the legacy default's values on the same subset. If either metric is below the legacy value, no promotion is made: the legacy default remains in place and the candidate stays selectable only via explicit configuration.
- **SC-010**: All feature 014 / 015 / 016 / 017 success criteria continue to hold for runs configured under this feature: PPStructureV3 constructed exactly once per process, GPU readiness probed at most once per process, single-device-per-process guard enforced, no silent CPU fallback after `ppstructurev3@gpu` is selected, warmup behavior under `--gpu-warmup` unchanged, `pipeline_version` continues to end in `.gpu0` / `.cpu0` per profile, feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked` semantics unchanged.
- **SC-011**: `schema_version`, `contract_set_version`, and the four canonical stage 1 artifact schemas are unchanged by this feature. Verified by `git diff main -- contracts/stage1_vendor_identity/` showing no schema or `contract_set.json` diff attributable to this feature.

- This feature builds directly on features 014, 015, 016, and 017. The `ppstructurev3@gpu` profile, the single-engine-construction guarantee, the `phase_timings` schema, the `kind: "run_summary"` stdout shape, the `--gpu-warmup` opt-in, the `@pytest.mark.gpu` test-marker convention, and feature 017's `module_set_id` / `det_rec_variant_id` / `ppstructure_modules_invoked` identifier surface are treated as established infrastructure, not as work to redo.
- The workstation ROCm Paddle path used for verification is the host WSL `.venv-paddle-rocm` environment with `paddlepaddle-dcu` bound to `gpu:0`, as established in features 014 and 015. CI continues to run CPU and stub paths only.
- The "small stage 1 vendor identity corpus subset" used for benchmarking is a fixed subset of `tests/stage1_vendor_identity/inv_*` chosen at `/speckit.plan` time. The same subset is used for every cell in the four-corner matrix evaluated under FR-005 so quality and timing numbers are comparable. Where possible, the subset matches feature 017's so cross-feature comparison is meaningful.
- "Reduced-DPI" preset values target the smallest DPI at which the existing PaddleOCR detection / recognition variants and PPStructureV3 module set still produce a `preprocess_output.json` that downstream stages and the evaluator accept on the chosen subset. Exact numeric DPI values are resolved at `/speckit.plan` time by the FR-005 benchmark; they are not part of the user-facing surface (FR-001).
- "Region-first / header-first" preset targeting is heuristic-based on PDF page geometry (page index, page bounds, header band ratios) and is deterministic by FR-006. The exact heuristic and the chosen header band proportion are resolved at `/speckit.plan` time. On multi-page invoices the `header-first-v1`-class preset processes the header band on page 1 only; pages 2..N MUST appear in `preprocess_output.json.pages[]` as empty records (valid geometry from PDF, `blocks: []`, `raw_ocr_lines: []`) and MUST NOT be rasterized or inferred. The `pages.length == page_count` invariant is preserved (resolved 2026-05-10 in `/speckit.clarify` Q2).
- The configuration-identifier surface for FR-008 / FR-011 lands on `run_summary` per features 015/016/017's additive-only pattern, NOT inside `preprocess_output.json` (which is schema-frozen by FR-020). Identifier shape is two additive top-level string fields on `run_summary` — `raster_profile_id` and `region_strategy_id` — both human-readable strings, both emitted on every run regardless of profile, alongside (not replacing) feature 017's `module_set_id` and `det_rec_variant_id`. The exact CPU-default and legacy GPU-default string values for each field (e.g., `cpu-default`, `legacy`, `full-page`) are agreed at `/speckit.plan` time.
- The FR-007 disposition is resolved (2026-05-10, `/speckit.clarify` Q1): on "no vendor-identity-relevant evidence" the system MUST fall back to the full-page strategy on that document and MUST record the fallback on `run_summary` via `region_strategy_fallback_count` (FR-009). The trigger condition (Q3) is deterministic — the concatenation of `blocks[].text` in the targeted region on page 1, with whitespace stripped, is empty. Failing fast in this scenario is NOT permitted; "silent blank output" remains forbidden.

- Workstation GPU verification of FR-005 / FR-016 / FR-025 is best-effort at landing time. If GPU hardware is unavailable, those verifications are tracked as follow-ups under FR-025 rather than blocking merge of CPU-safe code; the deferral is captured in `tasks.md`.
- No new persisted benchmark artifact is needed at landing time. The benchmark numbers from FR-005 / FR-017 land in this feature's `research.md` (and/or quickstart) under FR-021. If `/speckit.plan` later finds `run_summary` + harness outputs insufficient, FR-021's escape hatch applies.
